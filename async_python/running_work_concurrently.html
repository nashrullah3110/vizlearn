Running Work Concurrently: gather and TaskGroup

Async Python·By Ashish Jangra·Updated 11 September 2026

Fan out many awaits at once, collect the results, and decide what should happen when one of them fails.

Overview

The shape of the win

The reason to reach for async is almost always the same: you have many independent waits — requests, queries, file reads — and doing them one after another wastes the time each one spends idle. Running them together collapses the total time from the sum of the waits to the longest single wait.

asyncio.gather is the direct tool. Hand it several coroutines and it schedules them all as tasks, waits for every one, and returns their results in the order you passed them — not the order they finished.

These editors run inside a browser event loop that is already going, so the examples finish with await main(). In a standalone .py script — run with python file.py — you write asyncio.run(main()) instead, which starts a loop, runs the coroutine, and closes it. The two are the same program with different entry points.

example_01.pyPython
import asyncio, time

async def fetch(name, seconds):
    await asyncio.sleep(seconds)
    return f"{name}:{seconds}"

async def main():
    t0 = time.time()
    results = await asyncio.gather(
        fetch("A", 0.3),
        fetch("B", 0.2),
        fetch("C", 0.1),
    )
    print("results:", results)
    print(f"elapsed {time.time()-t0:.2f}s")

await main()
Output
results: ['A:0.3', 'B:0.2', 'C:0.1']
elapsed 0.30s
Three waits of 0.3, 0.2 and 0.1 seconds finish in 0.30, not 0.60 — the total is the longest one, because all three timers ran at once. And the results came back in call order (A, B, C) even though C finished first: gather lines the results up with the arguments, so you can index them without tracking which finished when.

Running Work Concurrently: gather and TaskGroup

                
Fan out many awaits at once, collect the results, and decide what should happen when one of them fails.

            

            

                
                

                    
What happens when one fails

                    
By default, the first exception in any of the gathered coroutines stops the wait and propagates out of gather. The other coroutines are not cancelled, but their results are lost — you get the exception, not a partial list.
example_02.pyPython
import asyncio

async def square(n):
    await asyncio.sleep(0.1); return n * n

async def boom():
    await asyncio.sleep(0.05); raise ValueError("failed")

async def main():
    try:
        await asyncio.gather(square(2), boom(), square(3))
    except ValueError as e:
        print("gather re-raised the first exception:", e)

    res = await asyncio.gather(square(2), boom(), square(3),
                               return_exceptions=True)
    print("return_exceptions=True:", res)

await main()

Output
gather re-raised the first exception: failed
return_exceptions=True: [4, ValueError('failed'), 9]
The default hands you the first exception and hides the successful results. Passing return_exceptions=True changes the contract: nothing is raised, and the exception is placed in the results list where that coroutine's value would have been. That is the right choice when you want every result you can get and intend to inspect the failures yourself — and the wrong one if a failure should abort the whole batch, because it quietly turns errors into data you might forget to check.

                

                

                    
TaskGroup: the modern default

                    
gather has an awkward gap: when one coroutine fails, the others keep running unsupervised, and cleaning them up is your problem. Python 3.11 added asyncio.TaskGroup to close it, and it is now the recommended way to run concurrent work.
example_03.pyPython
import asyncio

async def work(n):
    await asyncio.sleep(0.05 * n)
    print(f"done {n}")
    return n

async def main():
    async with asyncio.TaskGroup() as tg:
        tasks = [tg.create_task(work(i)) for i in range(1, 4)]
    print("results:", [t.result() for t in tasks])

await main()

Output
done 1
done 2
done 3
results: [1, 2, 3]
The async with block does not exit until every task created inside it has finished, so the work is scoped: when control passes the closing line, all of it is done. This is structured concurrency — tasks live and die within a visible block rather than floating free — and it gives one guarantee gather does not: if any task raises, the group cancels all the others and then raises, so a failure never leaves siblings running in the background.

                

                

                    
Failures come back as a group

                    
Because several tasks can fail at once, a TaskGroup raises an ExceptionGroup, unpacked with the except* syntax also new in 3.11:
example_04.pyPython
import asyncio

async def ok():  await asyncio.sleep(0.1); print("ok ran")
async def bad(): await asyncio.sleep(0.02); raise ValueError("x")

async def main():
    try:
        async with asyncio.TaskGroup() as tg:
            tg.create_task(ok())
            tg.create_task(bad())
    except* ValueError as eg:
        print("TaskGroup raised ExceptionGroup:", [str(e) for e in eg.exceptions])

await main()

Output
TaskGroup raised ExceptionGroup: ['x']
When bad raises, the group cancels ok before it can finish — note that "ok ran" never prints — and surfaces the failure inside an ExceptionGroup. The except* form is how you handle it, and it is built for the real case the group creates: more than one task failing together.

                

                

                    
Which to reach for

                    
WantUse
Results in call order, siblings independentgather
Every result including failures, as datagather(return_exceptions=True)
A failure to cancel the rest, cleanly scopedTaskGroup
Results as they finish, not in orderas_completed
For new code on Python 3.11 or later, TaskGroup is the sensible default, and gather is for the cases where you specifically want the siblings to survive a failure.

                

                

                    
Results as they finish

                    
gather lines results up with the arguments, which is convenient and means you wait for the slowest one before you see anything. When you want to act on each result the moment it arrives, asyncio.as_completed hands them over in completion order instead.
example_05.pyPython
import asyncio

async def fetch(name, seconds):
    await asyncio.sleep(seconds)
    return f"{name} after {seconds}s"

async def main():
    jobs = [fetch("A", 0.3), fetch("B", 0.1), fetch("C", 0.2)]
    for finished in asyncio.as_completed(jobs):
        print(await finished)

await main()

Output
B after 0.1s
C after 0.2s
A after 0.3s
The same three coroutines as the first example, in the same order in the list, arriving back in the order they actually completed — B, C, A. The loop yields an awaitable each time one finishes, so the first result is available after 0.1 s rather than after 0.3.
That matters whenever partial results are useful: streaming rows to a client as each query returns, updating a progress bar, or stopping early once you have enough. The cost is that you lose the correspondence with your input list, so if you need to know *which* job a result came from, return it as part of the value — as the name above does — rather than relying on position.

                

                

                    
First answer wins, cancel the rest

                    
gather waits for everything and as_completed hands you everything in turn. asyncio.wait is the third shape: it returns as soon as a condition is met and gives you two sets, done and pending, leaving what to do with the stragglers up to you.
example_06.pyPython
import asyncio

async def replica(name, seconds):
    await asyncio.sleep(seconds)
    return name

async def main():
    tasks = [asyncio.create_task(replica("fast", 0.1)),
             asyncio.create_task(replica("slow", 0.4))]

    done, pending = await asyncio.wait(tasks, return_when=asyncio.FIRST_COMPLETED)
    print("first answer:", done.pop().result())

    for t in pending:
        t.cancel()
    await asyncio.gather(*pending, return_exceptions=True)
    print("cancelled the rest:", len(pending))

await main()

Output
first answer: fast
cancelled the rest: 1
This is the hedged request pattern: ask two replicas the same question, take whichever answers first, and cancel the other so it stops consuming a connection. It cuts tail latency at the cost of extra load, and it is only expressible with wait, because gather insists on waiting for both and as_completed gives you no handle on the ones still running.
Two things about the API catch people. It takes tasks, not coroutines — passing coroutines was deprecated and is now an error, which is why the create_task calls are explicit here. And it returns sets, so there is no ordering to rely on; with more than one task in done you inspect them rather than indexing. The other return_when values are FIRST_EXCEPTION and the default ALL_COMPLETED, which makes wait the general form the other two are conveniences over.

                

                

                    
Limiting how much runs at once

                    
gather over ten coroutines is fine. gather over ten thousand starts ten thousand at once, and whatever they talk to now has ten thousand simultaneous callers — which is how an async rewrite accidentally becomes a denial-of-service attack on your own database. Async removed the thread-count ceiling that used to limit concurrency by accident, so the limit now has to be deliberate.
An asyncio.Semaphore is the standard bound. It holds N permits; async with sem takes one and waits if none are free.
example_07.pyPython
import asyncio, time

async def fetch(sem, live):
    async with sem:                       # only N get past this at a time
        live.append(1)
        peak = len(live)
        await asyncio.sleep(0.05)
        live.pop()
        return peak

async def main():
    sem = asyncio.Semaphore(3)
    live = []
    t0 = time.time()
    peaks = await asyncio.gather(*(fetch(sem, live) for _ in range(9)))
    print("most in flight at once:", max(peaks))
    print(f"elapsed {time.time()-t0:.2f}s for 9 waits of 0.05s, 3 at a time")

await main()

Output
most in flight at once: 3
elapsed 0.17s for 9 waits of 0.05s, 3 at a time
Nine coroutines were scheduled at once and never more than three ran at a time — the live list is the evidence, and its peak is exactly the semaphore's count. The elapsed time follows: three rounds of 0.05 s, plus scheduling overhead, rather than the 0.05 s an unbounded gather would have taken or the 0.45 s a sequential loop would.
The pattern to remember is that the semaphore goes *inside* the coroutine, around the part being limited, not around the gather. All nine tasks still exist and all nine are still scheduled; the bound is on how many are past the async with at once. If the work arrives as an open-ended stream rather than a known list, a bounded queue with a fixed number of workers is the better shape — same idea, different plumbing.

                

                

                    
Where it goes wrong

                    
Gathering a huge list at once. gather over ten thousand coroutines starts ten thousand at once and can exhaust connections or memory. Cap the concurrency with a semaphore, or batch.
Ignoring return_exceptions results. With it on, a failure is a value in the list. Code that does not check for exceptions there treats an error as a success.
Expecting gather to cancel on failure. It does not; the other coroutines run on. TaskGroup is what cancels siblings.
Passing plain values to gather. Everything you gather must be awaitable. A non-coroutine in the list is an error, not a constant that passes through.

                

                

                    
Questions people ask

                    
gather or TaskGroup? TaskGroup for new code on 3.11 or later: it cancels the siblings when one task fails, so a failure never leaves work running unsupervised. Reach for gather when you specifically want the siblings to survive a failure, or when you need the results lined up with the arguments.
Does gather cancel the others when one raises? No, and this is the single most common wrong assumption about it. The first exception propagates and the other coroutines carry on running with nobody watching them. That gap is exactly what TaskGroup was added to close.
When is return_exceptions=True right? When a failure is data you intend to inspect — nine of ten shards answered, report the tenth. It is wrong when a failure should abort the batch, because it converts errors into list entries that code can silently treat as results.
How many is too many to gather? Whatever the other end can take, which is a property of the remote service and not of asyncio. Once the list is long enough that you are asking the question, bound it with a semaphore rather than guessing.
Can I mix await and tasks in one function? Yes, and it is normal: start the slow independent work as tasks, do other things, then await the handles when you finally need the results. What you cannot do is expect a row of plain awaits to overlap.
What is except* for? Unpacking an ExceptionGroup, which is what a TaskGroup raises because several tasks can fail at once. It selects the matching exceptions from the group and leaves the rest to propagate — a plain except ValueError will not match a group that contains one.

                

                

                    
Recap in one screen

                    
  • The win is collapsing many independent waits from their sum to their maximum: 0.3, 0.2 and 0.1 s together take 0.30, not 0.60.
  • gather returns results in call order however they finished, and by default raises the first exception while leaving the siblings running.
  • TaskGroup scopes the work to an async with block and cancels every sibling if one fails — structured concurrency, and the sensible default on 3.11+.
  • Several tasks can fail at once, so a TaskGroup raises an ExceptionGroup, which except* exists to unpack.
  • as_completed trades the input ordering for the first result arriving as soon as it is ready.
  • Async removed the accidental concurrency ceiling threads used to impose, so bound it on purpose — a Semaphore inside the coroutine, around the part being limited.
