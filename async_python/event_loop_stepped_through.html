The Event Loop, Stepped Through

Async Python·By Ashish Jangra·Updated 11 September 2026

One thread, one queue of ready work, and coroutines that step aside at every await. Everything else about async Python is a consequence of this.

Overview

The whole machine, in one sentence

Asynchronous Python runs on a single thread. There is no parallelism here and no second core doing work behind your back. What there is instead is an event loop: a plain loop that keeps a queue of coroutines that are ready to run, takes one, runs it until it voluntarily steps aside, and moves to the next.

That "steps aside" is the entire trick, and it happens at exactly one kind of place: an await. Between two awaits a coroutine has the thread to itself and nothing can interrupt it. At an await it hands control back to the loop, which is then free to run something else while the first coroutine is waiting for whatever it awaited.

The Event Loop, Stepped Through

One thread, one queue of ready work, and coroutines that step aside at every await. Everything else about async Python is a consequence of this.

Watch two coroutines take turns

The clearest way to see the loop switching is to make two coroutines that yield control on purpose, with await asyncio.sleep(0) — a sleep of zero seconds whose only effect is to return to the loop.

These editors run inside a browser event loop that is already going, so the examples finish with await main(). In a standalone .py script — run with python file.py — you write asyncio.run(main()) instead, which starts a loop, runs the coroutine, and closes it. The two are the same program with different entry points.

example_01.pyPython
import asyncio

async def task(name, steps):
    for i in range(steps):
        print(f"{name} step {i}")
        await asyncio.sleep(0)          # hand control back to the loop

async def main():
    await asyncio.gather(task("A", 3), task("B", 3))

await main()
Output
The output is not A A A B B B. It is interleaved:
A step 0
B step 0
A step 1
B step 1
A step 2
B step 2
A runs until its first await and stops. The loop then runs B until *its* first await. Then A again, because its sleep(0) has resolved and it is back on the ready queue. The two advance in lockstep, one step each per turn, and the point where a turn ends is always an await. Delete the await asyncio.sleep(0) and A runs all three steps before B starts at all, because without an await it never gives the loop a chance to switch.

                

                

                    
Where the concurrency actually comes from

                    
Nothing above ran in parallel. A and B took turns on one thread, and the total work was the same as doing them one after another. So what is the loop for?
The answer is that real awaits are not instant. When a coroutine does await on a network read, a timer, or a database reply, it is saying "I have nothing to do until this arrives — run someone else." The loop does exactly that. While A waits 200 ms for a server, B is not blocked; it is running, or waiting on its own reply. A thousand coroutines can all be waiting at once on one thread, which is the thing threads are too expensive to do at that scale.
The loop is therefore an overlap machine for waiting, not a way to do two computations at once. That distinction decides everything about when async helps — it is covered in running work concurrently, and its most common failure, a coroutine that does not step aside, is the whole subject of the blocking call that freezes the loop.

                

                

                    
The three states a coroutine is in

                    
At any moment the loop sees each coroutine in one of three states, and following them is enough to predict any async program's behaviour:
StateMeaning
Runningit has the thread right now, between two awaits
Readyit is waiting in the queue for its turn
Waitingit is suspended at an await, until that await resolves
Exactly one coroutine is ever *running*. When it hits an await it becomes *waiting*, and the loop promotes the next *ready* one to running. When an await resolves — a timer fires, a reply arrives — its coroutine moves from *waiting* back to *ready*, and will run again when its turn comes.

                

                

                    
Why "cooperative" is the word that matters

                    
This scheduling is cooperative: the loop can only switch when the running coroutine chooses to await. It cannot preempt. A thread-based system is different — the operating system can pause a thread mid-instruction and run another — but an event loop has no such power, because there is only one thread and it is currently executing your code.
The upside is that between awaits your code is atomic: no other coroutine can observe a half-finished update, which removes a whole category of race condition that threads suffer from. The downside is the mirror image: if a coroutine runs for a long time *without* awaiting, the entire loop is frozen for that whole time, because nothing can take the thread away from it. Cooperation only works if everyone cooperates.

                

                

                    
What one turn of the loop actually does

                    
The loop is not a metaphor. It is a while loop over three data structures, and knowing them is enough to predict any scheduling question:
  • a ready queue of callbacks to run now;
  • a heap of timers, ordered by when each is due;
  • an I/O selector holding the sockets the loop is watching.
One iteration does four things in order. Run everything currently on the ready queue. Work out how long until the earliest timer is due. Ask the selector for I/O events, using that as its timeout. Then move whatever fired — sockets that became readable, timers that came due — onto the ready queue for the next pass.
await asyncio.sleep(0) is the smallest possible interaction with that machinery: it puts the current coroutine straight back on the ready queue and returns to the loop, so anything already queued runs before your next line. loop.call_soon appends a plain callback to the same queue, and loop.call_later puts one on the timer heap instead.
example_02.pyPython
import asyncio

async def main():
    loop = asyncio.get_running_loop()
    ran = []
    loop.call_soon(lambda: ran.append("soon A"))
    loop.call_soon(lambda: ran.append("soon B"))
    loop.call_later(0.05, lambda: ran.append("timer 50ms"))

    await asyncio.sleep(0)          # one trip through the loop
    print("after one turn: ", ran)

    await asyncio.sleep(0.1)        # long enough for the timer
    print("after the timer:", ran)

await main()

Output
after one turn:  ['soon A', 'soon B']
after the timer: ['soon A', 'soon B', 'timer 50ms']
After a single await asyncio.sleep(0) both call_soon callbacks have already run, because one trip through the loop drains the ready queue. The 50 ms timer has not, because it is not due yet — it is sitting on the heap until an iteration whose selector timeout expires moves it across. That is the entire scheduler: a queue for now, a heap for later, and one poll that waits for whichever arrives first.

                

                

                    
One loop per thread, and why these editors say await main()

                    
asyncio.run is not a way of calling a coroutine. It creates a fresh event loop, runs the coroutine until it finishes, and then closes the loop. That is why it belongs at the top of a program and nowhere else — and why calling it while a loop is already running is an error rather than a nested run:
example_03.pyPython
import asyncio

async def work():
    return "done"

# This editor already has a loop running, so asyncio.run cannot start another.
coro = work()
try:
    asyncio.run(coro)
except RuntimeError as e:
    print("RuntimeError:", e)
finally:
    coro.close()

print("there is a running loop here:", asyncio.get_running_loop() is not None)

Output
RuntimeError: asyncio.run() cannot be called from a running event loop
there is a running loop here: True
That error is exactly why every editor on this track finishes with await main(). The page already has a loop — the browser's — and from inside a running loop a coroutine can simply be awaited. A standalone script has no loop yet, so there asyncio.run(main()) is how you get one.
Two related functions come up constantly. asyncio.get_running_loop() returns the loop that is running and raises if there is none, which is what you want inside a coroutine. The older asyncio.get_event_loop() would *create* one when none existed, which made starting a second loop by accident easy; that is why it is deprecated. If you need the loop, ask for the running one.
The loop is also per-thread. A second thread has no loop until something creates one there, and an object belonging to one loop cannot be awaited on another. That constraint is what asyncio.run_coroutine_threadsafe exists for — it is how synchronous code on another thread hands work to a loop.

                

                

                    
Where it goes wrong

                    
Expecting parallelism. The loop runs one thing at a time. For work that is genuinely CPU-bound, async does nothing; you need processes.
A coroutine that never awaits. It monopolises the single thread, and every other coroutine stalls until it finishes. This is the most common async bug and has its own article.
Assuming order across awaits. Between two awaits your code is safe. Across an await, anything else may have run, so state you read before the await may have changed after it.
Confusing "started" with "running". Creating a coroutine object does not run it, and neither does the loop until you hand it over — which is what coroutines, tasks and await is about.

                

                

                    
Questions people ask

                    
Is async faster than threads? Not at running code — it runs strictly less at once, because there is one thread. It is far cheaper at *waiting*: a coroutine suspended at an await costs a small object, where a blocked thread costs a stack and a context switch. Thousands of simultaneous waits are routine for a loop and expensive for threads.
Does async help CPU-bound work? No. One thread, no preemption, so a computation holds it until it finishes and every other coroutine stops. Processes are the answer there — multiprocessing or a ProcessPoolExecutor.
What does await asyncio.sleep(0) actually do? It returns to the loop and puts the coroutine straight back on the ready queue, so whatever was already queued runs before your next line. It is the idiomatic way to yield the thread partway through a long loop, and that is the only reason to call it.
Can I run two loops at once? Not in one thread — asyncio.run inside a running loop raises the RuntimeError above. Separate threads may each own a loop, and work moves between them with run_coroutine_threadsafe.
Why does my coroutine never run? Because you called it rather than awaiting or scheduling it. main() builds a coroutine object and runs nothing; something has to drive it. Python's "coroutine was never awaited" warning says precisely this, and is worth promoting to an error.
Can another coroutine run between two of my lines? Only if one of them is an await. That is the guarantee cooperative scheduling buys: your code between two awaits is atomic with respect to other coroutines, so none of them can observe a half-finished update. Across an await, assume anything may have run.

                

                

                    
Recap in one screen

                    
  • One thread, one loop, and a coroutine that runs until it voluntarily awaits. No preemption, no parallelism.
  • The loop is a ready queue, a timer heap and an I/O selector. An iteration drains the queue, then polls for whichever event comes due first.
  • await is the only place a switch can happen, which is what makes the code between two awaits atomic against other coroutines.
  • Three states, and following them predicts any async program: exactly one coroutine *running*, the rest *ready* in the queue or *waiting* on an unresolved await.
  • The win is overlapped waiting, not parallel computing. A thousand coroutines can be waiting at once on one thread; a thousand threads is a different proposition.
  • Cooperation is mandatory. A coroutine that runs a long time without awaiting freezes every other one for exactly that long.
