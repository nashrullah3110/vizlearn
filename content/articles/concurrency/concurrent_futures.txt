title: concurrent.futures: One Interface for Both
intro: One API over threads and processes, and a Future is a small state machine you can drive by hand to see exactly what it promises.

## The core idea

<code>concurrent.futures</code> makes the choice from the previous page a
one-word change. Both executors use the same methods. Switching between them
means changing the class name:

## One interface, two backends

```python
from concurrent.futures import ThreadPoolExecutor, ProcessPoolExecutor

with ThreadPoolExecutor(max_workers=8) as pool:      # waiting-bound work
    results = list(pool.map(fetch, urls))

with ProcessPoolExecutor(max_workers=4) as pool:     # computing-bound work
    results = list(pool.map(crunch, chunks))
```

That symmetry is the library's main selling point. But it does not change the
pickle boundary. A thread pool accepts any callable and argument. A process
pool accepts only values that can be pickled and sent to another process. The
one-word change therefore works in one direction more often than the other. A
thread design that closes over a database connection will not become a process
pool just by changing the class name.

Two things are worth using instead of the older <code>threading.Thread</code>
plumbing even when you only want threads. The pool is bounded, so you cannot
accidentally start ten thousand workers. And **exceptions come back to you**
rather than being printed by a dying thread and lost.

The editors here run in a browser interpreter with no OS threads, so
<code>ThreadPoolExecutor</code> raises and the pool examples are shown with
their CPython output. The <code>Future</code> itself, though, needs no threads
at all &mdash; and it is the part worth understanding, because everything the
executors do is described by it.

## A Future is a small state machine

A <code>Future</code> is a box that does not have a result yet. It has four
states, and you can put one through all of them by hand:

```python-run
from concurrent.futures import Future

f = Future()
print("fresh:            state", f._state, "| done?", f.done())

f.set_running_or_notify_cancel()
print("running:          state", f._state, "| cancel now?", f.cancel(), "<- too late")

f.set_result(42)
print("finished:         state", f._state, "| done?", f.done(), "| result()", f.result())

g = Future()
print()
print("cancel while pending:", g.cancel(), "->", g._state)
print("  result() on it now raises:", end=" ")
try:
    g.result()
except Exception as e:
    print(type(e).__name__)
```

```
fresh:            state PENDING | done? False
running:          state RUNNING | cancel now? False <- too late
finished:         state FINISHED | done? True | result() 42
 
cancel while pending: True -> CANCELLED
  result() on it now raises: CancelledError
```

That is the entire contract. A future is <code>PENDING</code> until a worker
picks it up. It is <code>RUNNING</code> while the worker has it, and
<code>FINISHED</code> once a result or exception is set. It is
<code>CANCELLED</code> if cancelled before it starts.

The line that answers the most common question is the third one:
<code>cancel()</code> returns <code>False</code> once the work is running.
There is no mechanism to interrupt a running Python function, so
"cancelling" a submitted job only works if it has not started. A queue of a
thousand submitted tasks can be cancelled almost fully; the handful in
flight will run to completion whatever you do.

## Where the exception goes

Submitting work that raises does not raise at submit time, and does not print
anything. The exception is stored on the future and re-raised when you ask for
the result:

```python-run
from concurrent.futures import Future

f = Future()
f.set_running_or_notify_cancel()
f.set_exception(ValueError("the worker failed"))

print("done?     ", f.done())
print("exception():", repr(f.exception()))
print("result() re-raises it here:", end=" ")
try:
    f.result()
except ValueError as e:
    print(repr(e))

log = []
g = Future()
g.add_done_callback(lambda fu: log.append(("callback saw", fu.result())))
g.set_running_or_notify_cancel()
g.set_result("done")
print()
print("add_done_callback fired:", log)
```

```
done?      True
exception(): ValueError('the worker failed')
result() re-raises it here: ValueError('the worker failed')
 
add_done_callback fired: [('callback saw', 'done')]
```

<code>exception()</code> asks without raising; <code>result()</code> raises.
Which means the way you consume the results decides whether you ever find out
about a failure, and that is the trap in the next section.

<code>add_done_callback</code> runs as soon as the future settles. If it has
already settled when you attach the callback, it runs at once; the output above
shows this. The callback runs on whichever thread set the result, so keep it
short and do not raise from it.

## The mistake that swallows errors

Three ways to consume the same pool, and one of them silently discards
failures:

```python
from concurrent.futures import ThreadPoolExecutor, as_completed

def work(n):
    if n == 3:
        raise ValueError("three is bad")
    return n * 2

with ThreadPoolExecutor(max_workers=4) as pool:
    # 1. submit and never look: the exception is stored and dropped.
    for n in range(5):
        pool.submit(work, n)
    print("submitted and ignored: no error appeared")

with ThreadPoolExecutor(max_workers=4) as pool:
    # 2. map: raises when you reach the bad item while iterating.
    try:
        for value in pool.map(work, range(5)):
            print("map gave", value)
    except ValueError as e:
        print("map raised at the bad item:", e)

with ThreadPoolExecutor(max_workers=4) as pool:
    # 3. as_completed: every result is inspected, failures included.
    futures = {pool.submit(work, n): n for n in range(5)}
    for fut in as_completed(futures):
        n = futures[fut]
        if fut.exception():
            print(f"n={n} failed: {fut.exception()}")
        else:
            print(f"n={n} -> {fut.result()}")
```

```
submitted and ignored: no error appeared
map gave 0
map gave 2
map gave 4
map raised at the bad item: three is bad
n=0 -> 0
n=1 -> 2
n=2 -> 4
n=3 failed: three is bad
n=4 -> 8
```

The first block is the bug. Five jobs ran, one failed, and the program printed
a cheerful line and carried on &mdash; because nothing ever called
<code>result()</code>, so nothing ever re-raised. A fire-and-forget
<code>submit</code> is how a pool loses errors, and it is extremely common in
code that only cares about side effects.

<code>map</code> is convenient and lazily ordered. It yields results in argument
order. When it reaches a failure, iteration stops and you never see later
results. Use it for "all or nothing", not when you want the other four.

<code>as_completed</code> is a good default. Results arrive as they finish, and
the dictionary maps each future back to its input. Check <code>exception()</code>
on each future so no failure is missed. It takes more lines, but it is the only
one of the three that reports everything.

## Waiting on some, not all

<code>wait</code> is the general form both of the others are conveniences over.
It returns two sets and lets you decide what to do with the stragglers:

```python-run
from concurrent.futures import Future, wait, as_completed, FIRST_COMPLETED

quick, slow = Future(), Future()
for f in (quick, slow):
    f.set_running_or_notify_cancel()
quick.set_result("fast replica answered")

done, pending = wait([quick, slow], return_when=FIRST_COMPLETED)
print("done:", len(done), "pending:", len(pending))
print("first answer:", done.pop().result())

for f in pending:
    print("cancelling the straggler:", f.cancel(), "<- it is already RUNNING")

settled = sorted(str(f.result()) for f in as_completed([quick])
                 if not f.exception())
print("as_completed over settled futures:", settled)
```

```
done: 1 pending: 1
first answer: fast replica answered
cancelling the straggler: False <- it is already RUNNING
as_completed over settled futures: ['fast replica answered']
```

The last two lines are the honest ending to the hedged-request pattern. You can
take the first answer, and you cannot actually stop the other worker, because
it is already running. What <code>cancel</code> saves you is the *queued* work,
not the in-flight work &mdash; so hedging in Python buys latency and costs the
duplicated effort whatever you do.

<code>shutdown(wait=False, cancel_futures=True)</code> is the same idea for the
whole pool: it drops everything still queued and lets whatever started finish.

## Sizing a pool, and the defaults you inherit

Leaving <code>max_workers</code> unset is common and the two executors default
very differently, because they are sized for different constraints:

```python-run
import os
from concurrent.futures import ThreadPoolExecutor

print("os.cpu_count() here:", os.cpu_count())

# Constructing an executor starts no threads, so the default is readable
# even in a sandbox that cannot run one.
tp = ThreadPoolExecutor()
print("ThreadPoolExecutor() max_workers:", tp._max_workers,
      "= min(32, cpu_count + 4)")

for n in (1, 4, 8, 64):
    print(f"  on a {n:>2}-core machine: threads default to {min(32, n + 4):>2},"
          f" processes default to {n:>2}")
```

```
os.cpu_count() here: 1
ThreadPoolExecutor() max_workers: 5 = min(32, cpu_count + 4)
  on a  1-core machine: threads default to  5, processes default to  1
  on a  4-core machine: threads default to  8, processes default to  4
  on a  8-core machine: threads default to 12, processes default to  8
  on a 64-core machine: threads default to 32, processes default to 64
```

The process default is <code>cpu_count()</code>. That fits parallel computing,
which is limited by cores. The thread default is
<code>min(32, cpu_count + 4)</code>. This is a compromise, not a universal
answer. Threads are for waiting, so useful concurrency does not track core
count. The <code>+ 4</code> lets a single-core machine overlap some I/O. The cap
of 32 helps prevent accidental bursts of hundreds of connections.

For I/O work, set the number on purpose. Base it on what the *other end* can
handle. Consider its rate limit, connection pool size, and your request budget
for an API. The right number may be above 32 or much lower.

## Giving each worker its own setup

This API has a direct answer to the pickle boundary from
[the previous page](threads_or_processes.html). It is easy to miss:
<code>initializer</code> runs once in each worker before that worker takes a job.

```python
from concurrent.futures import ProcessPoolExecutor

connection = None

def setup(dsn):
    global connection
    connection = connect(dsn)          # built in the worker, never pickled

def handle(row_id):
    return connection.fetch(row_id)    # uses the worker's own connection

with ProcessPoolExecutor(max_workers=4,
                         initializer=setup,
                         initargs=("postgres://...",)) as pool:
    results = list(pool.map(handle, row_ids))
```

This is the standard pattern when a worker needs something unpicklable. The DSN
is a string, so it can cross to the worker. The worker builds its own connection
and keeps it for its lifetime. Four workers then make four connections, not one
per task. The same pattern works for a loaded model, compiled regex cache, or
open file handle.

Two cautions. A module-level global is the right tool here. Each process has
its own copy, so there is no shared value to race over. This is one place where
a mutable global is not a smell. An exception inside <code>initializer</code>
appears as <code>BrokenProcessPool</code> on the *first submit*. That can be
confusing, so keep the initializer small and let it fail loudly.

## What it does not give you

It is worth being clear about the edges, because the interface is clean enough
to suggest it solves more than it does.

**No cancellation of running work.** Covered above and worth repeating, because
it is the single most common false expectation. There is no safe way to
interrupt a running Python function, so a "cancel" button built on
<code>Future.cancel</code> works only for the queue behind the workers.

**No progress reporting.** A future is either pending or settled. If you need
"37% done", the worker has to publish progress. It can use a
[queue](queues_between_threads.html), a shared counter under a
[lock](locks_and_the_ways_they_go_wrong.html), or a callback. Counting finished
items with <code>as_completed</code> is often the cheapest approximation.

**No backpressure.** <code>submit</code> never blocks. A producer faster than
the pool queues work without limit, and the queue is unbounded. So a loop that
submits a million jobs builds a million futures in memory before the pool has
finished the first hundred. If the work arrives as a stream rather than a list,
a bounded queue with a fixed number of workers is the shape that applies
pressure back &mdash; which is the [next page](queues_between_threads.html).

**No ordering guarantees beyond <code>map</code>.** Completion order is
whatever it is. If order matters, either use <code>map</code> or carry the index
in the result.

## Where it goes wrong

**Fire-and-forget <code>submit</code>.** The exception is stored on a future
nobody reads, and the failure disappears. Keep the futures and check them.

**Expecting <code>cancel()</code> to stop running work.** It cannot. It only
un-queues work that has not started.

**Using the executor as a context manager and expecting it to be quick.**
<code>with</code> calls <code>shutdown(wait=True)</code> on exit, so the block
does not finish until every submitted job does.

**Submitting to a <code>ProcessPoolExecutor</code> what cannot be pickled.** A
lambda, a local function, an open file, a lock. It fails at submit, which is at
least loud &mdash; see [the boundary](threads_or_processes.html).

**Sizing the pool by cores for I/O work.** Cores are the limit for computing.
For waiting, the limit is what the other end tolerates, and it is usually much
higher.
