title: The GIL, and What It Actually Locks
intro: Python's threads are real OS threads that are not allowed to run Python at the same time. One lock explains why threads help a program that waits and do nothing for a program that computes.

## The core idea

A CPython process has a global interpreter lock, and the rule around it is short: a thread must hold the GIL to execute Python bytecode.

## One lock, and what holds it

Two results follow. Most advice about Python threads comes from these points.

A program that spends its time **waiting** can get faster with threads. A thread
blocked on a socket, file, or timer is not running bytecode. It has handed the
GIL back. Ten threads can wait at once.

A program that spends its time **computing** does not get faster with regular
threads. Computing *is* running bytecode, and only one thread may do that at a
time. Two threads doing arithmetic take turns. Their total time is about one
thread's time plus the cost of switching.

These editors run in a browser interpreter that has no OS threads at all, so
<code>Thread.start()</code>, <code>ThreadPoolExecutor</code> and
<code>multiprocessing</code> raise here rather than working. That is worth
proving rather than asserting:

```python-run
import threading

try:
    threading.Thread(target=lambda: None).start()
except RuntimeError as e:
    print("in this sandbox:", e)

print("threads alive right now:", threading.active_count())
print("and this one is:", threading.main_thread().name)
```

```
in this sandbox: can't start new thread
threads alive right now: 1
and this one is: MainThread
```

Every runnable block on this track shows a method that works in single-threaded
Python: the bytecode for an increment, the lock protocol, the pickle boundary,
or a Future's state machine. A method that needs a second thread appears as a
plain code block with its CPython output. Each case is labelled on the page.

## Where the switch happens

The GIL is not held for the whole of a function. The interpreter drops and
reacquires it at times, and the period is a setting you can read:

```python-run
import sys, dis

print("switch interval:", sys.getswitchinterval(), "seconds")
print("so a one-second pure-Python loop offers about",
      int(1 / sys.getswitchinterval()), "chances to switch")

def tight(n):
    total = 0
    for i in range(n):
        total += i
    return total

ops = [i.opname for i in dis.get_instructions(tight)]
print()
print("bytecodes in that loop body:", len(ops))
print("the loop itself:", [o for o in ops if "FOR" in o or "JUMP" in o])

sys.setswitchinterval(0.001)
print()
print("after setswitchinterval(0.001):", sys.getswitchinterval())
```

```
switch interval: 0.005 seconds
so a one-second pure-Python loop offers about 200 chances to switch

bytecodes in that loop body: 15
the loop itself: ['FOR_ITER', 'JUMP_BACKWARD']

after setswitchinterval(0.001): 0.001
```

Five milliseconds is the default. It is a **time** interval, not a bytecode
count. Python changed this in 3.2, so older explanations about "every 100
ticks" describe the interpreter as it worked before then. A thread runs for up
to 5 ms. Then the interpreter asks it to drop the GIL so another thread can run.

Lowering the interval makes switching more responsive and adds cost, since
every switch costs work and cache locality. Raising it does the reverse. It is
very rarely the right thing to change: if switching cadence is your problem,
the shape of the program usually is.

The important word above is *offers*. A switch can only happen between
bytecodes, and a single bytecode is atomic with respect to other threads. That
is the fact the [next page](race_conditions_in_python.html) is built on,
because it means the safety of a step depends on how many bytecodes it
compiles to.

## What "releases the GIL" really means

The GIL is released around steps that do not need the interpreter. There
are two large categories and knowing which you are in predicts whether threads
will help:

| Operation | GIL | Threads help? |
|---|---|---|
| <code>time.sleep</code> | released | yes |
| socket read/write, <code>requests.get</code> | released while waiting | yes |
| file read/write | released | yes |
| <code>hashlib</code> on a large buffer | released | yes |
| numpy elementwise maths on a big array | released | yes |
| a pure-Python <code>for</code> loop | **held** | no |
| building or walking a dict or list | **held** | no |
| <code>json.loads</code> | **held** | no |

C code that does not touch Python objects can drop the lock while it runs.
That is why a NumPy-heavy program may scale with threads while the same loop
written in Python does not. It also makes "is this library a thin wrapper over
C?" a practical question, not a pedantic one.

## Two threads on CPU work

This is the measurement that cannot run here, so here it is with the output it
gives on CPython:

```python
import time
from concurrent.futures import ThreadPoolExecutor

def work(n):
    total = 0
    for i in range(n):
        total += i * i
    return total

N = 5_000_000

t0 = time.perf_counter()
work(N); work(N)
print(f"one after the other: {time.perf_counter() - t0:.2f}s")

t0 = time.perf_counter()
with ThreadPoolExecutor(max_workers=2) as pool:
    list(pool.map(work, [N, N]))
print(f"two threads:         {time.perf_counter() - t0:.2f}s")
```

```
one after the other: 1.18s
two threads:         1.21s
```

Two cores were available, yet two threads took slightly *longer* than running
the work in sequence. Nothing is broken. The threads took turns holding the
GIL, so the arithmetic was still serial. Switching added a few per cent. Swap
<code>ThreadPoolExecutor</code> for <code>ProcessPoolExecutor</code> and the time
roughly halves. That is the subject of
[threads or processes](threads_or_processes.html).

Run the same check with <code>time.sleep(1)</code> as the work and the numbers
invert: two seconds in sequence, one second with two threads. Sleeping releases
the lock. The threads and pool are the same. Only the need for the interpreter
has changed.

## Deciding before you commit

Before writing the threaded version, it is worth knowing which side of the
table above your program is on, and there is a two-line measurement that
answers it. <code>time.perf_counter</code> measures elapsed time;
<code>time.process_time</code> measures CPU time really consumed by the
process. Their ratio is the answer:

```python
import time

w0, c0 = time.perf_counter(), time.process_time()
run_the_thing()
wall = time.perf_counter() - w0
cpu = time.process_time() - c0
print(f"wall {wall:.2f}s  cpu {cpu:.2f}s  ratio {cpu/wall:.2f}")
```

```
a pure-Python loop   wall 0.61s  cpu 0.61s  ratio 1.00
an HTTP request      wall 0.42s  cpu 0.01s  ratio 0.02
```

A ratio near 1 means the process was computing the whole time: the work is
CPU-bound, it was holding the GIL, and threads will do nothing for it. A ratio
near 0 means the process was mostly waiting with the lock released, and threads
will overlap that waiting almost perfectly.

This one is shown rather than run because <code>time.process_time</code>
returns 0 under the browser interpreter &mdash; it is not implemented there, so
the ratio would read 0.00 for both cases and tell you nothing. On CPython it
is the fastest useful measurement in this whole area.

The number also tells you the speed-up ceiling. A ratio of 0.7 means the work
spends 70% of its time holding the GIL. Even infinitely many threads could
remove only the other 30%. That is Amdahl's law, with the serial fraction
measured instead of guessed. It is drawn for all three models on
[choosing between threads, processes and async](choosing_threads_processes_or_async.html).

## Why it is there at all

The GIL is easy to present as a historical embarrassment, and it is worth
knowing what it buys, because that explains why removing it took twenty years.

It makes **reference counting** safe without per-object locks. Every Python
object carries a count of how many things refer to it, updated constantly
&mdash; on every assignment, every function call, every list append. Making
those updates safe for concurrent threads means either one big lock, or atomic
steps on every single one, which costs speed in the single-threaded case
that most programs really are.

It also gives **C extension authors** a guarantee they have relied on for
decades: while your extension holds the GIL, no other thread is mutating
Python objects below it. A large amount of the scientific stack was
written against that promise.

Two newer options are worth knowing about. The CPython C API can create
**subinterpreters** with separate GILs, so they can run Python at the same time
inside one process. Starting with Python 3.13, CPython also offers optional
**free-threaded** builds that can run without the GIL. These builds are not the
default. Some C extensions may turn the GIL back on, so check package support
before relying on free threading. In a standard GIL-enabled build, the rule at
the top of this page still holds.

See the [Python free-threading guide](https://docs.python.org/3.14/howto/free-threading-python.html)
and the [C API guide to subinterpreters](https://docs.python.org/3/c-api/subinterpreters.html)
for current support and limitations.

## Where it goes wrong

**Reaching for threads to speed up work.** The most common mistake, and
the GIL means it gives no speed-up at all. CPU-bound work needs processes.

**Concluding threads are useless.** They are the right tool for waiting, which
is what most programs spend their time doing. A web scraper, a file crawler
and an API client all scale with threads.

**Assuming a C library releases the lock.** Many do and some do not, and the
documentation often does not say. The only reliable answer is to measure the
threaded version against the sequential one.

**Tuning the switch interval.** It almost never helps, and a lower value
increases cost. Change the structure instead.
