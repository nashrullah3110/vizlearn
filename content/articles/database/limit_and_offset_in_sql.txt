title: LIMIT and OFFSET: Paginate a Query Reliably
intro: LIMIT caps the number of returned rows and OFFSET skips rows, but stable pagination also needs a deterministic order.

## A page is an ordered slice
A query without `ORDER BY` has no guaranteed result order. If rows can tie on the sort key, add a unique tie-breaker so that repeated requests produce a stable sequence.


```sql-run
SELECT order_id, created_at
FROM orders
ORDER BY created_at DESC, order_id DESC
LIMIT 20 OFFSET 40;
```


This requests the third page of twenty rows. The unique `order_id` resolves ties between orders created at the same time. Without it, rows may move between pages even if the data changes little.

## Deep offsets have a cost
With a large offset, the engine may still need to find and skip all preceding rows before returning the page. The work can grow as a user moves deeper into a large result set. Concurrent inserts and deletes can also shift offsets, causing repeated or skipped rows across page requests.

For feeds with a stable key, keyset pagination can instead ask for rows after the last item from the previous page:


```sql-run
SELECT order_id, created_at
FROM orders
WHERE (created_at, order_id) < (:last_created_at, :last_id)
ORDER BY created_at DESC, order_id DESC
LIMIT 20;
```


Tuple comparison and NULL behavior differ by engine; the equivalent can be written as explicit conditions. Keyset pagination is efficient for sequential browsing but does not directly jump to an arbitrary page number.

## Define what “page” means
Decide whether users need a total count, a stable snapshot, random page access, or just “load more.” Exact counts can be expensive and may change while paging. An index matching the filter and order can help; inspect a plan and benchmark. See [indexes](indexes_in_sql.html) and [ORDER BY](order_by_in_sql.html).

## What happens when data changes
Suppose page one ends with item 20. Before page two is requested, five new records are inserted at the front. OFFSET 20 now starts at a different item, so the user may see repeats. A keyset cursor anchored on the last ordering key avoids this shift for forward navigation, though updates to sort keys can still move rows. If pages must represent one consistent snapshot, keep a transaction or use a snapshot/version token where supported; long-lived snapshots have operational costs.

## Keep the cursor complete
A keyset cursor must contain every expression needed to define a unique sort position. If results are ordered by score descending and then ID ascending, the cursor must carry both score and ID, and the predicate must respect the opposite direction for the ID tie-breaker. Nullable sort keys need explicit handling. Treat the cursor as opaque to the client or validate it before use. This prevents malformed cursor values from changing query logic and keeps pagination behavior consistent across requests.
