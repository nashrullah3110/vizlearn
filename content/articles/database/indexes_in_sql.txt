title: Database Indexes: Faster Reads, More Work on Writes
intro: An index stores data in a structure that can help the database find or order rows without scanning the entire table.

## What an index changes
A B-tree index keeps indexed values ordered with references to table rows. When a query filters on an indexed column, the database can often navigate to matching entries instead of checking every row. An index can also support ordering or a join, depending on its columns and the query.


```sql-run
CREATE INDEX orders_by_customer
ON orders(customer_id);
```


This may help queries that select orders for one customer. It does not guarantee the index will be used: a table scan can be cheaper when many rows match or the table is small. The optimizer chooses based on estimates and engine-specific rules.

## Match indexes to query patterns
Index columns used in selective filters, join keys, and ordering. A composite index's column order matters; see [composite and covering indexes](composite_and_covering_indexes.html). Expressions or leading wildcards can prevent use of a simple index, although some engines offer specialized indexes for those cases.

Check a query plan before and after creating an index. A `SEARCH` or index scan is not inherently better than a table scan; measure the workload that matters.

## Indexes have a cost
Every extra index uses storage and must be maintained when rows are inserted, updated, or deleted. Too many indexes can slow writes and make cache use worse. Start with the slow query and its plan, add the smallest index likely to help, then measure reads and writes.

Database engines support different structures and options—B-tree, hash, full-text, spatial, or specialized index types—and their guarantees vary. Do not copy an index design from another engine without checking its documentation.

## A selectivity example
An index on status may help when only a small fraction of rows have status = 'failed'. If nearly every row is status = 'active', reading the table directly may be cheaper. The same index could still help a query that also filters by a selective customer ID, depending on available composite indexes. The planner uses statistics to estimate this choice; stale statistics can produce poor plans. Maintain statistics using the engine's recommended process, and measure both common and worst-case query shapes before keeping a new index.

## Remove indexes that no longer earn their cost
An index that once helped may become redundant after a composite index is added or a query is retired. Inventory index usage using the target engine's statistics, but account for startup time and rare maintenance queries before dropping anything. Compare duplicate indexes, including differences in uniqueness, order, expressions, and included columns. A safe index change is measured on representative traffic and deployed with a rollback path. Avoid changing many indexes at once because it becomes difficult to explain a performance regression.
