title: MVCC: Multi-Version Concurrency Control
intro: MVCC lets a database keep row versions so readers can see a consistent snapshot while changes are being made.

## Why keep multiple versions
Multi-Version Concurrency Control (MVCC) is a concurrency technique. Instead of overwriting a row in place for every change, the engine records enough version information to decide which version a transaction can see. A reader can then continue using a snapshot while another transaction writes, reducing some read-write blocking.

The exact implementation differs by engine. PostgreSQL stores tuple versions in the table and later reclaims obsolete versions; SQLite uses journaling or WAL snapshots with its own locking model. “MVCC” does not mean that every read and write happens without locks.

## Visibility is transaction-specific
When a transaction reads a row, the database checks whether a version is visible according to the transaction's snapshot and isolation level. A second read may see a newer version under one isolation level and the same snapshot under another. This is why snapshot behavior and isolation guarantees need to be considered together. See [isolation levels](isolation_levels.html).

## The cleanup cost
Old versions cannot be removed while active transactions may still need them. Long-running transactions can therefore delay cleanup and increase storage or maintenance work. In PostgreSQL, vacuum reclaims space from obsolete tuples for reuse and maintains visibility information. Monitor the engine's own maintenance signals rather than assuming MVCC is free.

MVCC can improve concurrency, but it does not prevent write-write conflicts, deadlocks, or every serialization anomaly. Use constraints and transaction logic to protect business rules; see [transactions and ACID](transactions_and_acid.html).

## MVCC does not remove all blocking
Two transactions that update the same row still need to coordinate. DDL and explicit locks can block readers or writers, and a database may abort a transaction when its snapshot is no longer safe. In PostgreSQL, an update creates a new tuple version; old versions remain until no active transaction needs them and vacuum can reclaim them. In SQLite WAL mode, readers can continue on a snapshot while a writer commits, but SQLite still permits only one simultaneous writer. The label MVCC does not make engine behavior identical.

## Keep transactions short-lived
A transaction that remains open while a user waits on a page or an external service can pin an old snapshot. That may delay cleanup of obsolete versions, increase storage, and make maintenance less effective. Fetch what is needed, commit, and do network work outside the transaction when consistency permits. If a workflow truly needs a long snapshot, monitor its duration and understand the engine's cleanup behavior. MVCC improves concurrent access, but old snapshots are resources the database must preserve.
