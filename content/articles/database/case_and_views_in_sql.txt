title: CASE Expressions and Views in SQL
intro: CASE derives a value from conditions; a view gives a reusable name to a query.

## Two different tools
A <code>CASE</code> expression selects a result for each row based on conditions. A view stores a query definition under a name so other queries can reuse it. Neither changes the underlying rows by itself. They solve different problems: conditional logic in a result, and reuse of a query shape.

## Use CASE for conditional values
A searched <code>CASE</code> checks conditions in order and returns the result for the first true condition. If none match, <code>ELSE</code> supplies the fallback; without it, the result is <code>NULL</code>.

<pre><code>SELECT order_id,
       CASE
         WHEN total &gt;= 100 THEN 'large'
         WHEN total &gt;= 40 THEN 'medium'
         ELSE 'small'
       END AS size_band
FROM orders;</code></pre>

The order matters: a condition that catches too much can make later branches unreachable. Comparisons with <code>NULL</code> are not true, so add an explicit <code>WHEN total IS NULL</code> branch if missing totals need their own label. A simple <code>CASE expression WHEN value</code> form is useful for equality checks, but cannot express ranges.

Conditional aggregation combines <code>CASE</code> with aggregates, for example <code>SUM(CASE WHEN status = 'paid' THEN amount ELSE 0 END)</code>. For a portable alternative, some engines also support <code>FILTER</code>; check the target dialect.

## A view is a saved query
Create a view when a query expresses a stable, reusable concept such as active customers:

<pre><code>CREATE VIEW active_customers AS
SELECT customer_id, name
FROM customers
WHERE status = 'active';</code></pre>

Selecting from the view runs its underlying query; a regular view is not automatically a stored copy of the results. Updates through views have engine-specific restrictions. A materialized view stores results and needs a refresh strategy; SQLite does not provide native materialized views.

Views can reduce repetition and restrict which columns users see, but they are not a substitute for permissions on the underlying data. Keep the view definition clear, and inspect its query plan when it becomes slow. See [query plans](explain_and_query_plans.html).

## Keep branch results compatible
The result branches of a CASE expression should have compatible types. If one branch returns a number and another returns text, the database may coerce values or reject the expression depending on its type rules. Give the expression a meaningful alias so callers can understand the derived field. A view can also expose a stable set of columns while hiding joins from consumers, but changing its output columns can break dependent queries. Treat view definitions as part of the interface and migrate them deliberately.
