title: Datatypes: The Contract Every Column Signs
intro: Choosing a type decides what values are legal, how much disk they consume, and whether your arithmetic is exact.

## Quick Context

A <strong>datatype</strong> declares what a column may contain. The database uses it to reject invalid data, to decide how many bytes each value occupies, and to choose how comparisons and arithmetic behave. Get it wrong and you pay in storage, in speed, or &mdash; worst &mdash; in silently incorrect numbers.

## Integers: Pick the Smallest That Fits

Integer types differ only in width, and width sets the range. <span class="mono-font">TINYINT</span> holds &minus;128 to 127 in one byte; <span class="mono-font">INT</span> covers roughly &plusmn;2.1 billion in four; <span class="mono-font">BIGINT</span> uses eight.

The classic production incident is an <span class="mono-font">INT</span> primary key on a fast-growing table. At 2,147,483,647 rows the next insert fails outright &mdash; and migrating a hot table's key type is painful. Type <span class="mono-font">3000000000</span> into the value box with INT selected and watch the overflow.

## Never Store Money in FLOAT

<span class="mono-font">FLOAT</span> and <span class="mono-font">DOUBLE</span> are binary floating point. They cannot represent 0.1 exactly, for the same reason base 10 cannot write 1/3 exactly. Errors are tiny individually and accumulate over millions of rows.

The demo above adds 0.10 + 0.20 in both types. FLOAT does not produce 0.30 &mdash; it produces something imperceptibly different, and <span class="mono-font">= 0.30</span> is then false. <span class="mono-font">DECIMAL(10,2)</span> stores the digits themselves and is exact.

<strong>Rule:</strong> money, quantities and anything a human will audit go in <span class="mono-font">DECIMAL</span> / <span class="mono-font">NUMERIC</span>. Reserve FLOAT for measurements where a rounding error in the fifteenth digit genuinely does not matter.

## CHAR vs VARCHAR vs TEXT

- <span class="mono-font">CHAR(n)</span> &mdash; fixed width. Always consumes n characters, padding with spaces. Only sensible when values really are uniform, like a 2-letter country code.
- <span class="mono-font">VARCHAR(n)</span> &mdash; variable width up to n, storing only what you use plus a small length prefix. The sane default.
- <span class="mono-font">TEXT</span> &mdash; unbounded. Convenient, but some engines store it separately from the row, which can slow reads.

The <span class="mono-font">n</span> in <span class="mono-font">VARCHAR(n)</span> is mostly a <em>constraint</em>, not an allocation &mdash; declaring VARCHAR(255) everywhere does not waste space, but it also fails to document what the column really holds.

## Dates, Times and the NULL Question

Store dates in <span class="mono-font">DATE</span> / <span class="mono-font">TIMESTAMP</span>, never in a string. Only a real date type gives you correct sorting, date arithmetic, and rejection of 2024-02-31. For anything spanning time zones, prefer <span class="mono-font">TIMESTAMP WITH TIME ZONE</span>.

Finally, every type also permits <span class="mono-font">NULL</span> unless you say <span class="mono-font">NOT NULL</span>. NULL means <em>unknown</em>, which is genuinely different from 0 or an empty string &mdash; and it propagates through arithmetic and comparisons in ways that surprise people.

## Experiments to try

1. <strong>Select TINYINT and enter 200.</strong> Rejected &mdash; out of range. Now try 100, which fits comfortably.
2. <strong>Select INT and enter 3000000000.</strong> Overflow again, at exactly the boundary that has broken many real systems.
3. <strong>Compare the storage figures.</strong> Switching a column from BIGINT to INT on a billion-row table saves four gigabytes.
4. <strong>Read the money demo closely.</strong> The FLOAT sum is not 0.30, and the equality test fails. That is not a bug in this page &mdash; it is how binary floating point works everywhere.
5. <strong>Select CHAR(10) and type a short word</strong> to see how much of the fixed width is wasted on padding.

## Worth remembering

Pick the narrowest type that will hold every legitimate value, use DECIMAL for anything monetary, use real date types for dates, and add NOT NULL wherever a missing value would be meaningless. These choices are hard to change later and quietly govern correctness forever.
