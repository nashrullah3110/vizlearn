title: Database Partitioning: Split One Table into Partitions
intro: Partitioning divides a large logical table into smaller pieces managed by one database system, often using a key such as date or region.

## One table, several partitions
With table partitioning, queries and applications can work with one logical table while the database stores rows in separate partitions. A partitioning rule assigns each row—for example, a range of dates per month or a hash bucket based on a tenant key.

Partitioning can help with lifecycle operations and queries that filter by the partition key. When a predicate excludes partitions, partition pruning lets the engine skip those pieces. It does not automatically make every query faster, and queries that scan all partitions may gain little.

## Choose the key from access patterns
A useful partition key appears in frequent filters and divides data with predictable boundaries. Range partitioning suits ordered values such as time; hash partitioning can distribute values more evenly when range scans are not the main need. Too many tiny partitions increase planning and operational overhead.

Constraints, unique indexes, foreign keys, and maintenance behavior vary by engine. PostgreSQL, for example, has rules for unique constraints across partitioned tables. Test inserts, query plans, retention, and backups with the actual database and version.

## Partitioning is not sharding
Partitions are usually managed inside one database system; sharding distributes data across separate servers or nodes and adds routing and cross-shard coordination. Partitioning does not by itself add horizontal capacity. See [sharding](sharding_in_databases.html).

## A time-based retention example
A log table partitioned by month can let a query for one month avoid scanning older data, provided the filter exposes the partition key and the planner prunes other partitions. Retention may also be simpler when an old partition can be detached or dropped instead of deleting millions of individual rows. This depends on engine features, foreign-key relationships, backup policy, and whether the partition is still needed for historical queries. Partition boundaries should cover inserts deliberately; an uncovered date can cause writes to fail or enter a catch-all partition.

## Test pruning with the real predicate
A query can fail to prune partitions if it wraps the key in a function, casts it unexpectedly, or uses a predicate the planner cannot prove. Compare the plan for a bounded date range with a query that omits the date condition. Confirm that only the intended partitions are scanned and that boundary timestamps land in the correct interval. Partitioning creates operational work too: monitor partition creation, statistics, backups, and retention so the table does not accumulate empty or obsolete pieces.

## Balance partition size and count
A monthly partition is not automatically right for every time series. A small table may gain nothing from partitioning, while a very high-volume table may need daily or weekly boundaries to keep maintenance manageable. Too many partitions increase planning and catalog overhead; partitions that are too large can make retention and archival operations cumbersome. Choose a size using row volume, query ranges, maintenance windows, and engine limits. Revisit that choice as data grows rather than treating it as a one-time schema detail.
