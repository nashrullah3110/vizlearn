title: OLTP, OLAP, and Columnar Storage
intro: OLTP and OLAP describe different workloads; row and column layouts describe how data is physically organized.

## Two workload shapes
Online Transaction Processing (OLTP) handles many small operations that read or change a few records, such as placing an order. It usually needs low-latency lookups, concurrent writes, and transactional guarantees.

Online Analytical Processing (OLAP) answers questions across large datasets, such as monthly revenue by region. It often reads many rows but only a few columns, and can benefit from scans and aggregation. These are workload patterns, not mutually exclusive kinds of product. A system may support both, though one workload can interfere with the other.

## Rows and columns
A row-oriented layout keeps fields from one record together, which suits retrieving or updating a complete record. A columnar layout stores values from the same column together. An analytic query that reads only region and revenue can avoid unrelated fields and may compress repeated values well.

Column storage does not guarantee a particular speedup. Results depend on compression, data distribution, query shape, hardware, and engine. Column stores also have trade-offs for point updates and transactional access.

## Choose for the workload
Start from actual query and concurrency needs. Use a transactional store for frequent, small updates; use an analytical warehouse or columnar engine when broad scans and aggregations dominate. Moving data between systems introduces freshness, failure, and reconciliation questions. Benchmark both workloads under realistic concurrency. For an analytical dimensional design, see [star schema](star_schema.html).

## Example: two queries, two bottlenecks
A checkout query that fetches one customer's current cart needs a fast point lookup and a small write. A monthly revenue report may scan many transactions, group them by region, and return only a few columns. The first workload tends to value predictable response time under concurrent updates; the second values scan throughput and compression. Combining them on one system can work at modest scale, but a large report may compete with checkout. Run representative concurrent tests before separating the workloads.

## Measure interference, not labels
A mixed workload can remain on one engine if transactions and reports meet their latency targets. Measure transaction p95 latency while the analytical query runs, not only each query in isolation. If the report disrupts writes, options include a replica, scheduled extraction, workload limits, or a dedicated warehouse. Each introduces data freshness and operational cost. Row versus column storage is one design factor; caching, indexes, partitioning, concurrency control, and hardware also affect the outcome.
