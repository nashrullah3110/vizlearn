intro: Four guarantees, wrapped around every BEGIN...COMMIT.

## What this is

A transfer between two accounts is two split <a href="dml_in_sql.html" style="color: var(--accent-primary)">UPDATE</a> statements. If the database crashes between them, one account has lost money and the other never got it. Unless the two are wrapped in a deal. It guarantees they happen together or not at all.

A deal starts with `BEGIN` (or `START Deal` in MySQL) and ends with either `COMMIT`. It makes all changes permanent. Or `ROLLBACK`, which discards them as if they never happened. All between `BEGIN` and `COMMIT` is a single unit of work. The database guarantees that no outside observer will ever see a half-finished deal. Either all the changes are visible or none of them are.

The four properties that make this guarantee possible are Atomicity, Consistency, Isolation and Durability &mdash; collectively ACID. Atomicity means all-or-nothing: if any statement in the deal fails, each change made so far is rolled back. Consistency means the deal moves the database from one valid state to another, never leaving constraints violated. Isolation means concurrent deals do not interfere with each other: one deal's uncommitted changes are invisible to others. Durability means that once `COMMIT` returns, the changes survive a crash, a power failure or a restart.

These guarantees are not free. Isolation in given needs the database to coordinate concurrent access, often through locks or multi-version concurrency control (MVCC). The stronger the isolation level, the more coordination is needed and the more throughput suffers. Most databases default to a level called Read Committed. It stops dirty reads but lets effects like non-repeatable reads. Choosing the right isolation level is a trade-off between correctness and performance. And grasp what each level permits is a real requirement for anyone writing multi-user uses.

## The four letters

- <strong>Atomicity</strong> — the whole deal commits or none of it does. A failure midway rolls all back, with steps that now ran cleanly.
- <strong>Consistency</strong> — a deal moves the database from one valid state to another. It cannot leave money existing that came from nowhere.
- <strong>Isolation</strong> — concurrent deals do not see each other's half-finished work, to a degree controlled by the isolation level.
- <strong>Durability</strong> — once COMMIT returns, the change survives a crash the instant after.

## Isolation levels, briefly

<strong>READ UNCOMMITTED</strong> lets one session see another's uncommitted changes. A "dirty read". <strong>READ COMMITTED</strong>, the default in most engines, blocks that: a session just ever sees data that has really been committed. Stricter levels (REPEATABLE READ, SERIALIZABLE) exist to stop other classes of anomaly, at a cost in concurrency.

## The bank transfer. And why it needs a deal

Move &pound;100 from account A to account B and two statements are involved:

```sql
UPDATE accounts SET balance = balance - 100 WHERE id = 'A';
UPDATE accounts SET balance = balance + 100 WHERE id = 'B';
```

If the server loses power between them, &pound;100 has vanished. Not been delayed &mdash; vanished, permanently, with the database in a state that no accounting rule lets.

A deal makes the pair inseparable:

```sql
BEGIN;
  UPDATE accounts SET balance = balance - 100 WHERE id = 'A';
  UPDATE accounts SET balance = balance + 100 WHERE id = 'B';
COMMIT;
```

Now either both updates are permanent or neither happened. A crash before `COMMIT` leaves the database just as it was. A crash after it leaves both changes in place, since the engine wrote them durably before acknowledging the commit.

All else in this topic is about the guarantees that make that promise trustworthy. And about what happens when a few deals run at once.

## The four letters, with the failure each one stops

<strong>Atomicity</strong> &mdash; all or nothing. Stops: half a transfer. Built with an undo log. So an aborted deal can be rolled back to its starting point.

<strong>Consistency</strong> &mdash; the database moves from one valid state to another, with all constraints satisfied. Stops: a foreign key pointing at a deleted row, a negative balance where a `CHECK` forbids it. This is the letter that depends partly on you: the database enforces the rules you declared, not the ones you just had in mind.

<strong>Isolation</strong> &mdash; concurrent deals do not see each other's unfinished work. Stops: reading a balance mid-transfer and finding a total that never really existed. This is the letter with dials on it. And the next section is about them.

<strong>Durability</strong> &mdash; once committed, it survives a crash. Stops: losing an acknowledged write to a power cut. Built by writing to a log on stable storage before reporting success. It is why commit latency is bounded by how fast your disk can flush.

## Isolation levels, and the anomalies they let

Perfect isolation is costly. So SQL sets levels that trade correctness guarantees for concurrency.

|Level|Dirty read|Non-repeatable read|Phantom read|
|---|---|---|---|
|Read Uncommitted|Possible|Possible|Possible|
|Read Committed|No|Possible|Possible|
|Repeatable Read|No|No|Possible*|
|Serializable|No|No|No|

The three anomalies, in plain terms:

- <strong>Dirty read</strong> &mdash; you read a change another deal has not committed and may still roll back.
- <strong>Non-repeatable read</strong> &mdash; you read the same row twice in one deal and get other vals, since someone committed in between.
- <strong>Phantom read</strong> &mdash; you run the same query twice and get other <em>rows</em>, since someone inserted or deleted matching records.

Read Committed is the default in PostgreSQL, Oracle and SQL Server. MySQL's InnoDB defaults to Repeatable Read. The asterisk above is since PostgreSQL's Repeatable Read, built with snapshots, stops phantoms too. The standard permits them, this build does not.

Serializable is the just level that guarantees the result is the same to running the deals one after another. It costs throughput, either through locking or through aborting deals that would have conflicted. So it is reserved for the parts of a system where correctness genuinely outranks speed. Money, inventory, seat booking.

## Making a few statements into one

A deal is the promise that a group of statements happens fully or not at all. The demonstration is short since the idea is short -- and the interesting part is what the promise costs and what it does not cover.

```sql-run
-- The classic case: move money, and never lose it in transit.
-- Two UPDATEs that must both happen.

CREATE TABLE accounts (id INTEGER PRIMARY KEY, owner TEXT, balance REAL);
INSERT INTO accounts VALUES (1, 'Ada', 500.0), (2, 'Bala', 120.0);

SELECT owner, balance FROM accounts ORDER BY id;

-- Committed: both halves stick.

BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;

SELECT owner, balance FROM accounts ORDER BY id;
```

A rollback reverses all changes made in the deal, still those that now executed successfully.

```sql-run
-- Rolled back: neither half survives, including the one that had
-- already run.

CREATE TABLE accounts (id INTEGER PRIMARY KEY, owner TEXT, balance REAL);
INSERT INTO accounts VALUES (1, 'Ada', 400.0), (2, 'Bala', 220.0);

BEGIN;
UPDATE accounts SET balance = balance - 400 WHERE id = 1;
UPDATE accounts SET balance = balance + 400 WHERE id = 2;
ROLLBACK;

SELECT owner, balance FROM accounts ORDER BY id;

-- That is ATOMICITY, the A. The other three:
--
-- CONSISTENCY  the database moves between valid states -- constraints
--              hold before and after, never halfway.
-- ISOLATION    concurrent transactions do not see each other's
--              unfinished work. This is the one with settings: read
--              committed, repeatable read, serializable, each trading
--              strictness for concurrency.
-- DURABILITY   once COMMIT returns, the change survives a crash.
--
-- Isolation is the one that leaks into application code, because the
-- weaker levels permit specific anomalies -- a row that changes between
-- two reads in the same transaction, or a sum that includes a row that
-- was not there when you counted. Which anomalies you can tolerate is a
-- decision, and the default in most engines is not the strictest one.
--
-- And the limit worth knowing: a transaction protects the DATABASE. If
-- your handler charges a card and then writes a row, the rollback undoes
-- the row and not the charge.
```

## Guided tour

1. <strong>Step through a clean transfer.</strong> BEGIN, debit Alice, credit Bob, COMMIT. Session B's balances just change at the very last step.
2. <strong>Switch to READ UNCOMMITTED and step again.</strong> Now B sees Alice's balance drop the instant A's UPDATE runs — before COMMIT. That is a dirty read. And it is why READ UNCOMMITTED is rarely the default.
3. <strong>Tick "Fail after the second UPDATE" and step through again.</strong> Both writes ran. Alice was debited, Bob was credited. But the deal rolls back instead of committing. And Session A's own view snaps back to the first balances. Atomicity in one demonstration: a done write is not a committed write.

## In one line

A deal makes a group of writes behave as one unit: Atomicity guarantees all-or-nothing, Consistency guarantees the result is valid, Isolation controls what concurrent sessions can see of work in progress. And Durability guarantees a commit survives a crash. Isolation is a dial, not a switch. READ UNCOMMITTED trades correctness for speed by permitting dirty reads. It is why READ COMMITTED is the default almost all over.

## Locks, deadlocks, and how to avoid them

When two deals want the same row, one waits. When two deals each hold something the other wants, both wait forever &mdash; a <strong>deadlock</strong>. Databases detect this and kill one of the deals with an error rather than hanging.

The classic recipe:

```
Transaction 1: UPDATE accounts SET ... WHERE id = 'A';   -- holds A
Transaction 2: UPDATE accounts SET ... WHERE id = 'B';   -- holds B
Transaction 1: UPDATE accounts SET ... WHERE id = 'B';   -- waits for 2
Transaction 2: UPDATE accounts SET ... WHERE id = 'A';   -- waits for 1
```

Three practices remove most deadlocks in practice:

1. <strong>Always touch rows in a steady order</strong>. Sort account IDs before updating them. And the cycle above cannot form.
2. <strong>Keep deals short.</strong> Never hold a deal open across a network call, a user's think time. Or an external API. The most common cause of lock contention is a deal that started before it needed to.
3. <strong>Retry on deadlock.</strong> Deadlock errors are expected under load, not exceptional. Use code that touches contended rows should catch the error and retry with a short random delay.

A fourth, for the set case of updating a row you have just read: use `SELECT ... FOR UPDATE` to lock it at read time. Or you have a lost-update race where two deals both read 100, both write 90. And one update disappears.

## Deals in use code

Two patterns cause most production incidents in this area.

<strong>The long deal.</strong> Opening a deal, calling a payment provider. And committing on the response holds locks for the duration of an unpredictable network call. Do the external work first. Or split the work so the deal covers just the database changes.

<strong>The forgotten rollback.</strong> An exception path that leaves a deal open ties up a connection and holds its locks until a timeout. Use the language's context manager or deal decorator rather than manual `BEGIN`/`COMMIT` pairs:

```python
with connection.transaction():          # commits on success, rolls back on error
    debit(account_a, 100)
    credit(account_b, 100)
```

<strong>Savepoints</strong> are worth knowing for long multi-step work: they mark a point you can roll back to without abandoning the whole deal. It lets one step fail and be retried while the earlier steps stand.

## Questions people ask

<strong>Do I need a deal for a single statement?</strong> No. Each single statement runs in its own implicit deal. You need one when two or more statements must succeed or fail together.

<strong>Does a rollback undo all?</strong> All transactional. Sequence and auto-increment counters often do not roll back. It is why IDs can have gaps. And anything you did outside the database certainly does not.

<strong>What does NoSQL give up here?</strong> Varies by system. Many offer atomicity within a single document or partition but not across them. And eventual rather than immediate consistency across replicas. A few document databases have added multi-document deals since.

<strong>Is Serializable always the safest choice?</strong> Safest. And slowest, and it makes serialisation-failure retries a normal part of use logic. Use it where the correctness matters most rather than all over by default.

<strong>What is two-phase commit?</strong> A protocol for making a deal atomic across a few databases: all participants promise they can commit, then all commit. It works, and it is slow and fragile enough that most modern designs prefer a saga. A sequence of local deals with compensating actions &mdash; instead.

<strong>Why did my deal fail with a serialisation error?</strong> Since the engine detected that committing it would break the illusion of one-at-a-time execution. It is not a bug. Retry the deal.

## Recap in one screen

- A deal makes a few statements succeed or fail as one unit.
- Atomicity: all or nothing. Consistency: constraints hold. Isolation: concurrent work stays invisible. Durability: committed means survived.
- Isolation levels trade guarantees for concurrency. Read Committed is the common default, Serializable the strict one.
- Deadlocks are normal under load. Order your writes always, keep deals short, and retry.
- Never hold a deal open across a network call.
