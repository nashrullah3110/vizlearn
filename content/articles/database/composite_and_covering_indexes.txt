title: Composite and Covering Indexes
intro: A composite index stores multiple columns in one ordered structure, so column order determines which searches and sorts it can support well.

## How column order shapes a composite index
An index on (last_name, first_name) is ordered first by last name, then by first name within each last name. It is useful for searches on last_name and often for searches on both columns. It is generally less useful for a query that filters only by first_name.

For example, (customer_id, created_at) can support a customer's orders in date order:


```sql-run
SELECT order_id, created_at
FROM orders
WHERE customer_id = 42
ORDER BY created_at DESC;
```


Equality conditions on leading columns commonly narrow the search before later columns are used. A range condition changes how later columns can help. The planner and engine matter: PostgreSQL can sometimes use skip scans, so the “leftmost prefix” is a useful design guide, not a universal absolute.

## Covering an entire query
An index is covering for a query when it contains all the columns needed to find and return the requested rows. The engine may then avoid reading the table for some or all results. In SQLite this is reported as a “covering index” in <code>EXPLAIN QUERY PLAN</code>. PostgreSQL's index-only scans have additional visibility requirements, so an index containing every selected column does not guarantee a table-free read.

## Design and trade-offs
Choose the column order from real query patterns: equality filters, range filters, joins, and requested ordering. Then inspect representative plans. Do not add every selected column to the index automatically. Larger indexes consume storage, slow inserts and updates, and increase cache pressure. Two separate indexes can help independent filters, but are not equivalent to one composite index when the query needs a particular combined order.

Start from the simpler [indexing guide](indexes_in_sql.html), then compare plans before and after an index change.

## Equality, range, and ordering example
For an index on (tenant_id, created_at), a query that filters tenant_id by equality and then asks for a created_at range can often use both parts effectively. A query filtering only on created_at cannot generally navigate the same ordered structure as directly as an index beginning with that column. If the query also sorts by created_at, the index direction and filter shape may let the engine avoid a separate sort. Verify the exact plan and data selectivity; one index cannot optimally serve every combination of filters.

## Check the full query shape
The best index depends on all parts of the query, not just its WHERE clause. If a report filters by tenant, sorts newest-first, and selects a few columns, test an index ordered by tenant and timestamp, with included columns only if the database supports them and measurements justify the extra size. An index can satisfy a sort in one direction or its reverse, but mixed directions and NULL ordering may change that. Read the plan for both a common tenant and a tenant with unusually many rows.
