title: Query Execution Order in SQL: A Practical Guide
intro: SQL is written SELECT first and executed SELECT almost last. Nearly every confusing SQL error - unknown alias, aggregate in WHERE - is explained by that gap.

## Written order versus execution order

A query is written in this order:

SELECT &rarr; FROM &rarr; WHERE &rarr; GROUP BY &rarr; HAVING &rarr; ORDER BY &rarr; LIMIT

It is executed in this one:

FROM &rarr; JOIN &rarr; WHERE &rarr; GROUP BY &rarr; HAVING &rarr; SELECT &rarr; DISTINCT &rarr; ORDER BY &rarr; LIMIT

The database first works out which rows it is dealing with (FROM and JOIN), filters them (WHERE), groups what survives (GROUP BY), filters the groups (HAVING), and only then computes the output columns (SELECT). Sorting and limiting happen last, on the finished result.

## The two errors this explains

<strong>"Column does not exist" on an alias in `WHERE`:</strong>

```sql
SELECT price * quantity AS line_total
FROM   order_lines
WHERE  line_total > 100;          -- error
```

`WHERE` runs at step 2 and `SELECT` at step 5, so `line_total` does not exist yet. Repeat the expression, or wrap the query:

```sql
SELECT * FROM (
  SELECT price * quantity AS line_total FROM order_lines
) t WHERE line_total > 100;
```

<strong>"Aggregate not allowed in WHERE":</strong>

```sql
SELECT   customer_id, SUM(total)
FROM     orders
WHERE    SUM(total) > 1000        -- error
GROUP BY customer_id;
```

The sum is produced at step 3; `WHERE` runs at step 2. `HAVING` is the clause that runs after grouping, and is therefore the one that can see it.

The mirror image is why `ORDER BY` <em>can</em> use an alias: it runs at step 6, after `SELECT` has created it.

## WHERE and HAVING are not interchangeable

<p>Both filter, at different stages, and the distinction matters for correctness as well as speed:</p><ul><li><strong>WHERE</strong> filters individual <em>rows</em>, before grouping. Excluded rows never reach the aggregate.</li><li><strong>HAVING</strong> filters <em>groups</em>, after aggregation. All rows contribute to the aggregate; whole groups are then discarded.</li></ul><span class="mono-font">WHERE status = 'paid'</span> computes totals from paid orders only. <span class="mono-font">HAVING SUM(amount) &gt; 1000</span> computes totals from every order and keeps the customers whose total exceeds 1000. Moving a condition between them changes the answer.<p>When a condition <em>could</em> go in either &mdash; a plain column filter &mdash; put it in WHERE. Filtering earlier means fewer rows to group, which is almost always faster.</p>

## Written order versus the order things happen

SQL is written in an order designed to read like English and executed in a different one. Almost every confusing error message in SQL comes from that mismatch.

|Written|Executed|
|---|---|
|1. `SELECT`|5. `SELECT`|
|2. `FROM` / `JOIN`|1. `FROM` / `JOIN`|
|3. `WHERE`|2. `WHERE`|
|4. `GROUP BY`|3. `GROUP BY`|
|5. `HAVING`|4. `HAVING`|
|6. `ORDER BY`|6. `ORDER BY`|
|7. `LIMIT`|7. `LIMIT`|

So the real sequence is: assemble the rows, filter them, group them, filter the groups, work out what to display, sort, then cut.

(Strictly, this is the <em>logical</em> order. The planner may physically do things in another order entirely &mdash; pushing a filter down into an index scan, for instance &mdash; as long as the result is what this sequence would produce.)

## Following one query through all seven steps

```sql
SELECT   c.country, COUNT(*) AS orders, SUM(o.total) AS revenue
FROM     orders o
JOIN     customers c ON c.id = o.customer_id
WHERE    o.status = 'complete'
GROUP BY c.country
HAVING   SUM(o.total) > 5000
ORDER BY revenue DESC
LIMIT    5;
```

1. <strong>`FROM`/`JOIN`</strong> &mdash; build the combined set of order-and-customer rows. If 50,000 orders match 8,000 customers, this is where the row count is decided.
2. <strong>`WHERE`</strong> &mdash; drop everything not complete. Say 30,000 rows survive.
3. <strong>`GROUP BY`</strong> &mdash; collapse those into one row per country. Perhaps 40 rows now.
4. <strong>`HAVING`</strong> &mdash; drop countries under 5,000 in revenue. Perhaps 12 rows.
5. <strong>`SELECT`</strong> &mdash; compute and name the output columns, including the aliases `orders` and `revenue`.
6. <strong>`ORDER BY`</strong> &mdash; sort those 12 rows by revenue, using the alias created one step earlier.
7. <strong>`LIMIT`</strong> &mdash; keep the top 5.

Reading it this way answers most "why is this slow?" questions too: the expensive steps are the ones operating on the largest row counts, which are almost always the join and the filter. Narrowing step 2 helps everything after it.

## Exploration guide

1. <strong>Step through a query.</strong> Press <strong>Step</strong> repeatedly and watch which clause runs at each stage. FROM produces the rows, WHERE removes some, GROUP BY collapses the rest, and SELECT is near the end.
2. <strong>Break it deliberately.</strong> Enable the option that uses a SELECT alias in WHERE. It fails, because at that point the alias has not been created.
3. <strong>Then use the same alias in ORDER BY.</strong> Enable that option instead. It works &mdash; same alias, different clause, and the execution order is the only reason.
4. <strong>Reset and compare.</strong> Press <strong>Reset</strong> and run a working query, watching how many rows survive each stage. Filtering early leaves far less work for everything downstream.

## What usually goes wrong

- <strong>Using a SELECT alias in WHERE or GROUP BY.</strong> Repeat the expression, or wrap the query in a subquery or CTE where the alias already exists.
- <strong>Putting an aggregate in WHERE.</strong> Use HAVING.
- <strong>Using HAVING for row filters.</strong> Correct results, more work &mdash; the rows are grouped before being discarded.
- <strong>Expecting LIMIT to speed up an aggregate.</strong> LIMIT runs last, so the database has already grouped and sorted everything before it truncates.
- <strong>Filtering an outer join in WHERE.</strong> A condition on the right-hand table in WHERE discards the NULL rows and silently turns the LEFT JOIN into an INNER JOIN. Put it in the ON clause instead.

## Key takeaway

SQL executes FROM, WHERE, GROUP BY, HAVING, SELECT, ORDER BY, LIMIT &mdash; not the order it is written in. That single fact explains why SELECT aliases work in ORDER BY but not WHERE, why aggregates belong in HAVING rather than WHERE, and why filtering early is faster. When a query does something surprising, walking it through the execution order usually answers it in one step.

## Where the other clauses fit

Several things do not appear in the classic seven-step list and need placing.

- <strong>`DISTINCT`</strong> runs after `SELECT` and before `ORDER BY`. That is why `SELECT DISTINCT x FROM t ORDER BY y` fails in strict engines &mdash; `y` was removed before the sort could use it.
- <strong>Window functions</strong> are computed after `HAVING` and before `DISTINCT`. They can see the grouped rows, and `WHERE`/`HAVING` cannot see them. Filtering on a window function always needs an outer query.
- <strong>CTEs (`WITH`)</strong> are conceptually evaluated first, as named inputs to the main query, though modern planners inline them and optimise across the boundary.
- <strong>`OFFSET`</strong> runs with `LIMIT`, at the very end, after everything has been produced and sorted &mdash; which is exactly why deep offsets are slow.

Putting those together, the fuller order is:

<p class="mono-font">FROM &rarr; WHERE &rarr; GROUP BY &rarr; HAVING &rarr; window functions &rarr; SELECT &rarr; DISTINCT &rarr; ORDER BY &rarr; LIMIT/OFFSET</p>

## What the planner is allowed to change

The logical order defines the <em>result</em>, not the physical work. The optimiser rewrites freely as long as the answer is identical:

- <strong>Predicate pushdown</strong> &mdash; a `WHERE` condition can be applied while scanning a table, before the join, rather than after it.
- <strong>Join reordering</strong> &mdash; inner joins can be executed in any order; the planner picks the one with the smallest intermediate results.
- <strong>Index-provided ordering</strong> &mdash; if an index already returns rows in the requested order, step 6 costs nothing.
- <strong>Early termination</strong> &mdash; with `LIMIT` and a matching index, the engine can stop as soon as it has enough rows, without producing the full result.

This is why `EXPLAIN` output does not look like the seven steps: it shows the physical plan. The logical order is what you reason about; the plan is what actually ran.

## Questions people ask

<strong>Why can `ORDER BY` use an alias but `WHERE` cannot?</strong> Because `SELECT` (which creates aliases) runs after `WHERE` and before `ORDER BY`.

<strong>Does `LIMIT` make the query faster?</strong> Sometimes dramatically &mdash; with a matching index the engine can stop early. Without one, it may still have to produce and sort everything first.

<strong>Is `SELECT *` slower?</strong> It transfers more data and can prevent index-only scans, so on wide tables, yes. Name the columns you need.

<strong>Where do subqueries fit?</strong> A subquery in `FROM` is evaluated as part of step 1; one in `WHERE` as part of step 2; a correlated one runs in the context of the row being tested.

<strong>Does this order apply to every database?</strong> The logical order is standard and consistent across engines. Which relaxations they allow &mdash; aliases in `GROUP BY`, for instance &mdash; varies.

<strong>Why does my query return more rows after adding a join?</strong> Because step 1 happens first, and a one-to-many join multiplies rows before any filtering or grouping gets a chance to run.

## Recap in one screen

- Execution order is `FROM`, `WHERE`, `GROUP BY`, `HAVING`, window functions, `SELECT`, `DISTINCT`, `ORDER BY`, `LIMIT`.
- Aliases created in `SELECT` are unavailable in `WHERE` and `HAVING`, and available in `ORDER BY`.
- Aggregates do not exist until `GROUP BY` has run, which is why they belong in `HAVING`.
- The join happens first, so it decides the row count everything else works on.
- The planner may reorder the physical work freely &mdash; read `EXPLAIN` for what actually happened.
