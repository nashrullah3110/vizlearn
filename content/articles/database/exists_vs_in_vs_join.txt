title: EXISTS, IN, and JOIN: Choose by the Result You Need
intro: These SQL forms can relate rows, but they return different shapes and handle duplicates differently.

## Start with the question
Suppose you need customers who have placed at least one order. Three common approaches are a join, an `IN` subquery, and `EXISTS`. The right choice depends first on the result you need: matching pairs, membership, or just whether a match exists.

## Use JOIN when you need columns from both sides
A join combines matching rows. If one customer has five orders, joining customers to orders returns five rows for that customer. That multiplication is correct when the result is one row per customer-order pair. It becomes an accidental duplicate if you only wanted a list of customers.


```sql-run
SELECT DISTINCT c.customer_id, c.name
FROM customers AS c
JOIN orders AS o ON o.customer_id = c.customer_id;
```


`DISTINCT` can remove repeated customer rows, but it may hide a result-shape mistake and add work.

## Use EXISTS for a yes/no match
`EXISTS` tests whether its subquery returns at least one row. The outer row appears once, regardless of how many matching orders exist.


```sql-run
SELECT c.customer_id, c.name
FROM customers AS c
WHERE EXISTS (
  SELECT 1 FROM orders AS o
  WHERE o.customer_id = c.customer_id
);
```


For positive membership, `IN (subquery)` is also clear when the subquery produces the candidate values. The optimizer may transform these forms similarly; do not assume one is always faster. Compare plans on real data.

## The NULL trap in NOT IN
If the subquery used by `NOT IN` contains a `NULL`, a nonmatching value may evaluate to UNKNOWN rather than TRUE. `WHERE` keeps only TRUE rows, so expected results disappear. `NOT EXISTS` often expresses “there is no matching row” more safely, but write the correlation condition carefully and account for nullable keys.

This follows SQL's three-valued logic; see [NULL handling](null_handling_in_sql.html). For filtering before grouping, see [WHERE](where_clause_in_sql.html).

## Choose by multiplicity
To show every matching order, use JOIN because each result should represent a customer-order pair. To list a customer once if any order qualifies, use EXISTS because it tests membership without multiplying the outer row. IN is concise when the subquery is a list of IDs. These are semantic choices; modern optimizers may turn them into similar plans. A useful test is to add two matching orders for one customer: if the answer should still contain that customer once, the query should express existence or explicitly deduplicate.
