title: Database Sharding: Distribute Data Across Nodes
intro: Sharding splits a dataset across multiple database nodes so storage and work can be distributed horizontally.

## What a shard is
A shard is one part of a larger dataset stored on a separate node or cluster member. A sharding rule maps each record to a shard, commonly by range or hash of a shard key. An application or routing layer uses that key to locate the record.

Sharding can add capacity when one server no longer meets storage or throughput needs. It also adds coordination, operations, and failure modes. Scaling a single database, archiving old data, or adding indexes may be simpler; measure the bottleneck before sharding.

## The shard key shapes the system
A good shard key distributes writes and storage while appearing in common queries. A key with only a few values or one extremely popular value can create a hot shard. Queries that omit the key may need to contact many shards, and cross-shard transactions or joins can be more expensive.

Changing the shard key or adding nodes may require data movement and rebalancing. Design how routing metadata changes, how resharding is observed, and what happens when a shard is unavailable.

## Sharding versus partitioning
Partitioning divides a logical table into pieces managed within a database system. Sharding distributes data across separate nodes and therefore requires routing and coordination. Some products combine both ideas. See [partitioning](partitioning_in_databases.html).

## A tenant-key example
Sharding by tenant ID can keep each tenant's requests on one shard, making tenant-scoped reads and transactions local. But a few unusually large tenants can create hot shards, and an administrative query across all tenants must fan out. Hashing tenant IDs may balance count but not workload size. Range-based placement can make range scans easier but may concentrate new writes. Track per-shard storage, request rate, and latency, and plan for a tenant that outgrows one shard.

## Choosing a key when queries differ
There is rarely one key that makes every access local. A tenant-scoped request may fit a tenant key, while a global time-range report can touch all shards. Record the fraction of requests that include the proposed key and estimate the fan-out for the rest. Also check whether a single tenant can exceed one shard's capacity. If both tenant isolation and global reporting matter, the architecture may need a separate analytical copy rather than forcing one shard key to serve incompatible workloads.

## Plan resharding before launch
A shard map must support moving data when a node is added, removed, or overloaded. Define how routing changes without losing writes, how readers handle a moving range, and how progress is monitored. Consistent hashing or range splitting can help, but do not remove the need for a migration protocol and rollback plan. Backups and restores should be tested at both shard and whole-dataset levels. Operational complexity is part of the cost of sharding, even when the key distribution looks ideal on paper.
