title: Non-Relational Databases: Different Data Models
intro: Non-relational is a broad label for databases that do not organize all access around the relational table model.

## Several families, not one model
Document databases store records as documents, often with nested fields. Key-value stores retrieve values by a key. Wide-column systems organize data into column families for distributed workloads. Graph databases represent entities and relationships for traversal.

These models make different operations convenient; none is best for every workload. Some products combine multiple models or support SQL-like queries, transactions, and schemas. “NoSQL” does not mean that a database has no query language or no structure.

## Schema flexibility still needs a contract
A flexible storage format can make new fields easier to add, but the application still needs to agree on required fields, types, and meanings. Without validation, records written by different versions of a service may disagree in ways that break readers.

Document models can embed related values to make common reads efficient, but duplication and unbounded growth complicate updates. Graph models support relationship traversal, but a relational database can also represent relationships. See [document models and rows](document_model_vs_rows.html) and [key-value and graph models](key_value_and_graph_models.html).

## Choose from access and consistency needs
Write down the queries, update patterns, consistency expectations, growth, and operational skills required. Compare those needs against a relational design before choosing a specialized store. A multi-database architecture also needs clear ownership of each fact and a way to handle partial failure across stores.

## Compare the same application question
For an order history page, ask whether the application needs whole order documents, joins to shared product records, or several query patterns across customers and dates. A document layout may simplify fetching a bounded order with its lines; a relational design may make cross-order analysis and foreign-key constraints easier. A graph store is relevant when traversing relationships is central, not just because records refer to each other. Compare realistic reads, writes, consistency, and operational cost using the same example data.

## Plan for consistency across stores
When an application writes the same fact to a relational database and a cache or search index, those writes are not automatically one atomic transaction. A crash between them can leave the copies inconsistent. Decide which store is authoritative, how changes are propagated, how consumers detect lag, and how a failed update is retried. The operational cost of synchronizing two models can outweigh the query benefit. Start with one system when it meets the workload, then add another only for a measured need.
