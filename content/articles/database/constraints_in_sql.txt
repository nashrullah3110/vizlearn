title: SQL Constraints: NOT NULL, UNIQUE, CHECK, and FOREIGN KEY
intro: Constraints make the database reject invalid states, protecting data even when rows are written by different applications.

## Put durable rules beside the data
A constraint is a rule the database checks when data is inserted or changed. Unlike validation in one application screen, the rule applies to every writer that reaches the table. Use constraints for facts that must always hold, such as an identifier being unique or an order referring to an existing customer.


```sql-run
CREATE TABLE orders (
  id INTEGER PRIMARY KEY,
  customer_id INTEGER NOT NULL,
  total NUMERIC CHECK (total >= 0),
  FOREIGN KEY (customer_id) REFERENCES customers(id)
);
```


<code>NOT NULL</code> rejects missing values; <code>UNIQUE</code> prevents duplicate non-NULL keys in SQLite and PostgreSQL; <code>CHECK</code> requires a condition not to be false; and a foreign key enforces a reference when foreign-key checking is enabled. SQLite applications must enable <code>PRAGMA foreign_keys = ON</code> for each connection unless the build/configuration sets it otherwise.

## NULL and defaults need care
A <code>CHECK</code> condition that evaluates to <code>NULL</code> is not false, so it can pass. Combine it with <code>NOT NULL</code> when a value is required. In SQLite and PostgreSQL, a <code>UNIQUE</code> constraint permits multiple <code>NULL</code> values because NULLs are not treated as equal for this purpose. Other engines offer different options.

A <code>DEFAULT</code> is not a validation rule: it supplies a value when a column is omitted (or <code>DEFAULT</code> is requested). It does not replace an explicitly supplied <code>NULL</code>. Test the exact behavior in your target engine.

## Add rules safely
For an existing table, first find and correct rows that violate the proposed constraint. Then apply a migration and check how the engine validates or locks the table. Constraint enforcement and <code>ALTER TABLE</code> capabilities differ by database. See [primary and foreign keys](primary_and_foreign_keys.html) for choosing identifiers and [normalization](normalization_in_sql.html) for schema structure.

## Foreign-key actions are domain rules
A foreign key can reject deletion of a referenced parent, cascade the deletion to children, or set the child reference to NULL. These choices change what data survives, so they should reflect the domain. Cascading deletion may be correct for temporary child records but dangerous for invoices or audit history. Constraint failures are useful signals: surface a clear application error instead of retrying blindly. Also test enforcement in the deployed environment, especially with connection pools and SQLite where the foreign-key setting is connection-specific.
