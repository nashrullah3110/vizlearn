title: ORDER BY: SQL Results Have No Guaranteed Order Without It
intro: A database may return rows in any order unless the query explicitly requests one with ORDER BY.

## Ask for the order you need
Tables represent rows, not a sorted list. An index or insertion history may make results appear ordered, but SQL does not guarantee that order without ORDER BY. Add it whenever sequence matters, including reports, exports, and pagination.


```sql-run
SELECT order_id, created_at
FROM orders
ORDER BY created_at DESC, order_id DESC;
```


Sorting by only created_at leaves ties unordered. A stable unique tie-breaker such as order_id makes the requested order deterministic.

## NULLs and collations
The placement of NULL values and text comparison rules can vary by engine and collation. PostgreSQL supports NULLS FIRST and NULLS LAST; SQLite also supports explicit NULL ordering in current versions. Text order can depend on locale and collation. Test the target database when results must be portable.

## Sorting has a cost
The engine may satisfy an order using an index or sort rows at runtime. An index matching the filter and order can help, but adds storage and write cost. Check the plan rather than assuming either that an index is used or that every sort is expensive.

A final ORDER BY controls the result order; ordering inside a subquery does not generally guarantee the outer query's order. Specify order at the query level whose output the user consumes. See [LIMIT and OFFSET](limit_and_offset_in_sql.html) and [indexes](indexes_in_sql.html).

## Make a ranking deterministic
If the question is “top ten orders by total,” use ORDER BY total DESC and add a unique ID as the next key. Otherwise, orders with equal totals can exchange positions between executions. If NULL totals are possible, decide whether they should appear first or last rather than relying on a dialect default. Also check whether total is computed or stored: ordering by an expression may need a matching expression index or a sort. The output is only a stable ranking when all ordering ties are resolved.

## Limit only after a complete order
For a top-N query, apply LIMIT to the same SELECT whose ORDER BY expresses the ranking. If only the first key is ordered and ties remain, the chosen N rows can vary. If the ordering key can change between requests, even a tie-breaker may not preserve a user's place in the list; use a stable snapshot or cursor policy when that matters. Sorting in the application after fetching a limited subset cannot recover rows the database did not return.
