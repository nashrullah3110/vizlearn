title: Key-Value and Graph Database Models
intro: Key-value and graph databases organize access around different needs: direct lookup by key and traversal of relationships.

## Key-value: retrieve by a known key
A key-value store maps a unique key to a value. The central operation is usually retrieving, creating, or updating that value by key. This simple model can fit sessions, caches, counters, and state whose access patterns are known in advance. The value may be opaque to the store, limiting queries across its internal fields.

Redis is a common example and supports several richer data types beyond a plain string. Its data structures and persistence options mean it is not merely a simple dictionary; choose the operation and durability behavior deliberately.

## Graph: follow relationships
A graph database represents entities as nodes and their relationships as edges, often with properties on both. It is useful when a question requires traversing several connections, such as paths between people, dependencies, or recommendations. The relationship itself is a first-class part of the model.

A relational database can represent the same graph with tables and joins. A graph engine may make repeated, variable-depth traversal easier, but does not make every query faster. If most requests are simple lookups by ID, a graph model may add complexity without helping.

## Choose from the access pattern
Ask what the application needs to query and update, how relationships change, and what consistency and transaction guarantees are required. Do not choose a database because a category sounds newer. You may also combine stores, but then decide which system owns each fact and how updates remain consistent.

For comparisons with document databases and relational tables, see [relational databases](what_are_relational_databases.html) and [non-relational databases](what_are_non_relational_databases.html).

## A concrete model choice
A session store keyed by a random session token may need only set, get, expiry, and delete operations; a key-value model maps directly to that workload. A dependency explorer may need to walk from one service through several dependency levels; a graph model makes those edges central. If requirements later include rich filtering over arbitrary fields, the original simple model may need indexes, a different store, or a second representation. Capture expected queries and update rules before selecting the model.

## Account for durability and queries
A cache that can be rebuilt has different persistence needs from a store holding the only copy of a customer's state. Check whether the selected key-value product persists data, how replication and failover work, and what commands are atomic. For graph queries, define maximum traversal depth, path semantics, and cycle behavior. These concerns are part of choosing a data model, not details to leave until deployment. Prototype the hardest expected query and update before committing to the model.
