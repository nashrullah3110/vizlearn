title: DML: Insert, Update, and Delete Rows
intro: Data Manipulation Language changes table contents; careful predicates and transactions keep those changes scoped and recoverable.

## The commands that change rows
DML (Data Manipulation Language) includes statements that insert, update, and delete rows. <code>INSERT</code> adds data, <code>UPDATE</code> changes selected rows, and <code>DELETE</code> removes selected rows. <code>SELECT</code> is often taught alongside DML, though SQL classifications vary.

<pre><code>UPDATE inventory
SET quantity = quantity - 1
WHERE product_id = 17 AND quantity &gt; 0;</code></pre>

The <code>WHERE</code> clause limits which rows change. Before running a broad update or delete, run an equivalent <code>SELECT</code> with the same predicate and inspect the rows. A missing <code>WHERE</code> can change or delete every row.

## Make multi-step changes atomic
When several statements must succeed together, use a transaction: begin, perform the changes, then commit only when the required conditions hold. Roll back when any step fails. The exact syntax and error recovery behavior are engine-specific; see [transactions and ACID](transactions_and_acid.html).

For an operation that inserts a row or updates it on a key conflict, many engines provide an upsert syntax. Names and semantics differ (<code>ON CONFLICT</code>, <code>ON DUPLICATE KEY</code>, or <code>MERGE</code>), so consult the target engine. Make the conflict key explicit and consider whether a retry can duplicate an external side effect.

## Bulk changes and safety
Large changes can hold locks, generate substantial logs, and affect replication. Batch them only when the batches preserve the intended transaction semantics. Record how many rows changed and verify important invariants afterward. Use bound parameters for values supplied by users; see [SQL injection prevention](sql_injection_and_parameters.html).

## Verify the scope of destructive statements
For a critical update, check both the predicate and the number of affected rows. An update expected to change exactly one account should fail safely if it changes zero or several rows. Use a transaction when the count must be checked before commit. For deletion, decide whether records should be physically removed or retained with a status and audit trail; soft deletion changes every query that must hide inactive rows. See [WHERE](where_clause_in_sql.html) for predicate behavior.

## Use conditional updates for invariants
A read followed by a write can race when two clients act at once. For inventory, subtract one only where the current quantity is positive, then check that exactly one row changed. The database evaluates the predicate and update as one statement, avoiding an application-level gap between the check and the write. If several tables must change together, put those statements in a transaction. The correct isolation and locking strategy still depends on the database and the rest of the workflow.
