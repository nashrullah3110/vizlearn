title: SQL WHERE: Filter Rows with Conditions
intro: WHERE keeps only rows for which its condition is TRUE; NULL makes some familiar comparisons evaluate to UNKNOWN instead.

## Filter before grouping
WHERE applies a condition to input rows. For each row, SQL evaluates the condition and retains the row only when the result is TRUE. FALSE and UNKNOWN are both excluded. This filtering happens before GROUP BY and aggregate calculations.


```sql-run
SELECT order_id, total
FROM orders
WHERE status = 'paid'
  AND total >= 50;
```


This returns paid orders whose total is at least 50. Conditions can combine comparisons with AND, OR, and NOT; parentheses make mixed logic easier to review.

## NULL and three-valued logic
A comparison such as email = NULL is UNKNOWN, so it does not select missing emails. Use IS NULL or IS NOT NULL. Be careful with NOT IN when the candidate set may contain NULL; see [NULL handling](null_handling_in_sql.html) and [EXISTS vs IN](exists_vs_in_vs_join.html).

## Write filters the planner can use
A simple predicate on an indexed column can make an index useful, but the planner decides whether that is cheaper than scanning. Wrapping a column in a function may prevent a regular index from helping unless an expression index exists. Do not rewrite a correct condition based on guesswork; inspect [query plans](explain_and_query_plans.html) and measure.

For grouped results, use HAVING rather than trying to filter aggregates in WHERE. See [GROUP BY](groupby_in_sql.html).

## Test boundary cases
For a numeric filter such as quantity >= 5, test values 4, 5, and 6 to confirm the boundary is inclusive. For text and dates, check collation and time-zone assumptions. Parenthesize mixed AND and OR conditions because AND generally binds more tightly than OR. A predicate like status = 'paid' OR status = 'refunded' AND region = 'west' does not mean both statuses are limited to west; parentheses make the intended grouping clear. Test NULL separately because ordinary comparisons evaluate to UNKNOWN.

## Read predicates as truth tables
When conditions mix AND and OR, write the intended groups explicitly. For example, a paid or refunded order from the west region should group the two status alternatives before combining them with the region condition. Without parentheses, operator precedence can include paid orders from other regions. NULL adds a third outcome: NOT UNKNOWN remains UNKNOWN, so a row with a missing status still fails the WHERE filter. A small table with one row per boundary case is often the fastest way to validate a complicated predicate.
