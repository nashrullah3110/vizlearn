title: Relational Databases: Small Tables, Strong Links
intro: Fifty years on, the relational model is still the default way to store business data. This is why.

## The problem it solves

A <strong>relational database</strong> stores data in <strong>tables</strong> of rows and columns, where every table describes one kind of thing &mdash; customers, orders, products &mdash; and tables are connected by shared key values rather than by nesting data inside each other.

## Keys are the whole trick

|Key|What it does|
|---|---|
|Primary key|Identifies a row uniquely; never NULL|
|Foreign key|Points at another table's primary key|
|Composite key|A primary key made of several columns|
|Candidate key|Any column set that could serve as primary|
|Surrogate key|An artificial id (integer or UUID) with no business meaning|
|Natural key|A real-world identifier, such as an ISBN or email|

The foreign key is what turns a pile of tables into a database. Declared properly, it makes an order pointing at a non-existent customer impossible &mdash; not unlikely, not caught by a validation function somewhere, but rejected by the engine for every client that ever connects.

Surrogate versus natural keys is one of the few genuinely contested design questions. Surrogate keys are stable (people change email addresses) and compact, so most schemas use them. The right answer is usually both: a surrogate primary key for references, plus a `UNIQUE` constraint on the natural key so the real-world rule is still enforced.

## Why Split the Data at All?

<p>Switch this lab to <strong>one flat table</strong> and look at the red cells. The customer's name and city now repeat on every order they ever placed. That redundancy causes three classic problems:</p><ul><li><strong>Update anomaly</strong> &mdash; changing a customer's name means finding and editing every copy. Miss one and your data now contradicts itself. Press the rename button in both models and compare the counts.</li><li><strong>Insertion anomaly</strong> &mdash; you cannot record a new customer until they place an order, because there is nowhere to put them.</li><li><strong>Deletion anomaly</strong> &mdash; deleting a customer's only order erases the customer entirely.</li></ul><strong>Normalisation</strong> is the process of splitting tables until each fact is stored exactly once. The cost is that answering a question often requires a <span class="mono-font">JOIN</span> &mdash; and that trade, correctness for a little query effort, is the central bargain of the relational model.

## ACID: the other half of the promise

The relational model describes how data is arranged. ACID describes what happens when several people change it at once, and it is the reason banks and hospitals run on these systems.

- <strong>Atomicity</strong> &mdash; a transaction happens completely or not at all. No half-finished transfer.
- <strong>Consistency</strong> &mdash; every constraint holds before and after. No orphaned rows.
- <strong>Isolation</strong> &mdash; concurrent transactions do not see each other's unfinished work.
- <strong>Durability</strong> &mdash; once committed, it survives a power cut.

Together those guarantees mean the application does not have to reason about concurrency in the general case. Without them, every developer touching the system would have to get locking right, every time, for ever.

## Tables, rows and the idea underneath

A relational database stores data in tables: rows are records, columns are attributes, and every row in a table has the same columns. That much is just a spreadsheet.

What makes it <em>relational</em> is that tables refer to each other by value rather than by pointer. An order does not contain a customer; it contains a customer <em>id</em>, and the database can follow that id to the customers table whenever asked. Nothing is nested, nothing is duplicated, and the connections are made at query time.

That design decision, from Edgar Codd's 1970 paper, is why the model has outlasted everything built to replace it. Because relationships are values rather than structure, you can ask questions nobody anticipated when the schema was designed &mdash; join any two tables on any matching columns, and the answer comes out. A system that stored orders inside customers would answer "orders per customer" instantly and "customers per product" only with a full rewrite.

## Why split the data at all

Splitting has an obvious cost: getting a customer's name onto their order list requires a join. The benefits are less obvious until something goes wrong without them.

Store the customer's city on every order and one customer moving house means updating hundreds of rows. Miss one and the database now contains two contradictory answers to the same question, with no way to tell which is right.

Store it once, in the customers table, and the update touches a single row. Everything that references that customer sees the new value immediately, because there is only one value.

This is the argument for normalisation in a sentence: <strong>each fact should be stored in exactly one place</strong>. The join is the price, and the database is extremely good at joins.

## What "relational" actually buys you

The relational model is a small idea -- data in tables, relationships expressed as shared values rather than as pointers -- and its consequences are large. All of them are visible in four tables.

```sql-run
-- The whole database, listed. Four tables and nothing else: no
-- pointers, no nesting, no objects.

SELECT name AS table_name FROM sqlite_master WHERE type = 'table' ORDER BY name;

-- A relationship is a VALUE that appears in two places. orders.customer_id
-- holds the same number as customers.id, and that is the entire mechanism.

SELECT o.id AS order_id, o.customer_id, c.id AS customer_id_again, c.name
FROM orders o JOIN customers c ON c.id = o.customer_id
ORDER BY o.id LIMIT 3;

-- Because the link is a value rather than a pointer, the same data can be
-- traversed in any direction without being stored differently. Customers
-- to orders:

SELECT c.name, count(o.id) AS orders
FROM customers c LEFT JOIN orders o ON o.customer_id = c.id
GROUP BY c.id, c.name ORDER BY orders DESC LIMIT 3;

-- and products back to customers, through two tables the original
-- designer never had to anticipate:

SELECT p.name AS product, group_concat(DISTINCT c.name) AS bought_by
FROM products p
JOIN order_items i ON i.product_id = p.id
JOIN orders      o ON o.id = i.order_id
JOIN customers   c ON c.id = o.customer_id
GROUP BY p.id, p.name
ORDER BY p.name;

-- THAT is the payoff. Nobody stored "which customers bought a monitor";
-- the query derived it. A design that had nested orders inside customer
-- documents would answer the first question easily and this one only by
-- reading everything.
--
-- The other half of the model is that the database enforces the rules.

SELECT 'declared constraints' AS what, count(*) AS n FROM pragma_foreign_key_list('orders')
UNION ALL
SELECT 'columns in orders', count(*) FROM pragma_table_info('orders');

-- Those constraints hold for every writer -- your application, a
-- migration script, somebody at a console at 3am. That is the guarantee
-- being bought, and the price is a fixed schema: adding a column means
-- changing the table, which is exactly the trade the non-relational
-- models make differently.
```

## Summing up

Store each fact once, identify it with a primary key, and reference it with a foreign key. The database then enforces the relationships for you. Flattening everything looks simpler until the first time you have to change something.

## SQL, and why it survived

SQL is a <em>declarative</em> language: you describe the result you want, not the steps to produce it. `SELECT name FROM customers WHERE country = 'UK'` says nothing about indexes, scan order or join algorithms &mdash; the query planner decides all of that, and can change its mind as the data grows.

That separation is why a query written in 1995 still runs, and runs faster, on hardware and engines that did not exist then. It is also why two people write the same query differently and get the same plan.

The language is standardised (SQL:2023 is the current revision), and every engine adds its own extensions. The core &mdash; `SELECT`, joins, aggregation, transactions &mdash; is portable; date functions, string functions, upserts and window frame details are where dialects diverge.

## The main engines, briefly

|Engine|Character|
|---|---|
|PostgreSQL|Standards-compliant, extensible, strong JSON and geospatial support|
|MySQL / MariaDB|Ubiquitous in web hosting, fast simple reads, historically laxer about standards|
|SQLite|A single file, embedded in phones, browsers and applications everywhere|
|SQL Server|Microsoft's, deep integration with the .NET and Windows ecosystem|
|Oracle|Enterprise features and enterprise licensing|

SQLite deserves a mention beyond its size: it is probably the most widely deployed database in the world, and it is a full relational engine with transactions, constraints and window functions in a file you can email.

## Relational or not?

The honest comparison is not "relational versus NoSQL" but "which set of guarantees does this workload need".

Relational databases are the right default when your data has clear structure and relationships, when you need transactions across several records, when queries will be ad hoc and unpredictable, and when correctness matters more than raw write throughput. That covers the large majority of business applications.

Non-relational stores earn their place with genuinely schema-less documents, with write volumes that need horizontal sharding beyond what one node can serve, with key-value caching, with graph traversal many levels deep, and with time-series ingestion at enormous rates.

Note that the gap has narrowed from both sides. PostgreSQL stores and indexes JSON documents competently; several document databases now offer multi-document transactions. "Use the right tool" increasingly means "check whether the relational one already does it", because frequently it does.

## Questions people ask

<strong>Is a relational database slow?</strong> Not for the workloads it was designed for. A well-indexed PostgreSQL instance answers point queries in microseconds and handles tens of thousands of transactions a second on ordinary hardware.

<strong>What does "relation" mean?</strong> The mathematical term for a table &mdash; a set of tuples &mdash; not the relationships between tables, which is the common assumption.

<strong>Do I need to normalise everything?</strong> Normalise by default, denormalise deliberately for measured read paths. Starting denormalised because it might be faster is how schemas become unmaintainable.

<strong>Can relational databases scale?</strong> Vertically, very far. Horizontally, with more effort &mdash; read replicas are straightforward, sharding writes is not. Managed distributed SQL systems now offer horizontal scaling with relational semantics.

<strong>What is a view?</strong> A saved query that behaves like a table. It stores no data; it re-runs each time. A materialised view does store the result and needs refreshing.

<strong>Is JSON in a relational database a mistake?</strong> Not when used for genuinely variable data such as event payloads or user preferences. It becomes one when you put fields you regularly filter and join on inside a JSON blob instead of in columns.

## Recap in one screen

- Data lives in tables; rows are records and columns are attributes.
- Tables reference each other by value through foreign keys, which is what makes arbitrary joins possible.
- Each fact is stored once, so an update happens in one place.
- ACID transactions make concurrency the database's problem rather than yours.
- SQL is declarative: you state the result, the planner chooses how.
