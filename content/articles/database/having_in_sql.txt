title: HAVING: Filter Groups After Aggregation
intro: HAVING keeps or removes groups based on their aggregate values; WHERE filters individual rows before grouping.

## Two filters, two stages
Use `WHERE` for conditions on input rows. Use `HAVING` for conditions on groups, often involving an aggregate. For example, to find customers with at least three paid orders, remove unpaid orders first, then keep groups whose count reaches three.

<pre><code>SELECT customer_id, COUNT(*) AS paid_orders
FROM orders
WHERE status = 'paid'
GROUP BY customer_id
HAVING COUNT(*) &gt;= 3;</code></pre>

The result contains one row per qualifying customer. The `WHERE` clause reduces the rows that must be grouped; the `HAVING` condition cannot be applied until the counts exist.

## A common misplacement
A condition such as `status = 'paid'` belongs in `WHERE` when only paid rows should contribute to the count. Putting it in `HAVING` may require changing the grouping and can produce confusing results. Conversely, filtering on `COUNT(*)` in `WHERE` is invalid because that aggregate does not exist at the row-filter stage.

Some engines allow `HAVING` without `GROUP BY`, treating the input as one group; for portable SQL, use it with explicit grouping. Select the grouping key alongside aggregates so each output row is interpretable. See [GROUP BY](groupby_in_sql.html) and [aggregate functions](aggregate_functions_in_sql.html).

## Check the intended grain
Before adding `HAVING`, state what one result row should represent: a customer, month, product, or another key. Then verify the grouping columns and test a small dataset where one group is just below the threshold and another just above it. That catches off-by-one filters and accidental grouping by extra columns.

## Example: filter before and after grouping
Assume a customer has four orders, but only two are paid. With WHERE status = 'paid' and HAVING COUNT(*) >= 3, that customer is excluded because the group contains two qualifying rows. If instead all four orders should count but the customer must have at least one paid order, calculate both measures with conditional aggregation and filter on the paid count. Writing down the population for each metric prevents a subtle mistake where WHERE removes rows needed for another aggregate.

## Avoid changing the population accidentally
A filter before aggregation changes which rows contribute to every aggregate in the group. A HAVING predicate changes which completed groups are returned, but does not change the values already calculated inside those groups. If a query needs both all-order revenue and paid-order count, do not filter away unpaid rows in WHERE. Use conditional expressions or filtered aggregates for each measure, then apply HAVING to the calculated group values. This makes the data population for each metric explicit.
