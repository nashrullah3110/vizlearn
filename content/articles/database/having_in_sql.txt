title: HAVING: A Filter That Runs After the Grouping
intro: Same word, "filter". Different stage, different input, different answer.

## Quick Context

A grouped query runs in stages. Rows are read, <span class="mono-font kw">WHERE</span> discards the ones that fail a per-row test, what is left is collected into groups, each group is boiled down to its aggregates, and only then does <span class="mono-font kw">HAVING</span> get a look &mdash; at the groups, not the rows.

That ordering is the entire module. WHERE cannot see <span class="mono-font fn">SUM()</span> because no sum exists yet when WHERE runs. HAVING can, because by the time it runs the individual rows are gone.

## The order that explains everything

FROM &rarr; WHERE &rarr; GROUP BY &rarr; HAVING &rarr; SELECT &rarr; ORDER BY &rarr; LIMIT

Three consequences fall straight out of it:

- <strong>WHERE changes what the aggregates are.</strong> Filtering rows out before grouping removes their contribution from every SUM, AVG and COUNT downstream. Watch the totals in stage 2 move as you raise the WHERE threshold &mdash; the group is still there, but it is now the total of fewer rows.
- <strong>HAVING cannot bring anything back.</strong> It only ever removes whole groups from a set that has already been computed.
- <strong>Neither can see a SELECT alias in standard SQL</strong>, because SELECT runs after both. MySQL and SQLite allow an alias in HAVING as an extension; PostgreSQL and SQL Server do not.

## Which clause does a condition belong in?

A short decision rule that covers nearly everything:

|Condition|Goes in|
|---|---|
|On a raw column value (`status = 'paid'`)|`WHERE`|
|On a column you are grouping by|`WHERE` &mdash; cheaper, same result|
|On an aggregate (`COUNT(*) > 5`)|`HAVING`|
|On a `SELECT` alias for an aggregate|`HAVING`, and in most engines you must repeat the expression|
|On a window function|Neither &mdash; wrap in a CTE and use `WHERE` outside|

That last row catches people regularly. Window functions are computed after `HAVING`, so filtering on `ROW_NUMBER()` requires another query level.

Note also that `HAVING` without `GROUP BY` is legal: the whole result set is treated as one group. `SELECT SUM(amount) FROM sales HAVING SUM(amount) > 100000` returns either one row or none, which is occasionally a neat way to write a threshold check.

## Two things people are surprised by

<strong>HAVING works without GROUP BY.</strong> With no GROUP BY the whole table is one implicit group, so <span class="mono-font kw">SELECT</span> <span class="mono-font fn">SUM</span>(amount) <span class="mono-font kw">FROM</span> sales <span class="mono-font kw">HAVING</span> <span class="mono-font fn">SUM</span>(amount) &gt; 5000 returns either one row or none.<strong>An aggregate in HAVING need not appear in SELECT.</strong> You can filter on <span class="mono-font fn">COUNT</span>(*) while selecting only the region. The aggregate is computed either way; SELECT just decides what is shown.

## Two filters, two moments

`WHERE` and `HAVING` both remove rows. The difference is when they run, and everything else follows from that.

<p class="mono-font">FROM &rarr; WHERE &rarr; GROUP BY &rarr; HAVING &rarr; SELECT &rarr; ORDER BY &rarr; LIMIT</p>

`WHERE` runs before the grouping, so it sees individual rows and knows nothing about totals. `HAVING` runs after, so it sees one row per group and can test aggregates.

```sql
SELECT   region, SUM(amount) AS total
FROM     sales
WHERE    sale_date >= '2026-01-01'    -- individual rows: recent sales only
GROUP BY region
HAVING   SUM(amount) > 10000          -- whole groups: big regions only
ORDER BY total DESC;
```

Swap those two conditions and both fail. `WHERE SUM(amount) > 10000` is an error, because no sum exists yet when `WHERE` runs. `HAVING sale_date >= '2026-01-01'` is either an error or, worse, silently meaningless &mdash; the group has many dates and no single one to test.

## A worked example where the order changes the answer

Six sales, three regions:

|Region|Date|Amount|
|---|---|---|
|North|2025-11-02|8,000|
|North|2026-02-14|4,000|
|South|2026-01-20|7,000|
|South|2026-03-01|5,000|
|East|2025-12-10|9,000|
|East|2026-04-02|2,000|

Now run two queries that look similar and are not.

<strong>Filter first (`WHERE`), then group:</strong> only 2026 sales survive, so the totals are North 4,000, South 12,000, East 2,000. With `HAVING SUM(amount) > 10000`, only South is returned.

<strong>Group first, then filter groups (`HAVING` alone):</strong> totals are North 12,000, South 12,000, East 11,000 &mdash; all three exceed 10,000 and all three are returned.

Same data, same threshold, entirely different report. When someone says "these numbers don't match the other dashboard", this is frequently why.

The performance implication points the same way: `WHERE` throws rows away before the expensive grouping happens, so any condition that <em>can</em> go in `WHERE` should.

## WHERE and HAVING on the same query

WHERE filters rows before they are grouped and HAVING filters groups after. Running both on one query is the quickest way to see that they are not interchangeable, and to see the error you get when you reach for the wrong one.

```sql-run
-- WHERE runs first, on individual rows.
-- HAVING runs last, on the groups WHERE left behind.
--
-- Move the HAVING condition into the WHERE clause and re-run. SQLite
-- answers "misuse of aggregate: count()" -- at the moment WHERE is
-- evaluated the groups do not exist yet, so there is nothing to count.

SELECT c.name                  AS customer,
       count(o.id)             AS shipped_orders
FROM customers c
JOIN orders o ON o.customer_id = c.id
WHERE  o.status = 'shipped'      -- drops rows, before grouping
GROUP BY c.id, c.name
HAVING count(o.id) > 1           -- drops groups, after
ORDER BY shipped_orders DESC;
```

## Experiments to try

1. <strong>Start with HAVING alone.</strong> WHERE is at 0, so all 14 rows are grouped into 4 regions and <span class="mono-font kw">HAVING</span> <span class="mono-font fn">SUM</span>(amount) &ge; 800 removes one of them. Note which, and note its total.
2. <strong>Now add a row filter.</strong> Push <strong>WHERE amount &ge;</strong> to 200. Seven of the fourteen rows vanish from stage 1, every total in stage 2 drops, and every group that passed HAVING a moment ago now fails it &mdash; without HAVING itself changing at all.
3. <strong>Read the strike-throughs.</strong> Each group still lists the amounts WHERE removed, struck out. Those are the values missing from the totals above them.
4. <strong>Filter on a count instead.</strong> Set <strong>HAVING Aggregate</strong> to COUNT(*); the threshold slider retunes to a count-sized range and lands on 3. With WHERE at 0 every region qualifies, because the smallest has three sales. Push WHERE to 200 and none do.
5. <strong>Group by something finer.</strong> Put WHERE back to 0, set the aggregate to SUM(amount) with a threshold of 800, then set <strong>GROUP BY</strong> to rep. Nine small groups instead of four large ones, and not one reaches 800 &mdash; the biggest is 730. A HAVING threshold is only meaningful for the grouping it was chosen for.
6. <strong>Make HAVING empty-handed.</strong> Push the threshold past every group's total. Zero rows returned &mdash; which is a perfectly ordinary result, not an error.

## In one line

WHERE filters rows before grouping and HAVING filters groups after, which is why WHERE cannot mention an aggregate and why HAVING is the only place a condition on SUM or COUNT can live. The consequence people miss is that WHERE does not merely remove rows from the output &mdash; it changes what every aggregate downstream is computed from, so moving one condition between the two clauses changes the numbers, not just the row count. Put per-row conditions in WHERE, group conditions in HAVING, and when a condition is legal in both, put it in WHERE: filtering early is always the cheaper plan.

## Patterns worth knowing

<strong>Find duplicates.</strong> The canonical use of `HAVING`, and worth memorising:

```sql
SELECT   email, COUNT(*) AS copies
FROM     users
GROUP BY email
HAVING   COUNT(*) > 1
ORDER BY copies DESC;
```

<strong>Find customers meeting a volume threshold:</strong>

```sql
SELECT   customer_id, COUNT(*) AS orders, SUM(total) AS spend
FROM     orders
WHERE    order_date >= '2026-01-01'
GROUP BY customer_id
HAVING   COUNT(*) >= 3 AND SUM(total) > 500;
```

Several conditions combine with `AND`/`OR` exactly as in `WHERE`.

<strong>Compare a group against the overall average</strong>, using a scalar subquery inside `HAVING`:

```sql
SELECT   department, AVG(salary) AS dept_avg
FROM     employees
GROUP BY department
HAVING   AVG(salary) > (SELECT AVG(salary) FROM employees);
```

<strong>Exclude groups containing a value</strong>, which is a neat trick using a conditional count:

```sql
SELECT   order_id
FROM     order_lines
GROUP BY order_id
HAVING   COUNT(*) FILTER (WHERE status = 'cancelled') = 0;    -- PostgreSQL
-- portable form: HAVING SUM(CASE WHEN status = 'cancelled' THEN 1 ELSE 0 END) = 0
```

## Questions people ask

<strong>Can `HAVING` reference a `SELECT` alias?</strong> In MySQL and PostgreSQL, often yes; in standard SQL, no, because `SELECT` is evaluated after `HAVING`. Repeating the expression is the portable choice.

<strong>Is `HAVING` slower than `WHERE`?</strong> The clause itself is cheap; what costs is that `HAVING` operates after grouping, so more rows had to be grouped. Move conditions to `WHERE` whenever they can go there.

<strong>Can I use `HAVING` without an aggregate?</strong> Syntactically yes, on a grouped column, and it will work &mdash; but it is the same filter done later and more expensively, so put it in `WHERE`.

<strong>Why does my `HAVING COUNT(*) > 1` return nothing?</strong> Usually because the grouping is finer than intended &mdash; an extra column in `GROUP BY` makes every group unique. Check the grouping columns first.

<strong>Can I filter on a group's minimum or maximum date?</strong> Yes, that is exactly what `HAVING` is for: `HAVING MAX(order_date) < '2026-01-01'` finds customers who have not ordered this year.

<strong>Does `HAVING` work with `DISTINCT`?</strong> `HAVING COUNT(DISTINCT product_id) > 3` is valid and common &mdash; "orders containing more than three different products".

## Recap in one screen

- `WHERE` filters rows before grouping; `HAVING` filters groups after it.
- A condition on an aggregate can only live in `HAVING`; a condition on a raw column should live in `WHERE`.
- Which one you use changes the answer, not just the speed &mdash; filtering before grouping changes what is summed.
- `HAVING COUNT(*) > 1` is the standard duplicate finder.
- Window functions are computed later still, so filtering on them needs another query level.
