title: Self-Joins: Relate Rows in the Same Table
intro: A self-join uses two aliases of one table to compare or connect different rows in that table.

## One table, two roles
An employee table may include both an employee ID and a manager ID. To show each employee beside their manager's name, join the table to itself and assign each copy a clear alias.


```sql-run
SELECT e.name AS employee,
       m.name AS manager
FROM employees AS e
LEFT JOIN employees AS m
  ON e.manager_id = m.employee_id;
```


The aliases name the roles: e is the employee row and m is the referenced manager row. The left join keeps employees who have no manager, such as a top-level executive.

## Compare rows within a table
Self-joins can find pairs such as products in the same category or rows whose date ranges overlap. The join condition determines which pairs appear. For unordered pairs, use a strict condition like a.id &lt; b.id; using a.id &lt;&gt; b.id returns both (A, B) and (B, A).

The number of output rows can grow quickly when many rows match. Check uniqueness and cardinality before aggregating the result. If the problem is variable-depth traversal through a hierarchy, a [recursive CTE](recursive_ctes_in_sql.html) may be more suitable.

## Avoid common self-join mistakes
Joining each row to itself can create a trivial match; exclude it if the question needs distinct rows. Ambiguous column names are another risk, so qualify columns with aliases. A LEFT JOIN becomes effectively inner if a condition on the right alias is placed in WHERE and rejects NULLs; put match restrictions in ON when unmatched left rows must remain. See [joins](joins_in_sql.html).

## Pair each unordered relationship once
To find pairs of coworkers in the same team, joining on equal team IDs matches each person with themselves and returns both directions of every pair. Add a.id < b.id to exclude self-pairs and keep only one orientation. If the question instead concerns ordered relationships, such as employee and manager, do not impose that condition; use the directional foreign key. The pair condition encodes the meaning of the result, so state whether (A, B) differs from (B, A) before choosing it.

## Use a self-join for one-level relationships
A manager lookup is a one-level relationship: each employee row points to at most one manager row. For a chain of managers several levels above an employee, a single self-join only reaches the number of levels explicitly written. Use a recursive CTE when depth is variable. A self-referencing foreign key can ensure the manager ID exists, but it does not necessarily prevent a person from becoming their own manager or creating a longer cycle; those are separate integrity rules.
