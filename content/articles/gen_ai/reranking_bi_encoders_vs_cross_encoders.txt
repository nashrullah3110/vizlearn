title: Re-ranking: A Practical Guide
intro: Spend the expensive model only on the candidates that survived the cheap one.

## The idea in brief

A <a href="embeddings_and_vector_search.html" style="color: var(--accent-primary)">bi-encoder</a> embeds the query and every document <em>separately</em>, ahead of time — that is what makes the embeddings precomputable and search fast, but it also means the model never looks at a query and a document together. A <strong>cross-encoder</strong> takes both as one input and lets the model attend across them jointly, at the cost of running a full forward pass per query-document pair, at query time, with nothing precomputable.

## The two-stage pattern

Cross-encoders are far more accurate but cost too much to run over an entire corpus — a million documents means a million forward passes per query. The standard fix is two stages: a cheap bi-encoder (or BM25, or both) retrieves a shortlist of maybe 20-100 candidates, and only that shortlist is re-scored by the expensive cross-encoder, which then decides the final order. You pay the cross-encoder's cost dozens of times per query instead of millions of times.

## Two ways to score a query against a document

<strong>A bi-encoder</strong> embeds the query and the document <em>separately</em>, then compares the two vectors. Because documents can be embedded ahead of time, search is a fast vector comparison over a precomputed index.

<strong>A cross-encoder</strong> takes the query and one document <em>together</em> as a single input and outputs a relevance score. The model attends across both, so every query term can interact with every document term &mdash; and nothing can be precomputed.

<p class="mono-font">bi-encoder:&nbsp;&nbsp;&nbsp;score = cos(embed(q), embed(d))</p>
<p class="mono-font">cross-encoder:&nbsp;score = model(q, d)</p>

That structural difference produces the entire trade-off:

|&nbsp;|Bi-encoder|Cross-encoder|
|---|---|---|
|Documents embedded in advance|Yes|No|
|Query cost|One embedding, then vector search|One model pass <em>per document</em>|
|Scales to millions|Yes|No|
|Accuracy|Good|Substantially better|
|Interaction between q and d|None until the comparison|Full attention across both|

## Why the two-stage pipeline exists

A cross-encoder over a million documents means a million model passes per query. Impossible.

A bi-encoder over a million documents is one embedding plus an indexed vector search. Milliseconds.

So the standard arrangement uses each for what it is good at:

1. <strong>Retrieve</strong> 50&ndash;100 candidates with the bi-encoder (and BM25, fused). Fast, broad, some noise.
2. <strong>Rerank</strong> those candidates with the cross-encoder. Expensive per item, affordable on 50.
3. <strong>Pass</strong> the top 3&ndash;10 to the model.

The insight is that recall and precision can be separated. Stage one needs high recall &mdash; the right document must be <em>somewhere</em> in the 50. Stage two provides precision, ordering them accurately.

Measured on standard benchmarks, adding a cross-encoder reranker typically improves nDCG by 10&ndash;20% over dense retrieval alone. It is one of the highest-value additions to a RAG pipeline, and it is often skipped.

## In code

```python
from sentence_transformers import SentenceTransformer, CrossEncoder

# stage 1: bi-encoder, over the whole index
bi = SentenceTransformer("all-MiniLM-L6-v2")
q_vec = bi.encode([query], normalize_embeddings=True)[0]
candidates = top_k_by_dot_product(q_vec, index, k=50)

# stage 2: cross-encoder, over the 50
ce = CrossEncoder("cross-encoder/ms-marco-MiniLM-L-6-v2")
pairs = [(query, c.text) for c in candidates]
scores = ce.predict(pairs)

ranked = [c for _, c in sorted(zip(scores, candidates), reverse=True)][:5]
```

Note the shapes: the bi-encoder embeds once and compares against a precomputed matrix; the cross-encoder receives 50 (query, document) pairs and returns 50 scores. The second call is where the latency is, and it is batched.

Rough latency for 50 candidates with a small cross-encoder on a GPU: 20&ndash;50ms. On a CPU, several hundred milliseconds &mdash; which is why reranker size is a real deployment decision.

## Why one vector per document is not enough

The code above shows the two-stage API. What it cannot show is the reason the second stage helps at all -- that a bi-encoder commits to one vector per document before it knows the question. This builds both scorers from scratch on a case where that commitment is exactly the problem.

```python-run
import numpy as np

# 4 concept dimensions: price, battery, camera, screen
DIMS = ["price", "battery", "camera", "screen"]

# the numbers are how much each document actually SAYS about each topic
DOCS = {
    "D1 full review": np.array([0.90, 0.90, 0.90, 0.90]),
    "D2 battery deep-dive": np.array([0.05, 1.00, 0.05, 0.00]),
    "D3 camera deep-dive": np.array([0.05, 0.00, 1.00, 0.00]),
    "D4 pricing page": np.array([1.00, 0.00, 0.00, 0.00]),
    "D5 one battery sentence": np.array([0.00, 0.35, 0.00, 0.00]),
}
QUERIES = {
    "how long does the battery last": np.array([0.0, 1.0, 0.0, 0.0]),
    "how good is the camera": np.array([0.0, 0.0, 1.0, 0.0]),
}

def unit(v):
    return v / (np.linalg.norm(v) + 1e-12)

print("HOW MUCH EACH DOCUMENT ACTUALLY SAYS about each topic, and then")
print("the unit vector a bi-encoder would store for it:")
print("%-26s %s   |  %s"
      % ("document", "  ".join("%7s" % d for d in DIMS),
         "  ".join("%7s" % d for d in DIMS)))
for name, v in DOCS.items():
    print("%-26s %s   |  %s"
          % (name, "  ".join("%7.2f" % x for x in v),
             "  ".join("%7.2f" % x for x in unit(v))))
print("   NORMALISING IS THE STEP THAT MATTERS. D1 says 0.90 about every")
print("   topic and is stored as 0.50 on each, because a unit vector has a")
print("   fixed budget to spread across its dimensions. D5 says 0.35 about")
print("   one topic and is stored as 1.00 on it, because all of its very")
print("   small budget points one way.")
print("   after normalisation, the thin document looks MORE on-topic than")
print("   the thorough one. that is not a bug in the embedding, it is what")
print("   'direction only' means -- and it is the whole reason a second")
print("   stage exists.")
print()
print("at query time it embeds the query and takes a dot product:")
print("%-34s %s" % ("", "  ".join("%22s" % q[:22] for q in QUERIES)))
bi = {}
for name, v in DOCS.items():
    row = [float(unit(v) @ unit(q)) for q in QUERIES.values()]
    bi[name] = row
    print("%-34s %s" % (name, "  ".join("%22.4f" % x for x in row)))
print("   read the battery column top to bottom. D5 -- a single sentence")
print("   mentioning the battery -- scores %.4f, the HIGHEST of all five,"
      % bi["D5 one battery sentence"][0])
print("   ahead of the deep-dive at %.4f and far ahead of the full review"
      % bi["D2 battery deep-dive"][0])
print("   at %.4f. the retriever has ranked the least informative document"
      % bi["D1 full review"][0])
print("   first, and it is not malfunctioning: D5's direction is exactly")
print("   the query's direction, and direction is all cosine sees.")
print()

print("A CROSS-ENCODER never builds a document vector. it takes the PAIR")
print("and scores it jointly, so it can look at what the query asked about")
print("and read only that part of the document:")
def cross(q, d):
    # attend to the dimensions the query cares about, then read the
    # document's content there -- something no fixed vector can do
    attn = q / (q.sum() + 1e-12)
    return float((attn * d).sum())

ce = {}
print("%-34s %s" % ("", "  ".join("%22s" % q[:22] for q in QUERIES)))
for name, v in DOCS.items():
    row = [cross(q, v) for q in QUERIES.values()]
    ce[name] = row
    print("%-34s %s" % (name, "  ".join("%22.4f" % x for x in row)))
print("   now the order is by CONTENT. D5 drops to %.4f, which is what it"
      % ce["D5 one battery sentence"][0])
print("   actually says about batteries, and D1 rises to %.4f."
      % ce["D1 full review"][0])
print("   the cross-encoder never normalised anything, because it never")
print("   built a document vector to normalise. it looked at the query,")
print("   picked out the dimensions asked about, and read the document")
print("   there -- which it can only do because it has both in hand at")
print("   once.")
print()

print("THE RANKINGS THAT PRODUCES:")
for i, q in enumerate(QUERIES):
    print("   query: %s" % q)
    b = sorted(DOCS, key=lambda d: -bi[d][i])
    c = sorted(DOCS, key=lambda d: -ce[d][i])
    print("      bi-encoder:    %s" % "  >  ".join(x.split()[0] for x in b))
    print("      cross-encoder: %s" % "  >  ".join(x.split()[0] for x in c))
print("   they disagree at the TOP, not just below it. the bi-encoder's")
print("   first pick is a one-line mention; the cross-encoder's is the")
print("   deep-dive, with the full review second.")
print("   this is the everyday version of a well-known problem: short,")
print("   narrowly-worded chunks punch above their weight in a vector")
print("   index, because normalisation rewards them for having nothing")
print("   else to say. reranking is what puts them back in their place.")
print()

print("SO WHY NOT USE THE CROSS-ENCODER FOR EVERYTHING? because of when")
print("the work happens:")
N = 1_000_000
print("%-28s %26s %26s" % ("", "bi-encoder", "cross-encoder"))
for label, b, c in (
        ("document vectors stored", "%s" % "{:,}".format(N), "0"),
        ("work done offline", "%s encodes" % "{:,}".format(N), "none possible"),
        ("work done per query", "1 encode + a dot product",
         "%s forward passes" % "{:,}".format(N)),
        ("can use an ANN index", "yes", "no -- no vectors to index")):
    print("%-28s %26s %26s" % (label, b, c))
print("   the last row is the fatal one. an ANN index works by comparing")
print("   PRECOMPUTED vectors, and a cross-encoder has none to compare --")
print("   its score only exists once a specific query and a specific")
print("   document are put in together. there is nothing to build an index")
print("   over, so it must look at every document, every time.")
print()

print("HENCE THE TWO STAGES. numbers for a %s-document corpus:"
      % "{:,}".format(N))
BI_MS_PER_DOC, CE_MS_PER_DOC = 0.0000, 1.0
print("%-40s %16s %14s" % ("design", "cross-encoder calls", "latency"))
print("%-40s %16s %14s"
      % ("cross-encoder on everything", "{:,}".format(N),
         "%.0f minutes" % (N * CE_MS_PER_DOC / 1000 / 60)))
for k in (10, 50, 200):
    print("%-40s %16d %14s"
          % ("bi-encoder, then rerank the top %d" % k, k,
             "%.0f ms" % (k * CE_MS_PER_DOC + 5)))
print("   the same cross-encoder, applied to %d candidates instead of a" % 50)
print("   million, is %s times cheaper and sees every document that had"
      % "{:,}".format(N // 50))
print("   a serious chance. the bi-encoder's job is not to rank well -- it")
print("   is to be CHEAP and to not lose anything, and that is why it is")
print("   evaluated on recall@k and never on precision@1.")
print()
print("   and it sets the ceiling. anything the first stage misses is")
print("   invisible to the reranker, whatever the reranker's quality:")
missed = "D2 battery deep-dive"
print("      if the top-%d misses %s, the reranker cannot recover it."
      % (3, missed.split()[0]))
print("      so tune k by watching recall@k of stage one, not by watching")
print("      the final answer -- the final answer cannot tell you the")
print("      difference between a bad reranker and a first stage that")
print("      never handed it the right document.")
```

## Try it yourself

1. <strong>Read Stage 1.</strong> Pure cosine similarity over word overlap. One candidate about python <em>the snake</em> ranks deceptively high — it shares the words "python" and "memory" with the query, and a bi-encoder scoring query and document independently has no way to notice they mean something different in context.
2. <strong>Turn on the reranker.</strong> The final order changes: the snake document drops sharply, and a genuinely on-topic document that Stage 1 under-ranked moves up. This is what "reading query and document together" catches that comparing two independent vectors cannot.
3. <strong>Turn it back off.</strong> The order reverts to pure Stage 1 — the reranker did not change what was retrieved, only the order the survivors are returned in.
4. <strong>Read the cost panel.</strong> The bi-encoder cost is already paid, before the query ever arrived. The cross-encoder cost is exactly the number of candidates it re-scores — six forward passes, not a million.

## Worth remembering

A bi-encoder scores query and document independently, which is what makes it fast enough to search a whole corpus but blind to interactions between them — a lexical coincidence can outrank a genuine match. A cross-encoder reads both together and catches that, at a cost that only scales with the shortlist, not the corpus. Two-stage retrieval — cheap and broad, then expensive and narrow — is how production search gets both speed and accuracy instead of choosing one.

## Choosing a reranker

|Option|Character|
|---|---|
|MiniLM cross-encoder|Small, fast, strong baseline|
|Larger cross-encoders|Better, several times slower|
|Multilingual variants|When the corpus is not English|
|ColBERT (late interaction)|Between the two &mdash; token-level vectors, precomputable|
|LLM-as-reranker|Prompt a model to score relevance; flexible, expensive|

<strong>ColBERT</strong> deserves a mention as the genuine middle ground. It stores a vector per <em>token</em> rather than per document, and scores by matching query tokens against document tokens at query time. That gives much of a cross-encoder's fine-grained interaction while keeping the document side precomputable &mdash; at the cost of a far larger index.

<strong>LLM reranking</strong> &mdash; asking a language model to rate each candidate's relevance, or to order a list &mdash; is flexible and adapts to instructions, and it is slow and expensive enough that it is usually reserved for small candidate sets or offline evaluation.

## How many candidates to rerank

The parameter to tune, and it is a straight latency-versus-quality trade.

|Candidates|Effect|
|---|---|
|10|Fast, and the reranker can only reorder what stage one already ranked highly|
|50|The usual choice &mdash; enough room to rescue a mid-ranked document|
|100&ndash;200|Better recall, noticeably slower|

The number to measure is stage one's <strong>recall@n</strong>: if recall@50 is 0.95 and recall@100 is 0.96, reranking 100 buys almost nothing. If recall@50 is 0.7, the bottleneck is retrieval, not ranking, and fixing chunking or adding hybrid search matters more than a bigger reranker.

That diagnostic ordering is worth stating plainly: <strong>reranking cannot recover a document that was never retrieved.</strong>

## Questions people ask

<strong>Do I need a reranker?</strong> If retrieval quality limits your system and latency allows 20&ndash;50ms, it is one of the best available improvements.

<strong>Can a cross-encoder replace the bi-encoder?</strong> Only on a very small corpus. It cannot be indexed.

<strong>How many candidates should I rerank?</strong> 50 is the standard starting point; tune from measured recall.

<strong>Is an LLM a good reranker?</strong> Effective and expensive. Use a purpose-trained cross-encoder for production paths.

<strong>Does reranking help with the "lost in the middle" problem?</strong> Yes &mdash; it puts the most relevant chunk first, where the model attends to it most.

<strong>Can I fine-tune a reranker?</strong> Yes, on (query, relevant, irrelevant) triples from your own data. It often beats a general model by a wide margin on a specific domain.

## Recap in one screen

- A bi-encoder embeds query and document separately, so documents can be indexed and search is fast.
- A cross-encoder reads both together, which is far more accurate and cannot be precomputed.
- Use both: broad cheap retrieval for recall, then reranking for precision.
- Rerank around 50 candidates; measure stage-one recall to know whether that is the bottleneck.
- Reranking cannot rescue a document that retrieval never returned.
