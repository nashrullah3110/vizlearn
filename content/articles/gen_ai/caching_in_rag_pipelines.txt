title: Query, embedding and prompt caching: A Practical Guide
intro: What are the different caches in a RAG system, and what does each one actually save?

## Embedding cache: the easy one

Keyed on a hash of the text and the model name. Embedding is deterministic, so the same text always gives the same vector &mdash; which makes this cache both trivially correct and permanently valid, until you change models.

Include the model identifier in the key. Vectors from different models are not comparable, and a cache that silently mixes them produces retrieval results that look plausible and are meaningless. The biggest win is at indexing time: re-indexing a corpus after a chunking tweak re-embeds only the chunks that actually changed.

## Query cache: the highest saving, and the highest risk

Keyed on the question, storing the final answer. A hit skips retrieval, reranking and generation &mdash; often seconds and most of the cost. Real traffic is heavily repetitive, so hit rates can be high.

Two problems. <strong>Staleness:</strong> the answer was correct for the corpus as it was, so any document update can invalidate it, and there is no cheap way to know which entries. Most systems use a short TTL and flush on re-index. <strong>Exact matching:</strong> "what is the refund policy" and "how do refunds work" are one question and two keys. Semantic caching &mdash; keying on the embedding and accepting a near match &mdash; raises the hit rate and introduces the risk of returning the answer to a subtly different question.

## Prompt caching: inside the model

Provider-side, and a different mechanism entirely: the model keeps the attention state (the <a href="context_window_and_kv_cache.html">KV cache</a>) for a prefix it has already processed. Send the same long system prompt and the prefill for that portion is skipped.

It is prefix-based, so it only helps if the shared part comes <em>first</em>. Put the system prompt and any fixed instructions at the front and the retrieved chunks and the question after them; putting the variable part first defeats it entirely. Typical savings are large on time-to-first-token and on input cost, and nothing about correctness changes &mdash; the model computes the same thing.

## Semantic caching, and the risk it introduces

An exact-match query cache misses on any rewording, and real users reword constantly. Semantic caching keys on the question's embedding instead and returns a stored answer when a previous question is close enough.

It raises the hit rate substantially and introduces a failure the exact cache cannot have: returning the answer to a <em>similar but different</em> question. "What is the refund policy for digital goods?" and "What is the refund policy?" are close in embedding space and have different answers. The threshold is the whole design, and it should be set from measured false-hit rate on real traffic, not chosen.

Two safeguards are worth the effort: exclude anything user-specific or permission-scoped from the cache entirely, and log hits so a wrong answer can be traced back to the question that seeded it.

## Invalidation, which is where these systems actually break

The embedding cache never goes stale &mdash; embedding is deterministic, so the same text and model always give the same vector. Include the model name in the key and it is correct forever.

The query cache is the opposite. It stores a conclusion drawn from a corpus at a moment in time, and nothing in it knows when a document changed. The practical options are all imperfect: a short TTL, which trades hit rate for staleness; a flush on re-index, which is coarse but honest; or tracking which chunks contributed to each cached answer and invalidating precisely, which is correct and rarely worth the bookkeeping.

Prompt caching sidesteps the question because it caches computation rather than conclusions. The model recomputes the same thing it would have anyway, so there is nothing to go stale &mdash; which is why it is the safest of the three and the one to reach for first.

## Four places a RAG pipeline repeats work

A retrieval pipeline does the same expensive things over and over. Each stage can be cached, and they have very different hit rates and risks.

|Layer|What is cached|Keyed on|Typical saving|
|---|---|---|---|
|Embedding|Query vectors|Normalised query text|One model call|
|Retrieval|Result ids|Query + filters|One index search|
|Reranking|Scores|Query + document id|One cross-encoder pass|
|Generation|Final answers|Query + context|The whole LLM call|
|Prompt prefix|KV cache for a shared prefix|Prefix tokens|Prefill compute|

The last row is different in kind and is the one with the best return in production: if every request begins with the same long system prompt, its KV cache can be computed once and reused, removing that prefill work from every subsequent request.

## Exact caching, and its keys

The simplest and safest form. Normalise the query, hash it, look up the result.

```python
import hashlib, json

def cache_key(query, filters, user_groups):
    payload = json.dumps({
        "q": " ".join(query.lower().split()),   # normalise whitespace and case
        "f": filters,
        "g": sorted(user_groups),               # permissions are part of the key
    }, sort_keys=True)
    return hashlib.sha256(payload.encode()).hexdigest()
```

Two things in that function are the ones that go wrong.

<strong>Normalise the query text,</strong> or "How do I reset my password?" and "how do i reset my password" are separate entries and the hit rate collapses.

<strong>Include the permission context in the key.</strong> This is not an optimisation detail &mdash; a cache keyed only on query text will serve one user's authorised results to another user who is not authorised to see them. It is the most common way a correctly-built permission filter is defeated, because caching is added later by someone optimising latency.

## Semantic caching, and why it is risky

Exact caching only helps on repeated queries. Semantic caching extends it: embed the query, and if it is within some similarity threshold of a cached query, return that entry.

The appeal is a much higher hit rate &mdash; "reset password", "how to change my password" and "forgot password" all hit one entry.

The risk is that <strong>similar is not the same</strong>. Consider:

|Query A|Query B|Cosine|Same answer?|
|---|---|---|---|
|"refund policy"|"refund policy for digital goods"|0.92|<strong>No</strong>|
|"how to cancel"|"how to cancel a subscription"|0.94|Maybe|
|"is X supported"|"is X not supported"|0.96|<strong>No</strong>|

The negation row is the dangerous one, and it is a known weakness of embeddings: "is X supported" and "is X not supported" are near-identical vectors and opposite questions.

So semantic caching needs a high threshold (0.97 and above), and it is unsuitable wherever a wrong answer is costly. A safer variant caches only the <em>retrieval</em> stage semantically &mdash; returning similar documents for a similar query is far more defensible than returning a previous answer.

## Three caches, three hit rates, three ways to serve a stale answer

A RAG pipeline has several independent places to cache, and they differ in what they key on, how often they hit, and how badly they fail when the underlying data changes. This measures all three on the same traffic.

```python-run
import numpy as np

# a day of traffic: the same questions asked in different words
TRAFFIC = [
    "what is the refund window",
    "what is the refund window",
    "how long do I have to return something",
    "what is the refund window",
    "how long do I have to return something",
    "what is your shipping cost",
    "what is the refund window",
    "how much does delivery cost",
    "what is your shipping cost",
    "do you ship to Canada",
    "what is the refund window",
    "how long do I have to return something",
]
# which underlying question each one really is
INTENT = {
    "what is the refund window": "refund",
    "how long do I have to return something": "refund",
    "what is your shipping cost": "cost",
    "how much does delivery cost": "cost",
    "do you ship to Canada": "coverage",
}
N = len(TRAFFIC)

print("%d REQUESTS over one day, %d distinct strings, %d distinct"
      % (N, len(set(TRAFFIC)), len(set(INTENT.values()))))
print("underlying questions:")
from collections import Counter
for q, c in Counter(TRAFFIC).most_common():
    print("   %-46s x%-3d (%s)" % (q, c, INTENT[q]))
print()

print("CACHE 1 -- EXACT MATCH ON THE QUERY STRING. the whole answer,")
print("keyed on the literal text:")
seen, hits = set(), 0
for q in TRAFFIC:
    if q in seen:
        hits += 1
    seen.add(q)
exact = hits / float(N)
print("      hits %d of %d  ->  hit rate %.4f" % (hits, N, exact))
print("   it caught every literal repeat and nothing else. 'how long do I")
print("   have to return something' asks the same thing as 'what is the")
print("   refund window' and shares not one character of key with it.")
print()

print("CACHE 2 -- SEMANTIC. key on the query EMBEDDING, and count a hit")
print("when some cached query is within a similarity threshold:")
# stand-in embeddings. every query shares a component (all of them are
# short customer questions), then leans toward its own intent -- which is
# how real query embeddings sit: close together, and gradedly so.
SHARED = np.array([0.30, 0.30, 0.30])
QVEC = {
    "what is the refund window":              np.array([1.00, 0.05, 0.05]),
    "how long do I have to return something": np.array([0.80, 0.20, 0.05]),
    "what is your shipping cost":             np.array([0.05, 1.00, 0.10]),
    "how much does delivery cost":            np.array([0.15, 0.85, 0.10]),
    "do you ship to Canada":                  np.array([0.05, 0.30, 1.00]),
}

def embed(q):
    return QVEC[q] + SHARED

def cos(a, b):
    return float(a @ b / (np.linalg.norm(a) * np.linalg.norm(b)))

qs = list(QVEC)
print("   the similarities between the 5 distinct queries:")
print("      %s" % "  ".join("%6s" % ("Q%d" % i) for i in range(len(qs))))
for i, a_ in enumerate(qs):
    print("   Q%d %s   %s"
          % (i, "  ".join("%6.3f" % cos(embed(a_), embed(b_)) for b_ in qs),
             INTENT[a_]))
print("   same-intent pairs sit around %.3f and different-intent pairs"
      % cos(embed(qs[0]), embed(qs[1])))
print("   around %.3f. the threshold has to land between those two, and"
      % cos(embed(qs[0]), embed(qs[2])))
print("   the gap is narrower than it looks:")
print()

print("%-14s %10s %12s %14s" % ("threshold", "hits", "hit rate", "wrong hits"))
for t in (0.995, 0.97, 0.90, 0.70, 0.55):
    cache, h, wrong = [], 0, 0
    for q in TRAFFIC:
        e = embed(q)
        best, bq = -1.0, None
        for ce, cq in cache:
            sm = cos(e, ce)
            if sm > best:
                best, bq = sm, cq
        if bq is not None and best >= t:
            h += 1
            if INTENT[bq] != INTENT[q]:
                wrong += 1
        else:
            cache.append((e, q))
    print("%-14.3f %10d %12.4f %14d" % (t, h, h / float(N), wrong))
print("   at a tight threshold it behaves like the exact cache. loosen it")
print("   and it starts recognising paraphrases -- and eventually starts")
print("   serving the answer to a DIFFERENT question, which is the")
print("   'wrong hits' column.")
print("   that column is the whole risk of a semantic cache: a miss costs")
print("   you a generation, and a wrong hit costs you a confidently")
print("   incorrect answer to a question nobody asked.")
print()

print("CACHE 3 -- THE EMBEDDING CACHE. key on the query text, store its")
print("VECTOR. this one is different in kind:")
print("%-34s %s" % ("what it saves", "one embedding API call"))
print("%-34s %s" % ("what it cannot save", "the retrieval and the generation"))
print("%-34s %s" % ("risk of a wrong answer", "none -- text maps to one vector"))
print("      hits %d of %d  ->  hit rate %.4f" % (hits, N, exact))
print("   the same hit rate as the exact cache, because it uses the same")
print("   key. what makes it worth having anyway is that it is SAFE: the")
print("   embedding of a string does not change unless the model changes,")
print("   so there is no staleness question at all.")
print()

print("WHAT EACH ONE SAVES, per hit:")
EMB_MS, RET_MS, GEN_MS = 40.0, 60.0, 1400.0
TOTAL = EMB_MS + RET_MS + GEN_MS
print("%-26s %12s %14s %14s"
      % ("cache", "saves (ms)", "of the total", "hit rate here"))
for name, saved, hr in (("embedding cache", EMB_MS, exact),
                        ("retrieval cache", EMB_MS + RET_MS, exact),
                        ("full answer cache", TOTAL, exact)):
    print("%-26s %12.0f %13.0f%% %14.4f"
          % (name, saved, 100 * saved / TOTAL, hr))
print("   the generation is %.0f%% of the latency, so only a cache that"
      % (100 * GEN_MS / TOTAL))
print("   skips generation changes the experience. caching the embedding")
print("   saves %.0f%% and is worth doing because it is free and safe, not"
      % (100 * EMB_MS / TOTAL))
print("   because it is fast.")
print()

print("AND THE PART THAT DECIDES WHETHER YOU CAN CACHE AT ALL --")
print("INVALIDATION. each cache goes stale for a different reason:")
print("%-24s %-30s %s" % ("cache", "goes stale when", "how bad"))
for row in (("embedding", "the embedding model changes", "rare, and total"),
            ("retrieval", "a document is added or edited", "common"),
            ("full answer", "any of the above, or the prompt", "common"),
            ("full answer", "the model version changes", "silent")):
    print("%-24s %-30s %s" % row)
print("   the retrieval and answer caches must be invalidated whenever the")
print("   corpus changes, and 'the corpus changed' is not usually an event")
print("   anyone emits. the practical answers are a short TTL, or a cache")
print("   key that includes a corpus version.")
print("   a cached answer that is merely OLD is not the danger. the danger")
print("   is a cached answer that was correct when the policy said 30 days")
print("   and is now wrong because the policy says 14 -- it is confident,")
print("   fluent, sourced, and false, and nothing in the pipeline will")
print("   ever notice.")
```

## Things to try

1. Push <strong>exact repeats</strong> to 70%. The query cache dominates &mdash; and it is the cache that goes stale the moment a document changes.
2. Set exact repeats to 0 and reworded to 60%. The exact caches stop helping entirely; only the prompt cache, which keys on the shared prefix, still does.
3. Turn <strong>prompt caching</strong> off. Reworded queries lose their only remaining saving, which is why prompt order matters.

## What to remember

Three different caches share the name. The query cache stores a finished answer keyed on the question and saves the most per hit, at the risk of serving a stale one. The embedding cache stores a vector keyed on the text and is permanently valid until the model changes. Prompt caching lives in the provider and only helps when the shared text comes first in the prompt.

## Invalidation, which is the hard part

A cache that never expires eventually serves answers from documents that have been superseded &mdash; which is a correctness failure, not a performance one.

Four strategies, in increasing order of effort:

<strong>Time-based (TTL).</strong> Entries expire after an hour, a day, a week. Simple, and it guarantees a staleness window.

<strong>Version-based.</strong> Include a corpus version or index build id in the cache key. Re-indexing changes the version, so every entry misses and is naturally replaced. Clean and effective.

<strong>Event-based.</strong> When a document changes, invalidate the cached entries that cited it. Requires recording which documents each entry used &mdash; worth doing, and it is the only approach that is both fresh and efficient.

<strong>Manual.</strong> A flush endpoint for when something has gone wrong. Always have one.

The version-in-the-key approach is the one to reach for by default, because it makes staleness structurally impossible after a re-index rather than relying on a timer.

## What is worth caching, and what is not

<strong>Cache the embedding layer always.</strong> Deterministic, cheap to store, no correctness risk, and query repetition is high in real traffic.

<strong>Cache retrieval results</strong> with the permission context and corpus version in the key.

<strong>Cache the prompt prefix's KV</strong> if you control the serving stack. A long shared system prompt or a fixed instruction block is prefilled once instead of per request.

<strong>Be cautious caching generated answers.</strong> The saving is largest and so is the risk: a stale or mis-keyed answer is served with full confidence and a citation. Use exact keys, a short TTL, and a corpus version.

<strong>Do not cache when</strong> the answer depends on time ("what is outstanding today"), on per-user data beyond permissions, or on anything with legal or safety weight.

## Measuring it

Three numbers tell you whether the cache is earning its place:

<strong>Hit rate</strong> per layer. Embedding caches often reach 30&ndash;60% on real traffic; generation caches much less, because full queries repeat rarely.

<strong>Latency at the percentiles.</strong> A cache improves the median dramatically and may not move p99, which is what users notice.

<strong>Cost saved,</strong> in model calls avoided &mdash; usually the number that justifies the work.

And one to watch: <strong>staleness incidents</strong>. If nobody is measuring how often a cached answer was wrong, the cache is untested. A sampled comparison &mdash; recompute a small fraction of cached responses and diff them &mdash; catches invalidation bugs before users do.

## Questions people ask

<strong>Where should I start?</strong> Embedding caching &mdash; safe, cheap, and immediately useful. Then prompt-prefix caching if you control serving.

<strong>Is semantic caching safe?</strong> Only with a high threshold, and preferably applied to retrieval rather than to final answers. Negation and qualifiers break it.

<strong>How do I stop a cache leaking across users?</strong> Include the permission context in the key. Nothing else is sufficient.

<strong>What TTL?</strong> Matched to how often the corpus changes &mdash; and prefer a corpus version in the key over a timer.

<strong>Does caching hurt quality?</strong> Only through staleness and mis-keying, and both are avoidable. The cached computation is identical.

<strong>What hit rate should I expect?</strong> Highly traffic-dependent. Embeddings often 30&ndash;60%; exact answer caches frequently under 10%.

## Recap in one screen

- Cache embeddings, retrieval results, rerank scores, answers and the shared prompt prefix &mdash; different savings and risks each.
- Normalise the query text before hashing, or the hit rate collapses.
- Include the permission context in every key, or the cache defeats your access control.
- Put the corpus version in the key so re-indexing invalidates naturally.
- Semantic caching raises hit rates and breaks on negation and qualifiers &mdash; use a high threshold, and prefer caching retrieval over answers.
