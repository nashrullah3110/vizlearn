title: Multi-Query Retriever: A Practical Guide
intro: One question can be asked many ways, and vector search only finds what is phrased like the query it was given. A multi-query retriever generates several rewordings, searches with each, and merges the results.

## The vocabulary mismatch problem

Embedding-based retrieval finds documents whose vectors are near the query’s vector. That works well when the question and the document use similar language, and fails when they do not.

Ask “how do I speed up my model?” of a corpus that discusses “reducing inference latency”, “quantisation” and “batch throughput” and the embedding may simply not land near any of them. The information is present and the phrasing is wrong, and a single query gets a single shot at matching it.

The failure is silent. The retriever returns its nearest neighbours regardless, so you get plausible-looking, unhelpful chunks with no signal that anything was missed. A multi-query retriever fixes this by generating several alternative phrasings of the question &mdash; typically 3 to 5 &mdash; using a language model, then searching with each phrasing independently and merging the results. "How do I speed up my model?" becomes "reduce inference latency," "optimise batch throughput," and "quantise model weights" &mdash; three queries that together cover vocabulary the original missed. The merge step deduplicates by document id and can either union the results (maximise recall) or intersect them (maximise precision). The cost is N extra embedding calls and N extra vector searches per user query, which is small compared to the generation step that follows. This page demonstrates the vocabulary mismatch on a real corpus, shows the recall improvement from multiple queries, and covers the tradeoff between union and intersection merging.

## Generating several queries and merging

A multi-query retriever asks a language model to produce N alternative phrasings of the question &mdash; typically 3 to 5 &mdash; each approaching it from a different angle. The original question above might become:

- “What techniques reduce model inference latency?”
- “How can I improve throughput at serving time?”
- “What makes a neural network run faster in production?”

Each is embedded and searched independently, giving N result sets which are then combined and deduplicated. Because the rewordings cover different vocabulary, their nearest neighbours differ, and the union covers substantially more of the relevant material than any one query would.

Merging is usually done with <strong>reciprocal rank fusion</strong> rather than raw scores. RRF assigns each document a score of <span class="mono-font">&Sigma; 1/(60 + rank)</span> across the lists it appears in, which rewards documents that several rewordings agree on and avoids the problem that similarity scores from different queries are not directly comparable.

## One question, several searches

A single embedding of a question is one point in the space. If the question is phrased differently from the documents that answer it, that point sits in the wrong place, and no amount of index tuning will fix it.

Multi-query retrieval hedges by generating several rewrites of the question, searching with each, and combining the results.

<blockquote>Original: "How do I stop getting so many alerts?"</blockquote>
<blockquote>1. "How to reduce alert volume"</blockquote>
<blockquote>2. "Configuring notification thresholds"</blockquote>
<blockquote>3. "Suppressing duplicate alerts"</blockquote>

Each rewrite lands in a different region of the embedding space, and their union covers far more of the relevant material than any one of them. The third might be the only one that retrieves the deduplication documentation.

The mechanism is straightforward:

```python
prompt = """Generate 3 alternative phrasings of this question that would
retrieve relevant documents. One per line, no numbering.

Question: {question}"""

queries = [question] + model.generate(prompt).strip().split("\n")
ranked_lists = [index.search(q, k=20) for q in queries]
results = rrf(ranked_lists)          # fuse by rank
```

Note that the original question is included. The rewrites are additions, not replacements &mdash; a poor rewrite then dilutes the results slightly rather than destroying them.

## Why fusion rather than concatenation

The results from several searches must be combined, and how matters.

<strong>Concatenating and deduplicating</strong> loses the ranking information: a document ranked first by two rewrites is treated the same as one ranked twentieth by one.

<strong>Averaging scores</strong> requires the scores to be comparable across searches, and they are not reliably so.

<strong>Reciprocal rank fusion</strong> uses only ranks:

<p class="mono-font">score(d) = &Sigma;<sub>queries</sub> 1 / (60 + rank(d))</p>

A document retrieved highly by several rewrites accumulates from each, so <strong>agreement across rewrites becomes evidence</strong>. That is exactly the property you want: a document that only one rewrite found is plausible; one that all four found is probably right.

RRF also needs no normalisation, which is what makes it practical when combining an arbitrary number of retrievers.

## The costs

|Cost|Detail|
|---|---|
|One model call|To generate the rewrites, 200&ndash;500ms|
|N searches|Usually parallelisable, so latency is the slowest one|
|More candidates|N&times;k documents before fusion|
|Reranking load|More candidates to rerank, if reranking|

The searches parallelise, so the added latency is roughly one model call plus one search &mdash; not N searches. That makes the technique considerably cheaper in practice than it looks.

Three or four rewrites is the usual range. Beyond that, the additional rewrites are paraphrases of paraphrases and the returns flatten while the reranking load grows.

Cache aggressively: at temperature 0 the rewrites are deterministic, and repeated or similar questions are common in real traffic.

## What several searches recover that one does not

The sections above explain why the pattern generates variants and fuses them rather than concatenating. Here it is run -- three phrasings of one question against one corpus, the union measured against each variant alone, and the case where extra queries make the result worse.

```python-run
import numpy as np

DOCS = {"D1 delivery": [0.15, 0.05, 0.92, 0.35, 0.02], "D2 shipping": [0.15, 0.92, 0.05, 0.35, 0.02],
        "D3 postage": [0.92, 0.05, 0.05, 0.35, 0.02], "D6 late-fee": [0.12, 0.05, 0.94, 0.02, 0.30],
        "D7 price-list": [0.12, 0.94, 0.05, 0.02, 0.30], "D8 cost-notes": [0.94, 0.05, 0.05, 0.02, 0.30]}
RELEVANT = {"D1 delivery", "D2 shipping", "D3 postage"}

def unit(v):
    v = np.asarray(v, float)
    return v / np.linalg.norm(v)

def rank(q):
    sc = {d: float(unit(q) @ unit(v)) for d, v in DOCS.items()}
    return sorted(sc, key=lambda x: -sc[x]), sc

VARIANTS = {"V1 what-shipping-cost": [0.90, 0.05, 0.05, 0.30, 0.00],
            "V2 delivery-fee": [0.10, 0.05, 0.90, 0.30, 0.00],
            "V3 postage-price": [0.10, 0.90, 0.05, 0.30, 0.00]}
K = 3
print("ONE QUESTION, THREE PHRASINGS -- the corpus uses 'cost', 'fee'")
print("and 'price' in different documents. EACH VARIANT ALONE, top %d:" % K)
for name, q in VARIANTS.items():
    order, sc = rank(q)
    top = order[:K]
    r = len(set(top) & RELEVANT) / float(len(RELEVANT))
    print("%-24s %-32s %10.4f"
          % (name, " | ".join(top), r))
print("   each phrasing retrieves by its own WORD, not by the subject --")
print("   'delivery-fee' finds D1 and D6, and misses D2 entirely. which")
print("   word the user happens to type decides what they see.")
```

Fusing those three result lists with reciprocal rank fusion recovers what no single phrasing found on its own.

```python-run
import numpy as np

DOCS = {"D1 delivery": [0.15, 0.05, 0.92, 0.35, 0.02], "D2 shipping": [0.15, 0.92, 0.05, 0.35, 0.02],
        "D3 postage": [0.92, 0.05, 0.05, 0.35, 0.02], "D6 late-fee": [0.12, 0.05, 0.94, 0.02, 0.30],
        "D7 price-list": [0.12, 0.94, 0.05, 0.02, 0.30], "D8 cost-notes": [0.94, 0.05, 0.05, 0.02, 0.30]}
RELEVANT = {"D1 delivery", "D2 shipping", "D3 postage"}

def unit(v):
    v = np.asarray(v, float)
    return v / np.linalg.norm(v)

def rank(q):
    sc = {d: float(unit(q) @ unit(v)) for d, v in DOCS.items()}
    return sorted(sc, key=lambda x: -sc[x]), sc

VARIANTS = {"V1 what-shipping-cost": [0.90, 0.05, 0.05, 0.30, 0.00],
            "V2 delivery-fee": [0.10, 0.05, 0.90, 0.30, 0.00],
            "V3 postage-price": [0.10, 0.90, 0.05, 0.30, 0.00]}
K = 3

def rrf(lists, k=60):
    out = {}
    for lst in lists:
        for i, d in enumerate(lst):
            out[d] = out.get(d, 0.0) + 1.0 / (k + i + 1)
    return out

lists = [rank(q)[0] for q in VARIANTS.values()]
fused = rrf(lists)
order = sorted(fused, key=lambda x: -fused[x])
fused_top = order[:K]
print("NOW FUSE THEM. reciprocal rank fusion over the three result lists:")
print("%-14s %14s %14s" % ("document", "RRF score", "relevant?"))
for d in order:
    print("%-14s %14.6f %14s" % (d, fused[d], "YES" if d in RELEVANT else ""))
print("   top %d after fusion: %s" % (K, " | ".join(fused_top)))
print("   recall of 3 = %.4f"
      % (len(set(fused_top) & RELEVANT) / float(len(RELEVANT))))
print("   every single variant above was still missing at least one --")
print("   that gap is the entire product.")
```

That still leaves the question of why fusion beats simply concatenating the phrasings into one long query -- averaging vectors turns out to be a worse fix than combining rankings.

```python-run

    return v / np.linalg.norm(v)

    return sorted(sc, key=lambda x: -sc[x]), sc

print("phrasings into one long query instead, by averaging their vectors:")

o_cat, sc_cat = rank(CONCAT)
print("%-16s %-30s %10.4f"
      % ("concatenated", " | ".join(o_cat[:K]),
         len(set(o_cat[:K]) & RELEVANT) / 3.0))
print("   on THIS query it still finds all three -- averaging did not")
print("   break it here. what it DID do is spend the query's whole")
print("   budget pointing weakly at three vocabularies at once:")
for w, i in (("fee-word", 2), ("price-word", 1), ("cost", 0)):
    print("      axis %d highest single variant %.2f, averaged %.2f"
          % (i, max(v[i] for v in VARIANTS.values()), CONCAT[i]))
print("   it survived only because the shipping axis is shared by all")
print("   three phrasings. remove that shared signal and the averaged")
print("   vector has nothing left to discriminate with, while each")
print("   separate variant still matches its own vocabulary. fusion")
print("   combines RANKINGS, so no variant has to compromise;")
print("   concatenation combines VECTORS, and a vector points one way.")
```

The pattern is not free, and it is not foolproof either -- one more call on the critical path, and a bad variant can drag a good result set down with it.

```python-run

print()
print("AND WHEN IT MAKES THINGS WORSE. add a variant that drifts:")

lost = [d for d in order[:3] if d not in o4[:3]]
gained = [d for d in o4[:3] if d not in order[:3]]
print("   'return shipping' is a plausible model rewrite about a")
print("   different subject. %s dropped out of the top 3 and %s took"
      % (", ".join(lost) or "nothing", ", ".join(gained) or "nothing"))
print("   its place. RRF cannot tell that variant should not have had a")
print("   vote -- every list it is handed counts equally. generate few")
print("   variants, and check them: the failure is silent and looks")
print("   like a retrieval problem rather than a prompt problem.")
```

## Guided experiments

1. <strong>Compare a single query with the set.</strong> Look at what one phrasing retrieves against the union of all of them. The union is broader, and usually includes at least one document no single query found.
2. <strong>Find the documents only one variant retrieves.</strong> These are exactly the recall the technique is buying &mdash; material the original phrasing would have missed entirely.
3. <strong>Look for agreement.</strong> Documents retrieved by several variants are the strongest candidates, and that consensus is what rank fusion promotes to the top.
4. <strong>Watch the precision cost.</strong> The merged list is longer and contains more marginal results. Multi-query improves recall and dilutes precision, which is why a reranker usually follows it.

## What it costs, and what to use instead

Multi-query is not free. Generating the variants is an extra LLM call on the critical path, adding latency and cost to every request, and it runs N searches instead of one. For an interactive application that overhead is real.

Related approaches make different trades. <strong>HyDE</strong> generates a hypothetical <em>answer</em> and embeds that, on the argument that an answer is textually closer to the passage containing it than a question is. <strong>Query decomposition</strong> splits a multi-part question into separate sub-questions, which multi-query does not do &mdash; it rephrases rather than divides. And <strong>hybrid search</strong>, combining dense retrieval with BM25 keyword matching, addresses much of the same vocabulary problem for a fraction of the cost, because exact term matching catches precisely the rare words embeddings handle worst.

## Common mistakes

- <strong>Generating variants that all say the same thing.</strong> If the rewordings are near-identical, they retrieve the same documents and you have paid for nothing. The prompt must push for genuinely different angles and vocabulary.
- <strong>Merging by raw similarity score.</strong> Scores from different query embeddings are not comparable. Use rank-based fusion.
- <strong>Skipping deduplication.</strong> The same chunk retrieved by four variants will otherwise occupy four slots of context.
- <strong>Not reranking afterwards.</strong> The merged list is broader and noisier; a cross-encoder reranker recovers the precision.
- <strong>Using it where the problem is chunking.</strong> If the relevant text is split badly across chunks, no amount of query rewriting will retrieve it intact.

## What to remember

A multi-query retriever compensates for the fact that a single embedding gets one attempt at matching the corpus vocabulary: it generates several rewordings, retrieves with each, and fuses the ranked lists. It buys recall at the cost of an extra LLM call, N searches, and some precision &mdash; so it pairs naturally with a reranker. Where the mismatch is about rare or exact terms, hybrid search with BM25 gets much of the same benefit far more cheaply.

## Where it helps, and where it does not

<strong>It helps with vague or short queries.</strong> "It's broken" gives an embedding with almost no signal; several specific rewrites give several usable ones.

<strong>It helps when documents use different vocabulary</strong> from users &mdash; jargon, product names, formal register.

<strong>It helps with multi-faceted questions,</strong> where different aspects live in different documents. Decomposition is a related and sometimes better approach: split the question into its parts explicitly and retrieve for each.

<strong>It does not help much when the query already contains exact identifiers.</strong> Rewriting "error E4471" risks losing the code, which was the most retrievable part. Including the original query protects against this.

<strong>It does not help when recall is already high.</strong> If recall@20 is 0.97, there is almost nothing left to find and the extra latency buys nothing. Measure before adding it.

That last point generalises: <strong>multi-query addresses a recall problem</strong>. If your failures are ordering failures &mdash; the right document is retrieved at rank 15 &mdash; a reranker is the correct tool, not more queries.

## Related techniques, and how they combine

|Technique|What it changes|
|---|---|
|Multi-query|Several phrasings, fused|
|Decomposition|Splits a compound question into sub-questions|
|HyDE|Searches with a generated hypothetical answer|
|Step-back prompting|Asks a more general question first|
|Self-query|Extracts metadata filters from the question|

<strong>Step-back prompting</strong> is worth knowing: for a specific question, first ask a broader one ("what are the general principles of X?"), retrieve for both, and fuse. It surfaces background material that a narrow query misses.

<strong>Decomposition</strong> is the better choice for genuinely compound questions. "How do refunds differ from exchanges, and what are the deadlines?" is three questions; rewriting it three ways is less effective than splitting it into its actual parts.

These compose, and each adds latency. The ordering to add them in is by measured benefit on your own question set &mdash; and in most systems hybrid search and reranking come first.

## Questions people ask

<strong>How many rewrites?</strong> Three or four including the original. More flattens out.

<strong>Should I include the original query?</strong> Yes, always &mdash; it protects against a bad rewrite and preserves exact identifiers.

<strong>Which model for the rewrites?</strong> A small fast one. Paraphrasing a question is not a demanding task.

<strong>Does it increase hallucination?</strong> No &mdash; the rewrites are only search keys and are never shown to the user or to the answering model.

<strong>How do I combine the result lists?</strong> Reciprocal rank fusion, which needs only ranks.

<strong>Is it better than HyDE?</strong> They address the same gap differently and can be used together. HyDE matches the documents' register; multi-query covers several phrasings.

## Recap in one screen

- One embedding of a badly-phrased question searches from the wrong point; several rewrites cover more ground.
- Generate 3&ndash;4 phrasings, search with each, and fuse with reciprocal rank fusion.
- Always include the original query, so a poor rewrite cannot destroy the results.
- Agreement across rewrites is evidence, and RRF rewards it automatically.
- It fixes recall problems; ordering problems need a reranker instead.
