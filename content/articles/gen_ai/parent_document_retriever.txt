title: Parent Document Retrieval: A Practical Guide
intro: Index the needle, return the haystack it came from.

## The problem it solves

<a href="chunking_strategies_for_rag.html" style="color: var(--accent-primary)">Chunking</a> forces a trade-off. A small chunk concentrates the query's terms, so its similarity score is high and the match is precise &mdash; but on its own it may be a fragment that answers nothing. A large chunk carries the surrounding context that makes an answer possible, but dilutes the matching terms among hundreds of unrelated words, so it scores worse and may not be retrieved at all. A parent document retriever refuses the trade by indexing small child chunks for precision but returning the larger parent document for context. Each document is split into children (typically 200&ndash;400 tokens), and each child stores a pointer to its parent (typically 1,000&ndash;2,000 tokens). When a child wins the similarity search, the retriever looks up the parent and passes that to the language model instead. Two children from the same parent collapse into one context passage, so the model's context window is not spent sending the same document twice. In LangChain the implementation uses an in-memory or persistent `docstore` that maps child ids to parent documents, alongside a vector store that indexes only the children. This page splits a sample document into parents and children, runs a query, shows which child matched and which parent was returned, and covers the parent-size tradeoff.

## Searching one thing, returning another

A parent document retriever refuses the trade. It splits each document into small <strong>child chunks</strong> and indexes only those, so retrieval is as precise as small chunks allow. But when a child chunk wins, what gets passed to the model is the <strong>parent</strong> it came from. The score decides <em>which</em> document is relevant; the parent decides <em>how much text</em> the model sees. Two chunks from the same parent collapse to one passage, so the context window is not spent sending the same document twice.

## The chunk-size dilemma, and a way out of it

Chunking forces a compromise. Small chunks embed precisely &mdash; a 100-token passage is about one thing, so its vector is sharp. Large chunks carry context &mdash; the paragraph that explains what "this" refers to.

You cannot have both from one chunk size. The parent document retriever resolves it by using <strong>different units for retrieval and for generation</strong>.

<strong>Index small.</strong> Split documents into child chunks of 100&ndash;200 tokens and embed those. Retrieval operates on them, so matching is precise.

<strong>Return large.</strong> Each child records which parent section it came from. When a child matches, fetch and return the parent &mdash; 800&ndash;2,000 tokens of surrounding context &mdash; and pass that to the model.

<p class="mono-font">query &rarr; match a 150-token child &rarr; return its 1,000-token parent &rarr; into the prompt</p>

So precision comes from the small unit and context from the large one, with no compromise between them.

## Why it works

Consider a handbook section on parental leave. Somewhere in it: "Employees with two years' service are entitled to 39 weeks."

<strong>Indexed as one 2,000-token section:</strong> the embedding averages over pay, notice periods, eligibility, forms and return-to-work arrangements. A query about "39 weeks entitlement" matches weakly, because that sentence is 2% of the vector.

<strong>Indexed as 150-token children:</strong> one child is almost entirely about entitlement duration. The query matches it strongly.

<strong>But that child alone</strong> may not say which type of leave it refers to, or that the two-year condition is measured at a particular date. The parent does.

Retrieving the child and returning the parent gets both. This is the same reasoning behind sentence-window retrieval, at a coarser granularity.

## Deduplication, and the detail people miss

Several children frequently match the same parent &mdash; a query about parental leave may match three passages within one section.

Without deduplication, the same parent is returned three times, consuming the context budget and telling the model nothing new. Worse, it displaces other parents that would have added information.

So the retrieval step must:

1. Search over children and take the top k.
2. Map each to its parent id.
3. <strong>Deduplicate by parent id</strong>, keeping the best child's score.
4. Return the distinct parents, ordered by that score.

That means retrieving more children than the number of parents you want &mdash; ask for 20 children to end up with 5 distinct parents. A common implementation mistake is retrieving 5 children and returning 2 parents, silently halving the context passed to the model.

```python
def retrieve_parents(query, k_children=20, n_parents=5):
    children = child_index.search(query, k=k_children)
    seen, parents = set(), []
    for c in children:                      # already ordered best-first
        if c.parent_id not in seen:
            seen.add(c.parent_id)
            parents.append(parent_store[c.parent_id])
        if len(parents) == n_parents:
            break
    return parents
```

## Small chunks in, large chunks out

The sections above lay out the chunk-size dilemma and how searching one size while returning another escapes it. Here it is measured -- the same corpus indexed both ways, the retrieval scored, and the deduplication step that is easy to leave out and changes the answer when you do.

```python-run
import numpy as np

SENTS = [
    ("refund", "Refunds are available within 30 days of purchase."),
    ("refund", "The item must be unused and in its original packaging."),
    ("refund", "Email support@example.com with your order number."),
    ("refund", "Refunds appear on your statement in 5 to 10 days."),
    ("ship", "Standard delivery takes 5 to 7 business days."),
    ("ship", "Express delivery costs an extra 12 dollars."),
    ("ship", "We currently ship to 40 countries."),
    ("warranty", "Hardware is covered for 24 months from delivery."),
    ("warranty", "Accidental damage is excluded from the warranty."),
]
AXIS = {"refund": 0, "ship": 1, "warranty": 2}

def embed(texts):
    v = np.zeros(3)
    for t in texts:
        v[AXIS[t]] += 1.0
    v = v + 0.25
    return v / np.linalg.norm(v)

QUERY = embed(["refund"])
PARENT = 4
parents = [list(range(i, min(i + PARENT, len(SENTS))))
           for i in range(0, len(SENTS), PARENT)]
print("A DOCUMENT OF %d SENTENCES. SEARCH THE PARENTS DIRECTLY -- one" % len(SENTS))
print("vector per parent, and each has to represent everything in it:")
print("%-8s %-30s %14s" % ("chunk", "topics inside", "sim to query"))
for p, idxs in enumerate(parents):
    v = embed([SENTS[i][0] for i in idxs])
    print("%-8s %-30s %14.4f"
          % ("P%d" % p, ", ".join(sorted({SENTS[i][0] for i in idxs})),
             float(QUERY @ v)))
print("   P0 is entirely about refunds and scores highest, which is")
print("   correct, but the score is DILUTED wherever a parent mixes")
print("   topics -- and in a real document the boundaries never line")
print("   up neatly with the subject matter.")
```

Searching the children -- one vector per sentence instead of per parent -- fixes the dilution, at the cost of returning fragments instead of answers.

But precise matches are poor answers on their own -- three disconnected sentences give a model no sense of the whole policy. Parent document retrieval keeps the child match and returns its parent instead, and deduplicates when several children share one.

```python-run
import numpy as np
SENTS = [
    ("refund", "Refunds are available within 30 days of purchase."),
    ("refund", "The item must be unused and in its original packaging."),
    ("refund", "Email support@example.com with your order number."),
    ("refund", "Refunds appear on your statement in 5 to 10 days."),
    ("ship", "Standard delivery takes 5 to 7 business days."),
    ("ship", "Express delivery costs an extra 12 dollars."),
    ("ship", "We currently ship to 40 countries."),
    ("warranty", "Hardware is covered for 24 months from delivery."),
    ("warranty", "Accidental damage is excluded from the warranty."),
]
AXIS = {"refund": 0, "ship": 1, "warranty": 2}
def embed(texts):
    v = np.zeros(3)
    for t in texts:
        v[AXIS[t]] += 1.0
    v = v + 0.25
    return v / np.linalg.norm(v)
QUERY = embed(["refund"])
PARENT = 4
parents = [list(range(i, min(i + PARENT, len(SENTS))))
           for i in range(0, len(SENTS), PARENT)]
parent_of = {i: p for p, idxs in enumerate(parents) for i in idxs}
cs = sorted(((float(QUERY @ embed([t])), i) for i, (t, _) in enumerate(SENTS)),
            reverse=True)
top = [i for _, i in cs[:3]]
print("BUT SMALL CHUNKS ARE BAD ANSWERS. the top 3 children:")
for i in top:
    print("      C%d: %s" % (i, SENTS[i][1]))
print("   each is true and each is a fragment -- three disconnected facts,")
print("   with no sense of whether they are the whole policy.")
returned = list(dict.fromkeys(parent_of[i] for i in top))
print("PARENT DOCUMENT RETRIEVAL: match on children, RETURN their parents,")
print("   deduplicated -- children %s -> parents %s -> deduped %s"
      % (", ".join("C%d" % i for i in top),
         ", ".join("P%d" % parent_of[i] for i in top),
         ", ".join("P%d" % p for p in returned)))
print("      P%d = %s"
      % (returned[0], " ".join(SENTS[i][1] for i in parents[returned[0]])))
```

Skipping the dedup step is not a minor inefficiency -- it repeats the same passage in context, and repetition reads to a language model as corroboration rather than as the artefact of a retriever it actually is.

The two chunk sizes are a real design choice, not a formality -- each pairing trades off differently between how precisely you match and how much context you hand back.

```python-run
import numpy as np

N_SENTS = 9
print("THE SIZES ARE A REAL CHOICE. what each pairing costs:")
print("%-24s %14s %16s %18s"
      % ("child / parent", "vectors stored", "match precision", "answer context"))
for c, p in ((1, 4), (1, 9), (2, 4), (4, 4)):
    nvec = int(np.ceil(N_SENTS / c))
    print("%-24s %14d %16s %18s"
          % ("%d sent / %d sent" % (c, p), nvec,
             "high" if c == 1 else "medium" if c == 2 else "low",
             "%d sentences" % p))
print("   the last row is child = parent, which is ordinary chunking --")
print("   so this technique is not a different system, it is one extra")
print("   indirection on top of the same index. the child size is chosen")
print("   for MATCHING and the parent size for ANSWERING, and the point")
print("   of the method is that these two pressures no longer have to")
print("   be resolved into one number.")
```

There is also a cost most people do not expect: asking for a fixed number of children no longer means a fixed amount of context, because how many parents those children resolve to depends on how they cluster.

```python-run
import numpy as np

SENTS = [
    ("refund", "Refunds are available within 30 days of purchase."),
    ("refund", "The item must be unused and in its original packaging."),
    ("refund", "Email support@example.com with your order number."),
    ("refund", "Refunds appear on your statement in 5 to 10 days."),
    ("ship", "Standard delivery takes 5 to 7 business days."),
    ("ship", "Express delivery costs an extra 12 dollars."),
    ("ship", "We currently ship to 40 countries."),
    ("warranty", "Hardware is covered for 24 months from delivery."),
    ("warranty", "Accidental damage is excluded from the warranty."),
]
AXIS = {"refund": 0, "ship": 1, "warranty": 2}

def embed(texts):
    v = np.zeros(3)
    for t in texts:
        v[AXIS[t]] += 1.0
    v = v + 0.25
    return v / np.linalg.norm(v)

QUERY = embed(["refund"])
PARENT = 4
parents = [list(range(i, min(i + PARENT, len(SENTS))))
           for i in range(0, len(SENTS), PARENT)]
parent_of = {i: p for p, idxs in enumerate(parents) for i in idxs}
cs = sorted(((float(QUERY @ embed([t])), i) for i, (t, _) in enumerate(SENTS)),
            reverse=True)
print("WHERE IT COSTS YOU: more vectors to store (one per child, not per")
print("parent), a second lookup (child id -> parent text), and k meaning")
print("something different -- k children, but fewer parents:")
for k in (2, 3, 5, 9):
    ps = list(dict.fromkeys(parent_of[i] for _, i in cs[:k]))
    print("      k=%d children -> %d parent%s, %d sentences of context"
          % (k, len(ps), "" if len(ps) == 1 else "s",
             sum(len(parents[p]) for p in ps)))
print("   budget your context by the PARENT count, not the child count,")
print("   or a query that matches across several parents will quietly")
print("   overflow it.")
```

## Guided experiments

1. <strong>Read the child list at chunk size 8.</strong> The winning chunk is a short fragment. Read it alone and ask whether it actually answers the question &mdash; it names a duration but not what the duration applies to.
2. <strong>Turn off "Return the parent".</strong> The model now receives only those fragments. The word count drops sharply, and so does the chance of a usable answer.
3. <strong>Turn it back on and watch the passage count.</strong> Two separate child chunks hit the same document, but only one parent passage is returned &mdash; the deduplication is doing real work.
4. <strong>Drag the chunk size up to 24.</strong> Each child is now most of its parent. The top score actually goes <em>up</em> &mdash; a longer window catches more of the query's words &mdash; but the selection gets worse: the second slot now goes to a different product's document, and the model is sent 53 words instead of 29 for the same question.

## Summing up

Precision of retrieval and sufficiency of context are different requirements, and chunk size cannot satisfy both at once. Indexing small children while returning their parents lets the score come from the tightest possible match and the context come from the whole document. The cost is a larger prompt, which is why deduplicating parents matters: without it, three good chunks from one document would send that document three times.

## Choosing the two sizes

|Level|Typical size|Purpose|
|---|---|---|
|Child|100&ndash;250 tokens|Precise embedding and matching|
|Parent|600&ndash;2,000 tokens|Context for the model|

The ratio matters more than the absolute numbers. A parent roughly 5&ndash;10&times; the child is the usual arrangement.

Two sensible ways to define the parent:

<strong>Structural.</strong> The parent is a real section &mdash; a Markdown heading's content, an HTML section, a chapter. Semantically coherent by construction, and variable in size.

<strong>Fixed-window.</strong> The parent is a fixed number of tokens centred on the child. Predictable sizes, and it may cut across topic boundaries.

Structural parents are better where the documents have structure, which most real corpora do. Store the heading path with each parent and prepend it, so the model knows where in the document the passage sits.

A related variant, <strong>sentence-window retrieval</strong>, indexes single sentences and returns the two or three either side. Same idea, finer granularity, and it suits question answering where the answer is one sentence but its meaning depends on its neighbours.

## Costs and trade-offs

<strong>Storage.</strong> Both levels are stored &mdash; children as vectors in the index, parents as text in a document store. The parents are usually kept outside the vector index, since they are fetched by id rather than searched.

<strong>Context budget.</strong> Parents are large, so fewer fit. Five 1,000-token parents is 5,000 tokens before the question and instructions. That is the real constraint, and it is why parent size and the number returned must be chosen together.

<strong>Redundancy.</strong> Overlapping parents can repeat content. Structural parents avoid most of this; fixed windows do not.

<strong>Complexity.</strong> Two stores to keep consistent. When a document changes, both its children and its parent must be updated, and a partial update leaves children pointing at stale parents.

|&nbsp;|Flat chunking|Parent-child|
|---|---|---|
|Retrieval precision|Compromise|High|
|Context completeness|Compromise|High|
|Storage|One store|Two stores|
|Context tokens used|Moderate|Higher|
|Implementation|Simple|Moderate|

## When it helps most

<strong>Long structured documents</strong> &mdash; handbooks, manuals, legal texts, standards. The structure gives natural parents and the length makes flat chunking painful.

<strong>Questions whose answers need surrounding context</strong> to be interpreted &mdash; conditions, exceptions, definitions that appear earlier in the section.

<strong>Corpora with heavy cross-referencing</strong>, where a passage says "as described above".

Where it helps least: short documents that are already about one thing (FAQ entries, product descriptions, support tickets), where the whole document is a reasonable chunk and the extra machinery buys nothing.

## Questions people ask

<strong>Is this the same as sentence-window retrieval?</strong> The same pattern at a different granularity &mdash; sentence windows index single sentences and expand by neighbours; parent-child indexes small chunks and returns sections.

<strong>How many children should I retrieve?</strong> Enough that deduplication still leaves the number of parents you want &mdash; typically 3&ndash;5&times; as many.

<strong>Should parents overlap?</strong> Usually not, if they are structural sections. Overlapping fixed windows waste context.

<strong>Can I rerank?</strong> Yes, and rerank the <em>children</em> before mapping to parents &mdash; the child is the unit whose relevance you measured.

<strong>Does it work with hybrid search?</strong> Yes. Run both retrievers over the children, fuse the ranks, then map to parents.

<strong>What if a parent is enormous?</strong> Cap it, or introduce a middle level. A 10,000-token parent defeats the purpose by filling the context.

## Recap in one screen

- Index small chunks for precise matching; return their larger parent sections for context.
- It removes the chunk-size compromise rather than splitting the difference.
- Deduplicate by parent id, and retrieve several times more children than the parents you need.
- Structural parents (sections) beat fixed windows where documents have structure.
- Best on long structured documents; unnecessary on short self-contained ones.
