title: Vector Search: A Practical Guide
intro: Nearest neighbours, and the approximation everyone actually runs.

## Quick Context

An <a href="../natural_language_processing/what_are_embeddings.html" style="color: var(--accent-primary)">embedding model</a> maps a piece of text to a point, arranged so that texts about the same thing land near each other. Nothing about the words themselves survives the trip &mdash; "peel a mango" and "how to prepare tropical fruit" share no vocabulary and end up as neighbours anyway.

That is the whole trick behind semantic search, recommendation, deduplication and the retrieval half of <a href="rag.html" style="color: var(--accent-primary)">RAG</a>. Once meaning is a position, similarity is distance, and search becomes a nearest-neighbour problem.

## Cosine, and why it is the default

Retrieval almost always ranks by <a href="../machine_learning/cosine_similarity.html" style="color: var(--accent-primary)">cosine similarity</a>: the angle between the query vector and the document vector, ignoring how long either one is. Length in an embedding tends to carry things like document length or token count rather than meaning, so ignoring it is the point.

On vectors normalised to unit length, ranking by cosine and ranking by Euclidean distance give identical orders, which is why many systems normalise once at index time and then use whichever their hardware does faster. Switch the metric here and watch how little changes &mdash; and, on the points that are not near the unit circle, exactly where it does.

## Exact search does not scale

An exact search compares the query against every vector in the index. That is 18 comparisons here and 18 million in a real corpus, per query, and it is why nobody runs exact search at scale.

The standard fix is to partition the space. Cluster the vectors once, keep a centroid per cell, and at query time compare against the centroids first and then search only the nearest few cells. This is an inverted file index (IVF); HNSW does the same job with a navigable graph instead of cells. Both are <strong>approximate</strong>: they trade a small chance of missing a true neighbour for an enormous reduction in work.

That chance is what recall@k measures &mdash; the share of the true top k that the approximate search actually returned. It is a dial, not a defect: probing more cells raises recall and costs comparisons.

## Meaning as coordinates

An embedding turns text into a vector positioned so that similar meanings land near each other. Vector search is then a geometry problem: find the stored vectors closest to the query's vector.

That is what lets a search for "how do I reset my password" retrieve a document titled "Credential recovery procedure" &mdash; no shared words, similar meaning, nearby vectors.

The pipeline:

1. <strong>Embed</strong> every chunk once, at indexing time.
2. <strong>Store</strong> the vectors with their metadata.
3. <strong>Embed</strong> the query at search time, with the same model.
4. <strong>Compare</strong> against the stored vectors and return the nearest k.

Step 3's "same model" is not negotiable. Vectors from two different models occupy unrelated spaces, and comparing them produces noise that looks like results.

## Cosine similarity, and why length is discarded

The standard comparison is the angle between vectors:

<p class="mono-font">similarity = (a &middot; b) / (&#8214;a&#8214; &#8214;b&#8214;)</p>

Length in an embedding tends to reflect frequency or confidence rather than meaning, so ignoring it is deliberate: a long document and a short one about the same subject should be close.

On vectors normalised to length 1, cosine similarity and the dot product are identical, and Euclidean distance ranks the same way. That is why libraries normalise on the way in and then use fast dot products &mdash; a matrix multiply is far cheaper than computing norms per comparison.

Calibrate the threshold rather than assuming one. Many sentence-embedding models score unrelated text at 0.2&ndash;0.4, so a threshold of 0.5 admits considerable noise. Score a few hundred known-related and known-unrelated pairs and put the cut where the distributions separate.

## Approximate search, and why exact does not scale

Comparing a query against every stored vector is exact and linear. With a million 768-dimensional vectors that is 768 million multiply-adds per query &mdash; tolerable in a batch job, too slow for an interactive request at any real volume.

<strong>Approximate nearest neighbour</strong> indexes trade a small amount of recall for orders of magnitude of speed.

|Index|How it works|Character|
|---|---|---|
|Flat|Compare against everything|Exact, slow, fine below ~100k|
|IVF|Cluster, search only nearby clusters|Fast, needs training, tunable|
|HNSW|A navigable graph of neighbours|Very fast, high recall, memory-hungry|
|PQ / compression|Store compressed vectors|Large memory saving, some accuracy loss|

<strong>HNSW</strong> is the common default: build a multi-layer graph where each vector links to its neighbours, then walk it greedily from a coarse layer down to a fine one. Query time grows logarithmically rather than linearly.

The parameter to understand is the search-time breadth (`ef_search` in HNSW, `nprobe` in IVF). Higher means better recall and slower queries &mdash; a dial you set from measured recall against exact search, not from intuition.

## Filtering, and the interaction that surprises people

Real systems need constraints: only documents this user may see, only from the last year, only of a certain type.

Two ways to apply them, and the difference matters:

<strong>Pre-filter</strong> &mdash; restrict the candidate set, then search within it. Correct results, and it can defeat the index structure, since the graph or clusters were built over everything.

<strong>Post-filter</strong> &mdash; search first, then discard non-matching results. Fast, and it can return fewer than k results, or none, if the top matches are all filtered out.

Modern vector databases implement filtered search that navigates the index while respecting the filter, which is the right answer. Where that is unavailable, the workaround is to over-retrieve &mdash; ask for 10&times; k and filter &mdash; and accept that a highly selective filter may still come up short.

For permissions specifically, filtering must be enforced server-side at query time. Retrieving first and filtering in the application means the vectors of documents the user cannot see have already influenced what was returned.

## What the coordinates can and cannot do

"Meaning as coordinates" is the right picture, and it is worth being precise about which meanings survive the trip. This does the famous vector arithmetic, then measures the two properties of real embedding spaces that decide whether a retriever works -- and one of them is the reason opposites are neighbours.

```python-run
import numpy as np

# a hand-built 5-dimensional space so every coordinate is readable
DIMS = ["royal", "male", "female", "animal", "size"]
VOCAB = {
    "king":    [0.90, 0.85, 0.05, 0.05, 0.60],
    "queen":   [0.90, 0.05, 0.85, 0.05, 0.55],
    "man":     [0.05, 0.90, 0.05, 0.10, 0.55],
    "woman":   [0.05, 0.05, 0.90, 0.10, 0.50],
    "prince":  [0.85, 0.80, 0.05, 0.05, 0.35],
    "dog":     [0.02, 0.30, 0.30, 0.95, 0.35],
    "puppy":   [0.02, 0.30, 0.30, 0.95, 0.10],
}

def unit(v):
    v = np.asarray(v, float)
    return v / np.linalg.norm(v)

def cos(a, b):
    return float(unit(a) @ unit(b))

print("A 5-DIMENSIONAL SPACE, small enough to read every coordinate:")
print("%-10s %s" % ("word", "  ".join("%8s" % d for d in DIMS)))
for w, v in VOCAB.items():
    print("%-10s %s" % (w, "  ".join("%8.2f" % x for x in v)))
print()

print("THE COORDINATES ARE DIRECTIONS, so differences between words are")
print("directions too. king - man is whatever is left of 'king' once")
print("'man' is removed:")
d = np.array(VOCAB["king"], float) - np.array(VOCAB["man"], float)
print("   king - man = %s" % "  ".join("%6.2f" % x for x in d))
print("   the royal dimension survived (%.2f) and the male dimension" % d[0])
print("   cancelled (%.2f). the difference IS the concept 'royalty'." % d[1])
result = d + np.array(VOCAB["woman"], float)
print("   king - man + woman = %s" % "  ".join("%6.2f" % x for x in result))
print("%-14s %10s" % ("nearest words", "cosine"))
for w in sorted(VOCAB, key=lambda x: -cos(result, VOCAB[x]))[:4]:
    print("%-14s %10.4f" % (w, cos(result, VOCAB[w])))
print("   'queen' comes out on top, which is the famous result -- and it")
print("   works here because the dimensions were BUILT to be 'royal' and")
print("   'male'. in a real embedding nobody chose those axes, they are")
print("   whatever the training objective produced, and the arithmetic")
print("   works far less reliably than the demonstration suggests.")
print()

print("NOW THE PROPERTY THAT DECIDES WHETHER RETRIEVAL WORKS, and it is")
print("not similarity -- it is the SPREAD of similarities. compare a")
print("clean space with a realistic one:")
rng = np.random.default_rng(3)
D = 64
clean = rng.normal(0, 1, (400, D))
# real sentence embeddings share a large common component: they are
# anisotropic, all crowded into a narrow cone
common = rng.normal(0, 1, D)
real = rng.normal(0, 1, (400, D)) * 0.35 + common
def pair_sims(X):
    U = X / np.linalg.norm(X, axis=1, keepdims=True)
    S = U @ U.T
    iu = np.triu_indices(len(X), 1)
    return S[iu]
print("%-30s %12s %12s %12s %14s"
      % ("", "mean sim", "min", "max", "spread"))
for name, X in (("isotropic (a textbook)", clean),
                ("anisotropic (realistic)", real)):
    s = pair_sims(X)
    print("%-30s %12.4f %12.4f %12.4f %14.4f"
          % (name, s.mean(), s.min(), s.max(), s.max() - s.min()))
print("   in the realistic space every pair of unrelated vectors already")
print("   scores about %.2f. that is the FLOOR, not the signal -- two"
      % pair_sims(real).mean())
print("   documents about nothing in common look %.0f%% similar before"
      % (100 * pair_sims(real).mean()))
print("   any relatedness is measured.")
print("   the consequence is practical: an absolute similarity threshold")
print("   ('accept anything above 0.7') is meaningless without knowing")
print("   your space's floor, and the floor differs per model. always")
print("   calibrate the threshold against your own unrelated pairs.")
print()

print("AND THE LIMIT THAT SURPRISES PEOPLE MOST: cosine similarity")
print("measures RELATEDNESS, not agreement. opposites are neighbours,")
print("because they are used in the same contexts:")
OPPOSITES = {
    "increase":  [0.90, 0.10, 0.85, 0.05],
    "decrease":  [0.90, 0.10, 0.15, 0.05],
    "elephant":  [0.05, 0.90, 0.50, 0.85],
}
DIMS2 = ["quantity-change", "concrete-noun", "direction", "animal"]
print("%-12s %s" % ("word", "  ".join("%16s" % d for d in DIMS2)))
for w, v in OPPOSITES.items():
    print("%-12s %s" % (w, "  ".join("%16.2f" % x for x in v)))
print("%-30s %12.4f" % ("cos(increase, decrease)",
                        cos(OPPOSITES["increase"], OPPOSITES["decrease"])))
print("%-30s %12.4f" % ("cos(increase, elephant)",
                        cos(OPPOSITES["increase"], OPPOSITES["elephant"])))
print("   'increase' and 'decrease' are ANTONYMS and score %.4f, because"
      % cos(OPPOSITES["increase"], OPPOSITES["decrease"]))
print("   they share every property except the one that distinguishes")
print("   them. an unrelated word scores %.4f."
      % cos(OPPOSITES["increase"], OPPOSITES["elephant"]))
print("   so a search for 'did sales increase' happily returns a document")
print("   saying sales decreased. the retrieval is doing its job -- that")
print("   document IS about the topic -- and the answer is still wrong.")
print("   negation has the same problem, which is why 'find documents that")
print("   do NOT mention X' cannot be expressed as a vector search at all.")
print()

print("WHAT THIS MEANS FOR A RETRIEVER, in one table:")
print("%-38s %s" % ("vector search is good at", "and bad at"))
for a, b in (("paraphrase and synonyms", "exact identifiers"),
             ("topical relatedness", "distinguishing opposites"),
             ("cross-lingual matching", "negation"),
             ("fuzzy, natural questions", "numeric or date constraints")):
    print("%-38s %s" % (a, b))
print("   every item in the right column has a non-vector solution --")
print("   keyword search for identifiers, a metadata filter for dates, a")
print("   reranker or the model itself for negation and opposites. that")
print("   is why a production retriever is never just a vector index, and")
print("   why the interesting engineering is in the combination.")
```

## Guided tour

1. <strong>Look at the space.</strong> Four topics, four visible clumps. Nothing arranged them by keyword; they are grouped because their meanings are.
2. <strong>Search exactly.</strong> The default compares all 18 documents and returns the true nearest three. Recall is 100% by definition &mdash; this <em>is</em> the answer everything else is measured against.
3. <strong>Partition it.</strong> Switch <strong>Search Mode</strong> to partitioned with one cell probed. Comparisons drop to the cell's contents plus the four centroids, and recall usually stays at 100% &mdash; the neighbours were in the obvious cell.
4. <strong>Now find the failure.</strong> Raise <strong>k</strong> to 5 or 6 with one cell probed. The cell runs out of documents, so the search returns whatever it has and recall drops below 100%: real neighbours were sitting in a cell nobody looked at.
5. <strong>Buy the recall back.</strong> Raise <strong>Cells Probed</strong>. Recall climbs back to 100% and the comparison count climbs with it. That trade is the entire tuning surface of a vector database.
6. <strong>Probe everything.</strong> At 4 cells the search does 22 comparisons for an index of 18 documents &mdash; worse than the exact scan, because you pay for the centroids too. Partitioning only pays when you skip most of the index.
7. <strong>Change the metric.</strong> On the mango query, cosine calls "a summer fruit salad" and "peeling a ripe mango" a tie at 1.000, because they sit at almost the same angle from the origin. Euclidean puts "peeling a ripe mango" clearly first, because it is genuinely nearer. Same points, same query, different question being asked.

## Where this goes wrong

- <strong>Mixing embedding models.</strong> Vectors from two different models are not comparable, even at the same dimension. Re-embed everything when you change model, or the index quietly returns nonsense.
- <strong>Expecting exact matches.</strong> Embeddings are poor at part numbers, error codes and rare proper nouns, which is why serious systems run hybrid retrieval &mdash; keyword search alongside vectors.
- <strong>Ignoring recall.</strong> An approximate index that has drifted to 70% recall looks perfectly healthy from the outside; every query returns results. Measure against exact search on a sample.
- <strong>Chunk size chosen by accident.</strong> A vector represents its whole chunk, so a chunk covering three topics has an embedding that means none of them.
- <strong>No filtering plan.</strong> "Nearest neighbours, but only from this tenant, in the last 30 days" is a much harder query than pure similarity, and the index has to be built for it.

## The short of it

An embedding puts meaning somewhere in space, so similarity becomes geometry and retrieval becomes nearest-neighbour search, ranked by cosine because vector length carries length rather than meaning. Exact search costs one comparison per document and does not survive scale, so production indexes partition the space and probe only the nearest few cells &mdash; buying a large drop in work for a small, measurable chance of missing a true neighbour. That chance is recall@k, and it moves with how many cells you probe, which makes vector search a tuning problem rather than a solved one.

## Why hybrid search wins

Embeddings are strong at paraphrase and weak at exact tokens. They will happily return a document about "annual leave" for a query about "holiday allowance" &mdash; and will blur "invoice INV-2024-8871" into every other invoice number.

Keyword retrieval (BM25) is the opposite: precise on names, codes, numbers and rare terms, and blind to paraphrase.

Combining them beats either alone, reliably enough that it is the standard recommendation. <strong>Reciprocal rank fusion</strong> is the usual merge:

<p class="mono-font">score(d) = &Sigma;<sub>lists</sub> 1 / (k + rank(d))</p>

with k around 60. It needs no score normalisation between the two systems, which is what makes it practical &mdash; BM25 scores and cosine similarities are not on comparable scales.

Add a <strong>reranker</strong> on top: retrieve 50 candidates from the hybrid stage, then score each against the query with a cross-encoder that reads both together rather than comparing precomputed vectors. Substantially more accurate, and affordable because it runs on 50 items.

## Practical notes

```python
from sentence_transformers import SentenceTransformer
import numpy as np

model = SentenceTransformer("all-MiniLM-L6-v2")
vecs = model.encode(chunks, normalize_embeddings=True,
                    batch_size=64, show_progress_bar=True)

q = model.encode([question], normalize_embeddings=True)
scores = vecs @ q[0]                       # dot product = cosine, normalised
top = np.argsort(-scores)[:5]
```

Four things that matter at scale:

<strong>Batch the embedding calls.</strong> One call per chunk is dominated by overhead; batches of 32&ndash;128 are far faster.

<strong>Normalise once, at indexing time.</strong> Then every query is a dot product.

<strong>Store the dimension you need.</strong> 384 dimensions instead of 1,536 is a quarter of the memory and search time, and often a small accuracy cost. Some models support truncating dimensions deliberately (Matryoshka embeddings).

<strong>Version your index.</strong> Changing the embedding model means re-embedding everything, so record which model produced the index.

## Questions people ask

<strong>Which embedding model should I use?</strong> Start with a well-regarded general model, then evaluate alternatives on your own question set. Public benchmarks are a weaker signal than your own data.

<strong>Do I need a vector database?</strong> Below ~100,000 vectors, a NumPy array and a dot product is genuinely fine. Above that, an index earns its place.

<strong>How do I choose k?</strong> 3&ndash;10 chunks for generation. Measure recall@k on known answers to find where returns flatten.

<strong>Why does search miss obvious matches?</strong> Usually vocabulary the embedding model has not seen, or an exact identifier that embeddings blur. Hybrid search is the fix.

<strong>Can I search across languages?</strong> With a multilingual embedding model, yes &mdash; a query in one language retrieves documents in another.

<strong>What about updating documents?</strong> Re-embed the changed chunks and upsert them. HNSW handles insertions well and deletions less well; periodic rebuilds are normal.

## Recap in one screen

- Embeddings place similar meanings near each other, so search becomes finding the nearest vectors.
- Cosine similarity ignores length; on normalised vectors it is just a dot product.
- Exact search is linear and does not scale &mdash; HNSW and IVF trade a little recall for large speed gains.
- Filtering must happen inside the search for permissions to be enforced correctly.
- Hybrid retrieval plus a cross-encoder reranker is the reliable recipe for quality.
