title: Tuples and Unpacking: A Practical Guide
intro: A tuple is a sequence that cannot be changed once built. That single restriction is what makes it usable as a dictionary key, safe to hand around, and the natural way to return more than one value.

## The difference that matters

A list and a tuple both hold an ordered run of items, and both index the same way. The difference is one word: a tuple is immutable. Once it exists, no element can be replaced.


```python
point = (3, 4)
point[0] = 99  # TypeError
```


That sounds like a limitation and is mostly a guarantee. If you hand a list to a function, the function can change it under you. Hand it a tuple and it cannot.

## Why immutability buys you a dictionary key

A dictionary key has to be hashable, which in practice means it must never change &mdash; if it changed, the dictionary would look for it in the wrong place. Lists are mutable, so they are unhashable, so they cannot be keys. Tuples can.

grid[(2, 3)] = "wall"

That is how you key anything by a coordinate pair, a date triple, or any other small fixed group.

```python
type((5))   # int
type((5,))  # tuple
```
## Unpacking is the point

Unpacking assigns each position to a name in one statement:

```python
x, y = point
```

It is not a special tuple feature &mdash; it works on any sequence &mdash; but tuples are where you meet it. The number of names must match the number of items, or Python raises `ValueError`, which is a feature: it catches the case where the shape you expected is not the shape you got.

The swap idiom falls straight out of it:

```python
a, b = b, a
```

The right-hand side is evaluated first, into a tuple, and only then unpacked. No temporary variable, and no ordering bug.

## Returning more than one thing

Python has no special syntax for multiple return values because it does not need any. `return min(xs), max(xs)` returns a tuple, and the caller unpacks it:

```python
low, high = min_max(values)
```

This reads better than returning a list, because the shape is fixed: exactly two things, in a known order.

## When to reach for which

Use a list when the collection will grow, shrink or be sorted in place. Use a tuple when the group is fixed at creation and its positions mean something: a coordinate, an RGB colour, a row from a database. If you find yourself never mutating a list, a tuple states that intent and gets you hashability for free.

## Unpacking in places you did not expect

Unpacking is not limited to assignment. It is how a for loop reads pairs:

```python
for name, score in [("ana", 91), ("bo", 78)]:
    print(name, score)
```

Each item is a two-tuple, and the loop unpacks it into two names on the way
in. `dict.items()` yields tuples, which is why `for k, v in d.items()` works
at all, and `enumerate` yields `(index, value)` for the same reason.

A star collects the middle:

```python
first, *rest = [1, 2, 3, 4]      # first = 1, rest = [2, 3, 4]
head, *body, tail = "a b c d".split()
```

The starred name always becomes a list, even when it captures nothing, which
means `rest` is `[]` rather than `None` for a one-item sequence. That is worth
knowing before you write `if rest is None`.

## Where the wrong number of names bites

```python
x, y = (1, 2, 3)
```

raises `ValueError: too many values to unpack`. That looks like an annoyance
and is a safety net: it fires the moment the shape of your data changes. Code
that indexed `point[0]` and `point[1]` would have carried on quietly with a
three-element point and produced wrong answers much later.

The same error appears when a function you expected to return two things
returns one, which is usually the real bug rather than the unpacking.

## Why immutability is not just a restriction

It is tempting to read "cannot be changed" as a limitation you work around. In
practice it is a property you rely on. An immutable object can be shared freely
between functions, threads and data structures, because no holder of it can
surprise another holder by editing it. That is why the language reaches for
tuples in exactly the places where a surprise would be expensive: function
arguments arrive as a tuple, exceptions carry their arguments as a tuple, and a
function returning several values returns a tuple rather than a list.

The immutability is shallow, and this catches people. A tuple guarantees that
its slots keep pointing at the same objects; it says nothing about those
objects. A tuple containing a list will happily let you append to that list,
and the tuple is unchanged as far as Python is concerned, because it still
points at the same list. This is also why such a tuple is not hashable: its
contents can change, so any hash computed from them would go stale.

## Choosing between a tuple, a list and a small class

Three options, and the decision is usually about what the positions mean.

A list is right when the items are the same kind of thing and the collection
grows, shrinks or gets sorted: a list of scores, a list of users, a queue of
jobs. Position carries no meaning beyond order.

A tuple is right when the group is fixed at creation and each position means
something specific: a coordinate pair, an RGB colour, a database row. Position
is the meaning, which is exactly why the group must not change length.

A small class or a dataclass takes over when there are more than about three
fields, or when you find yourself writing a comment to remember what position
three was. Names beat positions the moment positions stop being obvious, and a
named tuple is the halfway house that keeps tuple behaviour while adding them.

## Why immutability is the point

A tuple cannot be changed after it is made, and that constraint is what makes
it useful rather than a limitation to work around.

It means a tuple can be a dictionary key or a set member, because its hash
cannot change underneath the container. That single property is why coordinates,
database keys and cache lookups are tuples rather than lists.

It means a tuple passed to a function cannot be modified by it, so no defensive
copy is needed.

And it means the shape is a promise. A list might have three items now and four
later; a tuple of three says the shape is fixed, which is why functions return
tuples for "several results" and lists for "a collection of similar things".

The rough guide: a list is a variable number of the same kind of thing, a tuple
is a fixed number of possibly different things.

## The comma makes the tuple

Parentheses are grouping; the comma is what creates a tuple.

```python
t = 1, 2, 3        # a tuple
t = (1, 2, 3)      # the same tuple
t = (1)            # just the integer 1
t = (1,)           # a one-item tuple
```

The one-item case is where this matters, and the trailing comma is easy to omit
and hard to see. A function that returns `(value)` returns the value; returning
`(value,)` returns a tuple containing it, and code expecting to unpack will
behave very differently between the two.

The same rule explains why a stray comma at the end of a line can silently turn
a value into a tuple &mdash; `x = compute(),` is a one-item tuple, and the
error appears wherever `x` is used.

## Unpacking is structural

Unpacking assigns by position, and the shape has to match:

```python
x, y = point
name, (lat, lon) = record
```

The second form matches nested structure, which is how you pull apart a tuple
of tuples in one statement.

A mismatch raises `ValueError`, and that is a feature: it fails at the
assignment, naming the counts, rather than producing something wrong that fails
later.

Starred unpacking handles a variable middle:

```python
first, *rest = items
first, *middle, last = items
```

`rest` is always a list, even when it captures nothing, and only one star is
allowed &mdash; two would be ambiguous about where the split falls.

## Where unpacking shows up

It is not a tuple feature. It works on any iterable, and it appears constantly:

**In loops** over pairs &mdash; `for k, v in d.items()` and
`for i, x in enumerate(xs)` are both unpacking.

**In swaps** &mdash; `a, b = b, a` builds a tuple on the right and unpacks it
on the left, which is why no temporary is needed and why the order is safe.

**In multiple returns** &mdash; a function returning `x, y` returns one tuple,
and the caller unpacking it is what makes it feel like two values.

**In function calls** &mdash; `f(*args)` is the spreading counterpart.

**Ignoring parts** &mdash; `_, value = pair` is the convention for "I do not
need this one".

## Named tuples, when positions stop being obvious

A tuple of two is readable. A tuple of six is a puzzle, and `row[4]` tells the
reader nothing.

```python
from collections import namedtuple
Point = namedtuple("Point", "x y")
p = Point(1, 2)
p.x           # and p[0] still works
```

`typing.NamedTuple` is the modern spelling with annotations, and a frozen
dataclass is the next step up when methods are wanted too.

The migration path is gentle: a named tuple is still a tuple, so existing code
that indexes or unpacks it keeps working while new code uses the names. That
makes it a low-risk improvement to a function that has grown to return four
things.

## The immutability is shallow

A tuple fixes its references, not the objects behind them:

```python
t = ([1, 2], "a")
t[0].append(3)      # allowed
t[0] = [9]          # TypeError
```

The list inside is still mutable. That surprises people, and it has a practical
consequence: a tuple containing a list is **not hashable**, so it cannot be a
dictionary key even though tuples usually can. The error appears at insertion
and names unhashability rather than the nested list.

## Common mistakes

**Forgetting the trailing comma** for a one-item tuple.

**A stray comma** turning a value into a tuple silently.

**Unpacking the wrong number of items**, which raises &mdash; usually because
the data's shape is not what was assumed.

**Using a tuple with a mutable item as a key**, which raises on insertion.

**Indexing a long tuple** where a named tuple or dataclass would say what the
field is.

**Assuming a tuple is faster in a way that matters** &mdash; it is marginally
lighter, and that is rarely the reason to choose one.
