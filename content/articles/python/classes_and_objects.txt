title: Classes and Objects: A Practical Guide
intro: A class bundles data with the functions that operate on it. The class is a template; each instance built from it carries its own copy of the data and shares the behaviour.

## Template and instance


```python
class Dog:
    def __init__(self, name, age):
        self.name = name
```


`Dog` describes what a dog is. `Dog("rex", 3)` builds one. Build two and they are independent: changing `a.age` leaves `b.age` alone, because each instance has its own attributes.

## What __init__ does

`__init__` runs immediately after the instance is created, and its job is to set up that instance's data. It is not a constructor in the C++ sense &mdash; the object already exists by the time it runs &mdash; but in practice it is where you put everything the object needs to start life.

The double underscores mark it as a name Python itself calls. You almost never call `__init__` directly.

## Class attributes are shared


```python
class Counter:
    total = 0      # one, for everybody
    def __init__(self):
        self.count = 0  # one per instance
```


`self.count` belongs to the object. `Counter.total` belongs to the class and every instance sees the same one. This is occasionally what you want &mdash; a registry, a shared cache, a constant &mdash; and is a bug the rest of the time, in the same family as the mutable default argument.

## __repr__ earns its keep immediately

By default, printing an object gives you something like `&lt;__main__.Point object at 0x104...&gt;`, which tells you nothing. Define `__repr__` and you decide:


```python
def __repr__(self):
    return f"Point({self.x}, {self.y})"
```


It costs two lines and pays for itself the first time you print a list of them.

## When to write one

Not for everything. If you have a function and some data it operates on, and they keep travelling together &mdash; passed to the same functions, returned in pairs &mdash; a class makes that relationship explicit. If you just need to return two values, a tuple is lighter and clearer.

## When a class is the right answer

Not everything should be a class. Python is not a language where you have to
wrap a function in one to run it, and a module full of functions is a perfectly
good design.

The signal that you want a class is data and behaviour travelling together. If
several functions all take the same three arguments, and those three arguments
always change as a group, they are describing one thing that does not have a
name yet. Giving it a name and hanging the functions off it as methods removes
the repetition and makes the relationship explicit.

The opposite signal is a class with one method and no state beyond what that
method was passed. That is a function wearing a costume, and the function is
easier to test, easier to import and easier to read.

## State is the thing to be careful with

An object's attributes are its state, and state is what makes code harder to
reason about, because the answer to "what does this method return" becomes "it
depends what happened earlier". That is not an argument against classes; it is
an argument for keeping state small and obvious.

Two habits help. Set every attribute in `__init__`, even if only to `None`, so
that reading the constructor tells you everything the object holds - attributes
appearing halfway through some other method are how objects become mysterious.
And prefer methods that return new values over methods that quietly mutate the
object, unless mutation is the point and the name says so.

## The underscore convention

Python has no private attributes. A leading underscore - `self._cache` - is a
convention meaning "this is internal, do not rely on it", and nothing enforces
it. That sounds weak and works surprisingly well: it marks the boundary between
what you promise and what you may change, which is all the distinction was ever
for.

A double leading underscore triggers name mangling, which is a different feature
aimed at avoiding clashes in subclasses rather than at privacy. It is rarely
what you want.

```python
from dataclasses import dataclass

@dataclass
class Point:
    x: float
    y: float
```
## What a class is for

A class bundles data with the functions that operate on it, and the useful test
for whether you need one is whether several functions keep taking the same
group of arguments.

```python
def area(w, h): ...
def perimeter(w, h): ...
def scale(w, h, factor): ...
```

Three functions all taking `w, h` is a `Rectangle` asking to exist. The class
version removes the repeated arguments and gives the pair a name.

The opposite is also true and more often ignored: a class with one method and
no state is a function with extra steps. If nothing is remembered between calls,
a function is the simpler thing.

## self is not magic

`self` is the instance, passed as the first argument. Python passes it
automatically when a method is called on an object, so `r.area()` is really
`Rectangle.area(r)`.

Knowing that explains several things that otherwise look arbitrary: why `self`
appears in the definition and not the call, why forgetting it produces an
argument-count error, and why the name is a convention rather than a keyword
&mdash; it can be called anything, and calling it anything else will confuse
every reader.

It also explains why attributes must be written `self.width` and not `width`.
The bare name is a local variable in the method; the attribute lives on the
instance and has to be reached through it.

## Instance state versus class state

An assignment inside `__init__` creates a **per-instance** attribute. An
assignment in the class body creates a **class attribute**, shared by every
instance:

```python
class Basket:
    items = []            # shared by all baskets - almost always a bug
    def __init__(self):
        self.items = []   # one per basket - what was meant
```

The first version gives every basket the same list, so adding to one adds to
all. It is the same mechanism as the mutable default argument, and it produces
the same class of confusing bug.

Class attributes are right for genuine constants shared by the type &mdash; a
default rate, a set of valid statuses, a counter of instances created &mdash;
and wrong for anything an instance should own.

## The methods worth defining

`__init__` sets up state and should do little else. Work that can fail belongs
in a classmethod constructor or a separate call, because an exception in
`__init__` leaves a half-built object.

`__repr__` decides what the object looks like in a debugger, a list, or a log.
Defining it is the highest-value five minutes available, because it changes
every future debugging session. Aim for something that shows the identifying
fields.

`__eq__` decides what equality means. Without it, two objects with identical
contents are unequal, because the default compares identity. Defining `__eq__`
without `__hash__` makes the object unhashable, which is deliberate &mdash; a
mutable object that compares by value cannot safely be a dictionary key.

`__str__` is optional; `str` falls back to `__repr__`, so one well-written
`__repr__` covers both.

## Dataclasses

For a class that is mostly data, `@dataclass` writes `__init__`, `__repr__` and
`__eq__` from the annotations:

```python
from dataclasses import dataclass

@dataclass
class Point:
    x: float
    y: float
```

That is the whole class, and it behaves better than most hand-written
equivalents because the generated methods are complete and consistent.

`frozen=True` makes instances immutable and hashable, which is the right choice
for value objects. `field(default_factory=list)` is how a mutable default is
declared safely &mdash; the dataclass machinery refuses a plain `[]`, which is
one of the few places Python protects you from that trap.

`NamedTuple` is the lighter alternative when the object is genuinely a tuple
with names, and a plain dictionary is the right answer when the shape is not
fixed.

## Properties, when an attribute needs logic

A property makes a method look like an attribute, which lets a plain attribute
grow validation or computation later without changing every caller:

```python
@property
def area(self):
    return self.width * self.height
```

The convention that makes this work is to start with plain attributes and add a
property only when there is a reason. Writing getters and setters for every
field up front is a habit from languages that cannot change an attribute into a
property later; Python can, so the ceremony buys nothing.

## Common mistakes

**A mutable class attribute**, shared by every instance.

**Forgetting `self`** in a method definition, or in an attribute reference.

**No `__repr__`**, so debugging shows an object and a memory address.

**Defining `__eq__` without `__hash__`**, making instances unusable in sets.

**Doing work that can fail in `__init__`**, leaving half-built objects.

**A class with no state**, which is a function.

**Getters and setters everywhere**, where properties exist for exactly the case
that needs them.
