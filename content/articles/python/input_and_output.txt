title: input() and Output: A Practical Guide
intro: input() reads one line from the user and returns it as a string &mdash; always a string, whatever it looks like. print() sends values the other way, with two options worth knowing.

## A note about this page

The editors here run Python in your browser, which has no keyboard attached to standard input, so `input()` raises `OSError`. The first program calls it inside a `try` so you can see exactly that, rather than the page pretending otherwise. Everything else uses a stand-in value, and behaves identically to what you would get from a real terminal.

## It is always text


```python
typed = input("Age: ")  # user types 42
typed + typed          # "4242", not 84
```


This is the first surprise everyone meets. `input` cannot know whether "42" is meant as a number, a house number or a password, so it does not guess. Convert explicitly:

```python
age = int(input("Age: "))
```

## Convert defensively

That one-liner raises `ValueError` the moment somebody types "forty" or presses enter on an empty line. For anything a real person will use:


```python
def read_int(text, default=0):
    try:
        return int(text.strip())
    except (ValueError, AttributeError):
        return default
```


`strip()` first, because people type spaces.

## The prompt is an argument

`input("Your name: ")` prints the prompt and reads on the same line. A separate `print` before it works too but puts the cursor on the next line, which reads worse.

## print has two useful options


```python
print("a", "b", sep="-")    # a-b
print(i, end=" ")         # no newline
```


`sep` sits between the values; the default is a single space. `end` goes after them; the default is a newline. `end=""` is how you build a line across several prints &mdash; and you then need a bare `print()` to close it, which the page demonstrates.

## print versus f-strings

`print` calls `str()` on whatever you give it, which is fine for quick output. When the formatting matters &mdash; decimal places, alignment, thousands separators &mdash; build the string yourself with an f-string and print that. The two are complementary, not competing.

One detail worth noticing: printing a list shows its `repr`, so strings appear with quotes. `", ".join(items)` is what you want when the output is for a person.

## Validating in a loop

A single `int(input())` is fine in an example and unusable in a program a person
will actually operate, because the first typo ends it. The shape that works asks
again:

```python
def ask_int(prompt):
    while True:
        raw = input(prompt).strip()
        try:
            return int(raw)
        except ValueError:
            print(f"'{raw}' is not a whole number - try again.")
```

Three things are worth copying from that. The prompt says what is wanted. The
error message repeats what was typed, so the person can see the typo. And the
loop only exits on success, so the caller can rely on getting a number.

## Sentinel values and ending a loop

When you do not know how many values are coming, a sentinel ends the input:

```python
while True:
    line = input("value (blank to finish): ").strip()
    if not line:
        break
    values.append(line)
```

An empty line is the usual choice because it is what pressing enter produces. If
blank is a legitimate value, pick something explicit like `done` and say so in
the prompt.

## Reading from a pipe rather than a person

`input` reads a line from standard input, and standard input is not always a
keyboard. If your program is run as `cat data.txt | python script.py`, the same
`input` calls read lines from the file, and an `EOFError` is raised when it runs
out - which is the same error you get if someone presses Ctrl-D.

That is worth handling in anything that might be piped:

```python
try:
    line = input()
except EOFError:
    line = None
```

It is also why this page's first program raises in the browser: there is no
standard input attached at all.

## Printing for people versus printing for programs

Output aimed at a person wants formatting, alignment and separators.
Output aimed at another program wants to be trivially parseable - one record per
line, a consistent separator, no decorative headers.

Mixing the two is what makes a script hard to use in a pipeline. If a program
might be consumed by another, keep the data on standard output and put the
progress messages, prompts and warnings on standard error:

```python
import sys
print("processing...", file=sys.stderr)
print(result)
```

Then `script.py > out.txt` captures exactly the results and leaves the chatter
on screen.

## Input is blocking, and that shapes programs

`input()` stops the program until a line arrives and the user presses Enter.
Nothing else happens in the meantime.

For a script run at a terminal that is exactly right. It is also why `input()`
belongs nowhere near code that runs unattended: a scheduled job, a web request
handler, or a test suite that calls it will simply hang, waiting for a keyboard
that is not there.

The symptom is a process that never finishes and produces no error, which is
harder to diagnose than a crash. If a function might be called from both a
terminal and a script, take the value as an argument and let the caller decide
where it came from:

```python
def greet(name):
    print(f"Hello, {name}")

greet(input("Name: "))        # interactive
greet(sys.argv[1])            # from the command line
greet("ana")                  # from a test
```

The function is now testable, and nothing inside it waits for anyone.

## End of input

When input comes from a file or a pipe rather than a person, it eventually runs
out. `input()` raises `EOFError` at that point.

```python
try:
    line = input()
except EOFError:
    line = None
```

That is the polite way to end a loop reading piped input, and it is why a
program that works interactively can crash when its input is redirected from a
file.

Reading everything at once avoids the question entirely:

```python
import sys
text = sys.stdin.read()
```

and iterating over `sys.stdin` gives one line at a time without the exception:

```python
for line in sys.stdin:
    process(line.rstrip("\n"))
```

That last form is the one to reach for when the program is meant to sit in a
pipeline, because it works for a file of any size and needs no `try`.

## Where output actually goes

`print` writes to standard output. Errors, warnings and progress messages
belong on standard error instead:

```python
import sys
print("done", file=sys.stdout)          # the result
print("skipping row 12", file=sys.stderr)   # the commentary
```

The distinction matters the moment anyone redirects the output. `script.py >
results.txt` captures only stdout, so the commentary stays on the screen where
it can be read and the file contains only the data.

Mixing the two means a results file full of progress notes, and a program whose
output cannot be piped into anything.

## Buffering, and why output appears late

Standard output is buffered when it is not a terminal. Python collects text and
writes it in blocks, which is faster and means a program whose output is piped
to a file may show nothing for a long time and then everything at once.

That is why a long-running script looks frozen when its output is redirected
and lively when it is not.

`print(..., flush=True)` forces one line out immediately. `python -u` turns
buffering off for the whole process, which is the usual fix for a script whose
progress needs watching in a log.

Standard error is not buffered the same way, which is another reason progress
messages belong there.

## Reading numbers safely

`int(input(...))` on a line the user typed is one bad keystroke from a crash.
The safe shape is a loop that keeps asking:

```python
while True:
    raw = input("Age: ").strip()
    try:
        age = int(raw)
    except ValueError:
        print("Please enter a whole number.")
        continue
    if not 0 <= age <= 130:
        print("That is not a plausible age.")
        continue
    break
```

Three things are worth copying from that shape. The conversion is inside the
`try` and nothing else is. The range check is separate from the type check, so
the messages can differ. And `strip()` runs first, because a trailing space is
the commonest reason a perfectly good number fails to convert.

## Passwords and hidden input

`input()` echoes what is typed, which is wrong for a password.

```python
import getpass
secret = getpass.getpass("Password: ")
```

`getpass` reads without echoing and falls back with a warning when the terminal
cannot support it. It is in the standard library, and it is the right answer
whenever the thing being typed should not appear on screen or in a screen
recording.

## Common mistakes

**Forgetting that input returns a string.** `input()` never returns a number,
so `"5" * 3` gives `"555"` and comparisons against integers are always false.

**Converting without a guard.** One non-numeric character and the program dies.

**Not stripping.** Trailing whitespace survives, and `"yes "` does not equal
`"yes"`.

**Printing progress to stdout**, which pollutes redirected output.

**Calling `input()` in library code**, which hangs anything that is not a
terminal.

**Assuming output appears immediately** when it is redirected, and concluding
the program is stuck.
