title: zip(): A Practical Guide
intro: zip walks several sequences in step, yielding one tuple per position. It is the clean answer to "I have two lists that line up" &mdash; with one behaviour worth knowing before it bites.

## The basic shape

```python
for name, score in zip(names, scores):
    print(name, score)
```

Each pass gives you the next item from each list. The alternative is
`for i in range(len(names))` followed by two lookups, which works and puts an
index between you and the values.

It takes any number of iterables:

```python
for name, score, grade in zip(names, scores, grades):
    ...
```

## Walking two things at once

The job `zip` does is small and comes up constantly: you have two or more
sequences whose positions correspond, and you want to work with matching items
together. Names and scores, keys and values, inputs and expected outputs,
columns and headers.

Without it, the loop goes through indices and reaches back into both lists,
which reintroduces exactly the off-by-one risk that looping over items avoids.
With it, each iteration hands you one item from each and the indices disappear.

## It truncates, and it does not tell you

This is the part that costs people an afternoon:

```python
zip(["ana", "bo", "cy", "dee"], [91, 78])
```

gives two pairs. `cy` and `dee` are gone. No error, no warning &mdash; `zip`
stops when its shortest input runs out, by design.

That design cuts both ways. It is convenient when you deliberately pair a
finite list against an infinite generator, because you get exactly as many
pairs as the finite side has. It is dangerous when the two lists were supposed
to be the same length and are not, because the extra items vanish in silence
and the program produces a short, plausible, wrong answer.

Two ways to be explicit:

```python
zip(a, b, strict=True)             # ValueError on mismatch (Python 3.10+)
zip_longest(a, b, fillvalue=0)     # pads instead, from itertools
```

Use `strict=True` whenever equal lengths are an assumption rather than a
coincidence. It turns a silent bug into an immediate error, which is nearly
always the better trade. `zip_longest` is the opposite choice: keep everything,
and fill the gaps.

## Building a dictionary from two lists

```python
dict(zip(keys, values))
```

This is the standard way to turn parallel lists into a mapping, and it reads
better than any loop version. It appears constantly when handling CSV rows,
where the header row supplies the keys and each data row supplies the values.

The truncation rule applies here too, and is easier to miss: a row with fewer
fields than the header produces a dict with fewer keys, silently, and the
missing ones surface later as a `KeyError` a long way from the cause.

## Unzipping

The same function undoes itself, which surprises people:

```python
pairs = [("ana", 91), ("bo", 78)]
names, scores = zip(*pairs)
```

The star spreads the list of pairs into separate arguments, so `zip` receives
each pair as its own iterable and re-pairs them by position.

Two details. The results are **tuples**, not lists, which matters only if you
intend to mutate them &mdash; wrap in `list()` if you do. And `zip(*[])` on an
empty list produces nothing to unpack, so the idiom raises on empty input,
which is worth guarding when the data can be empty.

## It is lazy

`zip` returns an iterator rather than a list. Printing it shows an object, and
consuming it twice gives nothing the second time.

In a `for` loop that is invisible and ideal &mdash; it is what lets `zip` work
on files and generators without loading them. The moment you want to keep the
result, or look at it twice, wrap it in `list()`.

```python
pairs = zip(a, b)
print(len(pairs))        # TypeError: no len() on an iterator
pairs = list(zip(a, b))  # now it has a length, and survives a second pass
```

## Where it fits among the alternatives

**`zip`** &mdash; several sequences, matched by position.

**`enumerate`** &mdash; one sequence, matched with its position.

**`zip(*rows)`** &mdash; transposing rows into columns.

**`itertools.product`** &mdash; every combination rather than matched pairs,
which is the thing people occasionally reach for `zip` expecting.

**`dict.items()`** &mdash; when the pairing already exists in a mapping, which
is better than zipping `keys()` against `values()`.

That last one is worth stating: `zip(d.keys(), d.values())` works and is a
longer way of writing `d.items()`.

## Common mistakes

**Assuming equal lengths.** The commonest and quietest. `strict=True` when they
should match.

**Calling `len()` on the result**, which raises because it is an iterator.

**Consuming it twice.** The second pass sees an exhausted iterator and does
nothing, with no error.

**Forgetting the star when unzipping.** `zip(pairs)` wraps each pair in another
tuple instead of transposing; `zip(*pairs)` is the transpose.

**Zipping `keys()` and `values()`** where `items()` says it directly.

## The short version

`zip` pairs sequences by position, lazily, stopping at the shortest.

It is the right answer whenever two collections line up, and it is one argument
away &mdash; `strict=True` &mdash; from being safe when they are supposed to.

The star form transposes, `list()` makes the result reusable, and `enumerate`
is its sibling for when the thing you need alongside the item is its position
rather than another sequence.
