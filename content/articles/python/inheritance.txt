title: Inheritance: A Practical Guide
intro: A class can be built on another one, taking its attributes and methods and changing only what differs. Used carefully it removes real duplication; used loosely it produces hierarchies nobody can follow.

## The basic move


```python
class Dog(Animal):
    def speak(self):
        return "woof"
```


`Dog` gets everything `Animal` has. Where it defines a method of the same name, that version wins &mdash; that is overriding.

The payoff shows up in methods the parent already wrote:


```python
def describe(self):
    return f"{self.name} says {self.speak()}"
```


`describe` was written once on `Animal` and calls whichever `speak` the actual object has. Add a tenth animal and `describe` needs no change. That is the whole argument for inheritance in one method.

## super()


```python
class Dog(Animal):
    def __init__(self, name, breed):
        super().__init__(name)
        self.breed = breed
```


A subclass `__init__` replaces the parent's, so the parent's setup does not happen unless you ask for it. Forget `super().__init__(name)` and `self.name` never gets set &mdash; the failure arrives later as an `AttributeError` from some unrelated method, which the page demonstrates.

`super()` also works for extending rather than replacing:

return super().speak().upper() + "!!!"

Take the parent's answer, then modify it.

## The lookup order

With several parents, Python walks a defined order &mdash; the MRO, visible as `Cls.__mro__` &mdash; taking the first match. Reading it is how you answer "which version actually ran".

Multiple inheritance is a sharp tool. Mixins with distinct responsibilities are fine; deep diamond hierarchies are how codebases become unreadable.

## is-a, not has-a

Inherit when the subclass genuinely <em>is</em> a kind of the parent and can be used wherever the parent is expected. A `Dog` is an `Animal`, so `describe` works on both.

When the relationship is "has a" &mdash; a `Car` has an `Engine` &mdash; hold the other object as an attribute instead. Composition is easier to change later, because it does not tie two classes together permanently to share a couple of methods.

The common failure is inheriting to reuse a method. If that is the only reason, a function or a held object is nearly always the better answer.

## Composition, concretely

"Prefer composition" is common advice and rarely shown. The difference is whether
the other object is *what you are* or *what you have*:

```python
class Car(Engine):            # inheritance: a Car IS an Engine - wrong
    ...

class Car:                    # composition: a Car HAS an Engine
    def __init__(self, engine):
        self.engine = engine

    def start(self):
        return self.engine.start()
```

The composed version costs one line of delegation and gains a great deal: the
engine can be swapped, tested on its own, or shared, and `Car` exposes only the
methods it chose to expose rather than everything `Engine` happens to define.

The test is substitutability. If code that expects the parent can be handed the
child and keep working, inheritance is honest. If not - if the child overrides
methods to raise, or ignores half of what it inherited - the relationship is not
"is a".

## Abstract base classes

When a parent exists to define an interface rather than to be instantiated,
`abc` makes that explicit:

```python
from abc import ABC, abstractmethod

class Shape(ABC):
    @abstractmethod
    def area(self): ...
```

Subclasses that forget `area` fail at construction with a clear message, rather
than at some later call site with `AttributeError`. That turns a runtime
surprise into an immediate, located error.

## Duck typing means you often need neither

Python does not require a shared base class for polymorphism. Anything with the
right method works:

```python
def describe(thing):
    return thing.speak()
```

This accepts any object with a `speak` method, related or not. A great deal of
Python code that would need an interface in another language needs nothing here,
which is worth remembering before building a hierarchy to enable something that
already works.

## Multiple inheritance and mixins

Multiple parents are legal, and the reasonable use is a mixin: a small class
providing one capability, with no state of its own and no expectation of being
instantiated - `JSONSerialisableMixin`, `TimestampMixin`.

Deep diamond hierarchies are the unreasonable use. When two parents both define
the same method and both call `super()`, the order of execution depends on the
MRO, and reasoning about it stops being possible for anyone who did not write it.
If you need `__mro__` to work out which code runs, the design has already cost
more than it saved.

## Overriding, and calling the original

Redefining a method in a subclass replaces it entirely. Calling `super()` runs
the parent's version as part of yours:

```python
class Account:
    def describe(self):
        return f"{self.owner}: {self.balance}"

class Savings(Account):
    def describe(self):
        return super().describe() + f" (rate {self.rate})"
```

That is the common and reasonable shape: extend the parent's behaviour rather
than reproduce it.

The failure to avoid is copying the parent's body into the child and editing
it. The two then drift, and a fix applied to one leaves the other wrong &mdash;
which is the duplication inheritance was supposed to remove.

## What a subclass promises

A subclass is a promise that it can be used anywhere the parent can. Code that
holds an `Account` should not need to know whether it is really a `Savings`.

Breaking that promise is the usual source of inheritance bugs, and it happens in
specific ways:

**Narrowing what a method accepts.** If the parent's `withdraw` takes any
positive amount and the child's rejects amounts over 100, existing code that
was correct against the parent is now wrong.

**Raising where the parent did not.** A child whose `save()` raises for some
inputs breaks every caller that had no reason to catch anything.

**Changing what a method returns.** A parent returning a list and a child
returning a single item will fail somewhere far away.

The test is simple to state: could someone replace the parent with the child
without reading the child's source? If not, the relationship is not
inheritance, whatever the class statement says.

## The classic wrong hierarchy

A square is a rectangle in geometry and not in code.

```python
class Rectangle:
    def set_width(self, w): self.w = w
    def set_height(self, h): self.h = h

class Square(Rectangle):     # tempting, and wrong
    def set_width(self, w): self.w = self.h = w
```

Any code that sets a width and a height and expects both to hold now breaks for
squares. The class hierarchy is inherited from mathematics, where the objects
are immutable; the code's objects are not.

The lesson generalises: inheritance is about **substitutable behaviour**, not
about whether the words are in an is-a relationship in English.

## When composition is the answer

If the child needs only some of the parent's behaviour, or needs to disable
part of it, that is composition:

```python
class Cache:
    def __init__(self):
        self._data = {}          # has a dict, is not a dict
    def get(self, k):
        return self._data.get(k)
```

Subclassing `dict` here would expose fifty methods you have not thought about,
each of which is now part of your interface and can be called by anyone.

The rule of thumb: inherit when you want everything the parent does and mean to
be usable in its place; compose when you want one capability and control over
what is exposed.

## Attributes and __init__

A subclass that defines `__init__` and does not call `super().__init__()` gets
an object the parent's methods cannot work with, because the attributes they
rely on were never set.

```python
class Savings(Account):
    def __init__(self, owner, balance, rate):
        super().__init__(owner, balance)     # not optional
        self.rate = rate
```

The failure appears later, as an `AttributeError` in a parent method, a long
way from the constructor that caused it.

The same applies to `__eq__`, `__hash__` and `__repr__`: overriding one without
thinking about the others produces objects that behave inconsistently in sets,
dicts and debug output.

## Depth

Two levels of inheritance is usually manageable. Four is usually a design that
grew rather than one that was chosen.

The cost of depth is that behaviour is assembled from pieces spread across
files, and answering "what does this method do?" means reading the whole chain.
`Class.__mro__` tells you the order, and needing it regularly is the signal that
the hierarchy has outgrown its usefulness.

Flattening usually means turning the middle layers into composed objects or
plain functions, which is more code in the class and less code to find.

## Common mistakes

**Copying the parent's method body** instead of calling `super()`.

**Subclassing to reuse code** rather than to be substitutable &mdash; the most
common misuse, and what composition is for.

**Forgetting `super().__init__()`**, which produces an `AttributeError` far from
its cause.

**Subclassing builtins** like `dict` or `list` without needing their full
interface.

**Deep hierarchies**, where finding the code that runs requires the MRO.

**Overriding a method with a different signature**, which breaks callers that
were written against the parent.
