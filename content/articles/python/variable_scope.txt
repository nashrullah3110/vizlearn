title: Variable Scope: A Practical Guide
intro: When Python meets a name, it looks in four places in a fixed order &mdash; local, enclosing, global, builtin &mdash; and stops at the first one that has it. Almost every scope surprise comes from one rule about assignment.

## The four places

LEGB is the order:

- <strong>Local</strong> &mdash; names assigned in the current function
- <strong>Enclosing</strong> &mdash; names in a function that wraps this one
- <strong>Global</strong> &mdash; names at module level
- <strong>Builtin</strong> &mdash; `len`, `print`, `range` and friends

The first match wins, which is why naming a variable `list` or `sum` shadows the builtin for the rest of that scope. It is legal and it will confuse you later.

## Reading is easy, assigning is the trap

A function can read an outer name without ceremony:


```python
x = "global"
def show():
    print(x)  # fine
```


But assigning to that name inside the function does not change the outer one. It creates a new local name that happens to be spelled the same, and it disappears when the function returns.

## The rule that catches everyone

<strong>If a name is assigned anywhere in a function, it is local for the entire function</strong> &mdash; including lines that run before the assignment.


```python
def broken():
    print(x)      # UnboundLocalError
    x = "too late"
```


That `print` looks like it should read the global, and it would have, if the line below it did not exist. Python decides local-or-not when it compiles the function, not while running it. The error message &mdash; "local variable referenced before assignment" &mdash; is precise once you know this, and baffling before.

## global and nonlocal

To rebind rather than shadow, say so:


```python
def bump():
    global count
    count += 1
```


`global` reaches module level. `nonlocal` reaches the nearest enclosing function, which is what makes closures able to keep state:


```python
def counter():
    n = 0
    def step():
        nonlocal n
        n += 1
```


Both are worth knowing and neither is worth reaching for often. A function that rebinds globals is a function whose behaviour depends on when you call it, which is exactly the kind of thing that makes bugs hard to find. Returning a value is nearly always better.

## Mutating is not assigning

One clarification that resolves a lot of confusion: `items.append(1)` is not an assignment. It mutates the object the name already points at, so it affects the outer list without needing `global`. `items = [1]` is an assignment, and creates a local. The distinction is the object versus the name.

## Why the rule exists

Deciding local-or-not at compile time looks like an odd choice until you
consider the alternative. If Python worked out scope while running, then whether
a name was local could depend on which branch had executed, and the same line
could mean two different things on two different runs. Instead the compiler
scans the whole function body once: if a name is assigned anywhere in it, that
name is local everywhere in it.

That single rule explains the `UnboundLocalError` that catches everyone. The
read on line one is a read of a local variable, because line five assigns to it,
and the local has no value yet. The error message is precise; it just describes
a decision made before the function ran.

## Closures, and why they are useful

A function defined inside another function can see the enclosing function's
variables, and it keeps seeing them after the outer function has returned. That
combination - an inner function plus the variables it captured - is a closure,
and it is how a function can carry state without a class or a global.

The counter on this page is the small version. The pattern scales to
configuration: a function that builds and returns another function with some
settings already baked in. `make_formatter(currency="GBP")` returns something
you can call many times without repeating the currency.

`nonlocal` exists because assigning inside the inner function would otherwise
create a new local there, exactly as it would at module level. It says "this
name belongs to the function that wraps me", and it is the only way to update
captured state rather than merely read it.

## Globals, and when they stop being harmless

Reading a module-level constant from inside a function is ordinary and fine -
that is what constants are for. Writing to a module-level name from inside a
function is where trouble starts, because the function's behaviour now depends
on what ran before it, and testing it in isolation stops being possible.

The practical test is whether calling the function twice with the same arguments
gives the same answer. If a `global` statement means it does not, the state
probably wants to be a parameter, a return value, or an attribute on an object -
all three of which make the dependency visible in the signature rather than
buried in the body.

## Shadowing builtins

`list`, `dict`, `set`, `id`, `type`, `sum`, `input` and `max` are all ordinary
names that happen to be defined in the builtin scope, and assigning to any of
them inside your code hides the original for the rest of that scope. It is legal
and it produces confusing failures later, usually when something calls `list(x)`
and gets a `TypeError` about your list not being callable.

## The rule, and its name

Python resolves a name by looking in four places, in order: the **local**
function, any **enclosing** functions, the **global** module, and finally the
**built-ins**. The first match wins, and the acronym LEGB is how it is usually
remembered.

The consequence that matters is that a function can read a global without doing
anything special, and cannot assign to one without saying so. Reading walks
outward; assignment always creates or updates a local unless declared
otherwise.

That asymmetry is deliberate. It means a function's assignments cannot silently
change the module around it, so reading a function tells you what it modifies.

## Assignment makes a variable local, everywhere in the function

The subtle part is that the decision is made for the **whole function** at
compile time, not line by line.

```python
count = 0

def bump():
    print(count)     # UnboundLocalError
    count = count + 1
```

The `print` fails even though the assignment is below it. Because `count` is
assigned somewhere in the body, it is local throughout, and it has no value yet
when the `print` runs.

The error message names the variable and not the cause, which makes this one of
the more confusing beginner errors. The fix is either `global count`, or &mdash;
usually better &mdash; returning the new value instead of mutating a module
variable.

## global and nonlocal

`global name` declares that assignment should target the module level.
`nonlocal name` targets the nearest enclosing function, which is what closures
need when they must update captured state.

Both work, and both are worth treating as a signal rather than a tool. A
function that needs `global` is usually one that would be clearer taking a
parameter and returning a result, because that version can be tested, called
twice, and read without knowing what else touches the same name.

`nonlocal` has fewer good alternatives, since a counter shared by an inner
function has to live somewhere, but a small class or a `functools.partial` is
often clearer than a closure mutating captured state.

## Mutation is not assignment

The rule constrains assignment, not modification.

```python
items = []

def add():
    items.append(1)      # fine: no assignment, so no local created
```

`append` modifies the object the global name refers to, which needs no
declaration. Rebinding `items` to a new list would.

So a function can change a module-level list or dictionary freely and silently.
That is a genuine hazard, and it is the reason the mutability module's advice
about not modifying shared structures matters here too: the scope rules will not
protect you, because nothing was assigned.

## Comprehensions and loops

A comprehension has its own scope. The loop variable inside it does not leak,
so `[x for x in range(3)]` leaves no `x` behind. That was a change in Python 3
and is why old examples sometimes rely on the leak.

An ordinary `for` loop does **not** have its own scope. Its variable survives
the loop and holds the last value, which is occasionally useful and a common
source of accidental reuse.

Neither `if` nor `with` nor `try` creates a scope either. A name first assigned
inside an `if` branch exists after it &mdash; or does not, if the branch did not
run, which produces a `NameError` that depends on the data.

## Closures capture names, not values

An inner function remembers the variable, not what it held at the time:

```python
fns = [lambda: i for i in range(3)]
[f() for f in fns]        # [2, 2, 2]
```

All three lambdas refer to the same `i`, which by the time they are called is
`2`.

The fix is a default argument, which is evaluated at definition time and so
captures the value:

```python
fns = [lambda i=i: i for i in range(3)]   # [0, 1, 2]
```

This is the same mechanism as the mutable-default trap, working in your favour
for once.

## Common mistakes

**Reading a name that is assigned later in the function**, which raises
`UnboundLocalError` rather than reading the global.

**Reaching for `global`** where a parameter and a return value would do.

**Assuming mutation needs a declaration**, which it does not &mdash; so
functions can change shared containers silently.

**Expecting a `for` variable to be scoped to the loop**, which it is not.

**Capturing a loop variable in a closure**, and finding every function sees the
final value.

**Shadowing a builtin** &mdash; naming a variable `list`, `dict`, `id`, `type`
or `sum` &mdash; which works until the builtin is needed in the same scope.
