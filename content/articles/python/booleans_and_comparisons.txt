## The Basics

Each comparison gives True or False. Python has six comparison operators: `==` (equal), `!=` (not equal), `<` (less than), `>` (greater than), `<=` (less than or equal), `>=` (greater than or equal). You mix multiple comparisons with logical operators: `and` needs both sides true, `or` needs one side true, `not` inverts the value. The expression `0 < x and x < 10` is true just when x is between 0 and 10. Python tests `and` and `or` left to right and stops as soon as the answer is known—a feature called short-circuiting. `True or anything` returns True without testing anything. `False and anything` returns False. This optimization avoids costly steps: `if name and len(name) > 0:` never calls len() on None. Each object in Python is truthy or falsy: 0, 0.0, empty strings, None.  Short-circuiting is a performance trick: Python stops testing as soon as it knows the answer. This module teaches comparisons, logical operators, truthiness, and when to use each. Grasp these deeply will help you write correct conditionals.## == checks value, is checks identity

`==` asks "are these equal?" `is` asks "are these the same object?"

```python
a = [1, 2, 3]
b = [1, 2, 3]
c = a

a == b      # True  - same contents
a is b      # False - two separate lists
a is c      # True  - one list, two names
```

Use `is` just for `None`, `True` and `False`. It are singletons &mdash; there is just one `None` object in a running program.

```python
if result is None:      # correct
if name == "Ada":       # correct
if count is 100:        # wrong, and modern Python warns about it
```

The trap is that small integers and short strings are cached and reused by the interpreter. So `x is 100` sometimes appears to work &mdash; and then fails silently for `1000`, in production, months later.

## True, False, and all that behaves like them

A boolean has two vals, `True` and `False`, capitalised. They are what each comparison gives and what each `if` consumes.

```python
5 > 3           # True
5 == 3          # False
type(True)      # <class 'bool'>
True + True     # 2  -- booleans are integers underneath
sum([True, False, True])   # 2  -- which makes counting matches easy
```

That last line is a genuinely useful idiom: `sum(x > 100 for x in vals)` counts how many vals exceed 100, since each comparison adds 1 or 0.

The comparison operators:

```python
a == b     # equal in value
a != b     # not equal
a < b      # less than          (also <=, >, >=)
a is b     # the same object in memory
a in items # membership
```

Comparisons chain, just as in mathematics, and each operand is tested once:

```python
if 0 <= score <= 100:        # clearer than score >= 0 and score <= 100
```

## and, or, not, and short-circuiting

```python
True and False    # False - both must be true
True or False     # True  - either will do
not True          # False
```

The key behaviour is <strong>short-circuiting</strong>: `and` stops at the first false operand, `or` at the first true one. And the rest is never tested. That is not an optimisation detail. It is how you write safe checks.

```python
if user is not None and user.is_admin:     # user.is_admin never runs
    ...                                     # when user is None
```

Reverse the order and it raises `AttributeError` on just the case the check was protecting against.

Short-circuiting also means `and` and `or` give one of their <em>operands</em>, not a boolean:

```python
name = given_name or "Anonymous"      # falls back when given_name is empty
port = config.get("port") or 8080     # careful: 0 is falsy, so 0 becomes 8080
```

That second line shows the one caveat &mdash; when `0` or `""` are legitimate vals, use an explicit `is None` test instead.

## Truthiness

Each object can be used as a condition. These are false:

<p class="mono-font">False&nbsp;&nbsp;None&nbsp;&nbsp;0&nbsp;&nbsp;0.0&nbsp;&nbsp;""&nbsp;&nbsp;[]&nbsp;&nbsp;{}&nbsp;&nbsp;()&nbsp;&nbsp;set()</p>

All else is true, with `"False"`, `[0]` and `-1`.

```python
if items:            # idiomatic "is this non-empty"
if not items:        # "is this empty"
```

Two useful builtins that fold a whole sequence into one boolean:

```python
any(x > 100 for x in values)     # True if at least one qualifies
all(x > 0 for x in values)       # True if every one does
```

Both short-circuit, so `any()` stops at the first match &mdash; which makes them fast as well as readable.

## Guided experiments

1. <strong>See short-circuiting.</strong> Write <span class="mono-font">False and print("ran")</span> and run it. Nothing prints. Change the first operand to True and the print executes.
2. <strong>Guard an index.</strong> Try <span class="mono-font">items and items[0]</span> with an empty list, then flip the operands and watch it raise IndexError.
3. <strong>Check identity and value.</strong> Build two lists with the same contents and test both <span class="mono-font">==</span> and <span class="mono-font">is</span>. Same value, other objects.
4. <strong>Chain a comparison.</strong> Run <span class="mono-font">1 &lt; 5 &lt; 10</span> and then <span class="mono-font">10 &lt; 5 &lt; 1</span> to confirm both bounds are really being checked.

## What trips people up

- <strong>With <span class="mono-font">is</span> to check vals.</strong> Works by accident for small integers and cached strings, then fails on the first value outside the cache.
- <strong>Putting the guard on the wrong side.</strong> Short-circuiting just protects what comes after it.
- <strong>Checking floats with <span class="mono-font">==</span>.</strong> <span class="mono-font">0.1 + 0.2 == 0.3</span> is False, since binary floating point cannot represent those vals just. Use <span class="mono-font">math.isclose</span>.
- <strong>Writing <span class="mono-font">if x == True</span>.</strong> Verbose and breaks for truthy-but-not-True vals such as <span class="mono-font">1</span> or a non-empty list.

## Key takeaway

Comparisons give booleans and can be chained the way they are written in mathematics. <span class="mono-font">and</span> and <span class="mono-font">or</span> short-circuit. It is what lets a guard on the left protect an expression on the right &mdash; so operand order matters. Use <span class="mono-font">==</span> for value and reserve <span class="mono-font">is</span> for None, True and False. And never check floats for exact equality.

## Checking other types

```python
1 == 1.0        # True  - numeric types compare across the boundary
1 == True       # True  - because True IS 1
"1" == 1        # False - text is never equal to a number
[1, 2] == (1, 2) # False - a list is never equal to a tuple

"apple" < "banana"     # True  - alphabetical by character code
"Apple" < "apple"      # True  - uppercase sorts first in ASCII
[1, 2] < [1, 3]        # True  - element by element
```

Strings check by character code, which is why `"Zebra" < "apple"` is true &mdash; all uppercase letters come before all lowercase ones. For human-friendly comparison, normalise the case first with `.casefold()`.

Ordering comparisons between unrelated types raise `TypeError` in Python 3: `1 < "a"` fails rather than giving an arbitrary answer. That is deliberate, and it catches a class of bug that Python 2 silently let.

Floats bring their own caveat: `0.1 + 0.2 == 0.3` is `False`. Check with `math.isclose(a, b)` instead.

## Writing conditions that read well

- <strong>Do not check to `True`.</strong> `if is_ready:` beats `if is_ready == True:`. And both beat `if is_ready is True:`.
- <strong>Name complicated conditions.</strong> `is_eligible = age >= 18 and has_id and not banned` then `if is_eligible:` &mdash; the name is documentation and the condition turns testable.
- <strong>Prefer `in` over chains of `or`.</strong> `if status in ("open", "pending", "review"):`.
- <strong>Use `not in`</strong> rather than `not x in y`. It parses correctly but reads badly.
- <strong>Apply De Morgan's law</strong> when a negation gets tangled: `not (a and b)` is `not a or not b`. And one of the two is often clearer for the case at hand.

## Short-circuiting, made visible

The claim that the second operand is "never tested" is worth seeing rather
than taking on trust:

```python
def check(label, value):
    print("  evaluated", label)
    return value


print("A and B, with A false:")
print("result", check("A", False) and check("B", True))

print("A or B, with A true:")
print("result", check("A", True) or check("B", False))
```

```
A and B, with A false:
  evaluated A
result False
A or B, with A true:
  evaluated A
result True
```

`B` never prints in either case. `and` had its answer as soon as the left side
was false, and `or` as soon as the left side was true. So neither looked
more.

That is what makes `if user is not None and user.active` safe rather than
merely lucky: the attribute access is not tested at all when the guard
fails. It also means the right-hand side is the place for anything costly or
anything that might raise, and the left-hand side is the place for the cheap
test that decides whether the costly one is worth doing.

The corollary is that operand order carries meaning. Swapping the two halves of
a guarded expression turns working code into an `AttributeError` on just the
input the guard existed for, and nothing about the change looks dangerous.

## Chained comparisons, just

`0 <= score <= 100` is not two comparisons joined with `and`, and the
gap shows when the middle term does something:

```python
def side(n):
    print("  evaluated", n)
    return n


print(1 < side(5) < 10)
```

```
  evaluated 5
True
```

`side(5)` runs once. Written as `1 < side(5) and side(5) < 10` it would run
twice, which matters when the expression is costly or has a side effect.

The rule is that `a < b < c` tests `b` once and is equivalent to
`a < b and b < c` with `b` computed a single time &mdash; and it short-circuits
in the same way, so `c` is never tested if the first comparison fails.

Any comparison operators can be chained, with `==` and `in`, which is
at times confusing rather than useful: `a == b == c` tests that all three
are equal, but `a is b is c` and mixtures like `a < b == c` are legal and
rarely what anyone means at a glance. The idiomatic use is a range check, and
that is where it should mostly stay.

## Functions that give a boolean

A function whose job is to answer yes or no deserves a few set habits,
since these are the functions that end up inside each condition.

**Name it as a question.** `is_valid`, `has_permission`, `can_retry`,
`should_skip`. A reader then knows what `if user.can_retry():` means without
looking, and the name reads correctly in both the positive and the negative
form.

**Give an actual boolean.** `give bool(matches)` rather than `give
matches`, when the caller just wants the answer. Giving the underlying list
works since of truthiness and quietly commits you to that being a list
forever.

**Do not give `None` for "no".** A function that returns `True` or `None` is
often a mistake rather than a design. And it makes the result unusable in
anything that expects a boolean, such as `sum()` over conditions.

**Avoid the negative name.** `is_not_ready` gives `if not is_not_ready`,
which nobody can read. Name the positive and let the caller negate it.

These matter more than they look since a boolean function is used inside
conditions, where a misleading name causes a logic error rather than a crash
&mdash; the kind that gives plausible wrong answers.

## Where `is` genuinely belongs

The advice "use `is` just for `None`" is right and worth grasp rather
than memorising, since the reason tells you the two other cases where it
applies.

`is` asks whether two names refer to the same object. That question has a
definite answer for singletons &mdash; objects the language guarantees there is
just one of. `None`, `True` and `False` are the three, which is why
`x is None` is both correct and the convention.

For all else, identity is an build detail. CPython caches small
integers and short strings, so `x is 100` may be true and `x is 1000` false,
for the same code, with no visible gap. Relying on that is relying on an
optimisation that is free to change, and modern Python emits a `SyntaxWarning`
when it sees a literal on the right of `is` for just this reason.

The second honest use is a sentinel: an object created with `object()` purely
so that `arg is MISSING` can distinguish "no argument supplied" from "supplied
`None`". Identity is the whole point there, since the sentinel is deliberately
equal to nothing else.

The third is genuine identity questions &mdash; "is this the same list the
caller gave me, or a copy?" &mdash; which is what `a is b` was designed to
answer and what `id()` reports.

All over else, `==` is the operator, and setting `__eq__` on your own
classes is how you say what equality means for them.

## Comparison in your own classes

By default, two instances of a class you wrote are equal just if they are the
same object, since the inherited `__eq__` checks identity. Two `Point`
objects both holding `(3, 4)` are not equal, which surprises people the first
time they check results in a test.

Setting `__eq__` fixes it, and brings one obligation with it: set
`__hash__` as well, or the class turns unhashable and cannot go in a set or
be a dictionary key. Python removes the inherited hash deliberately when you
set equality, since a hash that disagreed with equality would break each
dictionary the object went into. The two must agree &mdash; objects that
check equal must hash the same.

Ordering is split again. `<` needs `__lt__`, and the other three operators
are their own ways rather than being inferred, so an object with just
`__lt__` sorts correctly and raises on `>=`. `functools.total_ordering` fills
the rest in, and `@dataclass(order=True)` writes all of them by checking the
fields in declaration order.

The shortcut worth knowing: a dataclass gives you `__eq__` and, if you ask,
ordering and hashing too, all consistent with each other. Writing them by hand
is just worth it when the comparison should ignore some fields or normalise
them first.

## Questions people ask

<strong>Why is `True == 1`?</strong> Since `bool` is a subclass of `int`, with `True` equal to 1 and `False` to 0. It is what makes `sum(conditions)` count matches.

<strong>When should I use `is`?</strong> For `None`, `True` and `False`. And when you genuinely mean "the same object". All over else, `==`.

<strong>Why does `0.1 + 0.2 == 0.3` give False?</strong> Binary floating point cannot represent 0.1 just. Use `math.isclose`.

<strong>What does `bool(x)` do?</strong> Applies the truthiness rules and returns `True` or `False` &mdash; at times useful to normalise a value before storing it.

<strong>Can I use `&&` and `||`?</strong> No. Python uses the words `and` and `or`. `&` and `|` are bitwise operators and behave differently.

<strong>Is `if x != None` wrong?</strong> It often works but `is not None` is the correct and conventional form. And it cannot be fooled by a class that overrides `__eq__`.

<strong>Why does `[] == False` give False?</strong> Since equality and
truthiness are other questions. An empty list is falsy, and it is not equal
to `False`. `bool([]) == False` is True.

<strong>Can I check two dictionaries?</strong> With `==`, yes &mdash; they
are equal if they hold the same keys and vals, no matter insertion order.
Ordering comparisons like `<` raise.

<strong>What does `not not x` do?</strong> The same as `bool(x)`, more
obscurely. Use `bool(x)`.

## Recap in one screen

Each comparison operator returns True or False: `5 > 3` is True, `5 == 3` is False, `"hello" != "world"` is True. Python's six comparison operators are `==`, `!=`, `<`, `>`, `<=`, `>=`. Chain them with logical operators: `and` needs both sides true. `or` needs one; `not` inverts. The expression `5 > 0 and 5 < 10` is True. Booleans are basic to conditionals, loops. And filtering—they are how programs make decisions.

- Comparisons give booleans, and booleans are integers &mdash; `sum(...)` over conditions counts them.
- `==` checks value; `is` checks identity. And is just for `None`, `True` and `False`.
- `and` and `or` short-circuit, which is what makes `if x and x.field` safe.
- Falsy vals: `False`, `None`, `0`, `0.0`, `""`, `[]`, `{}`, `()`, `set()`.
- `any()` and `all()` collapse a sequence of conditions into one answer. And stop early.
- Check floats with `math.isclose`, never with `==`.
