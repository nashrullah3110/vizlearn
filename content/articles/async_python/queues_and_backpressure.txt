title: Queues, Producers and Backpressure
intro: The pattern most real async programs are built from, and the one number that stops a fast producer from burying a slow consumer.

## The shape of almost every async program

Once a program does more than a single fan-out, it tends to settle into the same
structure: something produces work, something else consumes it, and the two run
at different speeds. A crawler finds URLs faster than it can fetch them. A log
reader ingests lines faster than it can index them. A handler accepts requests
faster than a downstream service can answer.

An <code>asyncio.Queue</code> is the piece that connects the two. Producers
<code>put</code> items in, consumers <code>get</code> them out, and because both
operations are awaitable, the queue is also the place where one side can wait for
the other without either blocking the [loop](event_loop_stepped_through.html).

## Producer and consumer, running together

These editors run inside a browser event loop that is already going, so the examples finish with <code>await main()</code>. In a standalone <code>.py</code> script &mdash; run with <code>python file.py</code> &mdash; you write <code>asyncio.run(main())</code> instead, which starts a loop, runs the coroutine, and closes it. The two are the same program with different entry points.

```python-run
import asyncio

async def producer(q, n):
    for i in range(n):
        await q.put(i)
        print(f"produced {i}  (queue holds {q.qsize()})")
    await q.put(None)                            # sentinel: "no more"

async def consumer(q):
    while True:
        item = await q.get()
        if item is None:
            break
        await asyncio.sleep(0.1)                 # a slow consumer
        print(f"    consumed {item}")

async def main():
    q = asyncio.Queue(maxsize=2)                 # bounded
    await asyncio.gather(producer(q, 5), consumer(q))

await main()
```

```
produced 0  (queue holds 1)
produced 1  (queue holds 2)
produced 2  (queue holds 2)
    consumed 0
produced 3  (queue holds 2)
    consumed 1
produced 4  (queue holds 2)
    consumed 2
    consumed 3
    consumed 4
```

Read the queue-size column. It climbs to 2 and then stops: the producer put items
0 and 1 immediately, and when it tried to put item 2 the queue was full, so
<code>await q.put(2)</code> **suspended the producer** until the consumer took one
out. From then on the producer only advances when the consumer makes room, which
is why "produced 2" appears interleaved with "consumed" lines rather than all the
production happening first.

That pacing is the whole point, and it came from one argument.

## Backpressure is the maxsize

<code>maxsize=2</code> made the queue **bounded**, and a bounded queue is what
creates **backpressure**: when it is full, <code>put</code> waits, so a fast
producer is automatically slowed to the rate the consumer can keep up with. The
producer never runs more than two items ahead.

Remove the bound &mdash; <code>asyncio.Queue()</code> with no maxsize &mdash; and
the behaviour changes completely: the producer dumps all five items in instantly,
the queue holds all of them, and only then does the consumer start draining. With
five items that is harmless. With a producer reading a million-line file into an
unbounded queue faster than the consumer can process it, the queue grows without
limit and the program runs out of memory &mdash; a failure that looks like a leak
and is really a missing bound.

So the size of the queue is not a tuning detail; it is the contract between the
two sides. Bounded means "the producer may run at most this far ahead", and that
sentence is usually what you actually want.

## Fanning out to several consumers

One slow consumer is often the bottleneck, and the queue makes it trivial to add
more: start several consumer coroutines on the same queue and each takes the next
available item. The queue hands each item to exactly one consumer, so work is
shared without any coordination between them.

The clean way to know when everything is finished is <code>task_done</code> and
<code>join</code>. Each consumer calls <code>q.task_done()</code> after handling
an item; the producer, after putting everything, calls <code>await q.join()</code>,
which returns only once every item has been marked done. That removes the
awkward sentinel bookkeeping and gives a single, reliable "all work drained"
signal &mdash; the standard way to shut a worker pool down cleanly.

## Why a queue and not just gather

[gather and TaskGroup](running_work_concurrently.html) run a *fixed, known* set
of coroutines at once. A queue is for the other case: an *open-ended stream* of
work whose size you do not know in advance, arriving over time, to be processed
by a bounded number of workers. Crawlers, pipelines, and anything that consumes a
feed have that shape, and the queue is what decouples "how fast work arrives"
from "how fast we handle it" &mdash; with the bound as the safety valve between
them.

## A worker pool that shuts down cleanly

The section above describes <code>task_done</code> and <code>join</code>; this is
what they look like in the pattern you will actually write. Three workers share
one bounded queue, the producer waits for the queue to drain, and then the
workers are cancelled.

```python-run
import asyncio

async def worker(name, q, done):
    while True:
        item = await q.get()
        try:
            await asyncio.sleep(0.05)
            done.append((name, item))
        finally:
            q.task_done()                     # always, or join() never returns

async def main():
    q = asyncio.Queue(maxsize=3)
    done = []
    workers = [asyncio.create_task(worker(f"w{i}", q, done)) for i in range(3)]

    for i in range(9):
        await q.put(i)
    await q.join()                            # returns when every item is done

    for w in workers:
        w.cancel()
    await asyncio.gather(*workers, return_exceptions=True)

    print("items handled:", len(done))
    counts = {}
    for name, _ in done:
        counts[name] = counts.get(name, 0) + 1
    print("per worker:", dict(sorted(counts.items())))

await main()
```

```
items handled: 9
per worker: {'w0': 3, 'w1': 3, 'w2': 3}
```

Nine items, three each, with no coordination between the workers &mdash; the
queue hands each item to exactly one <code>get</code>, so the sharing is
automatic. Four details in that code are the ones that matter.

<code>task_done</code> is in a <code>finally</code>. If the work raises and the
call is skipped, <code>join</code> waits forever for an item that has been taken
but never acknowledged, and the program hangs at the end with no error. Putting
it in <code>finally</code> is not tidiness, it is what makes <code>join</code>
trustworthy.

<code>join</code> replaces the sentinel. The earlier example pushed
<code>None</code> to tell the consumer to stop, which needs one sentinel per
consumer and gets fiddly with several. <code>join</code> asks the queue directly
whether everything has been handled.

The workers are cancelled, not asked to stop. A <code>while True</code> worker
has no exit condition, and it does not need one: once <code>join</code> returns,
the work is provably finished, so cancelling is correct rather than abrupt.

And <code>gather(..., return_exceptions=True)</code> collects the cancellations.
Without it the <code>CancelledError</code>s surface as "task exception was never
retrieved" noise on shutdown.

## The other queue types, and the non-blocking calls

<code>asyncio.Queue</code> has two siblings that change only the order items
come out in. <code>LifoQueue</code> returns the most recent first, which turns a
crawler's frontier from breadth-first into depth-first with no other change.
<code>PriorityQueue</code> returns the smallest first and expects comparable
items, so the usual shape is <code>await q.put((priority, payload))</code>
&mdash; and a tuple whose second element is not comparable will raise when two
priorities tie, which is why an incrementing counter is often wedged in between.

Both <code>put</code> and <code>get</code> also have non-waiting forms.
<code>put_nowait</code> raises <code>asyncio.QueueFull</code> rather than
suspending, and <code>get_nowait</code> raises <code>asyncio.QueueEmpty</code>.
They exist for the case where waiting is the wrong behaviour &mdash; a metrics
pipeline that would rather drop a sample than slow the thing producing it, for
instance:

```python
try:
    q.put_nowait(sample)
except asyncio.QueueFull:
    dropped += 1          # shedding load on purpose, and counting it
```

That is a deliberate choice to trade data for latency, and the counter is what
keeps it honest. It is worth contrasting with the default: <code>await
q.put(...)</code> propagates the pressure back to the producer, while
<code>put_nowait</code> with a <code>QueueFull</code> handler absorbs it by
discarding. Both are legitimate and they are opposites, so the decision belongs
in the code with a comment rather than in whichever call you typed first.

## Where it goes wrong

**An unbounded queue with a fast producer.** It grows until memory runs out. Set
<code>maxsize</code> to whatever "too far ahead" means for your program.

**Forgetting the shutdown signal.** Consumers looping on <code>await q.get()</code>
wait forever once production stops, unless a sentinel or <code>join</code> tells
them to stop. A program that hangs at the end is usually this.

**Doing the slow work between get and task_done in a way that blocks the loop.**
The queue paces correctly, but a synchronous call in the consumer still freezes
everything &mdash; see [the blocking call](the_blocking_call_that_freezes_the_loop.html).

**Reading qsize and acting on it.** By the time you branch on
<code>q.qsize()</code>, another coroutine may have changed it. Let <code>put</code>
and <code>get</code> do the waiting; the count is for observing, not for control.

## Questions people ask

<strong>What should maxsize be?</strong> However far ahead of the consumer you are willing to let the producer run, expressed in items. It is a contract rather than a tuning number: a queue of 100 means "up to 100 items of work may be buffered", and the right value follows from how big an item is and how stale a buffered one may be.

<strong>Is an unbounded queue ever right?</strong> When the producer is naturally slower than the consumer, or the total volume is small and known. Otherwise it converts backpressure into memory growth, and the failure looks like a leak rather than a missing bound.

<strong>Sentinels or <code>join</code>?</strong> <code>join</code>, once there is more than one consumer &mdash; a sentinel needs one per worker and the bookkeeping gets error-prone. Sentinels stay useful when consumers must finish in a particular order, or when the producer cannot know the work is complete.

<strong>Why does my program hang at the end?</strong> Almost always a missing <code>task_done</code> on some path, so <code>join</code> is still waiting; or consumers blocked on <code>await q.get()</code> with nothing left to arrive and no cancellation. Both look like a deadlock and are really a missing shutdown signal.

<strong>Can I use a <code>queue.Queue</code> from the standard library?</strong> Not inside a coroutine. Its <code>get</code> blocks the thread rather than awaiting, which freezes the loop exactly as [any blocking call does](the_blocking_call_that_freezes_the_loop.html). <code>asyncio.Queue</code> is not thread-safe either &mdash; to bridge a thread and a loop, use <code>run_coroutine_threadsafe</code> or <code>janus</code>.

<strong>How many workers?</strong> Enough to saturate whatever they are waiting on, and no more than it tolerates &mdash; the same question a [semaphore](running_work_concurrently.html) answers for a fixed list of work. The queue makes it a single number you can change in one place, which is most of the appeal.

## Recap in one screen

- Producer, consumer and a queue between them is the shape most real async programs settle into, because the two sides run at different speeds.
- Both <code>put</code> and <code>get</code> are awaitable, so either side can wait for the other without blocking the loop.
- <code>maxsize</code> is the backpressure. A full queue suspends <code>put</code>, which paces the producer to the consumer's rate automatically.
- Unbounded means the producer never waits, and a fast producer then grows the queue until memory runs out.
- <code>task_done</code> in a <code>finally</code> plus <code>await q.join()</code> is the reliable "all drained" signal, and it replaces per-worker sentinels.
- Cancel the workers after <code>join</code> returns, and collect the cancellations with <code>gather(..., return_exceptions=True)</code>.
- <code>put_nowait</code> with a <code>QueueFull</code> handler is the opposite policy &mdash; shed load instead of applying backpressure &mdash; and should be a stated decision.
