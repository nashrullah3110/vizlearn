title: Running Work Concurrently: gather and TaskGroup
intro: Fan out many awaits at once, collect the results, and decide what should happen when one of them fails.

## The shape of the win

The reason to reach for async is almost always the same: you have many
independent waits &mdash; requests, queries, file reads &mdash; and doing them
one after another wastes the time each one spends idle. Running them together
collapses the total time from the sum of the waits to the longest single wait.

<code>asyncio.gather</code> is the direct tool. Hand it several coroutines and it
schedules them all as [tasks](coroutines_tasks_and_await.html), waits for every
one, and returns their results in the order you passed them &mdash; not the order
they finished.

These editors run inside a browser event loop that is already going, so the examples finish with <code>await main()</code>. In a standalone <code>.py</code> script &mdash; run with <code>python file.py</code> &mdash; you write <code>asyncio.run(main())</code> instead, which starts a loop, runs the coroutine, and closes it. The two are the same program with different entry points.

```python-run
import asyncio, time

async def fetch(name, seconds):
    await asyncio.sleep(seconds)
    return f"{name}:{seconds}"

async def main():
    t0 = time.time()
    results = await asyncio.gather(
        fetch("A", 0.3),
        fetch("B", 0.2),
        fetch("C", 0.1),
    )
    print("results:", results)
    print(f"elapsed {time.time()-t0:.2f}s")

await main()
```

```
results: ['A:0.3', 'B:0.2', 'C:0.1']
elapsed 0.30s
```

Three waits of 0.3, 0.2 and 0.1&nbsp;seconds finish in 0.30, not 0.60 &mdash; the
total is the longest one, because all three timers ran at once. And the results
came back in call order (A, B, C) even though C finished first: <code>gather</code>
lines the results up with the arguments, so you can index them without tracking
which finished when.

## What happens when one fails

By default, the first exception in any of the gathered coroutines stops the wait
and propagates out of <code>gather</code>. The other coroutines are not
cancelled, but their results are lost &mdash; you get the exception, not a
partial list.

```python-run
import asyncio

async def square(n):
    await asyncio.sleep(0.1); return n * n

async def boom():
    await asyncio.sleep(0.05); raise ValueError("failed")

async def main():
    try:
        await asyncio.gather(square(2), boom(), square(3))
    except ValueError as e:
        print("gather re-raised the first exception:", e)

    res = await asyncio.gather(square(2), boom(), square(3),
                               return_exceptions=True)
    print("return_exceptions=True:", res)

await main()
```

```
gather re-raised the first exception: failed
return_exceptions=True: [4, ValueError('failed'), 9]
```

The default hands you the first exception and hides the successful results.
Passing <code>return_exceptions=True</code> changes the contract: nothing is
raised, and the exception is placed in the results list where that coroutine's
value would have been. That is the right choice when you want every result you
can get and intend to inspect the failures yourself &mdash; and the wrong one if
a failure should abort the whole batch, because it quietly turns errors into data
you might forget to check.

## TaskGroup: the modern default

<code>gather</code> has an awkward gap: when one coroutine fails, the others keep
running unsupervised, and cleaning them up is your problem. Python 3.11 added
<code>asyncio.TaskGroup</code> to close it, and it is now the recommended way to
run concurrent work.

```python-run
import asyncio

async def work(n):
    await asyncio.sleep(0.05 * n)
    print(f"done {n}")
    return n

async def main():
    async with asyncio.TaskGroup() as tg:
        tasks = [tg.create_task(work(i)) for i in range(1, 4)]
    print("results:", [t.result() for t in tasks])

await main()
```

```
done 1
done 2
done 3
results: [1, 2, 3]
```

The <code>async with</code> block does not exit until every task created inside
it has finished, so the work is scoped: when control passes the closing line,
all of it is done. This is **structured concurrency** &mdash; tasks live and die
within a visible block rather than floating free &mdash; and it gives one
guarantee <code>gather</code> does not: if any task raises, the group
**cancels all the others** and then raises, so a failure never leaves siblings
running in the background.

## Failures come back as a group

Because several tasks can fail at once, a TaskGroup raises an
<code>ExceptionGroup</code>, unpacked with the <code>except*</code> syntax also
new in 3.11:

```python-run
import asyncio

async def ok():  await asyncio.sleep(0.1); print("ok ran")
async def bad(): await asyncio.sleep(0.02); raise ValueError("x")

async def main():
    try:
        async with asyncio.TaskGroup() as tg:
            tg.create_task(ok())
            tg.create_task(bad())
    except* ValueError as eg:
        print("TaskGroup raised ExceptionGroup:", [str(e) for e in eg.exceptions])

await main()
```

```
TaskGroup raised ExceptionGroup: ['x']
```

When <code>bad</code> raises, the group cancels <code>ok</code> before it can
finish &mdash; note that "ok ran" never prints &mdash; and surfaces the failure
inside an <code>ExceptionGroup</code>. The <code>except*</code> form is how you
handle it, and it is built for the real case the group creates: more than one
task failing together.

## Which to reach for

| Want | Use |
|---|---|
| Results in call order, siblings independent | <code>gather</code> |
| Every result including failures, as data | <code>gather(return_exceptions=True)</code> |
| A failure to cancel the rest, cleanly scoped | <code>TaskGroup</code> |
| Results as they finish, not in order | <code>as_completed</code> |

For new code on Python 3.11 or later, TaskGroup is the sensible default, and
<code>gather</code> is for the cases where you specifically want the siblings to
survive a failure.

## Results as they finish

<code>gather</code> lines results up with the arguments, which is convenient and
means you wait for the slowest one before you see anything. When you want to act
on each result the moment it arrives, <code>asyncio.as_completed</code> hands
them over in completion order instead.

```python-run
import asyncio

async def fetch(name, seconds):
    await asyncio.sleep(seconds)
    return f"{name} after {seconds}s"

async def main():
    jobs = [fetch("A", 0.3), fetch("B", 0.1), fetch("C", 0.2)]
    for finished in asyncio.as_completed(jobs):
        print(await finished)

await main()
```

```
B after 0.1s
C after 0.2s
A after 0.3s
```

The same three coroutines as the first example, in the same order in the list,
arriving back in the order they actually completed &mdash; B, C, A. The loop
yields an awaitable each time one finishes, so the first result is available
after 0.1&nbsp;s rather than after 0.3.

That matters whenever partial results are useful: streaming rows to a client as
each query returns, updating a progress bar, or stopping early once you have
enough. The cost is that you lose the correspondence with your input list, so if
you need to know *which* job a result came from, return it as part of the value
&mdash; as the <code>name</code> above does &mdash; rather than relying on
position.

## First answer wins, cancel the rest

<code>gather</code> waits for everything and <code>as_completed</code> hands you
everything in turn. <code>asyncio.wait</code> is the third shape: it returns as
soon as a condition is met and gives you two sets, <code>done</code> and
<code>pending</code>, leaving what to do with the stragglers up to you.

```python-run
import asyncio

async def replica(name, seconds):
    await asyncio.sleep(seconds)
    return name

async def main():
    tasks = [asyncio.create_task(replica("fast", 0.1)),
             asyncio.create_task(replica("slow", 0.4))]

    done, pending = await asyncio.wait(tasks, return_when=asyncio.FIRST_COMPLETED)
    print("first answer:", done.pop().result())

    for t in pending:
        t.cancel()
    await asyncio.gather(*pending, return_exceptions=True)
    print("cancelled the rest:", len(pending))

await main()
```

```
first answer: fast
cancelled the rest: 1
```

This is the **hedged request** pattern: ask two replicas the same question,
take whichever answers first, and cancel the other so it stops consuming a
connection. It cuts tail latency at the cost of extra load, and it is only
expressible with <code>wait</code>, because <code>gather</code> insists on
waiting for both and <code>as_completed</code> gives you no handle on the ones
still running.

Two things about the API catch people. It takes **tasks**, not coroutines
&mdash; passing coroutines was deprecated and is now an error, which is why the
<code>create_task</code> calls are explicit here. And it returns sets, so there
is no ordering to rely on; with more than one task in <code>done</code> you
inspect them rather than indexing. The other <code>return_when</code> values are
<code>FIRST_EXCEPTION</code> and the default <code>ALL_COMPLETED</code>, which
makes <code>wait</code> the general form the other two are conveniences over.

## Limiting how much runs at once

<code>gather</code> over ten coroutines is fine. <code>gather</code> over ten
thousand starts ten thousand at once, and whatever they talk to now has ten
thousand simultaneous callers &mdash; which is how an async rewrite
accidentally becomes a denial-of-service attack on your own database. Async
removed the thread-count ceiling that used to limit concurrency by accident, so
the limit now has to be deliberate.

An <code>asyncio.Semaphore</code> is the standard bound. It holds N permits;
<code>async with sem</code> takes one and waits if none are free.

```python-run
import asyncio, time

async def fetch(sem, live):
    async with sem:                       # only N get past this at a time
        live.append(1)
        peak = len(live)
        await asyncio.sleep(0.05)
        live.pop()
        return peak

async def main():
    sem = asyncio.Semaphore(3)
    live = []
    t0 = time.time()
    peaks = await asyncio.gather(*(fetch(sem, live) for _ in range(9)))
    print("most in flight at once:", max(peaks))
    print(f"elapsed {time.time()-t0:.2f}s for 9 waits of 0.05s, 3 at a time")

await main()
```

```
most in flight at once: 3
elapsed 0.17s for 9 waits of 0.05s, 3 at a time
```

Nine coroutines were scheduled at once and never more than three ran at a time
&mdash; the <code>live</code> list is the evidence, and its peak is exactly the
semaphore's count. The elapsed time follows: three rounds of 0.05&nbsp;s, plus
scheduling overhead, rather than the 0.05&nbsp;s an unbounded gather would have
taken or the 0.45&nbsp;s a sequential loop would.

The pattern to remember is that the semaphore goes *inside* the coroutine,
around the part being limited, not around the <code>gather</code>. All nine
tasks still exist and all nine are still scheduled; the bound is on how many are
past the <code>async with</code> at once. If the work arrives as an open-ended
stream rather than a known list, a bounded
[queue with a fixed number of workers](queues_and_backpressure.html) is the
better shape &mdash; same idea, different plumbing.

## Where it goes wrong

**Gathering a huge list at once.** <code>gather</code> over ten thousand
coroutines starts ten thousand at once and can exhaust connections or memory. Cap
the concurrency with a semaphore, or batch.

**Ignoring return_exceptions results.** With it on, a failure is a value in the
list. Code that does not check for exceptions there treats an error as a success.

**Expecting gather to cancel on failure.** It does not; the other coroutines run
on. TaskGroup is what cancels siblings.

**Passing plain values to gather.** Everything you gather must be awaitable. A
non-coroutine in the list is an error, not a constant that passes through.

## Questions people ask

<strong>gather or TaskGroup?</strong> TaskGroup for new code on 3.11 or later: it cancels the siblings when one task fails, so a failure never leaves work running unsupervised. Reach for <code>gather</code> when you specifically want the siblings to survive a failure, or when you need the results lined up with the arguments.

<strong>Does <code>gather</code> cancel the others when one raises?</strong> No, and this is the single most common wrong assumption about it. The first exception propagates and the other coroutines carry on running with nobody watching them. That gap is exactly what TaskGroup was added to close.

<strong>When is <code>return_exceptions=True</code> right?</strong> When a failure is data you intend to inspect &mdash; nine of ten shards answered, report the tenth. It is wrong when a failure should abort the batch, because it converts errors into list entries that code can silently treat as results.

<strong>How many is too many to gather?</strong> Whatever the other end can take, which is a property of the remote service and not of asyncio. Once the list is long enough that you are asking the question, bound it with a semaphore rather than guessing.

<strong>Can I mix <code>await</code> and tasks in one function?</strong> Yes, and it is normal: start the slow independent work as tasks, do other things, then await the handles when you finally need the results. What you cannot do is expect a row of plain awaits to overlap.

<strong>What is <code>except*</code> for?</strong> Unpacking an <code>ExceptionGroup</code>, which is what a TaskGroup raises because several tasks can fail at once. It selects the matching exceptions from the group and leaves the rest to propagate &mdash; a plain <code>except ValueError</code> will not match a group that contains one.

## Recap in one screen

- The win is collapsing many independent waits from their sum to their maximum: 0.3, 0.2 and 0.1&nbsp;s together take 0.30, not 0.60.
- <code>gather</code> returns results in **call** order however they finished, and by default raises the first exception while leaving the siblings running.
- <code>TaskGroup</code> scopes the work to an <code>async with</code> block and cancels every sibling if one fails &mdash; structured concurrency, and the sensible default on 3.11+.
- Several tasks can fail at once, so a TaskGroup raises an <code>ExceptionGroup</code>, which <code>except*</code> exists to unpack.
- <code>as_completed</code> trades the input ordering for the first result arriving as soon as it is ready.
- Async removed the accidental concurrency ceiling threads used to impose, so bound it on purpose &mdash; a <code>Semaphore</code> inside the coroutine, around the part being limited.
