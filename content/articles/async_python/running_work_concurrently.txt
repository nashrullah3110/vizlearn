title: Running Work Concurrently: gather and TaskGroup
intro: Fan out many awaits at once, collect the results, and decide what should happen when one of them fails.

## The core idea

Reach for async when you have many independent waits, such as requests, queries,
or file reads. Running them one after another wastes the time each spends idle.

## The shape of the win

<code>asyncio.gather</code> is the direct tool. Hand it several coroutines and it
schedules them all as [tasks](coroutines_tasks_and_await.html), waits for every
one, and returns their results in the order you passed them. That can differ
from the order in which they finished.

These editors run inside a browser event loop that is already going. So the examples finish with <code>await main()</code>. In a standalone <code>.py</code> script &mdash; run with <code>python file.py</code> &mdash; you write <code>asyncio.run(main())</code> instead. This starts a loop, runs the coroutine, and closes it. The two are the same program with different entry points.

```python-run
import asyncio, time

async def fetch(name, seconds):
    await asyncio.sleep(seconds)
    return f"{name}:{seconds}"

async def main():
    t0 = time.time()
    results = await asyncio.gather(
        fetch("A", 0.3),
        fetch("B", 0.2),
        fetch("C", 0.1),
    )
    print("results:", results)
    print(f"elapsed {time.time()-t0:.2f}s")

await main()
```

```
results: ['A:0.3', 'B:0.2', 'C:0.1']
elapsed 0.30s
```

Three waits of 0.3, 0.2 and 0.1&nbsp;seconds finish in 0.30, not 0.60. The
total is the longest wait because all three timers ran at once. The results came
back in call order (A, B, C), even though C finished first. <code>gather</code>
lines each result up with its argument, so you can index them without tracking
which one finished when.

## What happens when one fails

By default, the first exception in any of the gathered coroutines stops the wait
and propagates out of <code>gather</code>. The other coroutines are not
cancelled, but their results are lost &mdash; you get the exception, not a
partial list.

```python-run
import asyncio

async def square(n):
    await asyncio.sleep(0.1); return n * n

async def boom():
    await asyncio.sleep(0.05); raise ValueError("failed")

async def main():
    try:
        await asyncio.gather(square(2), boom(), square(3))
    except ValueError as e:
        print("gather re-raised the first exception:", e)

    res = await asyncio.gather(square(2), boom(), square(3),
                               return_exceptions=True)
    print("return_exceptions=True:", res)

await main()
```

```
gather re-raised the first exception: failed
return_exceptions=True: [4, ValueError('failed'), 9]
```

The default gives you the first exception and hides successful results.
Passing <code>return_exceptions=True</code> changes the contract. Nothing is
raised; each exception appears in the results list where that coroutine's value
would go. Use this when you want all available results and will inspect failures.
Avoid it when one failure should stop the batch. It turns errors into data that
you might forget to check.

## TaskGroup: the modern default

<code>gather</code> has an awkward gap: when one coroutine fails, the others keep
running unsupervised, and cleaning them up is your problem. Python 3.11 added
<code>asyncio.TaskGroup</code> to close it, and it is now the recommended way to
run concurrent work.

```python-run
import asyncio

async def work(n):
    await asyncio.sleep(0.05 * n)
    print(f"done {n}")
    return n

async def main():
    async with asyncio.TaskGroup() as tg:
        tasks = [tg.create_task(work(i)) for i in range(1, 4)]
    print("results:", [t.result() for t in tasks])

await main()
```

```
done 1
done 2
done 3
results: [1, 2, 3]
```

The <code>async with</code> block waits for every task created inside it. When
control passes the closing line, all the work is done. This is **structured
concurrency**: tasks live and end inside a visible block instead of floating
free. It also gives a guarantee <code>gather</code> does not. If any task raises,
the group **cancels all the others** and then raises. A failure cannot leave
sibling tasks running in the background.

## Failures come back as a group

Because several tasks can fail at once, a TaskGroup raises an
<code>ExceptionGroup</code>, unpacked with the <code>except*</code> syntax also
new in 3.11:

```python-run
import asyncio

async def ok():  await asyncio.sleep(0.1); print("ok ran")
async def bad(): await asyncio.sleep(0.02); raise ValueError("x")

async def main():
    try:
        async with asyncio.TaskGroup() as tg:
            tg.create_task(ok())
            tg.create_task(bad())
    except* ValueError as eg:
        print("TaskGroup raised ExceptionGroup:", [str(e) for e in eg.exceptions])

await main()
```

```
TaskGroup raised ExceptionGroup: ['x']
```

When <code>bad</code> raises, the group cancels <code>ok</code> before it can
finish. Notice that "ok ran" never prints. The group puts the failure inside an
<code>ExceptionGroup</code>. Use <code>except*</code> to handle it. This form
also covers the case where several tasks fail together.

## Which to reach for

| Want | Use |
|---|---|
| Results in call order, siblings independent | <code>gather</code> |
| Every result including failures, as data | <code>gather(return_exceptions=True)</code> |
| A failure to cancel the rest, cleanly scoped | <code>TaskGroup</code> |
| Results as they finish, not in order | <code>as_completed</code> |

For new code on Python 3.11 or later, <code>TaskGroup</code> is a sensible
default. Use <code>gather</code> when sibling tasks should survive a failure.

## Results as they finish

<code>gather</code> lines results up with the arguments, which is convenient and
means you wait for the slowest one before you see anything. When you want to act
on each result the moment it arrives, <code>asyncio.as_completed</code> hands
them over in completion order instead.

```python-run
import asyncio

async def fetch(name, seconds):
    await asyncio.sleep(seconds)
    return f"{name} after {seconds}s"

async def main():
    jobs = [fetch("A", 0.3), fetch("B", 0.1), fetch("C", 0.2)]
    for finished in asyncio.as_completed(jobs):
        print(await finished)

await main()
```

```
B after 0.1s
C after 0.2s
A after 0.3s
```

The same three coroutines as the first example, in the same order in the list,
arriving back in the order they actually completed &mdash; B, C, A. The loop
yields an awaitable each time one finishes, so the first result is available
after 0.1&nbsp;s rather than after 0.3.

That matters when partial results are useful. You might stream rows to a client
as each query returns, update a progress bar, or stop once you have enough. But
you lose the link to the input list. If you need to know *which* job produced a
result, return its name as part of the value instead of relying on position.

## First answer wins, cancel the rest

<code>gather</code> waits for everything and <code>as_completed</code> hands you
everything in turn. <code>asyncio.wait</code> is the third shape. It returns
when a condition is met and gives you two sets: <code>done</code> and
<code>pending</code>. You decide what to do with the tasks still running.

```python-run
import asyncio

async def replica(name, seconds):
    await asyncio.sleep(seconds)
    return name

async def main():
    tasks = [asyncio.create_task(replica("fast", 0.1)),
             asyncio.create_task(replica("slow", 0.4))]

    done, pending = await asyncio.wait(tasks, return_when=asyncio.FIRST_COMPLETED)
    print("first answer:", done.pop().result())

    for t in pending:
        t.cancel()
    await asyncio.gather(*pending, return_exceptions=True)
    print("cancelled the rest:", len(pending))

await main()
```

```
first answer: fast
cancelled the rest: 1
```

This is the **hedged request** pattern: ask two replicas the same question,
take whichever answers first, and cancel the other so it stops consuming a
connection. It cuts tail latency at the cost of extra load. And it is only
expressible with <code>wait</code>, because <code>gather</code> insists on
waiting for both and <code>as_completed</code> gives you no handle on the ones
still running.

Two things about the API catch people. It takes **tasks**, not coroutines
&mdash; passing coroutines was deprecated and is now an error, which is why the
<code>create_task</code> calls are explicit here. And it returns sets, so there
is no ordering to rely on; with more than one task in <code>done</code> you
inspect them rather than indexing. The other <code>return_when</code> values are
<code>FIRST_EXCEPTION</code> and the default <code>ALL_COMPLETED</code>, which
makes <code>wait</code> the general form the other two are conveniences over.

## Limiting how much runs at once

<code>gather</code> over ten coroutines is fine. <code>gather</code> over ten
thousand starts ten thousand at once, and whatever they talk to now has ten
thousand simultaneous callers &mdash; which is how an async rewrite
accidentally becomes a denial-of-service attack on your own database. Async
removed the thread-count ceiling that used to limit concurrency by accident, so
the limit now has to be deliberate.

An <code>asyncio.Semaphore</code> is the standard bound. It holds N permits;
<code>async with sem</code> takes one and waits if none are free.

```python-run
import asyncio, time

async def fetch(sem, live):
    async with sem:                       # only N get past this at a time
        live.append(1)
        peak = len(live)
        await asyncio.sleep(0.05)
        live.pop()
        return peak

async def main():
    sem = asyncio.Semaphore(3)
    live = []
    t0 = time.time()
    peaks = await asyncio.gather(*(fetch(sem, live) for _ in range(9)))
    print("most in flight at once:", max(peaks))
    print(f"elapsed {time.time()-t0:.2f}s for 9 waits of 0.05s, 3 at a time")

await main()
```

```
most in flight at once: 3
elapsed 0.17s for 9 waits of 0.05s, 3 at a time
```

Nine coroutines were scheduled at once, but no more than three ran at a time.
The <code>live</code> list shows this; its peak matches the semaphore's count.
The elapsed time also fits: three rounds of 0.05&nbsp;s plus scheduling
overhead. An unbounded gather would take about 0.05&nbsp;s, while a sequential
loop would take about 0.45&nbsp;s.

The pattern to remember is that the semaphore goes *inside* the coroutine,
around the part being limited, not around the <code>gather</code>. All nine
tasks still exist and all nine are still scheduled; the bound is on how many are
past the <code>async with</code> at once. If the work arrives as an open-ended
stream rather than a known list, a bounded
[queue with a fixed number of workers](queues_and_backpressure.html) is better.
It uses the same idea with different plumbing.

## Where it goes wrong

**Gathering a huge list at once.** <code>gather</code> over ten thousand
coroutines starts ten thousand at once and can exhaust connections or memory. Cap
the concurrency with a semaphore, or batch.

**Ignoring return_exceptions results.** With it on, a failure is a value in the
list. Code that does not check for exceptions there treats an error as a success.

**Expecting gather to cancel on failure.** It does not; the other coroutines run
on. TaskGroup is what cancels siblings.

**Passing plain values to gather.** Everything you gather must be awaitable. A
non-coroutine in the list is an error, not a constant that passes through.
