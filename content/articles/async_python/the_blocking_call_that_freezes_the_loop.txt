title: The Blocking Call That Freezes the Loop
intro: One synchronous call in a coroutine stops every other coroutine dead. It is the most common async bug, and the way it hides is worse than the way it looks.

## The core idea

Async Python runs on cooperative multitasking. The event loop runs on a single thread and can only switch coroutines when the running one hits an await .

## One thread means one blocker stops everything

Nothing enforces cooperation. The loop cannot preempt a coroutine mid-call, so a blocking line does not slow the loop down, it *pauses it entirely* until the line returns.

The danger is that nothing warns you. A call like
<code>requests.get(url)</code> inside a coroutine compiles and runs on its own.
The problem appears when other [coroutines and tasks](coroutines_tasks_and_await.html)
need to run at the same time. By then, the bug may be in production and show up
as mysterious latency spikes instead of a clear error.

This page shows how a blocking call freezes the loop and how to spot it. It
also shows how to move the work to a thread with
<code>run_in_executor</code>.

## Watch a heartbeat stall

Here a heartbeat prints a tick every 0.1&nbsp;seconds &mdash; the kind of steady
progress a healthy loop makes &mdash; while a second coroutine does a blocking
<code>time.sleep(0.3)</code> instead of an async one.

These editors run inside a browser event loop that is already going, so the examples finish with <code>await main()</code>. In a standalone <code>.py</code> script &mdash; run with <code>python file.py</code> &mdash; you write <code>asyncio.run(main())</code> instead, which starts a loop, runs the coroutine, and closes it. The two are the same program with different entry points.

```python-run
import asyncio, time

async def heartbeat():
    for _ in range(5):
        print("tick"); await asyncio.sleep(0.1)

async def blocker():
    time.sleep(0.3)                     # blocks the ONE thread the loop runs on
    print("blocker done")

async def main():
    await asyncio.gather(heartbeat(), blocker())

await main()
```

```
tick
blocker done
tick
tick
tick
tick
```

The first tick prints. The heartbeat hits its <code>await</code> and steps
aside. Then <code>blocker</code> runs <code>time.sleep(0.3)</code>. For those
0.3&nbsp;seconds, the thread is busy. The heartbeat's timer expires, but the
loop cannot act on it, so no tick appears. The loop catches up only after
<code>time.sleep</code> returns. It fires the four backed-up ticks in a burst.
That gap after the first tick is the loop frozen solid.

<code>time.sleep</code> stands in for any synchronous call that takes time. That
could be <code>requests.get</code>, a blocking database driver, or a large file
read. It could also be <code>json.loads</code> on a huge string or a tight
numeric loop. Each looks like ordinary code. Each freezes the loop for its full
duration.

## The fix: stop blocking the thread

The blocking call has to stop holding the thread. The direct fix &mdash; and the
one this editor can show &mdash; is to use the <em>async-native</em> version of
whatever you were doing. Here that means <code>await asyncio.sleep</code> in place
of <code>time.sleep</code>; in real code it means an async HTTP client
(<code>httpx</code>, <code>aiohttp</code>) instead of <code>requests</code>, or an
async database driver instead of a blocking one.

```python-run
import asyncio

async def heartbeat():
    for _ in range(5):
        print("tick"); await asyncio.sleep(0.1)

async def blocker():
    await asyncio.sleep(0.3)             # async-native: suspends, frees the loop
    print("blocker done")

async def main():
    await asyncio.gather(heartbeat(), blocker())

await main()
```

```
tick
tick
tick
blocker done
tick
tick
```

Now the ticks keep coming. <code>await asyncio.sleep</code> suspends only
<code>blocker</code> and gives the thread back to the loop. The heartbeat runs on
schedule, and <code>blocker done</code> appears between ticks rather than after a
gap. The wait still took 0.3&nbsp;seconds, but it no longer stopped the whole
program. Every async-native library does the same thing: its <code>await</code>
lets the loop run something else.

## When you cannot swap in an async version

Sometimes a blocking call has no async form. It may come from a legacy library
with only a synchronous API, or it may be pure computation. Then move it off the
loop to a worker thread and await it:

```python
async def blocker():
    await asyncio.to_thread(time.sleep, 0.3)   # run the blocking call on a thread
    print("blocker done")
```

<code>asyncio.to_thread</code> is the escape hatch for a blocking function you
cannot rewrite, and <code>loop.run_in_executor</code> is its older sibling. Two
caveats. It needs real threads, so it does nothing in a sandbox that has none
&mdash; the browser interpreter running these editors is one such sandbox, which
is why this snippet is shown rather than run. And for CPU-bound work a thread
does not help even where threads exist, because the work still contends for the
one interpreter; that belongs in a separate process.

## Why it hides so well

This bug can hide in development and show up under load. With one user, one
blocking call makes that request a little slow. It may look like a network
problem. With a hundred users, one blocking call in the request path freezes
*all* of them. They share the same thread. The symptom is not "one slow
endpoint" but "the whole service periodically stops responding", which is hard
to trace.

It is also invisible to a glance at the code. A blocking call has the same shape
as an async one; only knowing the library tells you which it is.
<code>requests.get(url)</code> and <code>await client.get(url)</code> look almost
identical and behave completely differently inside a loop.

## How to find them

The loop can tell you. Running with debug mode on makes asyncio warn about any
callback that holds the thread too long:

```python
import asyncio

async def main():
    ...

asyncio.run(main(), debug=True)     # warns: "Executing ... took N seconds"
```

With debug on, a blocking call produces a "slow callback" warning naming the
place it happened, which turns an invisible freeze into a log line. The habits
that prevent it in the first place: use async-native libraries in coroutines
(<code>httpx</code> or <code>aiohttp</code> over <code>requests</code>, an async
database driver over a blocking one), and wrap anything unavoidably synchronous
in <code>to_thread</code>.

## Measuring the freeze

"The loop froze" is a claim you can put a number on, and doing so is how this
bug gets found in a system too large to eyeball. The measurement is called
**loop lag**: ask the loop to wake you in 50&nbsp;ms, see how long it actually
took, and the difference is how long something else held the thread.

```python-run
import asyncio, time

async def monitor(samples, n):
    for _ in range(n):
        t0 = time.perf_counter()
        await asyncio.sleep(0.05)             # ask the loop for 50 ms
        samples.append(time.perf_counter() - t0)

async def hog():
    await asyncio.sleep(0.12)
    time.sleep(0.25)                          # a blocking call, mid-run

async def main():
    samples = []
    await asyncio.gather(monitor(samples, 6), hog())
    worst = max(samples)
    print(f"asked for 0.050s; worst actual was {worst:.3f}s")
    print(f"peak loop lag: {(worst - 0.05) * 1000:.0f} ms")

await main()
```

```
asked for 0.050s; worst actual was 0.270s
peak loop lag: 220 ms
```

A 50&nbsp;ms sleep took 270. The extra 220&nbsp;ms is the blocking call: the
monitor's timer came due on schedule and the loop could not act on it, because
<code>time.sleep</code> was holding the only thread. Nothing here inspects the
blocking code &mdash; the freeze is measured entirely from the outside, by a
coroutine that only knows how long it waited.

That is what makes the technique useful in production. A coroutine like
<code>monitor</code>, sampling continuously and reporting its worst lag, needs no
knowledge of what the rest of the program does and will catch any blocking call
anywhere in it. Healthy loops sit at a lag of a millisecond or two; sustained
tens of milliseconds means something is holding the thread, and the shape of the
spikes usually identifies which request path it is on.

The built-in version of the same idea is debug mode, which is cheaper to switch
on and coarser:

```python
import asyncio

async def main():
    ...

asyncio.run(main(), debug=True)     # warns: "Executing ... took N seconds"
```

With debug on, asyncio logs a warning naming any callback that ran longer than
<code>loop.slow_callback_duration</code> (0.1&nbsp;s by default, and adjustable).
That turns an invisible freeze into a log line with a source location in it,
which is usually enough to find the call. Debug mode also warns about coroutines
that were never awaited and tasks that were destroyed while pending, so it is
worth switching on in development regardless of this bug.

## An inventory of what actually blocks

The awkward part of this bug is that blocking calls do not look distinctive. Here
is the list that accounts for almost every real case, with what to do about each:

| Blocking call | Fix |
|---|---|
| <code>requests.get</code>, <code>urllib</code> | <code>httpx</code> or <code>aiohttp</code> |
| <code>time.sleep</code> | <code>await asyncio.sleep</code> |
| <code>psycopg2</code>, <code>sqlite3</code>, most DB drivers | an async driver: <code>asyncpg</code>, <code>aiosqlite</code> |
| <code>open().read()</code> on a large file | <code>aiofiles</code>, or <code>to_thread</code> |
| <code>json.loads</code> on a huge payload | <code>to_thread</code>, or parse less |
| A regex over a very long string | <code>to_thread</code> |
| <code>subprocess.run</code> | <code>asyncio.create_subprocess_exec</code> |
| A tight numeric loop, model inference | a **process** pool, not a thread |

There are three fixes, and each fits a different case. Use an async-native
library when one exists. It makes the wait a real await. Use
<code>to_thread</code> for an I/O call with no async version. The blocking call
can release the interpreter lock while it waits. Neither option helps with
CPU-bound work. That work needs the interpreter the whole time, so a thread
still contends for the same lock. A separate process moves the work off the loop.

The rule that follows is worth keeping as a habit rather than a debugging step.
Inside a coroutine, every call either awaits or returns fast. Anything that does
neither needs one of the three fixes above before it goes in.

## Where it goes wrong

**A synchronous HTTP or database call in a coroutine.** The classic. It freezes
the loop for the full round trip. Use the async client; or, if there is none,
<code>to_thread</code> where real threads exist.

**time.sleep instead of asyncio.sleep.** The single most common beginner version,
and the one to recognise on sight.

**CPU-bound work.** <code>to_thread</code> does not help, because a thread still
contends for the interpreter. Heavy computation belongs in a process pool.

**Trusting that it is fine because it works in testing.** One user hides the bug;
concurrency exposes it. Test the loop under load, or run with
<code>debug=True</code> and watch for slow-callback warnings.
