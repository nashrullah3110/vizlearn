title: Coroutines, Tasks and await
intro: Why calling an async function runs nothing, why a bare await is still sequential, and the one word that turns waiting into overlap.

## The core idea

Define a function with async def and calling it does not run it. It hands you back a coroutine object — a description of work that has not started.

## A coroutine is a plan, not an action

These editors run inside a browser event loop that is already going. So the examples finish with <code>await main()</code>. In a standalone <code>.py</code> script &mdash; run with <code>python file.py</code> &mdash; you write <code>asyncio.run(main())</code> instead. This starts a loop, runs the coroutine, and closes it. The two are the same program with different entry points.

```python-run
import asyncio

async def greet():
    return "hi"

c = greet()
print("type:", type(c).__name__)
print("is coroutine:", asyncio.iscoroutine(c))
print("running it needs the loop, not a call")
c.close()
```

```
type: coroutine
is coroutine: True
running it needs the loop, not a call
```

Calling <code>greet()</code> returned an object, not <code>"hi"</code>. This
trips people up at first. An <code>async def</code> looks like a function, but
it creates a coroutine object. That object does nothing until something drives
it. The thing that drives it is the
[event loop](event_loop_stepped_through.html), reached with
<code>asyncio.run</code> at the top of a program, or with <code>await</code> from
inside another coroutine.

The <code>c.close()</code> call prevents a "coroutine was never awaited" warning.
Creating a coroutine and then abandoning it is a bug; the final section covers
that case.

## await runs it, and waits for it

<code>await</code> does two things at once. It starts the coroutine, and it
suspends the current one until that coroutine finishes, handing control back to
the loop in the meantime. The value of the expression is whatever the coroutine
returned.

The catch is the "waits for it" half. Awaiting one coroutine, then awaiting
another, is strictly sequential &mdash; the second cannot start until the first
has returned, because <code>await</code> blocked on it. Overlap does not come
from <code>await</code> alone.

## Tasks are what run concurrently

To make two coroutines progress at the same time, wrap each in a
**task**. <code>asyncio.create_task</code> schedules the coroutine on the loop
and returns a handle. The task starts at the next await, even if you have not
awaited its handle yet.

```python-run
import asyncio, time

async def fetch(seconds):
    await asyncio.sleep(seconds)
    return seconds

async def main():
    t0 = time.time()
    await fetch(0.2); await fetch(0.2)                 # one then the other
    print(f"sequential: {time.time()-t0:.2f}s")

    t0 = time.time()
    a = asyncio.create_task(fetch(0.2))
    b = asyncio.create_task(fetch(0.2))
    await a; await b                                   # both already running
    print(f"concurrent: {time.time()-t0:.2f}s")

await main()
```

```
sequential: 0.40s
concurrent: 0.20s
```

Two the same waits of 0.2&nbsp;seconds. Awaited one after the other they take
0.40; wrapped in tasks they take 0.20, because both timers were counting down at
once. Nothing was faster &mdash; the waiting overlapped. That is the entire value
proposition of async, and it is visible in this one four-hundredth-versus-two-
hundredth difference.

The reason is scheduling order. <code>await fetch(...)</code> creates the
coroutine and waits for it. The second call does not happen until the first
returns. <code>create_task</code> puts both on the loop *before* either one is
awaited. By the time you <code>await a</code>, task <code>b</code> is already
running and its timer is ticking.

## The rule that follows

Use <code>await</code> when you need a result before continuing. Wrap work in a
task when you want it to run while you do something else. Two awaits in a row
run in sequence. Two tasks can overlap. A loop of <code>await do_one(x)</code>
over a list is correct, but it is no faster than a plain synchronous loop.
Each call finishes before the next one begins.

Managing tasks by hand is easy to get wrong. You might forget to await a task
and drop it before it finishes. An exception in a task you never await can also
go unnoticed. These risks are why
[running work concurrently](running_work_concurrently.html) reaches for
<code>gather</code> and <code>TaskGroup</code> instead of loose
<code>create_task</code> calls.

## await needs something awaitable

You can only <code>await</code> an **awaitable**: a coroutine, a task, or a
future. Awaiting a plain value is a <code>TypeError</code>, and &mdash; more
commonly &mdash; forgetting to await something that *is* awaitable is a silent
bug. <code>result = fetch(2)</code> without an await binds the coroutine object,
not its result. Arithmetic on that object fails a few lines later, far from the
missing <code>await</code> that caused the problem.

## Driving a coroutine by hand

"A coroutine is a plan, not an action" is literally true. And you can prove it
without a loop at all. A coroutine object is a *resumable* object: it supports
<code>send</code>, and driving it is exactly what the event loop does.

```python-run
async def greet():
    return "hi"

c = greet()
print("type:", type(c).__name__)
try:
    c.send(None)                  # the loop advances a coroutine exactly like this
except StopIteration as stop:
    print("returned:", stop.value)
```

```
type: coroutine
returned: hi
```

<code>send(None)</code> starts the coroutine and runs it until it suspends or
finishes. This one never awaits, so it finishes at once. A finished coroutine
signals its result by raising <code>StopIteration</code> with the return value
attached. Generators use the same protocol; coroutines were built on that model.

Now the whole mechanism is visible. The loop holds a coroutine and calls
<code>send</code>. If the coroutine suspends at an await, control returns to the
loop. The loop does other work, then calls <code>send</code> again when the
awaited value is ready. When <code>StopIteration</code> arrives, the loop takes
<code>.value</code> as the result and gives it to the code that was waiting.
"The loop drives it" means this small pattern repeated for each task.

You do not write this in normal code; <code>await</code> is the readable form.
Seeing it once makes the rest of asyncio less mysterious. A task owns a
coroutine and knows when to call <code>send</code> on it again.

## Cancelling a task

Creating tasks is half of managing them; stopping them is the other half, and
the half that is usually missing. A task can be cancelled, and cancellation
works by raising <code>CancelledError</code> *inside* the coroutine at whatever
await it is suspended on.

```python-run
import asyncio

async def slow():
    try:
        await asyncio.sleep(10)
        return "finished"
    except asyncio.CancelledError:
        print("slow: saw CancelledError")
        raise                       # re-raise: swallowing it breaks cancellation

async def main():
    t = asyncio.create_task(slow())
    await asyncio.sleep(0.05)
    t.cancel()
    try:
        await t
    except asyncio.CancelledError:
        print("main: task.cancelled() is", t.cancelled())

    try:
        await asyncio.wait_for(asyncio.sleep(10), timeout=0.1)
    except asyncio.TimeoutError:
        print("wait_for gave up and raised TimeoutError")

await main()
```

```
slow: saw CancelledError
main: task.cancelled() is True
wait_for gave up and raised TimeoutError
```

Three details in that output matter. <code>t.cancel()</code> does not stop the
task at once. It *requests* cancellation, and the loop delivers the error when
it next runs that task. Awaiting the cancelled task raises
<code>CancelledError</code> in the caller. That is why the <code>try</code>
around <code>await t</code> is needed. <code>asyncio.wait_for</code> adds a
deadline to the same cancellation process. On timeout, it cancels the inner
coroutine and raises <code>TimeoutError</code>. Python 3.11 and later also offer
<code>asyncio.timeout()</code>, a context manager that reads well around several
statements.

The <code>raise</code> in the <code>except</code> block is the part to copy.
Catching <code>CancelledError</code> to run cleanup is normal. But re-raise it
after cleanup. If you swallow it, the loop sees the task as still running. A
TaskGroup, <code>wait_for</code>, or shutdown handler that requested cancellation
can then wait forever.

## Where it goes wrong

**Calling instead of awaiting.** <code>fetch(2)</code> builds a coroutine and
runs nothing; you meant <code>await fetch(2)</code>. Python warns "coroutine was
never awaited" &mdash; a warning worth treating as an error.

**A loop of awaits, expecting overlap.** Sequential every time. Use tasks or
<code>gather</code>.

**Awaiting create_task too early.** <code>await asyncio.create_task(f())</code>
on one line is just a slower <code>await f()</code> &mdash; you scheduled it and
at once blocked on it, gaining nothing.

**An orphaned task.** A task nobody holds a reference to can be garbage-collected
mid-flight, and an unhandled exception inside it may never surface. Keep the
handle, and await it.
