title: Batch Processing in Networks: A Practical Guide
intro: Networks process many samples at once, not one at a time. Batching is what makes GPUs worth using - and the batch size quietly changes both how fast you train and how well the result generalises.

## A batch is a matrix, not a loop

Feeding one sample through a layer is a vector-matrix product. Feeding 32 samples is a <em>matrix</em>-matrix product &mdash; stack the 32 input vectors into a 32&times;n<sub>in</sub> matrix and multiply once by the same n<sub>in</sub>&times;n<sub>out</sub> weights.

Crucially the weights are unchanged. Batching does not alter the net. It changes how many samples pass through it per step. Since the hardware executes one large matrix multiply far more well than 32 small ones, a batch of 32 costs nothing like 32 times a single sample. The gradient computed on a batch is the average of the per-sample gradients. So more batches give a more exact estimate of the true gradient but update the weights fewer times per epoch. Small batches (8-64) add noise that acts as implicit [regularisation](regularization_in_neural_networks.html), often improving generalisation. Large batches (256-4096) are more stable but can converge to sharper minima that generalise worse. The batch size also finds GPU memory usage: each sample in the batch needs its own activations stored for [backpropagation](backpropagation.html). So doubling the batch size roughly doubles the memory. Gradient accumulation simulates a large batch by summing gradients across a few small forward passes before updating &mdash; same effective batch size, less memory. The relationship between batch size and learning rate matters: when you scale the batch size up by k, scaling the learning rate up by k (linear scaling rule) keeps training dynamics close, up to a point. This page runs the same net with other batch sizes, shows the loss curve and gradient variance for each. And covers the memory-accuracy tradeoff.

## Epoch, batch, iteration

These three get muddled constantly:

- <strong>Batch size</strong> &mdash; samples handled before one weight update.
- <strong>Iteration (step)</strong> &mdash; one forward pass, one backward pass, one update.
- <strong>Epoch</strong> &mdash; one complete pass over the training set.

With 10,000 samples and a batch size of 100, one epoch is 100 iterations. So 10 epochs means 1,000 weight updates. Halving the batch size to 50 doubles the updates per epoch to 200 &mdash; which is why batch size and learning rate cannot be tuned independently.

## Why cases are handled in groups

Training could update the weights after each single case. Or after seeing the whole dataset. Both are worse than the middle option, and for other reasons.

<strong>One case at a time</strong> gives an very noisy gradient estimate and, more importantly, wastes the hardware. A GPU has thousands of cores designed to do the same step on many vals at once. Feeding it one 784-item vector uses a fraction of a percent of that capacity.

<strong>The whole dataset</strong> gives an exact gradient at enormous cost per update. On a million rows, a single step needs a million forward and backward passes. And the net gets one weight update for all that work.

<strong>A mini-batch of 32 to 256</strong> is what everyone uses. The gradient is a reasonable estimate, the matrix multiplications are large enough to saturate the hardware. And the left noise is useful &mdash; it helps the optimiser escape saddle points.

The arithmetic is a matrix multiply either way: a batch of 64 cases with 784 features is a 64&times;784 matrix multiplied by the layer's weights. It is one step rather than 64.

## Epochs, steps and the counts that confuse people

|Term|Meaning|
|---|---|
|Batch size|Examples per update|
|Step / iteration|One forward pass, one backward pass, one update|
|Epoch|One full pass through the training data|
|Steps per epoch|dataset size / batch size|

With 50,000 training cases and a batch size of 64, one epoch is 782 steps &mdash; 782 weight updates, not one. Ten epochs is 7,820 updates.

That relationship has a consequence people trip over: <strong>doubling the batch size halves the count of updates per epoch</strong>. So a run with batch size 256 and the same count of epochs does a quarter of the updates of one with batch size 64. And will often be behind unless the learning rate is scaled up to compensate.

## Batch size, learning rate and generalisation

More batches give less noisy gradients, so more steps are safe. The standard rule is to <strong>scale the learning rate linearly with batch size</strong> &mdash; double the batch, double the rate &mdash; with a warm-up period, since the first few large steps are the risky ones.

That rule holds well up to a point. Beyond a few thousand cases per batch, the gradient noise turns so small that the implicit regularisation it provided disappears. And very large-batch training tends to generalise slightly worse. Techniques such as LARS and LAMB exist namely to push that ceiling more.

|Batch size|Character|
|---|---|
|1&ndash;8|Very noisy; slow on GPUs; sometimes necessary for huge inputs|
|32&ndash;256|The normal range; good hardware use, useful noise|
|512&ndash;2048|Faster wall-clock; needs a scaled learning rate and warm-up|
|8192+|Requires specialised optimisers; used in large-scale pretraining|

Note that batch normalisation adds a constraint of its own: with batches below about 8, its statistics turn unreliable and GroupNorm or LayerNorm is the better choice.

## Why we process many rows at once

One row at a time is correct and slow. The whole dataset at once is correct and will not fit. All in between is a trade between gradient quality and hardware efficiency, measured here.

```python-run
import numpy as np
import time

rng = np.random.default_rng(0)
N, D, H = 4096, 64, 128
X = rng.normal(size=(N, D))
W = rng.normal(0, 0.1, (D, H))

print("the same %d x %d @ %d x %d matmul, split into batches of different"
      % (N, D, D, H))
print("sizes. identical arithmetic every time -- only the call count changes:")
print()
print("%12s %10s %12s %16s" % ("batch size", "calls", "seconds", "us per row"))
for bs in (1, 8, 64, 512, 4096):
    t0 = time.time()
    for i in range(0, N, bs):
        _ = X[i:i + bs] @ W
    t = time.time() - t0
    print("%12d %10d %12.4f %16.2f" % (bs, N // bs, t, 1e6 * t / N))
print()
print("the multiplications are identical in every row. what changes is how")
print("much work happens per call: one row is a matrix-VECTOR product, which")
print("leaves most of the hardware idle, while a batch is a matrix-MATRIX")
print("product, which does not.")
print()
print("in this browser the gap is modest -- a factor of one and a half or so,")
print("because WebAssembly runs on a couple of CPU cores and the per-call")
print("overhead is small. on a GPU with thousands of cores the same")
print("comparison is a factor of a hundred or more, and that is the number")
print("that made batching universal. the SHAPE of the effect is what to take")
print("from this table, not its size.")
print()
```

Building on the same setup, the next block shows the left cases.

```python-run
import numpy as np
import time

print("now the statistical side. gradient quality against batch size:")
w_true = rng.normal(size=D)
y = X @ w_true + rng.normal(0, 1.0, N)
w0 = np.zeros(D)
full = 2 * X.T @ (X @ w0 - y) / N

print("%12s %18s %20s" % ("batch size", "cosine to full", "relative noise"))
for bs in (1, 4, 32, 256, 1024, 4096):
    sims, mags = [], []
    for _ in range(40):
        idx = rng.integers(0, N, bs)
        g = 2 * X[idx].T @ (X[idx] @ w0 - y[idx]) / bs
        sims.append(g @ full / (np.linalg.norm(g) * np.linalg.norm(full)))
        mags.append(np.linalg.norm(g - full))
    print("%12d %18.4f %20.4f"
          % (bs, np.mean(sims), np.mean(mags) / np.linalg.norm(full)))
print()
print("read the cosine column: a batch of 1 barely points toward the true")
print("gradient at all, and a batch of 256 is already at 0.90.")
print("the error falls as 1/sqrt(batch size), which is the same square root")
print("that governs every other average -- so quadrupling the batch halves")
print("the noise, and there are diminishing returns very quickly.")
```

## Things to try

1. <strong>Watch a single sample flow.</strong> Set <strong>Batch Size</strong> to 1 and press <strong>Simulate Flow</strong>. One activation pattern moves through the network and one update follows &mdash; maximally noisy and maximally frequent.
2. <strong>Batch it up.</strong> Set <strong>Batch Size</strong> to 32 and simulate again. Many samples traverse together and give a single averaged update. The averaging is where the noise reduction comes from.
3. <strong>Count the updates.</strong> Fix <strong>Epochs</strong> and check <strong>Batch Size</strong> 1 against 100. The same epoch count gives a hundred times fewer weight updates at the more batch &mdash; the usual reason a large-batch run appears to underfit.
4. <strong>Widen the network.</strong> Raise <strong>Input</strong> and <strong>Output</strong> and simulate at a large batch. More arithmetic per sample makes the batched matrix multiply proportionally more worthwhile.

## How batch size affects the result, not just the speed

More batches give a less-variance estimate of the true gradient. So the path to the min is smoother. That sounds strictly good and is not.

The noise in small-batch gradients acts as a regulariser. It shakes the optimiser out of sharp, narrow minima and toward flat, wide ones &mdash; and flat minima generalise better, since a small shift in the weights or the data distribution barely changes the loss. Large-batch training tends to settle into sharp minima and often generalises slightly worse, an effect known as the <strong>generalisation gap</strong>.

The standard mitigation is the <strong>linear scaling rule</strong>: when you multiply the batch size by k, multiply the learning rate by k as well, since each update is now averaged over k times as much data. Mixed with a short warmup this makes large-batch training match small-batch accuracy in most settings.

## Where this goes wrong

- <strong>Raising the batch size and leaving the learning rate alone.</strong> Fewer, no-more updates per epoch means visibly slower convergence. Scale the rate with the batch.
- <strong>Choosing the batch size purely by what fits in memory.</strong> The largest batch that fits is not automatically the best one. It is a regularisation choice as well as a throughput one.
- <strong>Batch normalisation with tiny batches.</strong> Batch norm estimates mean and variance from the batch. At a batch size of 2 or 4 those estimates are noise. Use group or layer normalisation instead.
- <strong>A final partial batch.</strong> When the dataset does not divide evenly the last batch is less. It skews batch-norm statistics and any per-batch averaging. Drop it in training if it is much less.
- <strong>Checking runs by epoch instead of by update.</strong> Two runs at other batch sizes have done very other amounts of optimisation after the same count of epochs.

## Key takeaway

Batching turns many small vector-matrix products into one large matrix-matrix product. It is what makes parallel hardware pay off, without changing the net at all. Batch size sets both the count of updates per epoch and the noise in each gradient. So it trades throughput against a regularising effect that favours flat minima. Change it and change the learning rate with it &mdash; roughly linearly &mdash; or the comparison is not fair.

## Gradient accumulation: a big batch on a small GPU

When the batch you want does not fit in memory, you can simulate it by accumulating gradients over a few small batches before updating:

```python
accum = 4                                   # effective batch = 4 x batch_size
opt.zero_grad()
for i, batch in enumerate(loader):
    loss = criterion(model(batch.x), batch.y) / accum    # scale to keep the mean right
    loss.backward()                                       # gradients accumulate
    if (i + 1) % accum == 0:
        opt.step()
        opt.zero_grad()
```

Two details matter. The loss must be divided by the accumulation count. Or the effective gradient is `accum` times too large. And PyTorch accumulates into `.grad` by default. It is just why this works &mdash; the same behaviour that makes forgetting `zero_grad()` a bug is the mechanism here.

The trade is wall-clock time: four small batches cost about as much as one large one would have. So you get the large-batch <em>statistics</em> without the large-batch <em>speed</em>.

## What limits batch size

Almost always <strong>activation memory</strong>, not the weights.

Each intermediate activation from the forward pass must be kept for the backward pass. A ResNet-50 at batch size 64 on 224&times;224 pics stores a few gigabytes of activations, against about 100MB of weights. That is why a net that "fits" can still fail with an out-of-memory error the moment you raise the batch size.

Three ways to buy memory back:

- <strong>Mixed precision</strong> stores activations in 16-bit, roughly halving the requirement and speeding up the arithmetic.
- <strong>Gradient checkpointing</strong> keeps just some activations and recomputes the rest, trading about 30% more compute for a large memory saving.
- <strong>Gradient accumulation</strong>, above, which keeps the memory small and the effective batch large.

## Batching at inference

The same idea applies when serving a net, with a other objective. Batching a few requests together uses the hardware far more well &mdash; often five to ten times the throughput of handling them one at a time.

The cost is latency: a request must wait for the batch to fill. Production systems use <strong>dynamic batching</strong>, collecting requests for a few milliseconds and then handling whatever has arrived. It captures most of the throughput gain with a bounded delay.

One correctness note: batch normalisation must be in eval mode at inference. Or the prediction for one input depends on which other inputs happen to share its batch. That is a genuinely confusing bug &mdash; the same input gives other answers &mdash; and `net.eval()` is the fix.

## Questions people ask

<strong>What batch size should I use?</strong> The largest that fits comfortably, up to about 256 for most work, then scale the learning rate accordingly.

<strong>Is a power of two needed?</strong> Not needed. And it aligns well with hardware. So 32/64/128/256 are conventional and marginally faster.

<strong>Why did my accuracy drop when I raised the batch size?</strong> Fewer updates per epoch and an unscaled learning rate. Scale the rate up and add warm-up.

<strong>Does batch size affect the final result?</strong> Somewhat. Very large batches tend to generalise slightly worse without specialised optimisers. And very small batches are slow and noisy.

<strong>Should the last partial batch be dropped?</strong> With batch normalisation, yes &mdash; a final batch of one or two gives wild statistics. `drop_last=True` handles it.

<strong>Is the loss averaged or summed over a batch?</strong> Averaged, by default. Summing makes the effective learning rate depend on batch size.

## Recap in one screen

- Mini-batches balance gradient quality, hardware efficiency and useful noise. 32&ndash;256 is the normal range.
- An epoch holds `dataset / batch_size` updates. So a more batch means fewer updates.
- Scale the learning rate with the batch size, and add warm-up.
- Activation memory, not the weights, is what limits batch size &mdash; mixed precision and checkpointing buy it back.
- Gradient accumulation gives a large effective batch on small hardware, at the cost of wall-clock time.
