title: Understanding One-Hot Encoding
intro: A deep explore converting categorical data into a machine-readable format.

## Core Concept

One-Hot Coding is a basic trick in data preprocessing, used to turn class-based vars into a numerical format that machine learning algorithms can understand. It takes a column with class-based data. It has been label encoded. And then splits the column into multiple columns. The counts are replaced by 1s and 0s, depending on which column has what value.

The reason counts alone are not enough is that a label-encoded column imposes a false ordering. If "red" is 0, "green" is 1 and "blue" is 2, the net sees blue as being "more" than red by a factor of two. And green as halfway between them. For a linear net, this means the coefficient for colour encodes a slope along a nonexistent axis. One-hot coding removes that problem by giving each group its own binary column: the "red" column is 1 when the value is red and 0 otherwise. And the same for green and blue.

The cost is dim count. A column with 1,000 groups gives 1,000 binary columns, most of which are zero for any given row. For high-cardinality features like postal codes or product IDs, this creates a sparse, high-dim grid that slows training and can overfit. Options for high-cardinality columns include target coding, hashing and embedding layers, each trading a other kind of information loss for a less form.

In scikit-learn, `OneHotEncoder` handles this and integrates with pipelines. Setting `handle_unknown="ignore"` ensures that a group absent from the training set does not crash the encoder at prediction time. It simply gets a row of zeros. Setting `drop="first"` removes one column per feature to avoid multicollinearity in linear nets.

## How It Works: The Feel

Imagine you have a feature like "Color" with groups: "Red", "Green", and "Blue". A machine learning net can't work with these text labels right. One-Hot Coding transforms this single "Color" column into three new columns, one for each group: "Is_Red", "Is_Green", and "Is_Blue".

- For a data point where the color is "Red", the "Is_Red" column will be <code class="mono-font/50 px-1.5 py-0.5 rounded">1</code>, while "Is_Green" and "Is_Blue" will be <code class="mono-font/50 px-1.5 py-0.5 rounded">0</code>.
- If the color is "Green", the "Is_Green" column gets the <code class="mono-font/50 px-1.5 py-0.5 rounded">1</code>. And the others get <code class="mono-font/50 px-1.5 py-0.5 rounded">0</code>.

This creates a sparse binary vec where just one bit is "hot" (set to 1), clearly and unambiguously showing the first group without implying any ordinal link between the groups.

## One column turns a few

One-hot coding replaces a class-based column with one new column per group, each holding 1 if the row has that group and 0 otherwise. Just one column is "hot" in each row. It is where the name comes from.

|City|is_London|is_Manchester|is_Leeds|
|---|---|---|---|
|London|1|0|0|
|Leeds|0|0|1|
|Manchester|0|1|0|
|Leeds|0|0|1|

What this buys you is the absence of a lie. Label coding says London=0, Manchester=1, Leeds=2. And a linear net reads that as an order and a spacing. One-hot says nothing except "this row is London". Each group sits the same distance from each other. It is the honest form of an unordered set.

The net can now learn a split coefficient for each city. In a linear net, `is_London` might get +45 and `is_Leeds` &minus;12, meaning London adds &pound;45k to a price and Leeds subtracts &pound;12k. Those are readable counts, which is a real secondary gain.

## The dummy var trap

Here is a subtlety that catches people in regression and confuses all else.

If a row must be just one of London, Manchester or Leeds, then the three columns always sum to 1. That means any one of them can be worked out from the other two. They are perfectly collinear. And if the net also has an intercept, there are infinitely many equally good coefficient sets. The grid turns non-invertible and the coefficients turn unstable or arbitrary.

The fix is to drop one group. It turns the <strong>reference level</strong>. With London dropped, `is_Manchester = 0` and `is_Leeds = 0` means London. And each left coefficient reads as "compared to London".

```python
from sklearn.preprocessing import OneHotEncoder

enc = OneHotEncoder(drop="first",              # avoid the dummy trap
                    handle_unknown="ignore",   # unseen category -> all zeros
                    sparse_output=True)        # do not materialise the zeros
```

Whether you need `drop="first"` depends on the net. Linear and logistic regression with an intercept: yes. Regularised nets, trees, forests, boosting and neural networks: no. And dropping a level can really hurt, since smoothing penalises the left groups asymmetrically tied to the hidden reference.

## The cost: width, sparsity and memory

One-hot coding is safe and it is costly. And the expense is a function of cardinality.

A column with 5 groups adds 5 columns. A postcode column with 2,000 distinct vals adds 2,000 columns, of which 1,999 are zero in each row. Three consequences follow:

- <strong>Memory.</strong> Stored densely, 1 million rows &times; 2,000 columns of floats is 16 GB. Stored sparsely &mdash; just the spots of the ones. It is a few megabytes. Always keep high-cardinality one-hot output sparse.
- <strong>Stats.</strong> A group appearing in 20 of 1,000,000 rows gives its column almost nothing to learn from. So the coefficient is mostly noise.
- <strong>Trees suffer namely.</strong> A binary column can just ever give the split "is it this group or not". So a tree needs many splits to isolate a group of groups that a single native class-based split would handle at once. This is why LightGBM and CatBoost's native group handling often beats one-hot on tree nets.

Two real mitigations. Group rare groups into an explicit "other" bucket. Anything under about 1% of rows is often a candidate. And above roughly 50 groups, look at target coding or learned embeddings instead.

## Pseudocode Logic

```
function oneHotEncode(corpus):
  // 1. Tokenize and find unique words
  tokens = tokenize(corpus)
  vocabulary = sorted(unique(tokens))
  
  // 2. Create a mapping from word to index
  word_to_index = {word: i for i, word in enumerate(vocabulary)}
  
  // 3. Generate vectors
  encoded_vectors = []
  for token in tokens:
    vector = create_zero_vector(length=len(vocabulary))
    index = word_to_index[token]
    vector[index] = 1
    encoded_vectors.append(vector)
    
  return encoded_vectors
                        
```

## Advantages and Disadvantages

<h4 class="font-bold mb-2">Advantages</h4>

- <strong>No Ordinality:</strong> It doesn't create a false order or ranking between groups. It is a common issue with simple label coding.
- <strong>Interpretability:</strong> The resulting vecs are easy to interpret. Each column clearly corresponds to a set group. <h4 class="font-bold mb-2">Disadvantages</h4>

- <strong>High Dim count (Curse of Dim count):</strong> If you have many unique groups (a large vocabulary), it creates a huge count of new features. This can slow down net training and sometimes hurt performance.
- <strong>Sparsity:</strong> The resulting grid is sparse (mostly zeros). It can be computationally inefficient to store and process.

## Beyond One-Hot Coding

While One-Hot Coding is a great starting point, for more complex tasks, especially in Natural Language Handling (NLP), more advanced tricks like <strong>Word Embeddings (e.g., Word2Vec, GloVe, FastText)</strong> are used. These ways represent words as dense, low-dim vecs that get semantic links (e.g., the vecs for "king" and "queen" are closer to each other). One-Hot Coding, in contrast, treats each word as equally other from all others.

## Choosing between the encodings

|Situation|Reach for|
|---|---|
|Under ~10 categories, linear model or network|One-hot|
|Ordered categories (small/medium/large)|Ordinal, with the order stated|
|Many categories, tree ensemble|Native categorical support, or label encoding|
|Many categories, strong relationship to the target|Out-of-fold target encoding|
|Huge cardinality, collisions acceptable|Feature hashing|
|Deep learning with many categories|A learned embedding layer|

The embedding option is worth a moment. Instead of 2,000 sparse columns, learn a dense vec of, say, 16 counts per group, trained along with the rest of the network. Close groups end up with close vecs. It one-hot can never express since each group is equidistant from each other. This is just how class-based features are handled in recommendation systems. And it is why an embedding of 10,000 products is routine while one-hot coding them is not.

## Getting it right in a pipeline

The single most common one-hot bug in production is a column-count mismatch: training data had 40 cities, today's batch has 38. And the net gets a grid of the wrong width.

The fix is to fit the encoder once and reuse the fitted object. Never to call `pd.get_dummies` apart on training and serving data. It is what causes this.

```python
from sklearn.compose import ColumnTransformer
from sklearn.pipeline import Pipeline
from sklearn.preprocessing import OneHotEncoder, StandardScaler

pre = ColumnTransformer([
    ("cat", OneHotEncoder(handle_unknown="ignore"), ["city", "product"]),
    ("num", StandardScaler(), ["price", "age"]),
])

model = Pipeline([("pre", pre), ("clf", LogisticRegression())])
model.fit(X_train, y_train)      # the encoder's vocabulary is now fixed
model.predict(X_new)             # unseen categories become all-zero rows
```

`handle_unknown="ignore"` is what stops an unfamiliar city from crashing the service: the row simply gets zeros across all the city columns. It the net reads as "none of the known cities". Not ideal, but far better than an exception at request time.

## Why not just count the groups

Label-coding a group invents an order that is not there. This shows the damage, the one-hot fix. And the column explosion that follows.

```python-run
import numpy as np
from sklearn.preprocessing import OneHotEncoder, OrdinalEncoder
from sklearn.linear_model import LinearRegression
from sklearn.ensemble import RandomForestRegressor
from sklearn.model_selection import cross_val_score
from sklearn.compose import ColumnTransformer
from sklearn.pipeline import make_pipeline

rng = np.random.default_rng(0)
cities = np.array(["london", "paris", "tokyo", "lagos", "lima"])
# rent depends on the city, in no particular order
base = {"london": 40, "paris": 32, "tokyo": 45, "lagos": 12, "lima": 15}
idx = rng.integers(0, 5, 1200)
city = cities[idx]
rent = np.array([base[c] for c in city]) + rng.normal(0, 3, 1200)
X_cat = city.reshape(-1, 1)

ordinal = OrdinalEncoder().fit(X_cat)
print("ordinal encoding assigns numbers alphabetically:")
for c, n in zip(ordinal.categories_[0], range(5)):
    print("   %-8s -> %d   (real average rent %.1f)" % (c, n, rent[city == c].mean()))
print()
print("that ordering says lagos < lima < london < paris < tokyo, and that")
print("the gap from lagos to lima equals the gap from paris to tokyo. neither")
print("is true. a linear model believes both:")
Xo = ordinal.transform(X_cat)
print("  linear regression on ordinal codes : R2 %.4f"
      % cross_val_score(LinearRegression(), Xo, rent, cv=5).mean())
```

```python-run
    print("   %-14s coefficient %8.3f" % (name, c))

print("  no ordering was assumed, so none was imposed.")
```


## Questions people ask

<strong>Should I one-hot encode the target?</strong> For multi-class sorting with a neural network and class-based cross-entropy, yes. With scikit-learn sorters and sparse class-based loss, no. Integer labels are what they expect.

<strong>Does one-hot coding need scaling afterwards?</strong> The columns are now 0/1. So scaling changes little. It matters just if you are also scaling other features and want the smoothing cost to fall evenly across them.

<strong>Is `pd.get_dummies` fine?</strong> For exploration, yes. For anything that will see new data later, no. It derives the columns from whatever data you hand it. So training and serving can disagree silently.

<strong>How many groups are too many?</strong> There is no hard line. But past 50 the sparsity starts to hurt and past a few hundred it often dominates. Measure it: check one-hot against target coding by cross-validation rather than guessing.

<strong>What about missing vals?</strong> Encode them as their own group. A blank field is often informative. And folding it into the most common group destroys that information.

<strong>Does one-hot coding cause overfitting?</strong> Indirectly. Adding hundreds of columns to a net with limited rows gives it more ways to fit noise. Smoothing and rare-group grouping are the usual answers.

## Recap in one screen

- One column per group, just one 1 per row, no invented ordering.
- Drop one level for linear nets with an intercept. Keep all levels for regularised nets and trees.
- Cardinality is the cost: width, sparsity and thin stats per column.
- Keep the grid sparse, group rare vals. And consider target coding or embeddings above ~50 groups.
- Fit the encoder once, inside a pipeline. And set `handle_unknown="ignore"` before it reaches production.
