title: Form Data and File Uploads
intro: What a browser form really sends. Why it's neither JSON nor a query string.

## The core idea

A browser form does not send JSON. When a user submits an HTML form, the browser packs the fields into a different format, and when the form includes a file, it uses yet another.

## Three body formats

This matters whenever you build a login page, a contact form, or anything that lets users upload a picture or a document. It also matters when you call your own API from tools that send forms. Getting the format wrong produces confusing errors that look like validation failures but are really a mismatch of expectations.



Next comes the small extra package that FastAPI needs before it can parse forms at all, and the error you see if it is missing. The last section covers UploadFile, the class that represents an uploaded file. It handles large files sensibly by spooling them to disk instead of loading everything into memory.

After reading, you will know which format a request uses and how to declare it correctly.

An HTTP request has one body. For an API there are three ways it's often coded.

**JSON** (`use/json`) is what a JavaScript client or another service sends. A Pydantic model param reads it.

**URL-coded form** (`use/x-www-form-urlencoded`) is what a plain HTML `<form>` posts. It looks like a query string in the body: `username=ada&password=hunter2`.

**Multipart** (`multipart/form-data`) is what a form with a file input sends. It carries a few named parts, each with its own headers. This is how a file and its metadata travel together.

FastAPI needs to be told which. A model param means JSON. `Form()` means one of the form encodings. `UploadFile` means a file part in a multipart body. Getting this wrong is a common source of confusing 422 errors.

## Form() reads a form field

A browser form posts <code>application/x-www-form-urlencoded</code>, which is not JSON. <code>Form()</code> says so explicitly.

```python-run
from fastapi import FastAPI, Form

app = FastAPI()

@app.post("/login")
def login(username: str = Form(), password: str = Form()):
    return {"username": username, "password_len": len(password)}

c = TestClient(app)
r = c.post("/login", data={"username": "ada", "password": "hunter2"})
print(r.status_code, r.json())
```

## Form fields validate like anything else

The same constraints, the same 422 &mdash; with <code>body</code> as the source, because a form is a body.

```python-run
from fastapi import FastAPI, Form

app = FastAPI()

@app.post("/signup")
def signup(email: str = Form(pattern=r"^[^@]+@[^@]+\.[^@]+$"),
           age: int = Form(ge=13)):
    return {"email": email, "age": age, "type": type(age).__name__}

c = TestClient(app)
print("good:", c.post("/signup",
                      data={"email": "ada@vizlearn.in", "age": 36}).json())

r = c.post("/signup", data={"email": "nope", "age": 9})
print("bad :", r.status_code)
for err in r.json()["detail"]:
    print("   ", err["loc"], err["type"])
```

## Form and JSON cannot share a request

One body, one content type. Declaring both a model and a Form field is a contradiction, and the error is confusing if you do not expect it.

```python-run
from fastapi import FastAPI, Form
from pydantic import BaseModel

app = FastAPI()

class Body(BaseModel):
    title: str

@app.post("/json")
def as_json(body: Body):
    return {"via": "json", "title": body.title}

@app.post("/form")
def as_form(title: str = Form()):
    return {"via": "form", "title": title}

c = TestClient(app)
print(c.post("/json", json={"title": "Vectors"}).json())
print(c.post("/form", data={"title": "Vectors"}).json())
print()
print("A request carries one body. Pick the content type the client sends.")
```

## Uploads arrive as UploadFile

A file part gives you a filename, a content type and a file-like object &mdash; streamed to disk rather than held in memory.

```python-run
from fastapi import FastAPI, UploadFile

app = FastAPI()

@app.post("/upload")
def upload(file: UploadFile):
    data = file.file.read()
    return {"filename": file.filename,
            "content_type": file.content_type,
            "bytes": len(data),
            "head": data[:24].decode("utf-8", "replace")}

r = TestClient(app).post("/upload", files={
    "file": ("notes.txt", b"Vectors have direction and magnitude.", "text/plain")})
print(r.status_code, r.json())
```

## Files and fields together

<code>multipart/form-data</code> carries both, which is what a real upload form sends.

```python-run
from fastapi import FastAPI, Form, UploadFile

app = FastAPI()

@app.post("/modules/{i}/asset")
def add_asset(i: int, caption: str = Form(), file: UploadFile = None):
    return {"module": i, "caption": caption,
            "filename": file.filename if file else None,
            "bytes": len(file.file.read()) if file else 0}

r = TestClient(app).post("/modules/7/asset",
        data={"caption": "A vector diagram"},
        files={"file": ("v.svg", b"<svg/>", "image/svg+xml")})
print(r.status_code, r.json())
```

## Validating an upload is your job

The framework gives you a filename and a declared content type. Neither is trustworthy, and nothing checks the size.

```python-run
from fastapi import FastAPI, HTTPException, UploadFile

app = FastAPI()
MAX = 32
ALLOWED = {"text/plain", "image/png"}

@app.post("/upload")
def upload(file: UploadFile):
    if file.content_type not in ALLOWED:
        raise HTTPException(415, "Unsupported type %r" % file.content_type)
    data = file.file.read(MAX + 1)
    if len(data) > MAX:
        raise HTTPException(413, "File too large (limit %d bytes)" % MAX)
    return {"filename": file.filename, "bytes": len(data)}

c = TestClient(app)
for label, spec in [
    ("ok      ", ("a.txt", b"short", "text/plain")),
    ("too big ", ("a.txt", b"x" * 100, "text/plain")),
    ("bad type", ("a.exe", b"MZ", "application/x-msdownload")),
]:
    r = c.post("/upload", files={"file": spec})
    print(label, r.status_code, r.json())
```

## Form()

```python
def login(username: str = Form(), password: str = Form()):
```

Without `Form()`, a plain `username: str` param would be read as a **query param**. The request would fail with a confusing 422 about a missing query field while the value sits in the body.

That is the one thing to note here. The marker isn't decoration. It's what tells FastAPI where to look.

all else behaves as it does elsewhere: constraints, defaults, needed-ness and the 422 all work the same way, with `loc[0] == "body"` because a form *is* the body.

## One body, one content type

A request can't be both JSON and a form. Declaring a model param alongside a `Form()` param is a clash. The resulting error doesn't always say so clearly.

Pick the encoding your client really sends. If it's a browser form, use `Form()`. If it's JavaScript, it's almost certainly sending JSON. A model is simpler and better documented.

A common middle case: an HTML form that you'd rather receive as a model. The clean answer is to have the front end send JSON. Failing that, a dependency can assemble a model from form fields. This keeps the handler tidy.

## python-multipart

Form and file endpoints need the `python-multipart` package. Without it FastAPI raises at startup. The message names the package rather than the endpoint. Which is helpful once you know, and puzzling the first time.

It's a runtime dependency of the framework's form support rather than a thing FastAPI bundles. It has to be installed by name.

## UploadFile

```python
def upload(file: UploadFile):
    data = file.file.read()
```

`UploadFile` gives you three things: `filename`, `content_type`, and `file`, a file-like object.

The key property is that a large upload is **spooled to disk** rather than held in memory. A `bytes` param would read the whole thing into RAM. This is fine for a small avatar and a denial-of-service vector for anything else. `UploadFile` is the right default.

It also offers `async` methods. `await file.read()` &mdash; for use in `async def` endpoints. A slow upload doesn't block the event loop.

## What the framework does not check

This is the part worth taking seriously, because the defaults are permissive.

**Size is unlimited.** Nothing caps an upload. Check it in the handler by reading with a limit rather than reading all and then measuring. And set a limit in what sits in front of the app too. By the time your code runs the bytes have already arrived.

**`content_type` is a claim.** It comes from the client and can say anything. If the type matters, check the actual content. Magic bytes for images, parsing for structured formats.

**`filename` is attacker-controlled.** It can hold `..`, abs paths, null bytes and characters your filesystem treats specially. **Never build a path from it.** make your own name. A UUID. And keep the first only as metadata if you need it for display.

**The content is unexamined.** An uploaded file is any bytes. If it will be served back to browsers, serve it from a split domain or with `Content-Disposition. Attachment` and a restrictive `Content-Type`. An HTML file can't execute in your origin.

## Documenting them

Form and file endpoints appear in the OpenAPI doc. The interactive docs render a file picker for `UploadFile`. This makes them truly testable from the browser.

`Form()` takes `description` like every other param. It's worth writing. A form field's name is often shorter and less obvious than a JSON key.

## When to use which

Reach for **JSON** by default. It's better documented, better checked, nests properly. Each client can give it.

Reach for **form data** when a browser form posts right to your API without JavaScript, or when an existing client already sends it.

Reach for **multipart** when files are involved. That is what it is for. It's the only one of the three that carries binary content alongside fields.

For anything large, consider not uploading through your API at all. A pre-signed URL to object storage moves the bytes right and keeps them out of your request path fully. That is more moving parts. It's the standard answer once files get big.

## Mistakes people make

**Losing `Form()`.** A plain param is read as a query param. The request 422s about a missing query field while the value sits in the body. The marker is what tells FastAPI where to look.

**Mixing a model and form fields.** One request, one body, one content type. Declaring both is a clash. The resulting error doesn't say so clearly.

**Missing `python-multipart`.** FastAPI raises at startup and names the package rather than the endpoint - obvious later, puzzling the first time.

**Reading an upload as `bytes`.** Fine for an avatar, a denial-of-service vector for anything larger. `UploadFile` spools to disk.

**Building a path from `filename`.** It's attacker-controlled and can hold `..`, abs paths. Characters your filesystem treats specially. make your own name.

**Trusting `content_type`.** It's a claim from the client. If the type matters, check the bytes.

**No size limit.** Nothing caps an upload by default. The bytes arrive before your handler runs - so cap it in the handler *and* in what sits in front of the app.

## Serving uploads back

A related risk that is easy to miss.

If uploaded files are served back to browsers from your own domain, an uploaded HTML file runs in your origin - which means it can read cookies, call your API as the viewer. Often behave as your own page.

The mitigations, in rough order of preference: serve user content from a split domain. Send `Content-Disposition: attachment` so it downloads rather than renders. And set a restrictive `Content-Type` rather than echoing the one the client claimed.

For anything at scale, uploading right to object storage with a pre-signed URL avoids the problem and keeps the bytes out of your request path fully.

## Getting a model out of a form

A recurring want: a browser posts a form. You'd rather work with a Pydantic model than six `Form()` params.

There's no built-in switch for it. A model param means JSON by meaning. The usual answers, in order of how much they cost:

**Have the front end send JSON.** A few lines of JavaScript. All downstream turns simpler - check, nesting, docs and error shapes all improve.

**Build the model in the handler.** `ModuleIn(**{"title": title, "minutes": minutes})` after declaring the fields as `Form()`. Honest. Repetitive across a few endpoints.

**A dependency that assembles it.** The tidy version. One function declaring the form fields and returning the model, then `module: ModuleIn = Depends(as_form)`. Handlers stay clean and the assembly lives in one place. That is the next tier's material.

What to avoid is a decorator that inspects a model and makes form params by reflection. a few exist, they work. They make the endpoint's signature a thing a reader can't see.

## Multiple files

`files: List[UploadFile]` accepts a few parts under the same name. This is what a multi-select file input sends.

Two cautions with it. The size limit now applies to the total and each item. A hundred small files can be as costly as one large one - cap the count with `max_length` as well. And checking each file means doing the work per item. So A slow check times.

For anything where the count could be large, an endpoint that accepts one file and is called again and again is easier to reason about, easier to retry. Gives the client better progress reporting.

## Where uploads should go

A last architectural note, because the default path is rarely the right one at scale.

Uploading through your API means the bytes travel into your process, through what sits in front of it. Often out again to storage. That consumes request room, occupies a worker for the duration of a slow link. Puts a size limit on a thing that has no natural one.

The option is a pre-signed URL: your API issues a short-lived credential, the client uploads right to object storage. Then tells your API the key. The bytes never touch your use.

It's more moving parts and it's what most systems end up doing. The failure mode of the simple approach is a worker pool full of slow uploads.
