title: Request Bodies: A Model Is the Contract
intro: all the Pydantic track taught, applied to an HTTP request.

## One annotation

A request body is the data a client sends along with a request, usually as JSON. You see it on POST, PUT, and PATCH calls, where the client needs to give the server something more structured than a few values in a URL. A new user, an order, or a set of settings all arrive this way.

FastAPI handles bodies with the tool you already know from Pydantic. You write a model that describes the fields and their types. You use that model as the annotation on a function argument. The framework reads the incoming JSON, validates it against the model, and gives you a real object. If the data is wrong, your handler never runs.

This article starts with that single annotation and what it does behind the scenes. It then looks at how failures happen first, before any of your code, and what the client sees. You will see how structure works for nested data, and how a body, a path parameter, and a query parameter can all appear on the same endpoint without confusion.

A common design question follows: should one model serve both input and output? The article argues for two models and explains why. It finishes with unknown keys, the extra fields a client might send that your model never mentioned, and the choices you have for handling them.

Read this one carefully if you build any API that accepts data. The model you write here is the contract your clients depend on.

If you have not read the Pydantic track, a quick look at it first will help. The model syntax is the same, and this article assumes you are comfortable reading a class with typed fields. Each section is short and ends with a habit you can apply straight away, so you finish with working knowledge and a clear picture of how bodies behave.

```python
@app.post("/modules", status_code=201)
def create(module: ModuleIn):
    ...
```

A param annotated with a Pydantic model is the request body. FastAPI reads the raw bytes, validates them with `model_validate_json`. Calls your handler with an object.

By the time the function runs, `module.minutes` is an int. Even if the client sent `"8"`. And each constraint on the model has passed. There's nothing to check at the top of the handler. This Is the point.

This is also the moment where the whole Pydantic track turns right applicable. Field constraints, nested models, checkers, aliases, enums, `Literal`, strict mode. All of it works here, unchanged, because this *is* Pydantic.


## A model parameter is the body

Annotate a parameter with a model and FastAPI parses the JSON, validates it, and hands you an object.

```python-run
from fastapi import FastAPI
from pydantic import BaseModel, Field

app = FastAPI()

class ModuleIn(BaseModel):
    title: str = Field(min_length=3)
    minutes: int = Field(default=10, gt=0, le=180)
    published: bool = False

@app.post("/modules", status_code=201)
def create(module: ModuleIn):
    return {"title": module.title, "minutes": module.minutes,
            "type": type(module.minutes).__name__}

client = TestClient(app)
r = client.post("/modules", json={"title": "Vectors", "minutes": "8"})
print(r.status_code, r.json())
print()
print("the string 8 became an int before the handler ran")
```

## Failures never reach your code

Every field is checked and the 422 carries the whole list, with <code>loc</code> starting at <code>body</code>.

```python-run
from fastapi import FastAPI
from pydantic import BaseModel, Field

app = FastAPI()
reached = []

class ModuleIn(BaseModel):
    title: str = Field(min_length=3)
    minutes: int = Field(gt=0)

@app.post("/modules")
def create(module: ModuleIn):
    reached.append(module.title)
    return {"ok": True}

client = TestClient(app)
r = client.post("/modules", json={"title": "no", "minutes": -1})
print("status:", r.status_code)
for err in r.json()["detail"]:
    print("  %-22s %-18s %s" % (".".join(str(p) for p in err["loc"]),
                                err["type"], err["msg"]))
print()
print("handler ran for:", reached)
```

## Nested and repeated structure

A model can contain models and lists of them. The error path reaches all the way down.

```python-run
from typing import List
from fastapi import FastAPI
from pydantic import BaseModel, Field

app = FastAPI()

class Lesson(BaseModel):
    name: str
    minutes: int = Field(gt=0)

class ModuleIn(BaseModel):
    title: str
    lessons: List[Lesson] = Field(min_length=1)

@app.post("/modules", status_code=201)
def create(module: ModuleIn):
    return {"title": module.title,
            "total": sum(l.minutes for l in module.lessons)}

client = TestClient(app)
print(client.post("/modules", json={"title": "Vectors", "lessons": [
    {"name": "Direction", "minutes": 4}, {"name": "Magnitude", "minutes": "6"}]}).json())

r = client.post("/modules", json={"title": "Vectors", "lessons": [
    {"name": "Direction", "minutes": 4}, {"name": "Magnitude", "minutes": "soon"}]})
print()
print("bad item:", r.json()["detail"][0]["loc"])
```

## Body plus path plus query

One handler can take all three. FastAPI works out where each comes from and the error says which.

```python-run
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()

class ModuleIn(BaseModel):
    title: str
    minutes: int

@app.put("/tracks/{track}/modules/{module_id}")
def replace(track: str, module_id: int, module: ModuleIn, notify: bool = False):
    return {"track": track, "module_id": module_id,
            "title": module.title, "notify": notify}

client = TestClient(app)
r = client.put("/tracks/maths/modules/7?notify=yes",
               json={"title": "Vectors", "minutes": 8})
print(r.json())

bad = client.put("/tracks/maths/modules/seven", json={"title": "V", "minutes": "x"})
print()
print("failures name their source:")
for err in bad.json()["detail"]:
    print("  ", err["loc"])
```

## Two models in one body

Two model parameters make FastAPI nest them under their names, which is occasionally what you want.

```python-run
from fastapi import FastAPI
from pydantic import BaseModel

app = FastAPI()

class Module(BaseModel):
    title: str

class Author(BaseModel):
    name: str

@app.post("/publish")
def publish(module: Module, author: Author, notify: bool = False):
    return {"module": module.title, "author": author.name, "notify": notify}

client = TestClient(app)
r = client.post("/publish?notify=1", json={
    "module": {"title": "Vectors"},
    "author": {"name": "Ada"},
})
print(r.json())
print()
print("body schema:", list(app.openapi()["paths"]["/publish"]["post"]
                           ["requestBody"]["content"]["application/json"]["schema"]))
```

## Rejecting keys you did not declare

By default unknown keys are ignored, which hides typos. <code>extra="forbid"</code> turns them into errors.

```python-run
from fastapi import FastAPI
from pydantic import BaseModel, ConfigDict

app = FastAPI()

class Lenient(BaseModel):
    title: str
    minutes: int = 10

class Strict(BaseModel):
    model_config = ConfigDict(extra="forbid")
    title: str
    minutes: int = 10

@app.post("/lenient")
def a(m: Lenient): return m.model_dump()

@app.post("/strict")
def b(m: Strict): return m.model_dump()

payload = {"title": "Vectors", "minuets": 30}     # typo

client = TestClient(app)
print("lenient:", client.post("/lenient", json=payload).json(),
      "<- typo vanished, minutes is the default")
r = client.post("/strict", json=payload)
print("strict :", r.status_code, r.json()["detail"][0]["loc"],
      r.json()["detail"][0]["type"])
```
## Failures happen first

If the body doesn't fit the model, your handler is never called. FastAPI returns 422 with a `detail` that is `e.errors()`.

The `loc` begins with `body`, then names the field, then the path within it. So `("body", "lessons", 1, "minutes")` is the `minutes` field of the second lesson. For a payload of any size that is the whole diagnosis.

each field is checked, so a client with four mistakes learns about all four at once rather than one resubmission at a time. This matters most for forms. Here The option is a truly unpleasant experience.

## Structure

Bodies nest as deeply as your models do. A `List[Lesson]` inside a `Module` validates each lesson with its own rules, and errors keep their index.

Two things worth carrying over from the Pydantic track.

**Constrain sets.** `Field(min_length=1)` says a module must have at least one lesson. `max_length` caps how many. This Is a cheap protection against a caller sending a hundred thousand.

**Extract models that repeat.** If `Address` appears in three request bodies, it's a model. The rules then live in one place.

## Path, query and body together

A handler can take all three. FastAPI decides which is which by the rules from the previous modules. Names in the route path are path params, Pydantic models are the body, all else is a query param.

```python
def replace(track: str, module_id: int, module: ModuleIn, notify: bool = False):
```

The signature reads as docs, and the 422 for a bad request names each source apart. `("path", "module_id")` and `("body", "minutes")` are other problems for the caller to fix.

## Two models

If you annotate two params with models, FastAPI nests them under their param names rather than merging:

```json
{"module": {...}, "author": {...}}
```

That is at times what you want. More often it's a sign that the two belong in one model. The client now has to know a structure that exists only because of how your function was written. A single model that holds both is often clearer, and easier to doc.

`Body(embed=True)` forces the same nesting for a single model, when an existing API expects it.

## Unknown keys

By default Pydantic skips keys it doesn't recognise. A client sending `minuets` instead of `minutes` gets no error and no field. `minutes` takes its default. The bug shows up later as a duration no one set.

`model_config = ConfigDict(extra="forbid")` makes that a 422 naming the offending key.

Which to choose is a real choice. For an inner API, forbid. A typo should be loud. For a public one, the arg for skipping is forward match. A client sending fields from a newer version shouldn't break against an older server.

What you shouldn't do is leave it unconsidered. This Is what often happens.

## Which methods take a body

`POST`, `PUT` and `PATCH` do. `GET` and `DELETE` usually don't. While FastAPI will let you declare a body on a GET, many clients, proxies and caches will drop it. If a GET needs structured input, that is a sign it wants query params, or that it's really a POST.

The gap between the three that do:

**POST** creates a thing, and the server decides its identity.

**PUT** replaces a resource fully at a known URL. So a PUT body should hold each field. Omitting one means clearing it.

**PATCH** updates part of one. This Is where `exclude_unset` from the Pydantic track earns its place. Dump only what the caller supplied. Untouched fields stay untouched.

Getting PUT and PATCH backwards is common and makes the bug where an update wipes fields the client never mentioned.

## Raw bodies

Not all is JSON. `Request` gives you the raw object, with `await request.body()` for the bytes. Needed for a webhook whose signature is found over the exact payload. Re-serialising a parsed model makes other bytes.

`Body(media_type="text/plain")` handles a plain-text body. Form data and file uploads have their own module in the next tier.

Reach for these on purpose. A raw body means no check, no schema. No docs. It should be a seen as exception rather than a way of avoiding writing a model.

## Designing the model

Two habits, both from the Pydantic track and both worth repeating because bodies are where they pay off most.

**A split model per direction.** `ModuleCreate` takes what a caller may supply, with no server-assigned id. `ModuleUpdate` has all optional. `ModuleOut` declares just what may be seen. One model with all optional docs nothing and promises nothing.

**show the fields.** A `description` on a body field appears next to it in the docs. An `examples` entry pre-fills the interactive request form. Which is the gap between a first-time caller succeeding and guessing.

## Documenting the body

all the Pydantic track said about schema metadata applies. Bodies are where it pays off most.

`description` on a field appears beside it in the interactive docs. `examples` pre-fills the request form. This Is the gap between a first-time caller pressing "Try it out" and getting a working request, or an empty box they've to guess at.

Model-level examples are even better for a body:

```python
model_config = ConfigDict(
    json_schema_extra={"examples": [{"title": "Vectors", "minutes": 8}]})
```

Now the docs show a full sample payload somebody can copy.

`Body(embed=True)` and `Body(examples=[...])` do the same at the param level when you need to replace what the model says.

## Size limits

FastAPI doesn't cap request body size by default. That is worth knowing. An endpoint accepting JSON will attempt to parse what arrives.

The cap most times belongs upstream. In nginx, in your ingress, in the platform &mdash; and it's one of the standard things to check before an API is public. Within the app, `max_length` on sets limits how many items a body may hold. This Handles the common case of a bulk endpoint being handed a hundred thousand records.

## Validation that needs the whole body

A rule spanning two fields belongs in a `model_validator(mode="after")`, just as in the Pydantic track. The error arrives with `loc: ["body"]`. No field. It belongs to the object. And a client needs one spot to display it.

A rule spanning the body *and* a path param is other. No model can see both. That is a dependency, or a check at the top of the handler raising a 400 or 409. It's one of the few cases where logic in the handler is the honest answer. The link is between HTTP concerns rather than within the data.

## Idempotency, briefly

A POST that creates a thing isn't idempotent: a client that times out and retries may create two.

The usual answer is an idempotency key. A header the client makes. This The server records alongside the result, returning the first response on a repeat. That is beyond a first tier. It's worth knowing the problem exists before an API is handling anything that matters. Retrofitting it after the copies appear is much harder.

## Summary

A model param is the body. all from Pydantic applies: constraints, nesting, checkers, aliases, strict mode.

check runs before your handler, and a 422 carries each problem with `loc` starting at `body`. Unknown keys are skipped unless you forbid them. split models per direction, and show the fields. The docs are made from them, and a good example is the cheapest thing you can do for whoever calls you.


## Mistakes people make

**Reusing one model for input and output.** The result is a model where all is optional. This Docs nothing and promises nothing in either direction.

**Leaving `extra` at the default on an inner API.** A misspelt key silently turns a defaulted field. The bug appears later as a value no one set.

**Treating PUT as PATCH.** A PUT body should be full. An omitted field means clearing it. Using PUT for partial updates is how an edit wipes six columns the client never mentioned.

**Declaring a body on a GET.** Some clients and proxies drop it. If a read needs structured input, it wants query params, or it's really a POST.

**Two model params where one model belongs.** It forces callers to learn a nesting that exists only because of how your function was written.

**No cap on set size.** `max_length` on a list field is what stops a bulk endpoint being handed a hundred thousand records.

**Re-serialising a body you needed verbatim.** A webhook signature is found over the exact bytes. `await request.body()` is the only thing that gives you those.

## The body is the contract

Of all an endpoint declares, the body model is the part consumers read most carefully. It's what they've to make.

Which makes it worth more care than the rest. Field names that read well. Descriptions on anything not self-evident. A full example. Constraints that state the real limits rather than leaving them to be found by rejection. needed fields that are truly needed. Defaults that are truly sensible.

None of that changes action. All of it changes how long somebody spends getting their first good request. This Is the number that decides whether they enjoy using your API.

## Accepting change from clients

The mirror of the previous point: how a body model can evolve without breaking senders.

**Adding an optional field is safe.** Old clients omit it and get the default.

**Adding a needed field is breaking.** each existing client at once starts getting 422s. If a field must become needed, give it a default first, deprecate the lack, then tighten.

**Loosening a constraint is safe.** Tightening one isn't. A `max_length` reduced from 100 to 50 rejects requests that worked yesterday.

**Renaming is breaking**, unless you accept both names for a while. This Is just what `AliasChoices` from the Pydantic track is for.

This is why `extra="skip"` is defensible on a public API though `forbid` catches typos. A client sending fields from a newer version keeps working against an older server. It's a trade between catching mistakes and handling drift. Which side you want depends on who is calling.

## What the model is really doing

A body model is doing three jobs that would else be three split pieces of code.

It **parses**, turning bytes into typed values. It **validates**, rejecting anything that doesn't fit before your logic sees it. And it **docs**, appearing in the schema so callers know what to send without reading your source.

Written by hand those drift apart: the parser accepts a thing the checker rejects. The docs shows a shape neither of them runs. One class keeps all three in match because they're all made from it.

## Questions people ask

<strong>How do I declare a request body?</strong> Add a parameter annotated with a Pydantic model. FastAPI reads the JSON body, validates it against the model, and passes the instance to your function.

<strong>Can a GET request have a body?</strong> The spec allows it, but many clients and proxies drop it. Use query parameters for GET and keep bodies for POST, PUT, and PATCH.

<strong>How do I accept more than one body parameter?</strong> Declare two model parameters. FastAPI then expects a JSON object with each parameter name as a key.

<strong>What happens to extra keys the client sends?</strong> By default Pydantic ignores them. Set model_config = ConfigDict(extra="forbid") to reject them with a 422.

<strong>Why use separate models for input and output?</strong> The input model describes what a client may send, while the output model controls what you return. They often differ, for example by a password or an id field.

<strong>How do I read the raw body instead?</strong> Take a Request parameter and call await request.body() or await request.json(). You lose validation and documentation for that body.

## A closing thought

Almost each question about request bodies turns out to be a Pydantic question wearing an HTTP hat. What will it coerce, what is needed, how do I express this rule, why did that fail.

Which is good news, because it means the body is the part of an API where the least framework-exact knowledge is needed. Get the models right and the endpoints are a formality.
