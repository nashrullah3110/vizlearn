title: Status Codes
intro: Which number to return when, and why 200-for-all discards data the client already understands.
## The class matters more than the number

A status code is the three-digit number at the start of every HTTP response. It tells the client, in a form machines understand, whether the request worked, and if not, whose fault it was. Clients, browsers, proxies, and monitoring tools all read it before they look at the body.

Returning 200 for everything throws that information away. A client that gets 200 with an error message inside has to parse the body to find out something the status line could have said immediately. Using the right code makes your API easier to use and easier to monitor.

This article begins with the idea that the class of the number matters more than the exact value. Codes starting with 2 mean success, 4 means the client made a mistake, and 5 means the server did. You can get most decisions right just from that.

It then picks out the success codes worth using, such as 201 for creation and 204 for a response with no content. The same treatment goes to the 4xx codes worth telling apart, including 401, 403, 404, and 409.

A dedicated section compares 422, 400, and 409, since those three cause the most debate. FastAPI uses 422 for validation, and the article explains when you should choose something different. You will leave with a short list of codes that covers nearly every real endpoint.

Before the exact code, a client reads the class.

**2xx** &mdash; it worked. **3xx** &mdash; look elsewhere. **4xx** &mdash; the caller must change a thing. **5xx** &mdash; the server must.

That first digit drives real action in code you didn't write: HTTP libraries retry 5xx and not 4xx, caches store 2xx, monitoring alerts on 5xx. A client's error handling branches on it before looking at anything else.

Returning 200 with `{"error": "not found"}` throws all of that away. each caller now has to parse your body to discover a thing the protocol had a field for, retries do the wrong thing. Your error rate looks like zero on each dashboard. Pick the right code and the protocol carries the meaning for you.


## The route's default, and overriding it

<code>status_code</code> on the decorator sets the default. A <code>Response</code> parameter lets one call differ.

```python-run
from fastapi import FastAPI, Response, status

app = FastAPI()
DB = {}

@app.put("/modules/{i}", status_code=status.HTTP_200_OK)
def upsert(i: int, response: Response):
    created = i not in DB
    DB[i] = {"id": i}
    if created:
        response.status_code = status.HTTP_201_CREATED
    return DB[i]

c = TestClient(app)
print("first  :", c.put("/modules/1").status_code, "<- created")
print("second :", c.put("/modules/1").status_code, "<- already existed")
```

## 204 carries nothing

The one rule with teeth. Declare it and return <code>None</code>; anything else produces a malformed response.

```python-run
from fastapi import FastAPI, status

app = FastAPI()
DB = {1: "Vectors"}

@app.delete("/modules/{i}", status_code=status.HTTP_204_NO_CONTENT)
def remove(i: int):
    DB.pop(i, None)
    return None

c = TestClient(app)
r = c.delete("/modules/1")
print("status      :", r.status_code)
print("body        :", repr(r.text), "<- empty, as 204 requires")
print("content-type:", r.headers.get("content-type"))
```

## The named constants

<code>fastapi.status</code> spells every code. Readable at the call site and autocompleted, which matters for the ones you use rarely.

```python-run
from fastapi import status

pairs = [
    ("HTTP_200_OK", status.HTTP_200_OK),
    ("HTTP_201_CREATED", status.HTTP_201_CREATED),
    ("HTTP_202_ACCEPTED", status.HTTP_202_ACCEPTED),
    ("HTTP_204_NO_CONTENT", status.HTTP_204_NO_CONTENT),
    ("HTTP_400_BAD_REQUEST", status.HTTP_400_BAD_REQUEST),
    ("HTTP_401_UNAUTHORIZED", status.HTTP_401_UNAUTHORIZED),
    ("HTTP_403_FORBIDDEN", status.HTTP_403_FORBIDDEN),
    ("HTTP_404_NOT_FOUND", status.HTTP_404_NOT_FOUND),
    ("HTTP_409_CONFLICT", status.HTTP_409_CONFLICT),
    ("HTTP_422_UNPROCESSABLE_ENTITY", status.HTTP_422_UNPROCESSABLE_ENTITY),
    ("HTTP_500_INTERNAL_SERVER_ERROR", status.HTTP_500_INTERNAL_SERVER_ERROR),
]
for name, value in pairs:
    print("%-32s %d" % (name, value))
```

## 401 and 403 are different questions

One means “I do not know who you are”, the other “I do, and no”. Clients act on the difference.

```python-run
from fastapi import FastAPI, Header, HTTPException, status
from typing import Optional

app = FastAPI()
USERS = {"tok-admin": "admin", "tok-reader": "reader"}

@app.delete("/modules/{i}")
def remove(i: int, authorization: Optional[str] = Header(default=None)):
    if authorization is None:
        raise HTTPException(status.HTTP_401_UNAUTHORIZED, "Sign in first",
                            headers={"WWW-Authenticate": "Bearer"})
    role = USERS.get(authorization.replace("Bearer ", ""))
    if role is None:
        raise HTTPException(status.HTTP_401_UNAUTHORIZED, "Unknown token")
    if role != "admin":
        raise HTTPException(status.HTTP_403_FORBIDDEN, "Admins only")
    return {"deleted": i}

c = TestClient(app)
def call(tok):
    h = {"authorization": "Bearer " + tok} if tok else {}
    r = c.request("DELETE", "/modules/1", headers=h)
    return r.status_code, r.json().get("detail")

print("no token   :", call(None))
print("bad token  :", call("nope"))
print("wrong role :", call("tok-reader"))
print("admin      :", call("tok-admin"))
```

## 409 for a conflict with current state

Not a validation failure and not a missing thing: the request was fine and the world disagrees.

```python-run
from fastapi import FastAPI, HTTPException, status
from pydantic import BaseModel

app = FastAPI()
SLUGS = {"vectors"}

class ModuleIn(BaseModel):
    slug: str

@app.post("/modules", status_code=201)
def create(body: ModuleIn):
    if body.slug in SLUGS:
        raise HTTPException(status.HTTP_409_CONFLICT,
                            "A module with slug %r already exists" % body.slug)
    SLUGS.add(body.slug)
    return {"slug": body.slug}

c = TestClient(app)
print("new      :", c.post("/modules", json={"slug": "norms"}).status_code)
r = c.post("/modules", json={"slug": "vectors"})
print("duplicate:", r.status_code, r.json()["detail"])
print()
print("422 would be wrong - the payload was perfectly valid.")
```

## Documenting the ones that are not 200

<code>responses=</code> puts the failure shapes in the schema, so a generated client knows what an error looks like.

```python-run
import json
from fastapi import FastAPI, HTTPException, status
from pydantic import BaseModel

app = FastAPI()

class ModuleOut(BaseModel):
    id: int

class Problem(BaseModel):
    detail: str

@app.get("/modules/{i}", response_model=ModuleOut,
         responses={404: {"model": Problem, "description": "No such module"},
                    410: {"model": Problem, "description": "Withdrawn"}})
def read(i: int):
    if i == 410:
        raise HTTPException(status.HTTP_410_GONE, "Withdrawn")
    if i != 1:
        raise HTTPException(status.HTTP_404_NOT_FOUND, "No such module")
    return {"id": 1}

c = TestClient(app)
print("ok  :", c.get("/modules/1").status_code)
print("gone:", c.get("/modules/410").status_code, c.get("/modules/410").json())
print()
print("documented responses:",
      sorted(app.openapi()["paths"]["/modules/{i}"]["get"]["responses"]))
```
## The 2xx ones worth using

**200 OK** for a good read or update that returns a thing.

**201 Created** when a thing new exists. Usually with a `Location` header pointing at it.

**202 Accepted** when you've taken the request but not finished it. A queued job. The body should say how to check on it.

**204 No Content** for a success with nothing to say. A delete, often.

204 has the one rule with teeth: **no body at all**. Declare `status_code=204` and return `None`. Returning a value makes a malformed response. Some clients will error on it while others silently skip the body, which is worse.

## The 4xx ones worth distinguishing

**400 Bad Request** &mdash; malformed in a way your own code found.

**401 Unauthorized** &mdash; badly named: it means *unauthenticated*. I don't know who you're. Should carry a `WWW-Authenticate` header.

**403 Forbidden** &mdash; I know who you're, and no.

**404 Not Found** &mdash; no such thing.

**409 Conflict** &mdash; the request was fine and conflicts with current state: a copy, a version mismatch, an action already taken.

**410 Gone** &mdash; it existed and on purpose doesn't any more. Rare. Handy when you want callers to stop asking.

**422 Unprocessable Entity** &mdash; well-formed and didn't fit the declared shape. FastAPI makes this on its own and you rarely raise it.

**429 Too Many Requests** &mdash; rate limited. Should carry `Retry-After`.

The 401/403 gap is the one most often merged. It's worth keeping. A client seeing 401 should prompt for credentials or refresh a token. One seeing 403 shouldn't. Retrying with the same identity will fail again. Merging them makes a login loop where there should be an error message.

The 404/403 choice has a security dim. Returning 403 for a resource that exists but isn't yours confirms it exists. For anything sensitive, 404 for both is the safer answer. on purpose. Always, or the timing gives it away anyway.

## 422 versus 400 versus 409

These three get confused, and the rule is about *who found the problem*.

**422** &mdash; check found it from your declared types and constraints. auto. You don't write it.

**400** &mdash; your code found the request was malformed in a way the schema couldn't express.

**409** &mdash; the request was fully valid and the current state makes it hopeless.

A copy slug is 409, not 422: nothing about the payload was wrong. The same payload would have succeeded a minute earlier.

## Setting them

`status_code=` on the decorator sets the route's default, and that default appears in the docs.

For one call to differ, declare a `Response` param and assign to `response.status_code`. That keeps output and the response model, unlike returning a `Response` object.

`HTTPException(status_code, detail)` raises one, and it accepts `headers=`. Which is how you attach `WWW-Authenticate` to a 401 or `Retry-After` to a 429.

Use the `status` module rather than bare ints. `status.HTTP_409_CONFLICT` is readable and autocompleted. `409` needs the reader to know it.

## Documenting the failures

`response_model` shows the success case only. all else is undocumented unless you say so:

```python
responses={404: {"model": Problem, "description": "No such module"}}
```

Now the schema shows the error shape. A made client can type it. Without this, consumers know they'll get *a thing* on failure and have to discover what by causing one.

Worth doing for the failures a caller is expected to handle. 404 on a lookup, 409 on a create. Not worth doing for each conceivable code.

## Mistakes people make

**200 with an error body.** The one that costs most. Retries, caches, monitoring and each client's error handling branch on the status class. A 200 tells all of them the call succeeded.

**A body on a 204.** Malformed. Some clients error, others silently skip it. This Is worse because it works until it doesn't.

**Merging 401 and 403.** A client seeing 401 re-authenticates. Seeing 403 it shouldn't. Merging them makes a login loop where there should be a message.

**422 for a missing resource.** The request was well-formed. Nothing with that id exists, which is 404.

**422 for a copy.** The payload was valid and would have worked a minute earlier. That is 409.

**500 for a caller's mistake.** If they could have avoided it, it's a 4xx. A 500 should mean your code failed, and should page somebody.

**Bare ints.** `409` needs the reader to know it. `status.HTTP_409_CONFLICT` doesn't, and your editor ends it.

## The header a status implies

a few codes are incomplete without a header. Omitting it makes a strictly-correct response in practice useless.

**401** should carry `WWW-Authenticate`, naming the scheme. Without it a client knows it must authenticate and not how.

**429** should carry `Retry-After`. Without it a client's only plan is guessing. This Often means retrying at once and making things worse.

**405** should carry `Allow`, listing the methods that do work.

**201** usually carries `Location`, pointing at what was created. A client doesn't have to make the URL itself.

`HTTPException` takes `headers=` for just this. It's the sort of detail that splits an API somebody enjoys using from one they merely handle.


## Choosing between 404 and 403

A choice with a security dim, worth making on purpose.

Returning 403 for a resource that exists but isn't yours confirms that it exists. For a sequential id that is an enumeration oracle. A caller can walk the range and learn how many records you've and which ids are real.

Returning 404 for both cases hides that, at the cost of a slightly less helpful message for a legitimate user who has truly lost access.

For anything sensitive - other users' data, private docs, anything under a permissions model - 404 for both is the safer default. For an inner API where enumeration tells an attacker nothing they don't already have, 403 is friendlier.

Whichever you choose, be steady. Returning 403 at times and 404 other times leaks just the data the 404 was meant to hide. Timing differences will give it away even if the status doesn't.

## Redirects, briefly

The 3xx codes come up less in an API than in a website, and two are worth recognising.

**307** preserves the method and body. **308** is its permanent equal. These are the ones FastAPI uses for the trailing-slash redirect. The reason it matters is that some clients still drop the body, turning a POST into an empty one.

**301** and **302** once allowed clients to change the method to GET on redirect. This Is why they're the wrong choice for anything that isn't a plain read.

If an API needs to move a resource permanently, 308 with a `Location` header is the honest answer. More often the better answer is to keep the old path working and doc the new one.

## The ones you will not write

Some codes exist and are made by infrastructure rather than by your handlers.

**502**, **503** and **504** come from a proxy or load balancer when your app is unreachable, overloaded or slow. Seeing them in production means the problem is in front of your code, not in it.

**413** may be returned by a reverse proxy before a request reaches you. This Is why an upload limit belongs there and in the handler.

Knowing which layer makes which saves time when a thing breaks: a 500 is yours, a 502 isn't.

## A closing thought

A status code is the smallest piece of an API and the one most consumed by machines.

each client library, cache, proxy, gateway and dashboard reads it. None of them read your response body. Returning the accurate one costs a keyword arg and buys correct action from all of them.

Returning 200 for all costs nothing to write and moves the work onto each caller, forever.


## A short reference

**Created** a thing: 201, with `Location`. **Deleted** a thing: 204, no body. **Queued** a thing: 202, with a way to check. **Read** a thing: 200.

Caller sent nonsense: **422** if check caught it, **400** if you did. Not signed in: **401** with `WWW-Authenticate`. Signed in, not allowed: **403** - or 404 if existence itself is sensitive. Not there: **404**. Conflicts with current state: **409**. Asking too often: **429** with `Retry-After`.

Your code failed: **500**, logged in full, returned as a plain message with an id.

## Summary

The class is what a client reads first. It drives retries, caching and alerting in code you didn't write. Returning 200 with an error body discards all of it.

201 for created, 204 for done-with-nothing-to-say and no body, 202 for accepted-but-not-finished. 401 for unauthenticated and 403 for not-allowed - they're other questions and clients act on the gap. 404 for missing, 409 for a valid request that conflicts with current state, 422 for a payload that didn't fit.

Set the route default with `status_code=`, vary it through a `Response` param, attach the headers a status implies. Doc the failures with `responses=`.

## Questions people ask

<strong>Which status code should a successful POST return?</strong> 201 Created when it makes a resource, ideally with a Location header. Use 200 when it only runs an action.

<strong>When do I use 204?</strong> For success with nothing to return, such as a DELETE. The response must carry no body.

<strong>What is the difference between 401 and 403?</strong> 401 means the caller is not authenticated, while 403 means they are authenticated but not allowed.

<strong>What is the difference between 400, 409, and 422?</strong> 422 is a validation failure, 409 is a conflict with current state such as a duplicate, and 400 is a general bad request.

<strong>How do I use constants instead of numbers?</strong> Import status from fastapi and write status.HTTP_201_CREATED.

<strong>Should I return 404 or 403 for a resource the user can't see?</strong> Return 404 if revealing that it exists would leak information, and 403 when the user is allowed to know it exists.

## A final note

Status codes are also a form of docs that no one has to read.

An endpoint returning 201 with a `Location` header has told a caller that a thing was created and where to find it, without a sentence of prose. One returning 200 with a body they must inspect has told them nothing. The prose now has to exist.
