title: Memoisation: caching with a dictionary
intro: How would you speed up a recursive function that recomputes the same values? What does functools.lru_cache do?

## The core idea

Memoisation caches results of function calls so repeated subproblems are computed once. It helps when inputs repeat and each result depends only on its arguments; a cache cannot fix an incorrect recurrence or excessive state space.

## Run it
The same recurrence three ways with call counts, then <code>cache_info()</code> showing the hit rate. Then the two conditions broken on purpose. An impure task and an unhashable input.

```python-run
from functools import lru_cache

import time

calls = {"plain": 0, "manual": 0}
cache = {}
counter = {"n": 0}

def fib_plain(n):
    calls["plain"] += 1
    return n if n < 2 else fib_plain(n - 1) + fib_plain(n - 2)

print("plain     :", fib_plain(22), "calls:", calls["plain"])
```

```python-run
from functools import lru_cache

import time

calls = {"plain": 0, "manual": 0}
cache = {}
counter = {"n": 0}

def fib_manual(n):
    calls["manual"] += 1
    if n in cache:
        return cache[n]                      # the whole optimisation
    cache[n] = n if n < 2 else fib_manual(n - 1) + fib_manual(n - 2)
    return cache[n]

print("manual memo:", fib_manual(60), "calls:", calls["manual"])
```

```python-run
from functools import lru_cache

import time

calls = {"plain": 0, "manual": 0}
cache = {}
counter = {"n": 0}

@lru_cache(maxsize=None)                     # the same thing, shipped
def fib_cached(n):
    return n if n < 2 else fib_cached(n - 1) + fib_cached(n - 2)

print("lru_cache  :", fib_cached(60), "|", fib_cached.cache_info())
```

```python-run
from functools import lru_cache

import time

calls = {"plain": 0, "manual": 0}
cache = {}
counter = {"n": 0}

@lru_cache(maxsize=None)
def impure():
    counter["n"] += 1
    return counter["n"]

print("impure     :", impure(), impure(), "<- cached, so unchanged")
```

```python-run
from functools import lru_cache

import time

calls = {"plain": 0, "manual": 0}
cache = {}
counter = {"n": 0}

@lru_cache(maxsize=None)
def total(numbers):
    return sum(numbers)

print("total      :", total((1,2,3)))
```

## The manual version, and why to know it
```python-run
def fib_manual(n, memo=None):
    if memo is None:
        memo = {}
    if n in memo:
        return memo[n]
    result = n if n < 2 else fib_manual(n-1, memo) + fib_manual(n-2, memo)
    memo[n] = result
    return result

print(fib_manual(30))
```
Note `memo=None` rather than `memo={}`. A mutable default input is created <strong>once, at task definition</strong>, and shared by each call that does not supply one. So yields leak between unrelated invocations. It happens to work for a pure task like Fibonacci and is a genuine bug broadly, and interviewers watch for it.

The manual version is worth knowing since it is what you write when the cache needs to be inspected, bounded by a custom rule, or shared by name between calls.

## When memoisation applies
Three conditions, and all three are needed:

<strong>The task is pure</strong> &mdash; same inputs always give the same yield, with no side effects. Memoising a task that reads a store or the clock returns stale answers.

<strong>Inputs are hashable.</strong> Lists and dictionaries cannot be cache keys. Turn to tuples or frozensets.

<strong>Subproblems repeat.</strong> Caching a task called once per distinct input adds cost for nothing.

That third point is the one that separates memoisation from a general speed-up. It is just the "overlapping subproblems" condition of dynamic programming. Memoisation <em>is</em> top-down dynamic programming.

|Problem|Overlapping subproblems|Memoisation helps|
|---|---|---|
|Fibonacci|Heavily|Enormously|
|Edit distance|Yes|Yes|
|Merge sort|No &mdash; independent halves|No|
|Binary search|No|No|
|Grid paths|Yes|Yes|

## Why it works at all
Naive recursion on overlapping subproblems recomputes the same vals an rapid count of times. Memoisation does not make each call faster. It makes the repeated ones disappear. So the work drops to the count of <em>distinct</em> subproblems.

This is dynamic programming from the top down. The bottom-up table computes the same vals in a loop with no call stack. Same cost, and see <a href="../dsa/dynamic_programming.html">dynamic programming</a> for both ways side by side.

## The two conditions
<p><strong>The task must be pure.</strong> Same inputs, same answer, no side effects. Caching a task that reads a file or the clock returns a stale answer for good. And the bug looks like the data being wrong rather than the cache being wrong.</p>

<p><strong>The inputs must be hashable.</strong> They turn dictionary keys, so a list input raises. That is why cached tasks take tuples where you might expect lists. The constraint comes from the cache, not the algorithm.</p>

## What lru_cache adds
<p><code>@lru_cache(maxsize=None)</code> is an unbounded dictionary and is what you want for a recursion. A finite <code>maxsize</code> evicts least-recently-used entries, which matters when the key space is large and unbounded. An in-memory cache with no eviction is a memory leak with good manners.</p>

It too gives you <code>cache_info()</code> for hits and misses, and <code>cache_clear()</code>. <code>functools.cache</code> is the unbounded alias added in 3.9. Mention that a manual dict is fine and the decorator is what you would really ship.

## `lru_cache` in practice
```python-run
from functools import lru_cache, cache

@lru_cache(maxsize=128)          # bounded: evicts least recently used
def expensive(x): ...

@cache                            # Python 3.9+: unbounded, same as maxsize=None
def expensive(x): ...

print(expensive.cache_info())            # hits, misses, maxsize, currsize
print(expensive.cache_clear())
```
`cache_info()` is the nearly useful part: it tells you whether the cache is earning its place. A hit rate near zero means the inputs rarely repeat and the decorator is pure cost.

Four constraints worth knowing:

<strong>Inputs must be hashable.</strong> `lru_cache` keys on the input tuple. So a list input raises `TypeError`.

<strong>Keyword and positional inputs key else.</strong> `f(1)` and `f(x=1)` are separate cache entries. This doubles memory and halves the hit rate if callers are inconsistent.

<strong>`maxsize=None` never evicts.</strong> On unbounded input that is a memory leak. A bounded size is safer in long-running processes.

<strong>Ways keep `self` in the key,</strong> so instances are held alive by the cache. A real source of leaks. `cachetools` or an explicit per-instance dictionary avoids it.

## Memoisation against tabulation
Two ways to write the same dynamic programming solution.

|&nbsp;|Memoisation (top-down)|Tabulation (bottom-up)|
|---|---|---|
|Style|Recursive plus a cache|Iterative, fills a table|
|Computes|Only the states reached|All states|
|Recursion limit|Yes &mdash; about 1,000 frames|No|
|Space optimisation|Harder|Often easy|
|Easier to write|Usually|Usually not|

Memoisation's edge is that just the subproblems really needed are computed &mdash; which matters when the state space is large and sparsely visited. Tabulation's gains are no recursion limit and easier space reduction.

Write memoisation first, since the recurrence is the part you have to think about. Turn to tabulation if you hit Python's recursion limit or need the O(1) space version.

## Where it is used beyond interviews
- <strong>Web response caching.</strong> Keyed on the request, with a TTL.
- <strong>Store query caching.</strong> Same query, same yield, until the data changes.
- <strong>Costly pure steps</strong> &mdash; parsing, compiling regular terms (`re.compile` is it cached), rendering templates.
- <strong>Property caching</strong> &mdash; `functools.cached_property` computes once per instance.
- <strong>API clients</strong> caching immutable lookups such as currency codes or country lists.

And the counterpart: <strong>invalidation is the hard part</strong>. A cache with no invalidation plan in time serves stale data, and "when does this turn wrong?" is the question to ask before adding one. For pure tasks the answer is never, which is why memoisation is the easy case.
