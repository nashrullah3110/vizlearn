title: Top k frequent elements
intro: Return the k most frequent elements in a list.

## The core idea

Top-k frequency asks for the k values with the largest counts. Counting is linear; then use a size-k heap for O(n log k), bucket grouping for O(n), or sorting when simplicity matters more than the bound.

## Run it
Sorting everything against a heap of size k, at 200,000 items.

```python-run
import heapq, random, time
from collections import Counter

random.seed(7)
words = [random.randint(0, 40_000) for _ in range(200_000)]
counts = Counter(words)
k = 10
print("n =", len(words), " distinct =", len(counts), " k =", k)

# 1. sort everything, take a slice: O(n log n)
t0 = time.perf_counter()
by_sort = [w for w, _ in sorted(counts.items(), key=lambda kv: -kv[1])[:k]]
a = time.perf_counter() - t0

# 2. a heap of size k: O(n log k)
t0 = time.perf_counter()
by_heap = [w for w, _ in heapq.nlargest(k, counts.items(), key=lambda kv: kv[1])]
b = time.perf_counter() - t0
```

And the O(n) version, which removes the log factor without necessarily winning the clock.

```python-run
import heapq, random, time
from collections import Counter

random.seed(7)
words = [random.randint(0, 40_000) for _ in range(200_000)]
counts = Counter(words)
k = 10

# 3. bucket by count: O(n), because a count cannot exceed n
def by_buckets(counts, k):
    if not counts:
        return []
    buckets = [[] for _ in range(max(counts.values()) + 1)]
    for key, c in counts.items():
        buckets[c].append(key)
    out = []
    for c in range(len(buckets) - 1, 0, -1):
        for key in buckets[c]:
            out.append(key)
            if len(out) == k:
                return out
    return out

t0 = time.perf_counter()
by_bucket = by_buckets(counts, k)
c = time.perf_counter() - t0

by_sort = [w for w, _ in sorted(counts.items(), key=lambda kv: -kv[1])[:k]]
by_heap = [w for w, _ in heapq.nlargest(k, counts.items(), key=lambda kv: kv[1])]
print("all three pick the same counts:",
      sorted(counts[w] for w in by_sort)
      == sorted(counts[w] for w in by_heap)
      == sorted(counts[w] for w in by_bucket))
print(f"  buckets     {c*1000:7.1f} ms   O(n), level with the heap at this size")
```

Where the log k actually comes from: how little of the input ever enters the heap.

```python-run
import heapq, random, time
from collections import Counter

random.seed(7)
words = [random.randint(0, 40_000) for _ in range(200_000)]
counts = Counter(words)
k = 10

# Where the log k actually comes from: how little ever enters the heap.
def top_k(pairs, k):
    heap = []
    entered = skipped = 0
    for key, cnt in pairs:
        if len(heap) < k:
            heapq.heappush(heap, (cnt, key)); entered += 1
        elif cnt > heap[0][0]:
            heapq.heapreplace(heap, (cnt, key)); entered += 1
        else:
            skipped += 1                # rejected by ONE comparison
    return sorted(heap, reverse=True), entered, skipped

kept, entered, skipped = top_k(counts.items(), k)
print()
print(f"of {len(counts):,} distinct values:")
print(f"  {entered:,} ever entered the heap")
print(f"  {skipped:,} were rejected by a single comparison against the root")
print(f"  the heap never held more than {k}")
```

## Why the root is the whole trick
<p>A min-heap of size k has a useful property: its root is the <em>weakest</em> member of the best k seen so far. So the question "could this candidate belong in the answer?" is one comparison against the root, and if the answer is no the candidate is discarded without ever entering the heap.</p><p>The editor below counts it: with 200,000 items and k = 10, only 136 of them ever touched the heap. The other 199,864 cost one comparison each. That is where the log k comes from &mdash; not from clever bookkeeping, but from rejecting almost everything cheaply.</p>

## The three answers, and when each is right
<p><strong>Heap of size k</strong> &mdash; O(n log k). The default answer, and the one to give first. <code>heapq.nlargest(k, ...)</code> is this, already written.</p><p><strong>Full sort</strong> &mdash; O(n log n). Better when k is a large fraction of n, because then log k is log n and the heap is paying overhead for nothing. Also better when n is small enough that constants dominate, which is more often than the complexity suggests: CPython's sort is C and a heap loop is Python.</p><p><strong>Bucket sort</strong> &mdash; O(n). Available because the counts are bounded: a count cannot exceed n, so you can bucket by count and read the buckets from the top with no comparisons at all. It is the answer an interviewer is fishing for when they ask "can you do better than n log k?" &mdash; though note what the editor measures: it comes out level with <code>nlargest</code> rather than ahead, because removing a log factor does not beat a C implementation at this size. The complexity win is real; the wall-clock win needs a much larger n or k.</p>

## Quickselect, and why it is usually the wrong answer to give
<p>There is an O(n) average-case option: partition around a pivot like quicksort but recurse into one side only, stopping when the pivot lands at position k. It is genuinely O(n) expected and O(n&sup2;) worst case, and <code>numpy.partition</code> implements it.</p><p>Mentioning it is good; reaching for it first is usually not. It mutates the input, it does not stream, the worst case needs median-of-medians to fix, and the constant factor means it rarely beats <code>nlargest</code> in practice. The strong answer is the heap, with quickselect named as the theoretical improvement.</p>

## What the question is testing
<p>Whether you notice that the answer set is bounded. A great many problems say "the best k" and the instinct is to sort everything and take a slice &mdash; which computes a total order nobody asked for. Keeping only k candidates and rejecting against the weakest of them is the reusable move, and it reappears in streaming top-n, nearest-neighbour search and leaderboards.</p><p>The second thing is whether you ask about ties. "The k most frequent" is ambiguous when counts are equal, and saying so before writing is the difference between a correct answer and a complete one.</p>

## Edge cases to raise
<p>Volunteering these is most of what separates a correct answer from a good one.</p>

<p><strong>Ties.</strong> "The k most frequent" is ambiguous when counts are equal. Ask, or state the tie-break - and note that the tuple in the heap already picks one for you, probably not the one you meant.</p>

<p><strong>k larger than the number of distinct values.</strong> <code>nlargest</code> returns everything; a hand-rolled heap should too, rather than raising.</p>

<p><strong>k = 0.</strong> An empty answer, and a loop that assumes the heap is non-empty will index a root that is not there.</p>
