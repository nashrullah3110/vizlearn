title: Sliding window maximum
intro: Return the maximum of every window of size k as it slides along the array.

## The problem

Given an array and a window size k, report the maximum of every window as it slides one position at a time.

`[1, 3, -1, -3, 5, 3, 6, 7]` with k = 3:

|Window|Contents|Max|
|---|---|---|
|0&ndash;2|`1, 3, -1`|3|
|1&ndash;3|`3, -1, -3`|3|
|2&ndash;4|`-1, -3, 5`|5|
|3&ndash;5|`-3, 5, 3`|5|
|4&ndash;6|`5, 3, 6`|6|
|5&ndash;7|`3, 6, 7`|7|

Output: `[3, 3, 5, 5, 6, 7]`.

Recomputing `max()` per window is O(nk) &mdash; correct and, for large k, slow. The target is O(n), and the tool is a <strong>monotonic deque</strong>.


## Run it

The deque version with its total push and pop counts against the recompute-every-window version, on an input sized to make O(n) against O(n&middot;k) unmistakable.

```python-run
# Sliding window maximum: a deque of indices with decreasing values.
from collections import deque
import time

def window_max(values, k, show=False):
    dq = deque()                             # indices, values decreasing
    out, pushes, pops = [], 0, 0
    for i, v in enumerate(values):
        while dq and values[dq[-1]] <= v:    # smaller behind: can never win
            dq.pop()
            pops += 1
        dq.append(i)
        pushes += 1
        if dq[0] <= i - k:                   # the front has expired
            dq.popleft()
            pops += 1
        if i >= k - 1:
            out.append(values[dq[0]])        # the front IS the maximum
            if show:
                print(f"    window {values[i-k+1:i+1]} -> max {values[dq[0]]}")
    return out, pushes, pops


def recompute(values, k):
    out, comparisons = [], 0
    for i in range(len(values) - k + 1):
        window = values[i:i + k]
        comparisons += len(window)
        out.append(max(window))
    return out, comparisons


values, k = [1, 3, -1, -3, 5, 3, 6, 7], 3
print(f"values {values}, k={k}")
answer, pushes, pops = window_max(values, k, show=True)
print("  maxima:", answer)
print(f"  {pushes} pushes, {pops} pops for {len(values)} elements")
print("  recompute agrees:", recompute(values, k)[0] == answer)

# --- how the two costs diverge as k grows ------------------------------
import random
random.seed(9)
big = [random.randint(0, 1000) for _ in range(15_000)]
print()
print(f"n = {len(big):,}")
for k in (10, 100, 400):
    start = time.perf_counter()
    a, pushes, pops = window_max(big, k)
    deque_time = time.perf_counter() - start

    start = time.perf_counter()
    b, comparisons = recompute(big, k)
    naive_time = time.perf_counter() - start

    print(f"  k={k:>4}: deque {deque_time:.3f}s ({pushes + pops:,} ops)   "
          f"recompute {naive_time:.3f}s ({comparisons:,} ops)   same: {a == b}")

print()
print("The deque's operation count barely moves with k. The naive one is")
print("proportional to it, because every window is rebuilt from scratch.")
```
## Why a heap is not quite enough

The natural first thought is a max-heap. It gives the maximum in O(1), and removing the element that just left the window is the problem &mdash; a heap cannot delete an arbitrary element efficiently.

The usual workaround is <strong>lazy deletion</strong>: push `(value, index)` and, before reading the top, discard entries whose index has fallen out of the window.

```python-run
import heapq

def max_sliding_window_heap(nums, k):
    heap = []                              # (-value, index)
    out = []
    for i, n in enumerate(nums):
        heapq.heappush(heap, (-n, i))
        while heap[0][1] <= i - k:         # stale: outside the window
            heapq.heappop(heap)
        if i >= k - 1:
            out.append(-heap[0][0])
    return out

print(max_sliding_window_heap([1,3,-1,-3,5,3,6,7], 3))
```
O(n log n), and the heap can grow to n entries. Correct, and worth stating as the intermediate step &mdash; then improving on it.

## The monotonic deque

Keep a deque of <em>indices</em> whose values are in <strong>decreasing</strong> order. The front is always the maximum of the current window.

Two rules, applied per element:

<strong>Evict from the front</strong> if the index there has slid out of the window.
<strong>Evict from the back</strong> while the value there is less than or equal to the incoming value &mdash; those elements can never be a maximum again, because the newcomer is at least as large and stays in the window longer.

```python-run
from collections import deque

def max_sliding_window(nums, k):
    dq = deque()                            # indices, values decreasing
    out = []

    for i, n in enumerate(nums):
        while dq and dq[0] <= i - k:        # front is out of the window
            dq.popleft()
        while dq and nums[dq[-1]] <= n:     # back is dominated
            dq.pop()
        dq.append(i)
        if i >= k - 1:
            out.append(nums[dq[0]])

    return out

print(max_sliding_window([1,3,-1,-3,5,3,6,7], 3))
```
O(n) time &mdash; each index is appended once and popped at most once &mdash; and O(k) space, since the deque never holds more than one window's worth of indices.

The second rule is the one that needs justifying, and the justification is short: if a later element is at least as large as an earlier one, the earlier one is <strong>dominated</strong>. It will leave the window first and it is not bigger, so no future window will ever report it as the maximum. Discarding it loses nothing.

<strong>Store indices, not values.</strong> The front-eviction rule needs to know <em>when</em> an element entered, and values alone cannot tell you that.

## Tracing it

`[1, 3, -1, -3, 5, 3, 6, 7]`, k = 3. The deque is shown as values for readability:

|i|num|After back-eviction|Deque|Output|
|---|---|---|---|---|
|0|1|&mdash;|`[1]`|&mdash;|
|1|3|popped 1|`[3]`|&mdash;|
|2|&minus;1|&mdash;|`[3, -1]`|<strong>3</strong>|
|3|&minus;3|&mdash;|`[3, -1, -3]`|<strong>3</strong>|
|4|5|popped &minus;3, &minus;1, 3|`[5]`|<strong>5</strong>|
|5|3|&mdash;|`[5, 3]`|<strong>5</strong>|
|6|6|popped 3, 5|`[6]`|<strong>6</strong>|
|7|7|popped 6|`[7]`|<strong>7</strong>|

At i = 4 three elements are discarded at once, and the total number of pops across the whole run is still bounded by n &mdash; which is the amortisation argument that makes the nested `while` loops linear.

## The observation that does the work

If <code>a[j]</code> comes before <code>a[i]</code> and <code>a[j] &le; a[i]</code>, then <code>a[j]</code> can never be the maximum of any future window &mdash; every window containing it from now on also contains the bigger, later <code>a[i]</code>. So it can be thrown away the moment <code>a[i]</code> arrives.

What survives is a decreasing sequence, and its front is the maximum of the current window by construction. No scan is ever needed.

## Why indices rather than values

The front must be discarded once it falls out of the window, and that needs its position. Storing values leaves no way to tell an expired maximum from a current one.

The expiry check is <code>dq[0] &lt;= i - k</code> &mdash; the front is older than the window's left edge. This is the other place an off-by-one lives, and it is worth writing out the first window's indices to check it.

## Why it is O(n), not O(n·k)

The inner <code>while</code> can pop several entries in one iteration, which looks quadratic. But each index is pushed exactly once and popped at most once across the entire run, so the total pops are bounded by n.

The alternatives are worth naming: recomputing <code>max</code> per window is O(n&middot;k), and a heap is O(n&nbsp;log&nbsp;k) and needs lazy deletion because you cannot remove an arbitrary element. The deque beats both.

## Details that matter

<strong>`<=` or `<` in the back-eviction?</strong> Both give correct maxima. Using `<=` discards equal values and keeps the deque smaller; using `<` retains duplicates, which matters only if you need to know how many copies of the maximum are present. For this problem, `<=`.

<strong>Why `if i >= k - 1`?</strong> The first complete window ends at index k&minus;1. Emitting earlier reports maxima of partial windows &mdash; which is sometimes the requirement, so it is worth confirming.

<strong>The output length</strong> is `n - k + 1`. Checking that is a fast way to catch off-by-one errors.

<strong>What if k > n?</strong> There is no complete window. Return an empty list, or the maximum of everything &mdash; ask rather than guess.

<strong>What if k = 1?</strong> The output is the input, and the code handles it: each element evicts its predecessor immediately.

## The pattern beyond this problem

A monotonic deque or stack applies whenever a problem asks for an extreme value over a moving range, or for the "next greater/smaller" element.

|Problem|Structure|Order|
|---|---|---|
|Sliding window maximum|Deque|Decreasing|
|Sliding window minimum|Deque|Increasing|
|Next greater element|Stack|Decreasing|
|Daily temperatures|Stack|Decreasing|
|Largest rectangle in histogram|Stack|Increasing|
|Trapping rain water|Stack|Decreasing|
|Shortest subarray with sum &ge; k (with negatives)|Deque|Increasing prefix sums|
|Jump game with a bounded jump|Deque|Decreasing DP values|

The shared shape: <strong>maintain a structure in which elements that can never again be the answer are discarded immediately.</strong> Once that is the framing, deciding which side to evict from and in which order follows from the specific question.

<strong>Constrained-DP problems</strong> are where this earns the most. "Maximum sum of a subsequence with no two elements more than k apart" is a DP whose recurrence needs a window maximum of previous states &mdash; the deque turns O(nk) into O(n).

## Alternatives worth naming

<strong>Sparse table or segment tree.</strong> O(n log n) preprocessing and O(1) or O(log n) per query. Overkill here, since the windows are contiguous and only slide forward, and the right answer when queries are arbitrary ranges instead.

<strong>Two-pass block partitioning.</strong> Split the array into blocks of size k, compute prefix maxima within each block from the left and suffix maxima from the right, and every window's maximum is the max of two precomputed values. O(n) time, O(n) space, and no deque &mdash; an elegant answer that surprises interviewers.

<strong>`max()` per window.</strong> O(nk), and genuinely the right choice when k is small and clarity matters.

## What it is testing

<strong>Do you get past O(nk)?</strong> Naming the naive approach and its cost is the correct opening; stopping there is not.

<strong>Can you justify the back-eviction?</strong> "A smaller element that leaves the window earlier can never be a maximum again" is the sentence the interviewer wants to hear.

<strong>Do you store indices?</strong> Storing values makes window expiry undetectable.

<strong>Do you see why nested `while` loops are still O(n)?</strong> Each index is pushed once and popped once.

<strong>Do you handle the output offset?</strong> Emitting only from index k&minus;1 onwards, and knowing the output has `n - k + 1` entries.

<strong>Do you recognise the family?</strong> Sliding-window minimum, next-greater-element and histogram problems all use the same structure.

## Recap in one screen

- Keep a deque of <em>indices</em> whose values decrease; the front is the window maximum.
- Evict from the front when the index expires, and from the back while the incoming value dominates.
- Each index enters and leaves once, so the nested loops are O(n) overall; space is O(k).
- Start emitting at index k&minus;1; the output length is `n - k + 1`.
- The same monotonic structure solves next-greater-element, daily temperatures and histogram rectangles.
