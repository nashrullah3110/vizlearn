title: What does slicing a string cost?
intro: What does s[2:6] cost, and is it a view or a copy?

## The answer

`s[a:b]` <strong>copies</strong> the selected characters into a new string. It costs O(b &minus; a) time and the same in memory.

Python strings are immutable, and slicing does not create a lightweight view onto the original &mdash; it allocates a new object and copies the bytes. Understanding that is the difference between code that scales and code that quietly becomes quadratic.

```python-run
s = "hello world"
print(s[0:5])        # 'hello'  -- a new 5-character string
print(s[:])          # returns s itself: an identical immutable object needs no copy
print(s[::2])        # 'hlowrd' -- a copy, with a step
print(s[::-1])       # 'dlrow olleh' -- reversal, O(n)
```
`s[:]` is the one exception, and it is an implementation optimisation rather than a rule to depend on: because the string is immutable, a full-slice copy can safely return the original object.

|Operation|Cost|
|---|---|
|`s[i]`|O(1) &mdash; single character|
|`s[a:b]`|O(b &minus; a)|
|`s[:]`|O(1) in CPython &mdash; returns the same object|
|`s[::-1]`|O(n)|
|`len(s)`|O(1) &mdash; stored, not counted|
|`s in t`|O(n &middot; m) worst case|
|`s + t`|O(n + m) &mdash; a new string|


## Run it

The same scan written twice &mdash; once slicing on every iteration, once carrying indices &mdash; timed at three sizes so the quadratic separates from the linear in front of you.

```python-run
import time

s = "algorithms"
part = s[2:6]
buf = memoryview(b"algorithms")

def peel_with_slices(text):
    """Walk the string by chopping the front off. Copies the rest each time."""
    n = 0
    while text:
        _first = text[0]
        text = text[1:]          # copies len(text) - 1 characters. Every time.
        n += 1
    return n

print("slicing off the front:", peel_with_slices("algorithms"))
```

```python-run
import time

s = "algorithms"
part = s[2:6]
buf = memoryview(b"algorithms")

def walk_with_index(text):
    """The same walk, carrying an index. Nothing is copied at all."""
    n = 0
    i = 0
    while i < len(text):
        _first = text[i]
        i += 1
        n += 1
    return n

print("moving an index      :", walk_with_index("algorithms"))
```
## Where it becomes quadratic

The classic failure is slicing inside a loop:

```python-run
def process_naive(s):
    result = []
    while s:
        result.append(s[0])
        s = s[1:]              # copies the ENTIRE remainder, every time
    return result

print("naive done:", process_naive("abcabcabc"))
```
For a string of length n, the copies total n + (n&minus;1) + (n&minus;2) + … = <strong>O(n²)</strong>. On 100,000 characters that is five billion character copies, and it looks like a perfectly ordinary loop.

The fix is to move an index rather than reslicing:

```python-run
def process_fast(s):
    return [s[i] for i in range(len(s))]      # or just list(s)

print("fast done:", process_fast("abcabcabc"))
```
The same trap appears in recursion, which is how it usually reaches production:

```python-run
def is_palindrome_slow(s):
    if len(s) <= 1:
        return True
    return s[0] == s[-1] and is_palindrome_slow(s[1:-1])   # O(n) copy per call

print(is_palindrome_slow("racecar"), is_palindrome_slow("hello"))
```
O(n²) because each of the n/2 recursive calls copies the string. Passing indices instead keeps it O(n):

```python-run
def is_palindrome_fast(s, lo=0, hi=None):
    hi = len(s) - 1 if hi is None else hi
    while lo < hi:
        if s[lo] != s[hi]:
            return False
        lo, hi = lo + 1, hi - 1
    return True

print(is_palindrome_fast("racecar"), is_palindrome_fast("hello"))
```
|Pattern|Complexity|Fix|
|---|---|---|
|`s = s[1:]` in a loop|O(n&sup2;)|Move an index|
|`f(s[1:])` recursively|O(n&sup2;)|Pass indices|
|`s += x` in a loop|O(n&sup2;)|Build a list, then `"".join`|
|Slicing to compare prefixes|O(k) per check|`s.startswith(prefix)`|
|Slicing to test a substring|O(k) per check|`x in s`|

`startswith` deserves the emphasis. `s[:len(p)] == p` allocates a copy before comparing; `s.startswith(p)` compares in place and short-circuits on the first mismatch. Same result, no allocation.

## Copy, not view

Some languages hand you a slice that points into the original buffer, so taking one is O(1). Python does not: <code>s[2:6]</code> allocates a new string object and memcpys four characters into it. The cost is proportional to the slice, not to the original.

You can prove it from the interpreter: the id differs, and mutating is impossible anyway, so there is no aliasing to observe. What you can measure is the time, which is what the editor below does.

## Where it actually hurts

One slice costs nothing worth thinking about. The problem is the shape where a slice is taken per iteration &mdash; checking every substring, or peeling a character off the front:

<p><code>while s: first, s = s[0], s[1:]</code></p>

Each iteration copies the entire remainder, so an O(n) walk becomes O(n&sup2;). The same bug appears in recursive solutions that pass <code>s[1:]</code> down: correct, elegant, and quadratic.

## What to do instead

Carry indices. Every algorithm on this track that scans text &mdash; two pointers, sliding window, KMP &mdash; keeps <code>i</code> and <code>j</code> into the original string and never slices inside the loop. Slice once at the end, when you need the answer as a string.

If you genuinely need a zero-copy view over a large buffer, that exists, but only for bytes: <code>memoryview(b)</code> slices in O(1) and shares the underlying memory.

## Avoiding the copy entirely

<strong>`memoryview`</strong> gives a genuine zero-copy view &mdash; over `bytes`, not `str`:

```python-run
data = b"hello world" * 1000
view = memoryview(data)
chunk = view[100:200]          # no copy: a view onto the same buffer
print(bytes(chunk))                    # copies, only when you ask
```
This is why binary protocol parsers work on `bytes` rather than `str`: slicing a `memoryview` is O(1) regardless of size. There is no `str` equivalent, because Unicode strings may use variable-width internal representations, so a character offset is not always a fixed byte offset.

<strong>`str.find` with a start offset</strong> searches a region without slicing it:

```python-run
s = "abcabcabcabc"

pos = 0
while (pos := s.find(",", pos)) != -1:     # no copies at all
    ...
    pos += 1

print("scanned to pos:", pos)
```
Compare with `s[pos:].find(",")`, which copies the remainder on every iteration &mdash; the same quadratic trap in a less obvious costume.

<strong>`re` module functions</strong> accept `pos` and `endpos` on compiled patterns, so matching within a region needs no slice either.

<strong>`io.StringIO`</strong> for incremental building, and `"".join(parts)` for assembling many pieces &mdash; one allocation instead of n.

## How Python stores strings

Since version 3.3, CPython chooses the narrowest representation that fits the string's characters:

|Content|Bytes per character|
|---|---|
|ASCII / Latin-1 only|1|
|Basic Multilingual Plane|2|
|Anything above U+FFFF|4|

So a 1,000-character ASCII string uses about 1KB plus roughly 50 bytes of header, while one emoji anywhere in it forces 4 bytes per character &mdash; the same text becomes four times larger. That occasionally explains a surprising memory measurement.

Consequences worth knowing:

<strong>Indexing is O(1)</strong> because the width is fixed per string, so the byte offset is a multiplication.
<strong>`len()` is O(1)</strong> &mdash; it returns a stored count of characters, not bytes.
<strong>Slicing must copy</strong>, since a view would need to carry both the buffer and its width, and immutability makes sharing unnecessary in the common cases.

## Questions people ask

<strong>Is `s[:]` free?</strong> In CPython it returns the same object, because immutability makes copying pointless. Do not build an algorithm on that guarantee.

<strong>Is slicing a list the same?</strong> Yes for cost &mdash; O(k) and a new list &mdash; but the copy is <em>shallow</em>: the new list holds the same element references.

<strong>Does negative indexing cost more?</strong> No. `s[-1]` is `s[len(s)-1]`, computed arithmetically.

<strong>What about out-of-range slices?</strong> They clamp silently. `"abc"[0:100]` is `"abc"` &mdash; no error, unlike indexing.

<strong>Is `s[::-1]` the fastest reversal?</strong> Yes for strings; `reversed(s)` gives a lazy iterator when you do not need the whole reversed string materialised.

<strong>How do I slice without copying?</strong> Convert to `bytes` and use `memoryview`, or work with indices and functions that accept offsets.

## Recap in one screen

- `s[a:b]` allocates and copies: O(b &minus; a) in time and memory, not a view.
- `s = s[1:]` in a loop, or `f(s[1:])` in recursion, is O(n&sup2;) &mdash; pass indices instead.
- Use `startswith`, `in`, and `find(sub, pos)` rather than slicing to inspect a region.
- `memoryview` over `bytes` gives true O(1) slicing; there is no `str` equivalent.
- CPython stores strings at 1, 2 or 4 bytes per character, so `len` and indexing are O(1).
