title: Two Sum
intro: Find two numbers in a list that add to a target. Return their indices.

## The core idea

Two Sum returns indices of two values whose sum equals a target. A hash map stores earlier values so each new value can check its complement in expected O(1) time, while preserving original indices.

## Run it
All three approaches with their operation counts, then the self-pairing bug demonstrated by moving one line, and finally a size where the quadratic version stops being viable.

```python-run
import time

values, target = [2, 7, 11, 15, 3], 18
big = list(range(1_800))

def brute_force(values, target):
    checks = 0
    for i in range(len(values)):
        for j in range(i + 1, len(values)):
            checks += 1
            if values[i] + values[j] == target:
                return (i, j), checks
    return None, checks

print("brute force :", brute_force([2,7,11,15,3], 18))
```

```python-run
import time

values, target = [2, 7, 11, 15, 3], 18
big = list(range(1_800))

def one_pass(values, target):
    seen = {}                                  # value -> index
    checks = 0
    for i, v in enumerate(values):
        checks += 1
        if target - v in seen:                 # CHECK before you store
            return (seen[target - v], i), checks
        seen[v] = i
    return None, checks

print("one pass    :", one_pass([2,7,11,15,3], 18))
```

```python-run
import time

values, target = [2, 7, 11, 15, 3], 18
big = list(range(1_800))

def two_pointers(sorted_values, target):
    """O(1) space - but only valid if the input is sorted."""
    lo, hi, checks = 0, len(sorted_values) - 1, 0
    while lo < hi:
        checks += 1
        total = sorted_values[lo] + sorted_values[hi]
        if total == target:
            return (lo, hi), checks
        if total < target:
            lo += 1
        else:
            hi -= 1
    return None, checks

print("two pointers:", two_pointers(sorted([2,7,11,15,3]), 18), "(indices into the SORTED copy)")
```

## The brute force, and why to mention it
```python-run
def two_sum_brute(nums, target):
    for i in range(len(nums)):
        for j in range(i + 1, len(nums)):
            if nums[i] + nums[j] == target:
                return [i, j]

print(two_sum_brute([2,7,11,15], 9))
```
O(n²) time, O(1) space. State it, give the complexity, and move on to the improvement &mdash; that sequence demonstrates you can see the baseline and improve on it, which is part of what is being assessed.

Do not spend time writing it out unless asked.

## The hash-map solution
```python-run
def two_sum(nums, target):
    seen = {}                                # value -> index
    for i, x in enumerate(nums):
        if target - x in seen:
            return [seen[target - x], i]
        seen[x] = i                          # store AFTER checking
    return []

print(two_sum([2,7,11,15], 9), two_sum([3,2,4], 6))
```
One pass, O(n) time and O(n) space.

The insight worth stating out loud: <strong>"for each number, I need to know whether its complement has already appeared" &mdash; that is a lookup, and a dictionary makes lookups constant time.</strong> The nested loop was re-scanning to answer a question a dictionary answers immediately.

Two details that matter:

<strong>Check before inserting.</strong> If you store `x` first and then look for `target - x`, an input like `nums = [3, 5], target = 6` matches 3 against itself and returns `[0, 0]`.

<strong>One pass is enough.</strong> A two-pass version &mdash; build the whole dictionary, then scan &mdash; also works and needs the same self-pairing guard. The one-pass version is cleaner and is what interviewers expect.

## Turning a search into a lookup
The nested-loop version asks "does any later element pair with this one?", which is n&sup2;/2 comparisons. The insight is to invert it: you know exactly which number you need, so the question becomes "have I already seen <code>target - value</code>?" &mdash; and that is a dictionary lookup, not a search.

This is the same move as grouping anagrams by a key. Whenever a problem asks you to find a pair with a known relationship, look for the version where one member is computed rather than searched for.

## The two orderings that matter
Check <em>before</em> you store. Storing first lets an element pair with itself when <code>target</code> is exactly twice it &mdash; <code>[3]</code> with target 6 returns <code>(0, 0)</code>, which is wrong.

Store <code>value &rarr; index</code>, not the reverse. The values are what you look up; the indices are what you return. Duplicates overwrite, which is fine because any one valid pair is usually acceptable &mdash; ask, if the question does not say.

## When to use two pointers instead
If the input is already sorted, converging pointers solve it in O(n) time and <strong>O(1)</strong> space: too small means move the left pointer right, too big means move the right pointer left. That is strictly better on memory.

If it is not sorted, sorting to enable that is O(n&nbsp;log&nbsp;n) &mdash; worse than the dictionary, and it destroys the original indices, which the question usually asks for. Say why you are choosing the dictionary; that reasoning is most of the mark.

## Walking through an example
`nums = [2, 7, 11, 15]`, `target = 9`:

|i|x|Need|In `seen`?|Action|
|---|---|---|---|---|
|0|2|7|No|`seen = {2: 0}`|
|1|7|2|<strong>Yes</strong>, at index 0|Return `[0, 1]`|

Two iterations. Tracing a small example aloud is worth doing in an interview &mdash; it catches off-by-one and ordering errors before the interviewer has to point them out.

## Edge cases to raise
|Case|Behaviour|
|---|---|
|No solution exists|Return `[]` or `None` &mdash; ask which is expected|
|Duplicate values, e.g. `[3, 3]` target 6|Works: the second 3 finds the first|
|Same element twice, `[3]` target 6|Must not match &mdash; the check-before-insert order handles it|
|Negative numbers|Works unchanged; the arithmetic does not care|
|Several valid pairs|Returns the first found; ask whether all are wanted|
|Empty or single-element array|Return the empty result|

Raising the "same element twice" case unprompted is a good signal, because it is the one the naive ordering gets wrong.

## The sorted variant: two pointers
If the array is sorted, O(1) space is achievable:

```python-run
def two_sum_sorted(nums, target):
    lo, hi = 0, len(nums) - 1
    while lo < hi:
        s = nums[lo] + nums[hi]
        if s == target:
            return [lo, hi]
        if s < target:
            lo += 1                # need a bigger sum
        else:
            hi -= 1                # need a smaller sum
    return []

print(two_sum_sorted([2,7,11,15], 9))
```
The correctness argument: if the sum is too small, the only way to increase it is to raise the left value; if too large, lower the right one. No pair is ever skipped.

|&nbsp;|Hash map|Two pointers|
|---|---|---|
|Requires sorted input|No|Yes|
|Time|O(n)|O(n)|
|Space|O(n)|O(1)|
|Returns original indices|Yes|Only if sorted in place|

That last row is a real trap: if you sort an unsorted array to use two pointers, the indices you return refer to the sorted array, not the original. Sorting `(value, index)` pairs preserves them, and at that point the hash map is simpler.

## What the question is testing
Two-sum is almost never about two-sum. It is checking whether you:

<strong>Recognise a lookup.</strong> Converting a nested scan into a hash-map lookup is the single most common optimisation in practical code, and this is the smallest problem that demonstrates it.

<strong>State complexity accurately,</strong> including space, without prompting.

<strong>Handle the self-pairing case,</strong> which is the one real subtlety.

<strong>Ask about the input.</strong> Sorted? Duplicates? Guaranteed solution? All valid pairs or one?

<strong>Communicate while coding</strong> rather than silently producing an answer.

The pattern generalises far beyond the interview: any time a loop contains a search, a dictionary built beforehand usually removes it. That is the transferable lesson.
