title: Implement a hash map from scratch
intro: Implement a hash map with put, get and remove, without using a dict.

## The requirement

Implement `put`, `get` and `remove` with O(1) average time, without using the language's built-in dictionary.

The design has three parts, and stating them upfront is the expected opening:

<strong>An array of buckets</strong> &mdash; the storage.
<strong>A hash function</strong> mapping keys to bucket indices.
<strong>A collision strategy</strong> for when two keys land in the same bucket.


## Run it

A working hash map with chaining, its bucket distribution printed before and after a resize, and the tombstone problem demonstrated on a small open-addressing version.

```python-run
class HashMap:
    def __init__(self, buckets=8):
        self.buckets = [[] for _ in range(buckets)]
        self.count = 0
        self.resizes = 0

    def _index(self, key):
        return hash(key) % len(self.buckets)      # hash picks the bucket

    def put(self, key, value):
        bucket = self.buckets[self._index(key)]
        for i, (k, _) in enumerate(bucket):
            if k == key:                          # compare KEYS, not hashes
                bucket[i] = (key, value)
                return
        bucket.append((key, value))
        self.count += 1
        if self.count / len(self.buckets) > 0.75:
            self._resize()

    def get(self, key, default=None):
        for k, v in self.buckets[self._index(key)]:
            if k == key:
                return v
        return default

    def remove(self, key):
        bucket = self.buckets[self._index(key)]
        for i, (k, _) in enumerate(bucket):
            if k == key:
                bucket.pop(i)                     # trivial with chaining
                self.count -= 1
                return True
        return False

    def _resize(self):
        old = self.buckets
        self.buckets = [[] for _ in range(len(old) * 2)]
        for bucket in old:
            for k, v in bucket:                   # every key moves
                self.buckets[self._index(k)].append((k, v))
        self.resizes += 1

    def spread(self):
        sizes = [len(b) for b in self.buckets]
        return f"{len(self.buckets)} buckets, longest chain {max(sizes)}, empty {sizes.count(0)}"

m = HashMap()
for i, w in enumerate("a b c d".split()): m.put(w, i)
print("HashMap  ->", m.get("c"), "| missing:", m.get("z"))
```

```python-run
class NaiveOpenAddressing:
    """Deletes by blanking the slot. Watch what that does to a probe."""
    def __init__(self, size=8):
        self.slots = [None] * size

    def _probe(self, key):
        i = hash(key) % len(self.slots)
        while self.slots[i] is not None and self.slots[i][0] != key:
            i = (i + 1) % len(self.slots)         # linear probing
        return i

    def put(self, key, value):
        self.slots[self._probe(key)] = (key, value)

    def get(self, key):
        i = hash(key) % len(self.slots)
        while self.slots[i] is not None:
            if self.slots[i][0] == key:
                return self.slots[i][1]
            i = (i + 1) % len(self.slots)
        return "NOT FOUND"

    def delete(self, key):
        self.slots[self._probe(key)] = None       # a hole, not a tombstone

m = NaiveOpenAddressing()
m.put("a", 1); m.put("b", 2)
print("naive open addressing ->", m.get("a"), m.get("b"))
```

```python-run
class Fixed:
    def __init__(self, name, h):
        self.name, self.h = name, h
    def __hash__(self):
        return self.h
    def __eq__(self, other):
        return isinstance(other, Fixed) and self.name == other.name
    def __repr__(self):
        return self.name
```

## Chaining: the straightforward answer

Each bucket holds a list of key-value pairs. On collision, append.

```python-run
class MyHashMap:
    def __init__(self, capacity=16):
        self.cap = capacity
        self.size = 0
        self.buckets = [[] for _ in range(capacity)]

    def _index(self, key):
        return hash(key) % self.cap

    def get(self, key):
        for k, v in self.buckets[self._index(key)]:
            if k == key:
                return v
        return None

    def put(self, key, value):
        bucket = self.buckets[self._index(key)]
        for i, (k, _) in enumerate(bucket):
            if k == key:
                bucket[i] = (key, value)       # update in place
                return
        bucket.append((key, value))
        self.size += 1
        if self.size / self.cap > 0.75:
            self._resize()

    def remove(self, key):
        bucket = self.buckets[self._index(key)]
        for i, (k, _) in enumerate(bucket):
            if k == key:
                bucket.pop(i)
                self.size -= 1
                return True
        return False

    def _resize(self):
        old = self.buckets
        self.cap *= 2
        self.buckets = [[] for _ in range(self.cap)]
        self.size = 0
        for bucket in old:
            for k, v in bucket:
                self.put(k, v)                 # rehash everything

m = MyHashMap(capacity=4)
for i, word in enumerate("vectors norms basis rank trace det".split()):
    m.put(word, i)
print("size      :", m.size, "buckets:", m.cap, "<- it resized")
print("get basis :", m.get("basis"))
print("get missing:", m.get("nope"))
print("remove    :", m.remove("norms"), "| now:", m.get("norms"))
```
O(1) average for all three operations, O(n) worst case when every key collides.

Two details are load-bearing:

<strong>`put` must check for an existing key</strong> before appending, or updating a value inserts a duplicate and `get` returns the stale one.

<strong>Resizing rehashes every entry,</strong> because the bucket index depends on the capacity. Copying buckets across without rehashing puts keys in the wrong places, and they become unreachable.

## Why the load factor matters

The <strong>load factor</strong> is entries divided by buckets. As it rises, buckets hold longer chains and lookups degrade from O(1) towards O(n).

|Load factor|Average chain length|Behaviour|
|---|---|---|
|0.25|~1.1|Fast, memory-wasteful|
|0.75|~1.4|The usual threshold|
|2.0|~2.4|Noticeably slower|
|10|~10|Effectively a linked list|

Resizing at 0.75 is the common choice (Java's `HashMap` uses exactly this; CPython uses about 2/3). Doubling the capacity is O(n), and amortised across the insertions that fit in the new space it is O(1) per operation &mdash; the same argument as list `append`.

Choosing a <strong>power-of-two capacity</strong> allows `hash & (cap - 1)` instead of a modulo, which is faster. It also means only the low bits of the hash are used, so a hash function that varies mainly in its high bits clusters badly &mdash; which is why Java's `HashMap` mixes the high bits down before masking.

## Chaining versus open addressing

<p><strong>Separate chaining</strong> puts colliding entries in a list per bucket. Simple, deletion is trivial, and it tolerates a high load factor. This is what to implement under time pressure.</p>

<p><strong>Open addressing</strong> stores everything in the array itself and probes for the next free slot on a collision. Better cache behaviour and less pointer chasing &mdash; it is what CPython actually uses &mdash; but deletion is genuinely hard.</p>

## Why deletion is hard in open addressing

Removing an entry leaves a hole, and a probe sequence that ran <em>through</em> that slot to reach a later entry now stops at the hole and reports the later entry missing.

The fix is a <strong>tombstone</strong>: mark the slot deleted rather than empty, so probes continue past it but inserts may reuse it. Tombstones accumulate and eventually force a rehash even without growth. Being able to say that is usually what the question is really checking.

## The load factor and the resize

Lookup is O(1) only while buckets stay short. Once entries divided by buckets passes roughly 0.75, chains lengthen and every operation drifts towards O(n).

So the table doubles and <em>every key is rehashed</em>, because the index is <code>hash(key) % size</code> and the size just changed. That single resize is O(n), and amortised over the insertions that caused it each insert is still O(1) &mdash; but any individual insert can be the expensive one.

## Open addressing, the alternative

Instead of a list per bucket, store entries directly in the array and probe for another slot on collision.

|&nbsp;|Chaining|Open addressing|
|---|---|---|
|Storage|List per bucket|One flat array|
|Extra memory|Pointers per entry|None|
|Cache behaviour|Poorer &mdash; pointer chasing|Better &mdash; contiguous|
|Deletion|Straightforward|Needs tombstones|
|Load factor tolerance|Above 1 is workable|Must stay well below 1|

<strong>Deletion is the awkward part.</strong> Removing an entry outright breaks probe sequences that passed through that slot &mdash; a later lookup would stop at the gap and report the key missing. So deleted slots hold a <strong>tombstone</strong> marker meaning "empty, but keep probing".

Tombstones accumulate and degrade performance until a resize clears them, which is why open-addressed tables need periodic rehashing even without growth.

CPython uses open addressing with a scattering probe sequence; Java uses chaining, converting long chains into trees above a threshold to bound the worst case.

## The hash function

For an interview, `hash(key) % capacity` is acceptable. If asked to write one:

```python-run
def string_hash(s, cap):
    h = 0
    for ch in s:
        h = (h * 31 + ord(ch)) % cap      # 31: a common odd prime multiplier
    return h

for word in ["basis", "rank", "trace"]:
    print("%-6s -> %d" % (word, string_hash(word, 16)))
```
Three properties a hash function needs:

<strong>Deterministic.</strong> The same key must always give the same value, or entries become unreachable.

<strong>Uniform.</strong> Keys should spread across buckets. A hash returning a constant is valid and turns the table into a linked list.

<strong>Fast.</strong> It runs on every operation.

It does <em>not</em> need to be cryptographic &mdash; that is a different requirement, and orders of magnitude slower.

Worth mentioning: Python randomises string hashes per process to prevent deliberate-collision denial-of-service attacks, which is why `hash("abc")` differs between runs.

## Follow-up questions

<strong>"What if keys are integers 0 to 1,000,000?"</strong> Use direct addressing &mdash; an array indexed by the key. No hashing, no collisions, O(1) guaranteed. Only viable when the key space is small and dense.

<strong>"How would you make it thread-safe?"</strong> A single lock serialises everything; striped locking &mdash; one lock per group of buckets &mdash; allows concurrency. Java's `ConcurrentHashMap` does this.

<strong>"What is the worst case?"</strong> O(n) when all keys collide. Java mitigates it by treeifying long chains, giving O(log n).

<strong>"How do you iterate in insertion order?"</strong> Maintain a doubly linked list of entries alongside the table &mdash; which is exactly `OrderedDict` and CPython's compact dict layout.

<strong>"What about memory?"</strong> Chaining costs a pointer per entry plus list overhead; open addressing wastes empty slots. Both trade memory for speed.

## What it is testing

<strong>Do you name the three components?</strong> Buckets, hash function, collision strategy.

<strong>Do you handle collisions explicitly?</strong> A design without a collision answer is incomplete.

<strong>Do you resize?</strong> Without it, performance degrades to O(n) as the table fills.

<strong>Do you rehash on resize?</strong> Copying buckets without recomputing indices is the classic bug.

<strong>Do you check for an existing key in `put`?</strong> Otherwise updates create duplicates.

<strong>Do you know the real implementations?</strong> CPython open-addresses, Java chains and treeifies &mdash; knowing that grounds the answer in reality.

## Recap in one screen

- Three components: an array of buckets, a hash function, and a collision strategy.
- Chaining stores a list per bucket; open addressing probes for another slot and needs tombstones for deletion.
- Resize when the load factor exceeds about 0.75, and <strong>rehash every entry</strong> because indices depend on the capacity.
- `put` must update an existing key rather than appending a duplicate.
- O(1) average, O(n) worst case; Java bounds the worst case by treeifying long chains.
