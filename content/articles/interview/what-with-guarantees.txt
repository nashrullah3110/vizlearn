title: What does `with` guarantee when the body raises?
intro: What does the with statement actually do, and what happens to an exception raised inside it?

## The core idea

A with statement runs a context manager’s entry and exit methods around a block. The exit method runs even when the block raises, allowing resources to be released and, when designed to, exceptions suppressed.

## Run it
All three exits observed from inside __exit__, the suppression case. And a return from the body that still runs the cleanup.

All three exits, observed from inside __exit__.

```python-run
class Tracked:
    def __init__(self, name, swallow=False):
        self.name, self.swallow = name, swallow

    def __enter__(self):
        print(f"  enter {self.name}")
        return self                      # this is what `as` binds

    def __exit__(self, exc_type, exc, tb):
        seen = exc_type.__name__ if exc_type else None
        print(f"  exit  {self.name}  (exception seen: {seen})")
        return self.swallow              # truthy SWALLOWS the exception

print("1. normal exit:")
with Tracked("A"):
    print("  body")

print()
print("2. the body raises - __exit__ still runs, and is told what:")
try:
    with Tracked("B"):
        raise ValueError("boom")
except ValueError as e:
    print("  propagated to here:", e)

print()
print("3. __exit__ returns True, so the exception is suppressed:")
with Tracked("C", swallow=True):
    raise ValueError("silenced")
print("  execution continues, with no except clause")
```


A return from inside the body cannot skip the cleanup either.

```python-run
class Tracked:
    def __init__(self, name):
        self.name = name
    def __enter__(self):
        print(f"  enter {self.name}")
        return self
    def __exit__(self, *exc):
        print(f"  exit  {self.name}")
        return False

def f():
    with Tracked("D"):
        return "returned"

print("f() ->", f())

print()
print("and the comma form nests, so an earlier exit still runs:")
try:
    with Tracked("E"), Tracked("F"):
        raise RuntimeError("inside both")
except RuntimeError as e:
    print("  propagated:", e)
```


The generator form, and why the try/finally is not optional.

```python-run
from contextlib import contextmanager, suppress

@contextmanager
def guarded(label):
    print(f"  enter {label}")
    try:
        yield label
    finally:
        print(f"  exit  {label}  (finally always runs)")

print("with the body raising:")
try:
    with guarded("G") as name:
        raise RuntimeError("from " + name)
except RuntimeError as e:
    print("  propagated:", e)

print()
print("contextlib.suppress is the whole of case 3:")
with suppress(FileNotFoundError):
    open("/no/such/file")
print("  carried on, nothing raised")
```

## The protocol, in full
<p><code>with expr as name:</code> does four things. It evaluates <code>expr</code>. It calls <code>__enter__()</code> on the result and binds the return value to <code>name</code>. Note that this is <em>not</em> always the object itself, which is why <code>open()</code> can return a file and a lock can return <code>None</code>. It runs the body. Then it calls <code>__exit__(exc_type, exc, traceback)</code>.</p><p>The last step is the point. It happens on a normal fall-through, on a <code>return</code> from inside the body, on a <code>break</code>. And on an error. That is a stronger promise than <code>try/finally</code> written by hand, only because it is harder to forget.</p>

## Suppression, and why it is rare
<p>A truthy return from <code>__exit__</code> tells Python the error has been handled, and execution goes on after the block. It is a real feature with one common use &mdash; <code>contextlib.suppress(FileNotFoundError)</code> is a context manager whose entire job is to return <code>True</code> for the types you named.</p><p>Writing it yourself is often a mistake because a manager that swallows errors silently is a manager that hides bugs. The convention is to return <code>None</code> and let the error through, doing cleanup on the way out. If you do suppress, suppress one set type and nothing else.</p>

## contextlib, and the generator form
<p>Writing a class with two dunder methods for a two-line cleanup is heavy, and <code>contextlib.contextmanager</code> removes it:</p><pre><code>@contextmanager
def timed(label):
    start = time.perf_counter()
    try:
        yield                  # the body runs here
    finally:
        print(label, time.perf_counter() - start)</code></pre><p>All of it before the <code>yield</code> is <code>__enter__</code>. All of it after is <code>__exit__</code>. The <code>try/finally</code> is not optional &mdash; without it, an error in the body propagates out of the <code>yield</code> and the cleanup never runs. This quietly defeats the entire purpose.</p><p><code>ExitStack</code> is the other one worth knowing. It manages a variable number of managers. So you can enter a list of files without a nested <code>with</code> per file.</p>

## The follow-up: why not just use try/finally
<p>You can, and <code>with</code> compiles to roughly that. The gap is that the cleanup lives with the <em>resource</em> rather than with each call site. So it cannot be forgotten at the twelfth place the resource is used. It also composes: <code>with a, b:</code> nests correctly. And both exits run even if the first one raises.</p><p>The async counterpart is <code>async with</code> and <code>__aenter__</code>/<code>__aexit__</code>. This is what an async HTTP client or store session uses. Same protocol, awaitable methods.</p>

## Edge cases to raise
<p>Volunteering these is most of what separates a correct answer from a good one.</p>

<p><strong><code>with a, b:</code> is not the same as two separate blocks on failure.</strong> It nests, so if <code>b</code>'s <code>__enter__</code> raises, <code>a</code>'s <code>__exit__</code> still runs -. This is the behaviour you want and the reason to prefer the comma form over two statements.</p>

<p><strong>A <code>@contextmanager</code> generator can only be used once.</strong> The object it returns is a one-shot generator. So re-entering the same manager instance raises. Call the factory again instead, or write a class.</p>

<p><strong>Suppressing broadly hides bugs.</strong> If <code>__exit__</code> returns <code>True</code> unconditionally, each error in each body disappears - including <code>KeyboardInterrupt</code> and typos. Suppress one named type or nothing.</p>
