title: Why does [[0]*3]*3 break?
intro: What does [[0] * 3] * 3 create, and why does writing to one row change all of them?

## The core idea

List multiplication repeats references to the same inner object; it does not clone that object. For independent nested rows, create each row separately with a comprehension.

## Run it
The broken grid and the correct one side by side with their row identities printed, then the three levels of copying, then the mutable-default-argument bug that has the same cause.

```python-run
import copy

wrong = [[0] * 3] * 3
right = [[0] * 3 for _ in range(3)]
wrong[0][0] = 9
right[0][0] = 9
original = [[1, 2], [3, 4]]
same = original                      # another NAME for the same list
shallow = original[:]                # new outer list, SAME inner lists
deep = copy.deepcopy(original)       # new objects all the way down
original[0][0] = 99

def broken(item, accumulated=[]):     # evaluated ONCE, at definition time
    accumulated.append(item)
    return accumulated

print("shared row :", broken("x", [[0]*3]*3))
```

```python-run
import copy

wrong = [[0] * 3] * 3
right = [[0] * 3 for _ in range(3)]
wrong[0][0] = 9
right[0][0] = 9
original = [[1, 2], [3, 4]]
same = original                      # another NAME for the same list
shallow = original[:]                # new outer list, SAME inner lists
deep = copy.deepcopy(original)       # new objects all the way down
original[0][0] = 99

def fixed(item, accumulated=None):
    if accumulated is None:           # a fresh list per call
        accumulated = []
    accumulated.append(item)
    return accumulated

print("own rows   :", fixed("x", [[0]*3 for _ in range(3)]))
```

## The fix
```python-run
grid = [[0] * 3 for _ in range(3)]      # a fresh list per row
grid[0][0] = 1
print(grid)        # [[1, 0, 0], [0, 0, 0], [0, 0, 0]]
```
The comprehension <em>evaluates</em> `[0] * 3` on every iteration, so each row is a distinct object.

|Expression|Rows are|Safe to mutate|
|---|---|---|
|`[[0] * 3] * 3`|The same object|<strong>No</strong>|
|`[[0] * 3 for _ in range(3)]`|Distinct|Yes|
|`[[0, 0, 0] for _ in range(3)]`|Distinct|Yes|
|`[list(row) for row in template]`|Distinct copies|Yes|
|`copy.deepcopy(template)`|Fully independent|Yes|
|`[[0] * 3] * 3` of immutables only|Shared, unobservably|Read-only|

The last row is why the bug is subtle: sharing immutable objects is harmless and invisible. `[0] * 1000` shares one integer object a thousand times and nothing can go wrong, because integers cannot be modified in place. The trouble begins only when the repeated element is mutable.

## The same mistake, other costumes
<strong>Mutable default arguments</strong> &mdash; the most consequential version, because the sharing spans calls:

```python-run
def add(item, target=[]):        # created ONCE, at definition
    target.append(item)
    return target

print(add(1))     # [1]
print(add(2))     # [1, 2]  -- the same list, still there
```
```python-run
def add(item, target=None):      # the fix
    if target is None:
        target = []
    target.append(item)
    return target

print(add("x"), add("y"))
```
<strong>Class attributes</strong> &mdash; sharing across instances:

```python-run
class Basket:
    items = []                   # ONE list for the whole class

a, b = Basket(), Basket()
print(a.items.append("apple"))
print(b.items)                          # ['apple']  -- shared
```
```python-run
class Basket:
    def __init__(self):
        self.items = []          # per instance

a, b = Basket(), Basket()
a.items.append("apple")
print("a:", a.items)
print("b:", b.items, "- separate lists, because __init__ runs per instance")
```
<strong>`dict.fromkeys` with a mutable default:</strong>

```python-run
d = dict.fromkeys(["a", "b"], [])
print(d["a"].append(1))
print(d)                                 # {'a': [1], 'b': [1]}

d = {k: [] for k in ["a", "b"]}  # the fix
```
<strong>Shallow copies of nested structures:</strong>

```python-run
original = [[1, 2], [3, 4]]
shallow = original[:]            # or list(original), or copy.copy
print(shallow[0].append(99))
print(original)                         # [[1, 2, 99], [3, 4]]  -- inner lists shared
```
All four are the same rule: <strong>Python assigns and copies references. A copy of a container duplicates the pointers, not the objects behind them.</strong>

## What multiplication actually does
<p><code>[x] * 3</code> builds a list holding the same reference three times. For immutable contents that is invisible &mdash; <code>[0] * 3</code> is fine, because you can never mutate a <code>0</code>. For a mutable inner object it is a trap, because all three names lead to one object.</p>

The tell is that the bug only appears on <em>write</em>. Building and printing the grid looks perfect; the first assignment to a cell is when it falls apart.

## The same idea, three ways
This is one instance of a general rule: assignment and shallow copies duplicate references, never the objects behind them.

<p><code>b = a</code> &mdash; another name for the same list. <code>b = a[:]</code> or <code>list(a)</code> or <code>copy.copy(a)</code> &mdash; a new outer list holding the same inner references. So nested contents are still shared. <code>copy.deepcopy(a)</code> &mdash; new objects all the way down, at the cost of walking the whole structure.</p>

## How to spot it in review
Any <code>* n</code> where the repeated element is a list, a dict, a set or a custom object is suspicious. The same rule explains the mutable default argument bug: <code>def f(acc=[])</code> creates the list once, when the function is <em>defined</em>, and every call that omits the argument shares it.

The fix in both cases is the same &mdash; build the mutable thing at the moment it is needed rather than once, up front.

## Copy semantics, precisely
|Operation|Copies|Nested objects|
|---|---|---|
|`b = a`|Nothing &mdash; a second name|Shared|
|`a[:]`, `list(a)`, `copy.copy(a)`|The outer container|<strong>Shared</strong>|
|`copy.deepcopy(a)`|Everything, recursively|Independent|
|`[f(x) for x in a]`|Per-element result|Depends on `f`|

`deepcopy` is the correct tool when independence is required at every level, and it is not free: it walks the whole structure, tracks already-copied objects to handle cycles, and can be surprisingly slow on large graphs. For a list of lists, `[list(row) for row in grid]` is faster and clearer.

For grids specifically, <strong>NumPy sidesteps the question</strong>:

```python
import numpy as np
grid = np.zeros((3, 3), dtype=int)
grid[0, 0] = 1                        # no aliasing: one contiguous buffer
```

Note that NumPy has its own version of the distinction &mdash; <strong>slices are views, not copies</strong>:

```python
a = np.arange(6)
b = a[2:4]
b[0] = 99
a            # array([ 0,  1, 99,  3,  4,  5])  -- a changed too
c = a[2:4].copy()                      # explicit copy when needed
```

The lesson generalises: whenever a library offers cheap slicing, ask whether you received a view or a copy.

## How to detect it
<strong>`is` and `id`</strong> answer the question directly:

```python-run
grid = [[0] * 3] * 3

print(grid[0] is grid[1])              # True means shared
print(len({id(row) for row in grid}))  # 1 means every row is the same object

print("rows share one list:", grid[0] is grid[1])
```
<strong>Mutate one element and look</strong> &mdash; the fastest check during debugging. Set `grid[0][0] = 1` and print the whole structure.

<strong>Watch for `*` on a list of mutables,</strong> and for any default argument or class attribute that is a list, dict or set. Linters flag mutable defaults (`B006` in flake8-bugbear, `W0102` in pylint), and enabling that rule catches the most damaging variant automatically.
