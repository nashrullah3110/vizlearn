title: Subarray sum equals k
intro: Count the contiguous subarrays that sum to k.

## The problem

Count the number of contiguous subarrays whose elements sum to exactly k.

|Input|k|Count|The subarrays|
|---|---|---|---|
|`[1, 1, 1]`|2|2|`[1,1]` at 0-1 and at 1-2|
|`[1, 2, 3]`|3|2|`[1,2]` and `[3]`|
|`[1, -1, 0]`|0|3|`[1,-1]`, `[0]`, `[1,-1,0]`|
|`[3, 4, 7, 2, -3, 1, 4, 2]`|7|4|Several|

<strong>Negative numbers are allowed</strong>, and that single fact rules out the sliding window. This is the crux of the problem.

The brute force sums every subarray: O(n²) with running sums, O(n³) if the sum is recomputed each time. The intended solution is O(n).

## Why the sliding window fails

A sliding window works when growing it increases the sum and shrinking it decreases the sum &mdash; that monotonicity is what makes "too big, shrink from the left" a valid decision.

With negatives, the sum is not monotonic. On `[1, -1, 1]` with k = 1, a window whose sum is already 1 might still be extendable to another valid window, and a window whose sum is too large might become correct by <em>growing</em>. There is no correct rule for when to move the left pointer.

|Constraint|Technique|
|---|---|
|All positive, find <em>a</em> subarray with sum k|Sliding window, O(n)|
|All positive, minimum length with sum &ge; k|Sliding window, O(n)|
|<strong>Negatives allowed, count subarrays summing to k</strong>|<strong>Prefix sums plus a hash map</strong>|
|Negatives allowed, maximum sum|Kadane's algorithm|

Recognising which of those four you have been asked is most of the work.

## Prefix sums and the key identity

Let `prefix[i]` be the sum of the first i elements. Then the sum of the subarray from index i to j&minus;1 is `prefix[j] - prefix[i]`.

So a subarray ending at j sums to k exactly when:

<p class="mono-font">prefix[j] &minus; prefix[i] = k&nbsp;&nbsp;&rArr;&nbsp;&nbsp;prefix[i] = prefix[j] &minus; k</p>

Which turns the problem into: <strong>while scanning, count how many earlier prefix sums equal `current - k`.</strong> A dictionary of prefix-sum frequencies answers that in O(1).

```python
from collections import defaultdict

def subarray_sum(nums, k):
    counts = defaultdict(int)
    counts[0] = 1                  # the empty prefix -- see below
    total = running = 0

    for num in nums:
        running += num
        total += counts[running - k]     # subarrays ending here
        counts[running] += 1

    return total
```

O(n) time and O(n) space.

<strong>`counts[0] = 1` is the line everything hinges on.</strong> It represents the empty prefix, and it is what allows a subarray starting at index 0 to be counted. Without it, `[1, 2, 3]` with k = 3 finds only `[3]` and misses the leading `[1, 2]`, because that subarray needs `prefix[i] = 0` to exist.

The order also matters: <strong>count before inserting</strong>. Inserting `running` first would let a subarray of length zero match when k = 0.

## From a difference to a lookup

Let <code>P(i)</code> be the sum of everything up to index i. The subarray from j+1 to i sums to <code>P(i) &minus; P(j)</code>, so it equals k exactly when <code>P(j) = P(i) &minus; k</code>.

That converts "search backwards for a matching start" into "have I seen this value before?", which a dictionary answers in O(1). It is the same move as Two Sum &mdash; compute the thing you need rather than hunting for it.

## Why {0: 1} and not an empty map

The empty prefix has sum 0, and it must be in the map before the loop starts. Otherwise a subarray beginning at index 0 &mdash; where <code>running</code> itself already equals k &mdash; has no earlier prefix to match against and is never counted.

Seeding with <code>{0: 1}</code> is the single most commonly missed line in this problem, and it fails on the simplest possible input: <code>[k]</code>.

## Why not a sliding window

A sliding window needs the sum to grow when the window grows, so shrinking from the left is a sound response to overshooting. With negative numbers that monotonicity is gone: extending the window can make the sum smaller, so there is nothing to slide on.

If the question guarantees all-positive values, say so and use the window &mdash; O(1) space instead of O(n). Noticing that the constraint changes the right answer is worth as much as the code.

## Tracing it

`[3, 4, 7, 2, -3, 1, 4, 2]` with k = 7:

|num|running|`running - k`|Found|counts after|
|---|---|---|---|---|
|&mdash;|0|&mdash;|&mdash;|`{0:1}`|
|3|3|&minus;4|0|`{0:1, 3:1}`|
|4|7|0|<strong>1</strong>|`{0:1, 3:1, 7:1}`|
|7|14|7|<strong>1</strong>|`{…, 14:1}`|
|2|16|9|0|`{…, 16:1}`|
|&minus;3|13|6|0|`{…, 13:1}`|
|1|14|7|<strong>1</strong>|`{…, 14:2}`|
|4|18|11|0|`{…, 18:1}`|
|2|20|13|<strong>1</strong>|`{…, 20:1}`|

Total: 4. The `14:2` entry is the reason a <em>count</em> is stored rather than a set &mdash; the same prefix sum recurring means several valid starting points, and a set would count only one of them.

## The variants

<strong>Return a subarray rather than a count.</strong> Store the <em>index</em> of each prefix sum instead of its frequency, and return on the first match.

<strong>Longest subarray with sum k.</strong> Store the <em>earliest</em> index for each prefix sum &mdash; `if s not in first: first[s] = i` &mdash; so the span found is maximal.

<strong>Subarray sums divisible by k.</strong> Key the dictionary on `running % k` instead of `running`. Watch for Python's `%` returning non-negative results for negative operands, which is actually convenient here; in languages where it does not, normalise with `((r % k) + k) % k`.

<strong>Binary subarrays with sum k,</strong> or "at most k" problems &mdash; these are usually sliding windows again, because the values are non-negative.

<strong>Contiguous array with equal 0s and 1s.</strong> Map 0 to &minus;1 and find the longest subarray summing to 0 &mdash; the same technique with a substitution.

<strong>2D version: submatrix sum equals target.</strong> Fix a pair of rows, compress the columns between them into a 1D array, and run this algorithm. O(n&sup2;m).

## Edge cases

|Case|Note|
|---|---|
|k = 0|Works; `counts[0] = 1` and the count-before-insert order matter most here|
|All zeros, k = 0|Answer is n(n+1)/2 &mdash; every subarray qualifies|
|Empty array|0|
|Single element equal to k|1|
|No subarray sums to k|0|
|All negative|Works &mdash; nothing assumes a sign|
|Large sums|Python integers are unbounded; other languages need care about overflow|

`[0, 0, 0]` with k = 0 giving 6 is a good self-check: the dictionary reaches `{0: 4}` and contributes 1 + 2 + 3.

## What it is testing

<strong>Do you notice the negatives?</strong> Reaching for a sliding window is the expected wrong turn, and identifying why it fails is the insight being probed.

<strong>Do you know the prefix-sum identity?</strong> `sum(i..j) = prefix[j] - prefix[i]` is the most reusable formula in array problems.

<strong>Do you initialise `counts[0] = 1`?</strong> The single most common bug, and it silently produces answers that are correct except at the start of the array.

<strong>Do you count before inserting?</strong> Reversing them breaks the k = 0 case.

<strong>Do you store counts rather than a set?</strong> Repeated prefix sums each contribute a subarray.

<strong>Can you adapt it?</strong> Longest-subarray and divisible-by-k variants follow from changing what the dictionary stores.

## Recap in one screen

- Negative values rule out a sliding window, because the sum is no longer monotonic in the window size.
- Use prefix sums: a subarray ending here sums to k when an earlier prefix equals `running - k`.
- A dictionary of prefix-sum frequencies answers that in O(1), giving O(n) overall.
- Seed it with `{0: 1}` for the empty prefix, or subarrays starting at index 0 are missed.
- Count first, then insert &mdash; and store frequencies, not a set.
