title: Implement a queue using two stacks
intro: Implement a FIFO queue using only stacks. What is the cost of each operation?

## The core idea

A queue returns items in first-in, first-out order; a stack returns them last-in, first-out. Two stacks can implement a queue by reversing the inbox into an outbox only when the outbox is empty, preserving amortised O(1) operations.

## Run it
FIFO through interleaved operations, which is the part worth checking.

```python-run
class Queue:
    """Amortised O(1): pour only when the outbox is empty."""
    def __init__(self):
        self.inbox, self.outbox = [], []
        self.moves = 0
    def enqueue(self, x):
        self.inbox.append(x)
    def dequeue(self):
        if not self.outbox:                  # ONLY when empty
            while self.inbox:
                self.outbox.append(self.inbox.pop())
                self.moves += 1
        if not self.outbox:
            raise IndexError("dequeue from an empty queue")
        return self.outbox.pop()

q = Queue()
for x in "abc":
    q.enqueue(x)
first, second = q.dequeue(), q.dequeue()
q.enqueue("d")                       # enqueued AFTER two dequeues
third, fourth = q.dequeue(), q.dequeue()
print("dequeue order:", first, second, third, fourth, " <- FIFO preserved")
print("c was enqueued before d, and c came out first:", third == "c")

try:
    Queue().dequeue()
except IndexError as e:
    print("empty queue ->", e)
```

The eager version that pours back and forth on every call does the same job, but far more of the work.

```python-run
class QueueEager:
    """The version that pours every time: O(n) per dequeue."""
    def __init__(self):
        self.inbox, self.outbox = [], []
        self.moves = 0
    def enqueue(self, x):
        self.inbox.append(x)
    def dequeue(self):
        while self.inbox:
            self.outbox.append(self.inbox.pop()); self.moves += 1
        v = self.outbox.pop()
        while self.outbox:                   # and pour back again
            self.inbox.append(self.outbox.pop()); self.moves += 1
        return v

N = 400
eager = QueueEager()
for i in range(N):
    eager.enqueue(i)
for i in range(N):
    eager.dequeue()
print(f"  eager (pour every time)      {N} enqueues + {N} dequeues -> {eager.moves:,} moves")
print("  each element crosses between the stacks ONCE in its whole life,")
print(f"  so the amortised total is {N} moves for n = {N} - not {N} moves per call.")
```

One dequeue can still be O(n) - amortised is a claim about the total.

```python-run
class Queue:
    """Amortised O(1): pour only when the outbox is empty."""
    def __init__(self):
        self.inbox, self.outbox = [], []
        self.moves = 0
    def enqueue(self, x):
        self.inbox.append(x)
    def dequeue(self):
        if not self.outbox:                  # ONLY when empty
            while self.inbox:
                self.outbox.append(self.inbox.pop())
                self.moves += 1
        if not self.outbox:
            raise IndexError("dequeue from an empty queue")
        return self.outbox.pop()

q = Queue()
for i in range(1_000):
    q.enqueue(i)

before = q.moves
q.dequeue()
print("a single dequeue after 1,000 enqueues moved", q.moves - before, "items")

before = q.moves
q.dequeue()
print("the next one moved", q.moves - before, "- the outbox was already full")

for _ in range(998):
    q.dequeue()
print()
print("total moves for the whole run:", q.moves, "for 1,000 items")
print("that is the amortised bound: O(n) in total, O(n) for one worst call.")
```

## Why reversing twice gives FIFO
<p>A stack reverses what you put into it. Pour one stack into another and you have reversed it again, which restores the original order &mdash; so the item pushed first ends up on top of the second stack, which is exactly the front of a queue.</p><p>That is the whole trick, and it is worth stating in one sentence in an interview: <em>the inbox has them newest-first, the outbox has them oldest-first, and pouring is what converts between the two</em>.</p>

## The emptiness check is the entire complexity argument
<p>The naive version pours on every dequeue &mdash; and, to keep enqueue working, pours back afterwards. That is O(n) per call and O(n&sup2;) for n dequeues. The editor below measures it: 400 operations cost 160,000 moves that way, against 400 the right way.</p><p>Pouring only when the outbox is empty means each element crosses once in its entire life. Total moves for n items is n, so the average cost per dequeue is constant even though one individual dequeue can touch every element. That is amortised O(1), and the distinction between "amortised O(1)" and "O(1) worst case" is what the follow-up question is about.</p>

## When amortised is not good enough
<p>Amortised bounds are about totals, and some systems care about the worst single call. A real-time audio callback or a request with a latency budget cannot afford the one dequeue that moves ten thousand items, even if the average is fine.</p><p>The honest answer is that this structure cannot fix that &mdash; and naming the alternatives is what a strong answer does. Move a constant number of items per operation instead of all of them (incremental rebuilding), or use a structure that is O(1) worst case outright, which in Python is <code>collections.deque</code>. Which leads to the real-world footnote: nobody builds a queue from two stacks in production. The question is about reasoning, and it is fair to say so while still answering it.</p>

## The mirror question
<p>"Now implement a stack using two queues." It is the same idea and strictly worse: one of the two operations has to become O(n), because a queue gives you the wrong end and no amount of shuffling amortises away. Either push moves everything into the second queue behind the new item, or pop moves n&minus;1 items across to reach the last one.</p><p>There is no trick that makes both O(1) here, and saying that directly is the right answer &mdash; the asymmetry between the two questions is the thing being tested.</p>

## Edge cases to raise
<p>Volunteering these is most of what separates a correct answer from a good one.</p>

<p><strong>Dequeue from empty.</strong> The outbox is empty and so is the inbox, so the pour moves nothing and the pop raises. Check it explicitly rather than letting an <code>IndexError</code> escape from an internal list.</p>

<p><strong><code>peek()</code> needs the same pour.</strong> Forgetting the emptiness check there is the standard bug in the extension, and it returns the newest item instead of the oldest.</p>

<p><strong>Nobody ships this.</strong> <code>collections.deque</code> is O(1) at both ends and is what production code uses. Saying that while still answering the question shows you know why it is being asked.</p>
