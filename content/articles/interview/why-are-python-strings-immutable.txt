title: Why are Python strings immutable?
intro: Why are Python strings immutable, and what does that buy you?

## The core idea

Python strings cannot be changed in place; operations that appear to modify text create a new string. Immutability makes strings safe to share and hash, while repeated concatenation can create avoidable copies.

## Run it
Object identities before and after a "change", then the cost of ignoring what that implies. Measured at three sizes so the shape of the curve is visible rather than asserted.

```python-run
# Immutability, and the one place it costs you.
import time

s = "cat"
t = s                       # a second NAME, not a second object
print("s =", s, " id:", hex(id(s)))
print("t =", t, " id:", hex(id(t)), " same object:", t is s)

u = s.upper()               # a NEW object; s is untouched
print("u =", u, " id:", hex(id(u)), " same object:", u is s)
print("s is still:", s)

try:
    s[0] = "C"
except TypeError as e:
    print("s[0] = 'C' ->", e)

# Hashability is the payoff: the value cannot change, so the hash cannot
# go stale, so a string can be a dictionary key.
print("hash stable:", hash("cat") == hash(s))
try:
    {["c", "a", "t"]: 1}
except TypeError as e:
    print("list as a key ->", e)

# --- the cost, measured -------------------------------------------------
class Buf:                  # an attribute, so CPython's in-place resize
    def __init__(self):     # special case cannot fire and hide the cost
        self.text = ""
```

Building on the same setup, the next block shows the remaining cases.

```python-run

print()
print(f"{'n':>7} {'+= in a loop':>14} {'list + join':>13} {'ratio':>7}")
for n in (20_000, 40_000, 80_000):
    b = Buf()
    start = time.perf_counter()
    for _ in range(n):
        b.text += "x"
    concat = time.perf_counter() - start

    start = time.perf_counter()
    parts = []
    for _ in range(n):
        parts.append("x")
    joined_text = "".join(parts)
    joined = time.perf_counter() - start
    print(f"{n:>7} {concat:>13.4f}s {joined:>12.4f}s {concat / joined:>6.1f}x")

print("Double n: join doubles, += quadruples. That is O(n) against O(n^2).")
```

## The performance consequence
The one real cost is building strings incrementally:

```python-run
words = ["never", " ", "concatenate", " ", "in", " ", "a", " ", "loop"]

# O(n^2) - each += allocates a new string and copies everything so far
result = ""
for word in words:
    result += word
print("loop  :", repr(result))

# O(n) - collect references, allocate once
result = "".join(words)
print("join  :", repr(result))
```
At 10,000 words the first version performs roughly 50 million character copies. `join` computes the total length, allocates once, and copies each piece in.

This is the most common Python performance mistake, and the reason it survives review is that the quadratic version is fine on ten words and catastrophic on ten thousand.

Two related points:

<strong>CPython has an optimisation</strong> that sometimes makes `+=` in a loop appear linear: if a string has exactly one reference, it can be resized in place. It is an implementation detail, it fails as soon as anything else holds a reference. And it does not exist in other Python implementations. Do not rely on it.

<strong>`io.StringIO`</strong> is the other when the pieces are produced incrementally and cannot be collected in a list first. It behaves like a writable buffer.

## What to use instead when mutation is needed
|Need|Use|
|---|---|
|Build a string from pieces|A list, then `"".join()`|
|Incremental writes|`io.StringIO`|
|Mutable bytes|`bytearray`|
|Character-level editing|A list of characters, join at the end|
|Templating|f-strings or `str.format`|
|Repeated replacement|`str.translate` with a mapping table|

`bytearray` is the genuinely mutable relative:

```python-run
b = bytearray(b"hello")
b[0] = ord("H")            # works - bytearray IS mutable
print(bytes(b))                    # b'Hello' - back to immutable
```
Note the pairing: `str` is immutable and `bytes` is immutable, while `bytearray` is the mutable byte sequence. There is no mutable `str` in Python, and a list of one-character strings is the usual stand-in.

## What immutability actually means
There is no operation in Python that changes a string in place. <code>s.upper()</code>, <code>s.replace()</code>, <code>s.strip()</code> and <code>s + t</code> all <em>return</em> a new string and leave the original exactly as it was. Assigning to an index &mdash; <code>s[0] = 'A'</code> &mdash; is not slow, it is a <code>TypeError</code>.

This is enforced, not advisory. There is no private method and no escape hatch, which is what lets the interpreter make assumptions it could not otherwise make.

## The three things it buys
<p><strong>Hashability.</strong> A dictionary stores a key in a slot chosen from its hash. If the key could change after insertion, its hash would no longer match its slot and the entry would become unreachable. Immutable types can be keys; mutable ones cannot, which is why <code>{[1,2]: 'x'}</code> raises and <code>{(1,2): 'x'}</code> does not.</p>

<p><strong>Free sharing.</strong> Passing a string to a function, storing it in two places, closing over it. None of these need a defensive copy, because no one can modify it behind your back. In a language with mutable strings, library code often copies on the way in just in case.</p>

<p><strong>Interning.</strong> CPython reuses one object for short string literals that look like identifiers. So equality can often be settled by an identity check. That is an optimisation immutability makes legal.</p>

## What it costs, and the one place it bites
Every edit allocates. Usually that is irrelevant &mdash; one <code>replace</code> on one line costs nothing you can measure. It matters in exactly one shape: building a string a piece at a time in a loop.

Each <code>+=</code> copies everything accumulated so far, so n appends copy 1 + 2 + 3 + ... + n characters, which is O(n&sup2;). The fix is <code>"".join(parts)</code>: one pass to total the lengths, one allocation, one copy. The editor below measures both.

## The follow-up you should expect
"If strings are immutable, why does <code>s += 'x'</code> sometimes look fast?" CPython has a special case that resizes a string in place when the target is a plain local variable and nothing else refers to it. It is real, it is invisible, and it stops firing the moment you store into an attribute or a list. Do not build on it.

## Interning and the `is` trap
Because strings are immutable, the interpreter may share one object for equal strings. That makes `is` behave unpredictably for strings:

```python-run
a = "hello"
b = "hello"
print(a is b)              # True - both are the same interned literal

c = "hello world"
d = "hello world"
print(c is d)              # often True for literals, and NOT guaranteed

e = "".join(["hel", "lo"])
print(e is a)              # False - computed at runtime, not interned
```
Short identifier-like literals are interned by itself at compile time. Strings built at runtime usually are not.

The rule that follows: <strong>use `==` for string comparison, always.</strong> `is` asks whether two names refer to the same object. This is almost never the question. Relying on interning produces code that works in testing and fails on computed input.

`sys.intern()` forces interning by name, which is sometimes worth it when the same strings are compared millions of times. Identity comparison is faster than character comparison. That is a genuine optimisation in parsers and interpreters, and rare in application code.

## Immutability elsewhere in Python
|Type|Mutable|Hashable|
|---|---|---|
|`str`|No|Yes|
|`bytes`|No|Yes|
|`bytearray`|Yes|No|
|`tuple`|No|Yes, if its contents are|
|`frozenset`|No|Yes|
|`list`|Yes|No|
|`dict`|Yes|No|
|`set`|Yes|No|

The pattern is consistent: <strong>mutable types are unhashable</strong>, for exactly the same reason strings must be immutable to be keys.

The tuple row has a subtlety worth knowing: a tuple is immutable, and if it <em>contains</em> a list it is unhashable, because its hash would depend on something that can change.

```python-run
print("hash((1, 2)) :", hash((1, 2)), "- fine")

try:
    hash((1, [2]))
except TypeError as e:
    print("hash((1,[2])):", type(e).__name__ + ":", e)
```

## How other languages compare
<strong>Java</strong> strings are immutable, for the same reasons, with `StringBuilder` as the mutable builder. The direct analogue of using a list and joining.

<strong>C++</strong> `std::string` is mutable, so in-place change and reversal are possible &mdash; which is why "reverse a string in place" is a C++ question that does not translate to Python.

<strong>JavaScript</strong> strings are immutable, and it has no separate builder type; array `join` is the idiom.

<strong>Rust</strong> distinguishes `&str` (an immutable borrowed slice) from `String` (an owned, growable buffer) in the type system.

The convergence is informative: most modern languages chose immutable strings, because the hashing, sharing and thread-safety benefits outweigh the cost of a separate builder for the one case where mutation is wanted.
