title: list vs tuple vs deque vs array — which and why?
intro: When would you use a tuple instead of a list? What about deque or array?

## The core idea

Lists, tuples, and deques all hold sequences, but support different trade-offs. Use lists for indexed mutable sequences, tuples for fixed records, and deques for efficient insertion and removal at both ends.

## Run it
The five containers measured rather than described: the operation each is fast at, the memory each uses for the same thousand integers, and the two errors that pick the container for you.

```python-run
# Choosing a container: measure the operation you actually repeat.
import time
from collections import deque

N = 30_000
print(f"{'operation':>28} {'list':>10} {'deque':>10}")
for label, action_list, action_deque in [
    ("append at the end",  lambda c: c.append(1),   lambda c: c.append(1)),
    ("insert at the front", lambda c: c.insert(0, 1), lambda c: c.appendleft(1)),
]:
    lst, dq = [], deque()
    start = time.perf_counter(); [action_list(lst) for _ in range(N)]
    list_time = time.perf_counter() - start
    start = time.perf_counter(); [action_deque(dq) for _ in range(N)]
    deque_time = time.perf_counter() - start
    print(f"{label:>28} {list_time:>9.4f}s {deque_time:>9.4f}s")

# Random access is the other direction.
lst = list(range(N)); dq = deque(range(N))
start = time.perf_counter(); [lst[N // 2] for _ in range(100_000)]
print(f"{'index the middle':>28} {time.perf_counter() - start:>9.4f}s", end="")
start = time.perf_counter(); [dq[N // 2] for _ in range(100_000)]
print(f" {time.perf_counter() - start:>9.4f}s   <- deque loses here")
```
Memory footprint and two errors that Python raises for you also help decide, along with the maxlen ring-buffer trick deques offer.

```python-run
import sys
from array import array
from collections import deque

# --- memory: references versus packed values ---------------------------
numbers = list(range(1000))
packed = array("i", range(1000))
as_tuple = tuple(range(1000))
print(f"list  of 1000 ints : {sys.getsizeof(numbers):>6} bytes (references)")
print(f"tuple of 1000 ints : {sys.getsizeof(as_tuple):>6} bytes")
print(f"array of 1000 ints : {sys.getsizeof(packed):>6} bytes (values, packed)")
print("The list does not include the integer objects it points at.")

# --- the two errors that decide it for you -----------------------------
try:
    {[1, 2]: "point"}
except TypeError as e:
    print("list as a dict key  ->", e)
print("tuple as a dict key ->", {(1, 2): "point"})

try:
    (1, 2).append(3)
except AttributeError as e:
    print("tuple.append        ->", e)

# --- deque with maxlen is a ring buffer --------------------------------
recent = deque(maxlen=3)
for event in "abcde":
    recent.append(event)
print("deque(maxlen=3) after abcde:", list(recent), "- oldest dropped for free")
```

## When to use each
<strong>`list`</strong> is the default. Random access, sorting, slicing, appending at the end &mdash; all good. Only reject it when you need something it cannot do.

<strong>`tuple`</strong> when the sequence is a fixed record rather than a collection, or when it must be hashable:

```python-run
cache, seen = {}, set()
user_id, date, result = 7, "2026-08-30", "cached value"

point = (3, 4)                          # a record, not a collection
cache[(user_id, date)] = result         # composite dict key
seen.add((2, 5))                        # set of coordinates
x, y = point                            # unpacking reads naturally

print("point   :", point, "-> x =", x, ", y =", y)
print("cache   :", cache)
print("seen    :", seen)
```
The hashability is the hard requirement &mdash; a list simply cannot be a dict key. The immutability is also a signal to the reader that the contents are not going to change, which is why returning a tuple from a function that produces a fixed set of values is idiomatic.

<strong>`deque`</strong> when you add or remove at the front:

```python-run
from collections import deque

queue = deque()
queue.append("build")       # enqueue at the right
print("dequeued:", queue.popleft())     # dequeue from the left -- O(1)

window = deque(maxlen=3)    # a bounded buffer: old items fall off
for reading in [10, 11, 12, 13, 14]:
    window.append(reading)
print("window  :", list(window), "- never grows beyond 3")
```
<strong>`maxlen` is the underrated feature.</strong> A bounded deque discards from the opposite end automatically, which gives you a rolling window or a fixed-size log buffer with no bookkeeping at all.

## The performance trap that matters
`list.pop(0)` and `list.insert(0, x)` are <strong>O(n)</strong>, because every remaining element shifts one position. Inside a loop, that makes the whole operation quadratic:

```python-run
queue = list(range(100_000))
while queue:
    item = queue.pop(0)      # O(n) each time -> O(n^2) total

print("list pop(0) drained")
```
Roughly five billion element moves. Swapping in a deque makes it linear:

```python-run
from collections import deque
result, task = [], "build"

queue = deque(range(100_000))
while queue:
    item = queue.popleft()   # O(1) each time -> O(n) total

print("deque popleft drained")
```
<strong>Any breadth-first search, task queue, or producer-consumer loop should use a `deque`.</strong> This is the single most common reason a straightforward-looking Python loop is slow, and it is invisible in small tests &mdash; a thousand elements finishes fine, and a hundred thousand does not.

The mirror-image mistake also exists: reaching for a deque and then indexing it in a loop. `dq[i]` walks the internal block list, so a positional loop over a deque is O(n²). Use a list when you index, a deque when you push and pop at the ends.

## tuple versus list
The textbook answer is "tuples are immutable", which is true and not the point. The consequence is that a tuple is <strong>hashable</strong> (if its contents are), so it can be a dictionary key or a set member &mdash; which is why coordinates, database rows and cache keys are tuples.

The secondary signal is meaning. A list is a homogeneous sequence of unknown length; a tuple is a fixed-size record where position carries meaning. <code>(x, y)</code> is a point; <code>[x, y]</code> is two numbers.

## deque versus list
<p><code>collections.deque</code> is a doubly linked list of blocks, so <code>appendleft</code> and <code>popleft</code> are O(1) where the list equivalents are O(n). Any queue, BFS frontier or "last N items" buffer should be a deque.</p>

The trade is random access: <code>d[5000]</code> walks the blocks, so it is O(n). If you index into the middle, keep the list. A deque also takes <code>maxlen</code>, which turns it into a fixed-size ring buffer that discards the oldest entry automatically.

## array and the memory question
A list holds <em>references</em>, so a list of a million integers is a million pointers plus a million integer objects. <code>array.array</code> packs the values inline in one typed block, which is several times smaller and much friendlier to the cache.

For real numeric work the answer is <code>numpy</code>, which adds vectorised operations on top of the same packed layout. Mentioning that a list of numbers is a list of pointers is usually the specific thing an interviewer is listening for.

## Why tuples are smaller and faster
```python-run
import sys
print(sys.getsizeof([1, 2, 3]))     # 88 bytes
print(sys.getsizeof((1, 2, 3)))     # 64 bytes
```
A list over-allocates so that `append` is amortised O(1), and it stores a capacity alongside its length. A tuple is fixed at creation, so it needs neither &mdash; less memory, one less indirection, and marginally faster iteration.

CPython also <strong>caches small tuples</strong> for reuse, and constant tuples are built at compile time:

```python-run
import dis
print(dis.dis("x = (1, 2, 3)"))     # LOAD_CONST (1, 2, 3)  -- one instruction
print(dis.dis("x = [1, 2, 3]"))     # BUILD_LIST -- constructed at runtime
```
So `for x in (1, 2, 3)` is very slightly faster than the list version. This is a real but tiny effect, and <strong>not a reason to choose a tuple</strong> &mdash; choose based on mutability and hashability, and take the memory win as a side benefit.

## Immutability is shallow
A tuple's immutability applies to its own slots, not to what they point at:

```python-run
t = ([1, 2], "fixed")
t[0].append(3)              # allowed -- the LIST inside is mutable
print("after append:", t)

try:
    t[0] = []               # the SLOT is not
except TypeError as e:
    print("reassigning :", type(e).__name__ + ":", e)

try:
    hash(([1], 2))
except TypeError as e:
    print("hashing     :", type(e).__name__ + ":", e)
```
The tuple guarantees its references will not change, and says nothing about the objects behind them. That is also why a tuple containing a list is unhashable: hashing recurses into the contents, so one mutable element makes the whole thing unhashable.

The practical rule: <strong>a tuple is only usable as a dict key if everything inside it is hashable too.</strong> Convert nested lists to tuples, and sets to `frozenset`.

## The rest of the family
|Need|Use|
|---|---|
|Fixed record with named fields|`NamedTuple` or `dataclass(frozen=True)`|
|Queue between threads|`queue.Queue` &mdash; deque plus locking|
|Priority queue|`heapq` on a list|
|Array of numbers, compact|`array.array` or NumPy|
|Sorted insertion|`bisect.insort` on a list|
|Immutable set|`frozenset`|
|Ring buffer|`deque(maxlen=n)`|

<strong>`NamedTuple`</strong> is the natural upgrade once a tuple's positions acquire meaning. `point.x` beats `point[0]`, it stays a tuple, and it costs no extra memory:

```python-run
from typing import NamedTuple

class Point(NamedTuple):
    x: int
    y: int

p = Point(3, 4)
print(p.x, p[0])           # both work; still hashable and unpackable
```
<strong>`deque` is thread-safe for `append` and `popleft`</strong> individually, because those are atomic at the C level. That does <em>not</em> make a check-then-pop sequence safe &mdash; use `queue.Queue` when several threads coordinate through it.
