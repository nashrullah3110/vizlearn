title: What does `yield` actually do?
intro: What does yield do, and how is a generator different from a function that returns a list?

## The core idea

`yield` returns a value while preserving the function’s execution state for the next request. Calling a generator function creates a lazy iterator; its body runs only as the iterator is advanced.

## Run it
The three states, the one-shot exhaustion, and the memory difference at a million items - printed rather than asserted.

The three states, driven by hand.

```python-run
import inspect

def countdown(n):
    print("  [the body starts only now]")
    while n > 0:
        yield n
        n -= 1

g = countdown(3)
print("calling it returned a:", type(g).__name__)
print("state:", inspect.getgeneratorstate(g))

print("first next() ->", next(g))
print("state:", inspect.getgeneratorstate(g))
print("the rest:", list(g))
print("state:", inspect.getgeneratorstate(g))

try:
    next(g)
except StopIteration:
    print("exhausted: a generator is one-shot")
```


One-shot is not a warning, it is silence - the second consumer sees an empty sequence and nothing complains.

```python-run
squares = (i * i for i in range(5))

print("sum once :", sum(squares))
print("sum again:", sum(squares), "<- not zero by accident; it is empty")

rows = (r for r in ["a", "b"])
first = [r for r in rows]
second = [r for r in rows]
print("first pass :", first)
print("second pass:", second, "<- already closed")
```


And what the laziness actually buys, in bytes.

```python-run
import sys

N = 1_000_000
as_list = [i * i for i in range(N)]
as_gen = (i * i for i in range(N))
print("memory for a million squares:")
print("  list     ", f"{sys.getsizeof(as_list):>9,}", "bytes")
print("  generator", f"{sys.getsizeof(as_gen):>9,}", "bytes")
print("  ratio    ", f"{sys.getsizeof(as_list) / sys.getsizeof(as_gen):>9,.0f}x")
print()
print("getsizeof on the list excludes the integers it points at,")
print("so the real gap is larger still.")
```

## A generator is a paused frame
<p>An ordinary function runs to a <code>return</code> and its stack frame is destroyed. A function containing <code>yield</code> does not run at all when you call it. You get a generator object that owns a frame which has never started.</p><p>Every <code>next()</code> resumes that frame, runs until the next <code>yield</code>, hands back the value, and freezes the frame again. Local variables, instruction pointer and all. That is the whole mechanism, and it is why <code>yield</code> can appear in the middle of a loop and still work. The loop variable survives between resumes. This is because the frame was never torn down.</p>

## What laziness buys, in one number
<p>The list version of a million squares allocates a million integers and a million pointers before you read the first one. The generator version allocates one object with a frame in it. And the editor below prints both sizes: a few megabytes against about a hundred bytes.</p><p>The other half is <em>latency</em>. A generator can hand you its first item at once. This matters when the sequence is being read from a file or a network, and matters absolutely when the sequence is infinite. <code>itertools.count()</code> is a valid generator and an impossible list.</p>

## The three things you give up
<p><strong>It is one-shot.</strong> Once exhausted, it stays exhausted. And a second <code>for</code> loop over it runs zero times without error. This is the bug people actually hit: passing a generator to two functions and finding the second one saw an empty sequence.</p><p><strong>No <code>len()</code>, no indexing, no slicing.</strong> The length is not known without running it. So there is nothing to report. <code>itertools.islice</code> is the slicing replacement.</p><p><strong>Exceptions surface late.</strong> A generator that will raise on its fourth item raises on the fourth <code>next()</code>. This may be a long way from where it was created. Inside a different function, or after a <code>with</code> block has already closed the file it was reading.</p>

## The follow-up you should expect
<p>"What is the difference between a generator and an iterator?" An iterator is the protocol. Anything with <code>__next__</code> and <code>__iter__</code>. A generator function is one common way to implement an iterator; classes and built-in objects can implement the protocol directly too.</p><p>And "what does a generator expression change?" Nothing but the syntax: <code>(x*x for x in xs)</code> creates a generator object without building a list. That is why <code>sum(x*x for x in xs)</code> can process the values as it iterates.</p>

## Edge cases to raise
<p>Volunteering these is most of what separates a correct answer from a good one.</p>

<p><strong>An exception raised inside the generator surfaces at the <code>next()</code> that triggers it</strong>, not where the generator was created - which can be in a different function. After the <code>with</code> block that opened the file has already closed it. Generators that read resources should own the <code>with</code>, not be handed an open handle.</p>

<p><strong><code>return</code> inside a generator sets <code>StopIteration.value</code></strong> rather than producing an item. <code>yield from</code> reads that value; a plain <code>for</code> loop discards it silently.</p>

<p><strong>Closing matters when there is cleanup.</strong> Abandoning a suspended generator in time runs its <code>finally</code> at collection time. This is not a schedule you control. <code>contextlib.closing</code> or an explicit <code>gen.close()</code> makes it deterministic.</p>
