title: What does `yield` actually do?
intro: What does yield do, and how is a generator different from a function that returns a list?

## The question, and what it is testing

<code>yield</code> turns the function into a <strong>factory for paused stack frames</strong>. Calling it runs nothing; each <code>next()</code> runs the body up to the next yield and freezes it there. The sequence is produced on demand, so memory is constant in the length &mdash; and it can only be walked once.

<p>Interviewers use this one because the answer separates people who have read the language from people who have only used it. Nothing here is obscure; all of it is observable, which is what the editor below is for.</p>

## Run it

The three states, the one-shot exhaustion, and the memory difference at a million items - printed rather than asserted.

The three states, driven by hand.

```python-run
import inspect

def countdown(n):
    print("  [the body starts only now]")
    while n > 0:
        yield n
        n -= 1

g = countdown(3)
print("calling it returned a:", type(g).__name__)
print("state:", inspect.getgeneratorstate(g))

print("first next() ->", next(g))
print("state:", inspect.getgeneratorstate(g))
print("the rest:", list(g))
print("state:", inspect.getgeneratorstate(g))

try:
    next(g)
except StopIteration:
    print("exhausted: a generator is one-shot")
```


One-shot is not a warning, it is silence - the second consumer sees an empty sequence and nothing complains.

```python-run
squares = (i * i for i in range(5))

print("sum once :", sum(squares))
print("sum again:", sum(squares), "<- not zero by accident; it is empty")

rows = (r for r in ["a", "b"])
first = [r for r in rows]
second = [r for r in rows]
print("first pass :", first)
print("second pass:", second, "<- already closed")
```


And what the laziness actually buys, in bytes.

```python-run
import sys

N = 1_000_000
as_list = [i * i for i in range(N)]
as_gen = (i * i for i in range(N))
print("memory for a million squares:")
print("  list     ", f"{sys.getsizeof(as_list):>9,}", "bytes")
print("  generator", f"{sys.getsizeof(as_gen):>9,}", "bytes")
print("  ratio    ", f"{sys.getsizeof(as_list) / sys.getsizeof(as_gen):>9,.0f}x")
print()
print("getsizeof on the list excludes the integers it points at,")
print("so the real gap is larger still.")
```

## A generator is a paused frame

<p>An ordinary function runs to a <code>return</code> and its stack frame is destroyed. A function containing <code>yield</code> does not run at all when you call it: you get a generator object that owns a frame which has never started.</p><p>Every <code>next()</code> resumes that frame, runs until the next <code>yield</code>, hands back the value, and freezes the frame again &mdash; local variables, instruction pointer and all. That is the whole mechanism, and it is why <code>yield</code> can appear in the middle of a loop and still work: the loop variable survives between resumes because the frame was never torn down.</p>

## What laziness buys, in one number

<p>The list version of a million squares allocates a million integers and a million pointers before you read the first one. The generator version allocates one object with a frame in it, and the editor below prints both sizes: a few megabytes against about a hundred bytes.</p><p>The other half is <em>latency</em>. A generator can hand you its first item immediately, which matters when the sequence is being read from a file or a network, and matters absolutely when the sequence is infinite. <code>itertools.count()</code> is a valid generator and an impossible list.</p>

## The three things you give up

<p><strong>It is one-shot.</strong> Once exhausted, it stays exhausted, and a second <code>for</code> loop over it runs zero times without error. This is the bug people actually hit: passing a generator to two functions and finding the second one saw an empty sequence.</p><p><strong>No <code>len()</code>, no indexing, no slicing.</strong> The length is not known without running it, so there is nothing to report. <code>itertools.islice</code> is the slicing replacement.</p><p><strong>Exceptions surface late.</strong> A generator that will raise on its fourth item raises on the fourth <code>next()</code>, which may be a long way from where it was created &mdash; inside a different function, or after a <code>with</code> block has already closed the file it was reading.</p>

## The follow-up you should expect

<p>"What is the difference between a generator and an iterator?" An iterator is the protocol &mdash; anything with <code>__next__</code> and <code>__iter__</code>. A generator is the easiest way to get one, written as a function instead of a class. Every generator is an iterator; most iterators in real code are generators.</p><p>And "what does a generator expression change?" Nothing but the syntax: <code>(x*x for x in xs)</code> is the same object as the equivalent <code>yield</code> function, which is worth knowing because it means <code>sum(x*x for x in xs)</code> never builds the list at all.</p>

## What to say out loud

<p>A function with yield returns a generator instead of running. Each next() resumes the body until the next yield, so values are produced lazily and memory stays constant however long the sequence is. The trade is that it is one-shot and has no len() - if I need to iterate twice or index it, I need a list.</p>

<p>Then stop. The commonest failure on a question like this is answering it correctly in one sentence and then talking for another minute until something wrong comes out.</p>

## What to notice while it runs

<ul>
<li>Calling the function runs <em>none</em> of the body &mdash; the state starts at <code>GEN_CREATED</code>.</li>
<li>Each resume ends at a <code>yield</code>, which is why the frame is <em>suspended</em> rather than finished.</li>
<li><code>GEN_CLOSED</code> is terminal: iterating again produces nothing, silently.</li>
</ul>

## Edge cases to raise

<p>Volunteering these is most of what separates a correct answer from a good one.</p>

<p><strong>An exception raised inside the generator surfaces at the <code>next()</code> that triggers it</strong>, not where the generator was created - which can be in a different function, after the <code>with</code> block that opened the file has already closed it. Generators that read resources should own the <code>with</code>, not be handed an open handle.</p>

<p><strong><code>return</code> inside a generator sets <code>StopIteration.value</code></strong> rather than producing an item. <code>yield from</code> reads that value; a plain <code>for</code> loop discards it silently.</p>

<p><strong>Closing matters when there is cleanup.</strong> Abandoning a suspended generator eventually runs its <code>finally</code> at collection time, which is not a schedule you control. <code>contextlib.closing</code> or an explicit <code>gen.close()</code> makes it deterministic.</p>

## The follow-ups interviewers ask

<p><strong>"What is the difference between a generator and an iterator?"</strong> An iterator is the protocol - anything with <code>__iter__</code> and <code>__next__</code>. A generator is the easiest way to produce one, written as a function rather than a class. Every generator is an iterator; most iterators you meet in real code are generators.</p>

<p><strong>"What does <code>yield from</code> do?"</strong> Delegates to another iterable, yielding everything it yields - and it forwards <code>send</code> and <code>throw</code> through to the inner generator, which is what made generator-based coroutines possible before <code>async def</code> existed.</p>

<p><strong>"Can a generator receive values as well as produce them?"</strong> Yes: <code>value = yield</code> makes the yield an expression, and <code>gen.send(x)</code> resumes it with <code>x</code> as that expression's value. This is how generators were used as coroutines for a decade, and it is worth knowing precisely because <code>async</code> replaced it.</p>

<p><strong>"How do you iterate a generator twice?"</strong> You do not. Either materialise it with <code>list()</code>, accepting the memory, or use <code>itertools.tee</code>, which buffers what the slower consumer has not read yet - so it trades the memory back in proportion to how far apart they get.</p>

## Common wrong answers

<p><strong>"It returns a list, just lazily."</strong> There is no list at any point. If the interviewer hears "list" they will ask what <code>len()</code> gives, and the answer is a <code>TypeError</code>.</p>

<p><strong>"Generators are faster."</strong> Not reliably. Each item costs a <code>__next__</code> call, so in wall-clock terms a generator is often a little slower than building the list. The win is memory and first-item latency, and saying "faster" invites a measurement you will lose.</p>

<p><strong>"You can index into it."</strong> You cannot. <code>itertools.islice</code> is the replacement, and it still has to walk the items it skips.</p>

## Recap in one screen

- Calling the function runs none of the body - the state starts at GEN_CREATED.
- Each resume ends at a yield, which is why the frame is suspended rather than finished.
- GEN_CLOSED is terminal: iterating again produces nothing, silently.
- The one-line answer: yield turns the function into a factory for paused stack frames.
- Worth trying: Replace list(g) with a second next(g) and watch the state stay GEN_SUSPENDED until the body actually returns.
- Worth trying: Add len(as_gen). The TypeError is the point: the length is not knowable without running it.
- Worth trying: Wrap the generator in itertools.tee(as_gen, 2) to get two independent iterators - and note it buffers, so it trades the memory back.
