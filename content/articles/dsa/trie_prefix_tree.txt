title: Trie (Prefix Tree)
intro: The structure that makes autocomplete feel instant.

## Before the details

A <strong>trie</strong> (from re<em>trie</em>val, usually pronounced "try") stores strings as paths through a tree. Each edge carries a character, so following a path from the root spells out a prefix. Words sharing a prefix share those nodes.

## Lookup Does Not Care How Many Words You Have

Searching for a word of length L costs <strong>O(L)</strong> &mdash; one step per character. Crucially, that is independent of how many words the trie contains. A dictionary of ten words and one of ten million both answer a five-letter query in five steps.

Compare that with a balanced BST at O(L log n), where n is the dictionary size. The trie wins because it navigates by <em>content</em> rather than by comparison.

## Prefix Queries Are the Real Superpower

A hash table can beat a trie for exact lookup &mdash; O(L) to hash versus O(L) to walk, with a smaller constant. But a hash table cannot answer <em>"which words start with 'car'?"</em> without scanning everything.

A trie answers it structurally: walk to the node for "car", then collect every word in the subtree beneath it. Press <strong>Autocomplete prefix</strong> and watch the subtree light up. That single property is why tries power search suggestions, IDE completion, and routing tables.

## Marking Where Words End

Not every node is a word. Inserting "car" and "care" means "car" ends partway down the path to "care", so each node carries an <strong>is-word</strong> flag, drawn here as a filled circle.

Without it you could not tell whether a path spells a real word or merely a prefix of one &mdash; and searching for "ca" would wrongly succeed.

## The Cost: Memory

Tries trade space for speed. A naive implementation gives every node an array of 26 child pointers, most of them null &mdash; enormously wasteful on sparse dictionaries.

Practical fixes: use a hash map of children instead of a fixed array, or switch to a <strong>radix tree</strong> (compressed trie), which merges chains of single-child nodes into one edge holding a whole substring. That is what IP routing tables use.

Watch the "saved by sharing" figure as you add words with common prefixes &mdash; sharing is what claws some of that memory back.

## Things to try

1. <strong>Load the sample words</strong> and note how <em>car</em>, <em>card</em>, <em>care</em> and <em>careful</em> all share one path for 'c-a-r'.
2. <strong>Insert a word starting with a new letter.</strong> A whole new branch appears from the root &mdash; nothing to share.
3. <strong>Search for 'car' after inserting 'card'.</strong> The path exists, but whether it is a word depends entirely on the end-of-word flag.
4. <strong>Autocomplete 'car'.</strong> Walk to that node, then every word beneath it is a completion &mdash; found without touching the rest of the dictionary.
5. <strong>Compare nodes with flat character count.</strong> The gap is exactly the memory prefix sharing saves.

## Worth remembering

A trie stores strings as paths, sharing common prefixes. Lookup is O(word length) regardless of dictionary size, and prefix queries fall out of the structure for free — which no hash table can match. The price is memory, mitigated by hash-map children or radix compression.
