title: Big-O Notation and Time Complexity
intro: The language for saying how an algorithm behaves when the data gets big.

## Quick Context

<strong>Big-O</strong> describes the <em>growth rate</em> of an algorithm's cost as input size n increases. It deliberately throws away constants and lower-order terms &mdash; an algorithm that takes <span class="mono-font">3n + 50</span> steps is simply <span class="mono-font">O(n)</span>, because for large n the 3 and the 50 stop mattering.

## Why Ignore the Constants?

Because hardware changes and growth does not. A machine twice as fast halves every constant, but an O(n&sup2;) algorithm is still O(n&sup2;) &mdash; double the input and you quadruple the work, forever.

Slide n and watch the table. At n = 10 every row looks affordable. By n = 1000 the quadratic column is a million operations and the exponential column has left the universe behind.

## The Six Classes You Will Meet

- <strong style="color:#4ade80">O(1) constant</strong> &mdash; cost never changes. Array index lookup, hash table access, stack push.
- <strong style="color:#22d3ee">O(log n) logarithmic</strong> &mdash; each step halves the problem. Binary search, balanced tree operations. Doubling n adds just <em>one</em> step.
- <strong style="color:#3b82f6">O(n) linear</strong> &mdash; touch every item once. Linear search, summing an array.
- <strong style="color:#8b5cf6">O(n log n)</strong> &mdash; the practical floor for comparison sorting. Merge sort, quick sort, heap sort.
- <strong style="color:#f59e0b">O(n&sup2;) quadratic</strong> &mdash; nested loops over the data. Bubble, insertion and selection sort. Fine for 100 items, painful for 100,000.
- <strong style="color:#ef4444">O(2&#8319;) exponential</strong> &mdash; every extra element doubles the work. Naive recursive Fibonacci, brute-force subsets. Intractable beyond roughly n = 40.

## Best, average and worst case

Big O usually refers to the worst case, and the other two matter in practice.

|Algorithm|Best|Average|Worst|
|---|---|---|---|
|Quick sort|O(n log n)|O(n log n)|O(n&sup2;)|
|Merge sort|O(n log n)|O(n log n)|O(n log n)|
|Insertion sort|O(n)|O(n&sup2;)|O(n&sup2;)|
|Hash table lookup|O(1)|O(1)|O(n)|

Two rows deserve comment.

<strong>Quick sort</strong> is O(n²) in the worst case and is the practical default anyway, because the worst case requires a pathological pivot sequence and randomised pivots make it vanishingly unlikely. Merge sort's guarantee is stronger and its constants are worse.

<strong>Insertion sort</strong> is O(n) on already-sorted input, which is why real sorting implementations use it for small or nearly-sorted subarrays inside a larger algorithm.

The related idea is <strong>amortised</strong> complexity: appending to a Python list is O(1) amortised, because occasional reallocations are spread across many cheap appends. Any individual append may be O(n); the average over a sequence is constant.

## Space Complexity Counts Too

The same notation describes <em>memory</em>. Merge sort is O(n log n) time but needs O(n) extra space for its temporary arrays; quick sort sorts in place with only O(log n) stack space. When memory is the constraint, that difference decides which one you use.

## Counting growth, not seconds

Big O describes how the work an algorithm does grows as the input grows. It deliberately ignores constants and hardware, because those change and the growth rate does not.

An algorithm that takes `3n + 50` steps is O(n). One that takes `n²/2` steps is O(n²). The constants are dropped, because for large enough n the shape of the curve is what decides whether the program finishes.

|Complexity|Name|n = 10|n = 1,000|n = 1,000,000|
|---|---|---|---|---|
|O(1)|Constant|1|1|1|
|O(log n)|Logarithmic|3|10|20|
|O(n)|Linear|10|1,000|1,000,000|
|O(n log n)|Linearithmic|30|10,000|20,000,000|
|O(n&sup2;)|Quadratic|100|1,000,000|10&#185;&sup2;|
|O(2&#8319;)|Exponential|1,024|astronomical|impossible|

That table is the whole argument. At n = 1,000,000, an O(n log n) algorithm does 20 million operations &mdash; a fraction of a second. An O(n²) algorithm does 10¹² &mdash; hours. The difference is not an optimisation; it is the difference between working and not.

## Reading complexity from code

The rules are mechanical once you see them.

<strong>A loop over the input is O(n).</strong>

<strong>Nested loops multiply.</strong> Two loops over n is O(n²); three is O(n³).

<strong>Sequential loops add,</strong> and the larger term wins: `O(n) + O(n²) = O(n²)`.

<strong>Halving the search space each step is O(log n).</strong> Binary search on a million items takes 20 steps, because 2²⁰ ≈ 1,000,000.

<strong>Dictionary and set lookups are O(1).</strong> This is the single most useful fact for writing fast Python.

```python
# O(n^2) - for each item, scan the whole list
for a in items:
    if a in other_list:      # this scan is O(n)
        ...

# O(n) - build a set once, then constant-time lookups
other = set(other_list)
for a in items:
    if a in other:           # O(1)
        ...
```

That transformation &mdash; replacing a repeated scan with a pre-built set or dictionary &mdash; is the most common and most effective optimisation in everyday code, and it usually makes the code shorter as well.

## Things to try

1. <strong>Start at n = 10.</strong> Every curve is bunched together &mdash; at small inputs, complexity genuinely does not matter and the constants dominate.
2. <strong>Slide to n = 60.</strong> The exponential curve leaves the chart almost immediately, then the quadratic. The separation is the entire point of the notation.
3. <strong>Read the table at n = 1,000,000.</strong> O(log n) needs about 20 operations; O(n&sup2;) needs 10&sup1;&sup2;. That is the difference between instant and never.
4. <strong>Tick log-scale y.</strong> Each class becomes a straight line with its own slope &mdash; the cleanest way to see that these are genuinely different families, not just different constants.
5. <strong>Compare O(n) with O(n log n).</strong> The gap is small even at large n, which is why an O(n log n) sort is considered essentially as good as linear in practice.

## Worth remembering

Big-O measures how cost grows, not how long something takes. Constants are ignored because growth is what survives faster hardware. Know roughly where each of your algorithms sits, and you can predict which one falls over first when the data gets big.

## Space complexity

The same notation applies to memory, and it is frequently the binding constraint.

|Approach|Time|Space|
|---|---|---|
|Sort in place|O(n log n)|O(1) extra|
|Merge sort|O(n log n)|O(n) extra|
|Recursion depth d|&mdash;|O(d) stack|
|Memoised recursion|Faster|O(states) extra|

Recursion's space cost is easy to overlook: each call holds a frame on the stack, so recursion depth n uses O(n) memory and can overflow. Python's default limit is around 1,000 frames, which is why deep recursion needs converting to iteration or an explicit stack.

Memoisation is the classic time-for-space trade: recursive Fibonacci is O(2ⁿ) time and O(n) space; memoised it is O(n) time and O(n) space. That single change turns an impossible computation into an instant one.

## Where it misleads

Big O is an asymptotic statement, and three caveats matter in real code.

<strong>Constants can dominate at realistic sizes.</strong> An O(n log n) algorithm with a huge constant can lose to an O(n²) one for n = 50. This is why real sorting implementations switch to insertion sort below a threshold.

<strong>Cache behaviour is invisible to the notation.</strong> Sequential array access can be several times faster than pointer-chasing through a linked list with the same complexity, because of memory locality.

<strong>The input's shape matters.</strong> Nearly-sorted data, many duplicates, or adversarial patterns can move an algorithm between its best and worst case.

So the discipline is: use Big O to rule out approaches that cannot possibly scale, and <strong>measure</strong> to choose between approaches that could. It is a filter, not a benchmark.

## Questions people ask

<strong>Why drop constants?</strong> Because they depend on hardware and implementation, while the growth rate is a property of the algorithm. `2n` and `100n` are both O(n).

<strong>What is the difference between O, &Theta; and &Omega;?</strong> O is an upper bound, &Omega; a lower bound, &Theta; both. In practice people say O and mean &Theta;.

<strong>Is O(log n) fast?</strong> Extremely. Twenty steps for a million items, thirty for a billion. Any O(log n) algorithm is effectively instant at realistic sizes.

<strong>Which base for the logarithm?</strong> It does not matter &mdash; changing base multiplies by a constant, which is dropped. Base 2 is conventional because halving is the common operation.

<strong>Is O(n log n) much worse than O(n)?</strong> Only by the log factor &mdash; 20&times; at a million items. Both are practical; O(n²) is where the wall is.

<strong>Does Big O tell me which is faster?</strong> Only asymptotically. For a specific input size, measure.

## Recap in one screen

- Big O describes how work grows with input size, ignoring constants and hardware.
- Loops over the input are O(n); nested loops multiply; halving is O(log n); dictionary lookups are O(1).
- Replacing a repeated scan with a set or dictionary is the most common real-world speed-up.
- Worst case is what Big O usually means; best and amortised cases explain why quick sort and list append are used anyway.
- Use it to rule out what cannot scale, then measure to choose between what can.
