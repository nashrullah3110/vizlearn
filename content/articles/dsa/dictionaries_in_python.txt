title: Python Dictionaries
intro: A dictionary maps unique keys to values. Python implements it as a hash table, giving average constant-time lookup and insertion while preserving insertion order.

## Look up by key

For `d[key]`, Python hashes the key to find a candidate slot, then checks equality to resolve collisions. Lookup and insertion are average <code>O(1)</code>, but can take <code>O(n)</code> in the worst case. Iterating a dictionary takes <code>O(n)</code> time and follows insertion order, a language guarantee since Python 3.7.

Use **Method**, **Key**, and **Value** in the visualizer, then press **Execute**. Compare a lookup of a present key with a missing one: direct indexing raises `KeyError` when the key is absent.

## Choose how to handle a missing key

```python
d = {"apples": 3}

d["pears"]                 # raises KeyError
d.get("pears", 0)          # returns 0 without inserting
d.setdefault("pears", 0)   # returns 0 and inserts the key
```

Use `get` when a default is needed without mutation. Use `setdefault` when creating a missing entry is intended. For counting or grouping, `collections.Counter` and `defaultdict` often express the operation more clearly.

Membership checks keys: `"apples" in d` is average <code>O(1)</code>. Checking `"apples" in d.values()` scans values and takes <code>O(n)</code>. `d.keys()`, `d.values()`, and `d.items()` return dynamic views; creating a view is constant-time, iterating it is linear.

## Keys must be hashable

Keys need a stable hash and equality behavior. Strings, numbers, and tuples of hashable values can be keys; lists and dictionaries cannot. A tuple containing a list is also unhashable. A custom type that defines equality must keep its hash consistent with that equality; mutating hash-relevant state after insertion can make a key impossible to find.

```python
counts = {}
for word in ["red", "blue", "red"]:
    counts[word] = counts.get(word, 0) + 1
# {"red": 2, "blue": 1}
```

## When to use another structure

Use a dictionary for key-to-value lookup. Use a set when only membership matters, a list when order and indexed access matter, and a `deque` for efficient operations at both ends. Hash tables do not maintain sorted order; sort keys or use an ordered-search structure when that is the requirement.

## Common mistakes

- **Assuming worst-case constant time:** average performance is constant, but collisions and resizing have costs.
- **Using `setdefault` to inspect:** it inserts a missing key as a side effect.
- **Checking values for membership repeatedly:** use a set if repeated membership checks are needed.
- **Using a mutable key:** its hash and equality behavior must remain stable.
