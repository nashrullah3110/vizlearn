title: Graph Representations
intro: Before BFS, DFS or Dijkstra can run, the graph has to live somewhere.

## What this is


A <strong>graph</strong> is a set of <em>vertices</em> connected by <em>edges</em>. Every graph algorithm on this site &mdash; BFS, DFS, Dijkstra, A* &mdash; assumes some way of storing those edges. And that choice quietly decides their performance.

The three standard representations are the adjacency matrix, the adjacency list. And the edge list. Each trades space for speed on different operations.

## Adjacency Matrix

A V&times;V grid where <span class="mono-font">M[i][j] = 1</span> means an edge exists from i to j.

- <strong style="color: var(--c-good)">Edge lookup is O(1)</strong> &mdash; one array access. Unbeatable.
- <strong style="color: var(--c-bad)">Space is O(V&sup2;)</strong> regardless of edge count. A graph with 10,000 vertices needs 100 million entries even if it has ten edges.
- Listing a vertex's neighbours costs O(V) &mdash; you must scan an entire row, mostly zeros.

For an undirected graph the matrix is symmetric, so half of it is redundant.

## Adjacency List

An array of lists: each vertex stores only the neighbours it actually has.

- <strong style="color: var(--c-good)">Space is O(V + E)</strong> &mdash; proportional to real edges, not possible ones.
- <strong style="color: var(--c-good)">Iterating neighbours is O(degree)</strong> &mdash; exactly what BFS and DFS do at every step. This is why they use lists.
- <strong style="color: var(--c-b)">Edge lookup is O(degree)</strong> &mdash; you scan the list rather than jumping to it.

## The same graph in both forms

Take four vertices A, B, C, D and edges A–B, A–C, C–D. The adjacency list stores `A: [B, C]`, `B: [A]`, `C: [A, D]`, `D: [C]`. An undirected adjacency matrix records the same links in a 4×4 grid, with mirrored entries for each edge. The list stores only the six neighbor references; the matrix reserves all 16 cells.

## The Rule of Thumb

Slide density and watch the two memory figures cross over.

- <strong>Sparse graphs</strong> (E &lll; V&sup2;) &mdash; use an <strong>adjacency list</strong>. Road networks, social graphs and web links are all sparse: most pairs are not connected.
- <strong>Dense graphs</strong> (E approaching V&sup2;) &mdash; a <strong>matrix</strong> becomes competitive on memory and wins outright on lookup speed.

Real-world graphs are by far sparse, which is why the adjacency list is the default in practice.

## It Changes Algorithm Cost

This is not just a storage detail. BFS and DFS are <strong>O(V + E)</strong> with an adjacency list but <strong>O(V&sup2;)</strong> with a matrix, because each vertex must scan a whole row. On a sparse graph with a million vertices that is the difference between seconds and hours.

Similarly, Dijkstra is O(V&sup2;) with a matrix and simple scanning, but O((V+E) log V) with an adjacency list and a binary heap.

## A Third Option: Edge List

Simply a list of <span class="mono-font">(u, v, weight)</span> triples. Terrible for asking "who are u's neighbours?" but ideal when an algorithm processes every edge in sorted order &mdash; which is exactly what Kruskal's MST algorithm does.

## Experiments to try

1. <strong>Start at 30% density.</strong> The matrix is mostly zeros &mdash; every one of them still occupies memory.
2. <strong>Switch to the adjacency list.</strong> The same graph, stored in a fraction of the space, with only real edges recorded.
