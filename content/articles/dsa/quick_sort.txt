## Partitioning, not merging



Quicksort partitions an array around a pivot, placing smaller values on one side and larger values on the other, then sorts each side recursively. Its average running time is O(n log n), but poor pivot choices can produce O(n²) work.

## Work one through by hand

Sort <span class="mono-font">[7, 2, 9, 4, 1, 8]</span> using the last element, 8, as pivot.

less than 8: [7, 2, 4, 1] &nbsp;|&nbsp; pivot: 8 &nbsp;|&nbsp; greater: [9]

8 is now final at index 4. Recurse left on <span class="mono-font">[7, 2, 4, 1]</span> with pivot 1:

less: [] &nbsp;|&nbsp; pivot: 1 &nbsp;|&nbsp; greater: [7, 2, 4]

Then <span class="mono-font">[7, 2, 4]</span> with pivot 4 gives <span class="mono-font">[2] | 4 | [7]</span>, placing the pivot in its final position. This partition is balanced; an earlier split with 0 elements on one side and 3 on the other illustrates the unbalanced case that can lead to quadratic work.

## Best case, worst case, and why the average holds

When the pivot lands near the median, each partition halves the array, giving log n levels of O(n) partitioning work: <strong>O(n log n)</strong>.

When the pivot is consistently the smallest or largest element, one side gets n&minus;1 elements and the other gets none. That gives n levels of O(n) work: <strong>O(n&sup2;)</strong>. With a fixed first- or last-element pivot, already-sorted input is one example that causes this behavior.

With randomized pivot selection, the expected running time is O(n log n) for a fixed input, though the worst case remains quadratic. A 90/10 split at every level is still logarithmic in depth, with a larger constant than balanced partitions.

## Exploration guide

1. <strong>Watch a pivot settle permanently.</strong> Set <strong>Array Size</strong> to 15 and press <strong>Next Step</strong> through one partition. When it completes, the pivot is in its final position and is never moved again. Unlike merge sort, elements finish one at a time.
2. <strong>Find a bad split.</strong> Press <strong>Randomize Array</strong> and <strong>Auto-Run</strong> a few times, watching the partition sizes. Sometimes one side gets almost all of it; that single unbalanced level is a small dose of the worst case.

## Why it beats merge sort in practice

Both are O(n log n) on average, yet quick sort is usually faster on arrays. Three reasons:

- <strong>No auxiliary array.</strong> Partitioning is in-place. The recursive stack is O(log n) on balanced partitions but can grow to O(n) in the worst case. Merge sort needs an O(n) buffer.
- <strong>Cache behaviour.</strong> Partitioning sweeps two pointers inward through contiguous memory. This is close to the ideal access pattern for a CPU prefetcher.
- <strong>Smaller constant factor.</strong> The inner loop is a comparison and a conditional swap, with no writes to a second array and no copy-back.

Production implementations use safeguards. Random pivots reduce dependence on input order; median-of-three helps on common patterns but is not a worst-case guarantee. Introsort, used by C++ `std::sort`, switches to heapsort when recursion gets too deep, preserving an O(n log n) worst-case bound.

## Common mistakes

- <strong>Always taking the first or last element as pivot.</strong> This makes already-sorted input the worst case. This is the input you are most likely to receive. Use median-of-three or a random pivot.
- <strong>Mishandling duplicates.</strong> An array of all-equal elements sends every element to one side under naive partitioning, giving O(n&sup2;). Three-way (Dutch national flag) partitioning splits into less / equal / greater and handles it in linear time.
- <strong>Recursing on the larger side first.</strong> Recursing into the smaller partition and looping on the larger caps stack depth at O(log n). Doing it the other way risks stack overflow on adversarial input.
- <strong>Expecting stability.</strong> Quick sort is not stable &mdash; partitioning swaps distant elements and reorders equal keys. If you need stability, use merge sort.
