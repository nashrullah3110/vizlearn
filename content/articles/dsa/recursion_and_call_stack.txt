## Quick Context

<strong>Recursion</strong> is a function calling itself on a smaller version of the same problem. It needs exactly two things: a <strong>base case</strong> that stops the descent, and a <strong>recursive case</strong> that moves toward it.<span class="kw">def</span><span class="fn">factorial</span><span class="kw">if</span><span class="lit">1</span><span class="kw">return</span><span class="lit">1</span><span class="cm"># base case</span><span class="kw">return</span><span class="fn">factorial</span><span class="lit">1</span><span class="cm"># recursive case</span>

## The Call Stack Does the Remembering

The confusing part is that a recursive function does not finish before calling itself again. <span class="mono-font">factorial(5)</span> must pause, wait for <span class="mono-font">factorial(4)</span>, and only then multiply.

Each paused call keeps its own frame &mdash; its own copy of <span class="mono-font">n</span> and its own place to resume. Step through and watch frames stack up on the way <em>down</em>, then unwind as answers travel back <em>up</em>. Nothing is computed until the base case is reached; everything is computed on the way back.

## Stack Overflow Is Real

Select <strong>countdown &mdash; no base case</strong>. Frames pile up and never pop, because nothing stops the recursion. Memory reserved for the stack is finite, so eventually the program crashes with a <em>stack overflow</em>.

Typical limits are a few thousand frames (Python defaults to 1000). Every recursive function you write needs a base case that is genuinely reachable &mdash; a base case that the recursion never hits is no base case at all.

## Naive Fibonacci: The Cautionary Tale

Choose <strong>fibonacci &mdash; naive</strong> and raise n. The call counter grows explosively, because <span class="mono-font">fib(n)</span> calls <span class="mono-font">fib(n-1)</span> and <span class="mono-font">fib(n-2)</span>, which recompute the same values over and over. That is <strong>O(2&#8319;)</strong>: fib(30) needs over 1.3 million calls to return a number you could compute by hand.

Now switch to <strong>memoised</strong> at the same n. Results are cached the first time, so each value is computed once and the call count collapses to roughly 2n &mdash; from exponential to linear, with a dictionary. That is dynamic programming in one change, and it is the subject of the next module.

## When to Use It

Recursion shines on <strong>self-similar</strong> problems: trees, nested structures, divide-and-conquer, backtracking. Traversing a BST recursively is three lines; iteratively it needs an explicit stack.

Prefer a loop when the problem is linear &mdash; a recursive sum of an array just burns stack frames for nothing. And note that some languages (though not Python or JavaScript) optimise <em>tail recursion</em> into a loop, avoiding the stack growth entirely.

## Guided experiments

1. <strong>Step through factorial(5).</strong> Watch five frames build downward, then multiply back up as each returns. Nothing multiplies until the base case is hit.
2. <strong>Note where the answer appears.</strong> All the real work happens during the unwinding, not the descent.
3. <strong>Run naive fibonacci at n=5, then n=10.</strong> The call count roughly quadruples for five extra steps &mdash; exponential growth, visible.
4. <strong>Switch to memoised at the same n.</strong> Same answer, a fraction of the calls, because repeats are served from the cache.
5. <strong>Select countdown with no base case.</strong> Frames accumulate without limit &mdash; a stack overflow in slow motion.

## Summing up

Recursion is the call stack made visible: each call gets a frame, frames build on the way down and unwind on the way back. Always ensure the base case is reachable, and watch for repeated subproblems &mdash; memoising them is the difference between exponential and linear.
