## Quick Context

<strong>Recursion</strong> is a function calling itself on a smaller version of the same problem. It needs exactly two things: a <strong>base case</strong> that stops the descent, and a <strong>recursive case</strong> that moves toward it.<span class="kw">def</span><span class="fn">factorial</span><span class="kw">if</span><span class="lit">1</span><span class="kw">return</span><span class="lit">1</span><span class="cm"># base case</span><span class="kw">return</span><span class="fn">factorial</span><span class="lit">1</span><span class="cm"># recursive case</span>

## The Call Stack Does the Remembering

The confusing part is that a recursive function does not finish before calling itself again. <span class="mono-font">factorial(5)</span> must pause, wait for <span class="mono-font">factorial(4)</span>, and only then multiply.

Each paused call keeps its own frame &mdash; its own copy of <span class="mono-font">n</span> and its own place to resume. Step through and watch frames stack up on the way <em>down</em>, then unwind as answers travel back <em>up</em>. Nothing is computed until the base case is reached; everything is computed on the way back.

## Stack Overflow Is Real

Select <strong>countdown &mdash; no base case</strong>. Frames pile up and never pop, because nothing stops the recursion. Memory reserved for the stack is finite, so eventually the program crashes with a <em>stack overflow</em>.

Typical limits are a few thousand frames (Python defaults to 1000). Every recursive function you write needs a base case that is genuinely reachable &mdash; a base case that the recursion never hits is no base case at all.

## Naive Fibonacci: The Cautionary Tale

Choose <strong>fibonacci &mdash; naive</strong> and raise n. The call counter grows explosively, because <span class="mono-font">fib(n)</span> calls <span class="mono-font">fib(n-1)</span> and <span class="mono-font">fib(n-2)</span>, which recompute the same values over and over. That is <strong>O(2&#8319;)</strong>: fib(30) needs over 1.3 million calls to return a number you could compute by hand.

Now switch to <strong>memoised</strong> at the same n. Results are cached the first time, so each value is computed once and the call count collapses to roughly 2n &mdash; from exponential to linear, with a dictionary. That is dynamic programming in one change, and it is the subject of the next module.

## When to Use It

Recursion shines on <strong>self-similar</strong> problems: trees, nested structures, divide-and-conquer, backtracking. Traversing a BST recursively is three lines; iteratively it needs an explicit stack.

Prefer a loop when the problem is linear &mdash; a recursive sum of an array just burns stack frames for nothing. And note that some languages (though not Python or JavaScript) optimise <em>tail recursion</em> into a loop, avoiding the stack growth entirely.

## A function that calls itself

Recursion solves a problem by solving a smaller instance of the same problem. Two parts are required, and omitting either is the classic failure:

<strong>A base case</strong> that returns without recursing.
<strong>A recursive case</strong> that moves towards the base case.

```python
def factorial(n):
    if n <= 1:              # base case
        return 1
    return n * factorial(n - 1)     # recursive case, strictly smaller
```

"Moves towards the base case" is the part that needs checking. `factorial(n - 1)` reduces n by one, so it must eventually reach 1. A recursive call that does not strictly reduce the problem produces infinite recursion, and Python raises `RecursionError` after about 1,000 frames.

## What the call stack actually holds

Each call allocates a <strong>frame</strong> containing the function's local variables, its arguments, and where to return to. Frames stack up, and unwind as calls return.

Tracing `factorial(4)`:

|Stack (top last)|Action|
|---|---|
|factorial(4)|calls factorial(3)|
|factorial(4), factorial(3)|calls factorial(2)|
|factorial(4), factorial(3), factorial(2)|calls factorial(1)|
|… factorial(1)|returns 1|
|… factorial(2)|returns 2|
|factorial(4), factorial(3)|returns 6|
|factorial(4)|returns 24|

Two consequences follow directly.

<strong>Recursion depth costs memory.</strong> Depth n means n frames, so recursion is O(n) space even when the equivalent loop is O(1).

<strong>The stack has a limit.</strong> Python's is around 1,000 frames by default, deliberately conservative to fail cleanly rather than segfaulting. That limit is why recursion over a large list or a long chain must be converted to iteration.

```python
import sys
sys.setrecursionlimit(10_000)      # raises the limit, up to the real C stack
```

Raising it works and moves the failure mode from a clean exception to a possible crash. Converting to iteration is the more robust answer.

## Where recursion is the natural expression

Recursion is not a general substitute for loops. It is the right choice when the <em>data</em> or the <em>problem</em> is recursive.

|Problem|Why recursion fits|
|---|---|
|Tree traversal|A tree's children are trees|
|Divide and conquer|Merge sort, quick sort, binary search|
|Backtracking|Try, recurse, undo|
|Nested structures|JSON, directory trees, expression parsing|
|Graph DFS|The recursion stack <em>is</em> the current path|
|Mathematical recurrences|Fibonacci, Catalan numbers, Ackermann|

Iterating over a flat list, by contrast, is a loop &mdash; writing it recursively adds stack frames for nothing.

The graph row is worth expanding: DFS's recursion stack holds exactly the path from the root to the current node, which is why cycle detection and topological sorting fall out so naturally. Reproducing that iteratively requires maintaining the path explicitly.

## Guided experiments

1. <strong>Step through factorial(5).</strong> Watch five frames build downward, then multiply back up as each returns. Nothing multiplies until the base case is hit.
2. <strong>Note where the answer appears.</strong> All the real work happens during the unwinding, not the descent.
3. <strong>Run naive fibonacci at n=5, then n=10.</strong> The call count roughly quadruples for five extra steps &mdash; exponential growth, visible.
4. <strong>Switch to memoised at the same n.</strong> Same answer, a fraction of the calls, because repeats are served from the cache.
5. <strong>Select countdown with no base case.</strong> Frames accumulate without limit &mdash; a stack overflow in slow motion.

## Summing up

Recursion is the call stack made visible: each call gets a frame, frames build on the way down and unwind on the way back. Always ensure the base case is reachable, and watch for repeated subproblems &mdash; memoising them is the difference between exponential and linear.

## Converting recursion to iteration

Two situations, and they need different techniques.

<strong>Tail recursion</strong> &mdash; the recursive call is the last operation, with nothing left to do after it &mdash; converts to a simple loop:

```python
def factorial_iter(n):
    result = 1
    for i in range(2, n + 1):
        result *= i
    return result
```

Some languages eliminate tail calls automatically so the stack does not grow. <strong>Python deliberately does not</strong>, on the grounds that stack traces are more valuable for debugging. So tail recursion in Python still consumes frames, and the loop is genuinely better.

<strong>Non-tail recursion</strong> &mdash; work remains after the recursive call, as in tree traversal &mdash; needs an explicit stack:

```python
def inorder_iter(root):
    out, stack, node = [], [], root
    while stack or node:
        while node:                      # go left as far as possible
            stack.append(node)
            node = node.left
        node = stack.pop()
        out.append(node.value)           # visit
        node = node.right                # then go right
    return out
```

That is what recursion was doing implicitly. The explicit version is longer and harder to read, which is exactly why recursion is preferred where depth allows.

## Memoisation: recursion made efficient

Naive recursive Fibonacci recomputes the same values enormously many times &mdash; O(2ⁿ) calls, because `fib(n-1)` and `fib(n-2)` share almost all their work.

Caching results collapses it to O(n):

```python
from functools import lru_cache

@lru_cache(maxsize=None)
def fib(n):
    return n if n < 2 else fib(n-1) + fib(n-2)
```

|n|Naive calls|Memoised calls|
|---|---|---|
|20|21,891|21|
|40|331,160,281|41|

One decorator, and an impossible computation becomes instant. The requirement is that arguments are hashable &mdash; tuples rather than lists.

This is dynamic programming in its top-down form, and it is the single most valuable thing to know about making recursion practical.

## Common mistakes

- <strong>No base case,</strong> or one that is unreachable &mdash; infinite recursion.
- <strong>A recursive call that does not shrink the problem,</strong> which is the same failure in disguise.
- <strong>Forgetting to return the recursive result.</strong> `factorial(n-1)` without `return` gives `None`.
- <strong>Mutable default arguments</strong> as accumulators &mdash; `def f(n, acc=[])` shares one list across all calls.
- <strong>Exceeding the recursion limit</strong> on deep input; convert to iteration.
- <strong>Recomputing subproblems</strong> without memoisation, turning a linear problem exponential.
- <strong>Recursing over a flat structure</strong> where a loop is clearer and cheaper.

## Questions people ask

<strong>Is recursion slower than iteration?</strong> In Python, yes &mdash; each call has function-call overhead and a frame. Prefer it for clarity on recursive structures, not for speed.

<strong>Why does Python limit recursion depth?</strong> To raise a clean `RecursionError` rather than overflowing the C stack and crashing.

<strong>Does Python optimise tail calls?</strong> No, deliberately &mdash; the maintainers prioritise usable stack traces.

<strong>How deep can I recurse?</strong> About 1,000 frames by default; raising the limit works up to the actual stack size.

<strong>When should I choose recursion?</strong> When the data is recursive &mdash; trees, nested structures, divide and conquer, backtracking.

<strong>What is mutual recursion?</strong> Two functions calling each other, which is common in recursive-descent parsers.

## Recap in one screen

- A base case and a strictly smaller recursive case are both required.
- Each call holds a stack frame, so depth n costs O(n) memory and Python caps it around 1,000.
- Recursion fits recursive data: trees, nested structures, divide and conquer, backtracking, DFS.
- Tail recursion converts to a loop; non-tail recursion needs an explicit stack, which is why recursion reads better.
- `@lru_cache` turns exponential recursion into linear &mdash; the most valuable single line in this topic.
