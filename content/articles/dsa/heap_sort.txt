title: Heap Sort
intro: The sort that never has a bad day &mdash; and never wins a benchmark either.

## Before the details



<strong>Heap sort</strong> turns the array into a max-heap, then repeatedly moves the largest element to the end. It sorts <em>in place</em> with a guaranteed O(n log n) in every case &mdash; best, average and worst.

That worst-case guarantee is its strongest property. Quicksort averages O(n log n) but degrades to O(n&sup2;) on adversarial input.

## Phase 1: Heapify in O(n)

Starting from the last non-leaf node and working backwards, sift each element down. Leaves are already valid heaps of size one, so half the array needs no work at all.

It looks like it should be O(n log n), but it is <strong>O(n)</strong>. Most nodes are near the bottom and can only sink a short distance; only the root can travel the full height. Summing the actual work gives a series that converges to O(n).

## Phase 2: Extract n Times

The maximum is always at index 0. Swap it with the last element of the heap, shrink the heap by one, and sift the new root down to restore the heap property.

The array splits into two regions: an unsorted heap at the front and a growing <strong>sorted tail</strong> at the back. Watch the green region grow from the right as you step.

Each extraction costs O(log n) and there are n of them &rarr; O(n log n). Adding the O(n) heapify leaves O(n log n) overall.

## Why It Loses to Quick Sort in Practice

Heap sort has better worst-case guarantees than quick sort (which can degrade to O(n&sup2;)) and uses less memory than merge sort (which needs O(n)). Yet quick sort is usually faster in the real world.

The reason is <strong>cache locality</strong>. Sifting jumps between indices i, 2i+1 and 2i+2 &mdash; wildly scattered addresses that defeat the CPU cache. Quick sort scans contiguously and stays cache-friendly. Heap sort also does more swaps and is <strong>not stable</strong>.

Its real niche is guaranteed worst-case behaviour with constant memory &mdash; embedded and real-time systems. It also appears inside <em>introsort</em> (used by C++'s <span class="mono-font">std::sort</span>), which starts with quick sort and switches to heap sort if recursion gets too deep, capping the worst case.

## Its position among the O(n log n) sorts

|&nbsp;|Heap sort|Quick sort|Merge sort|
|---|---|---|---|
|Worst case|O(n log n)|O(n&sup2;)|O(n log n)|
|Extra space|O(1)|O(log n) stack|O(n)|
|Stable|No|No|Yes|
|Cache behaviour|Poor|Excellent|Good|
|Typical speed|Slowest of the three|Fastest|Middle|

Heap sort is the only one with <strong>both</strong> a guaranteed O(n log n) and O(1) extra space. That combination is unique among the classical sorts, and it is why the algorithm survives.

It is also the slowest of the three in practice, and the reason is cache behaviour: sifting jumps between indices i, 2i+1 and 2i+2, which on a large array means touching memory pages far apart. Quick sort's partitioning scans sequentially, which modern CPUs handle far better.

So heap sort is rarely chosen on its own &mdash; and it is chosen as a <em>fallback</em>, which is a genuinely important role.

## Exploration guide

1. <strong>Watch phase 1.</strong> Sifting starts from the middle of the array, never the leaves &mdash; that is why heapify is O(n).
2. <strong>Note when the heap is valid.</strong> Every parent now beats its children, but the array is far from sorted &mdash; a heap is only partially ordered.

## Introsort: where heap sort actually runs

C++'s `std::sort` is <strong>introsort</strong>, and heap sort is its safety net.

The algorithm starts with quick sort. It tracks recursion depth, and if the depth exceeds roughly 2 log n &mdash; evidence that pivots are being chosen badly and the O(n²) case is developing &mdash; it switches to heap sort for that subarray. Below a small threshold it finishes with insertion sort.

The result combines all three strengths:

|Component|Provides|
|---|---|
|Quick sort|Speed in the common case|
|Heap sort|The O(n log n) worst-case guarantee|
|Insertion sort|Low overhead on small subarrays|

That is heap sort's real production role: it is never the fastest choice, and it is the one that makes quick sort's worst case impossible. Without it, `std::sort` would have no guarantee.

Python takes a different route &mdash; Timsort, which is a stable merge sort &mdash; because Python guarantees stability and heap sort is not stable.
