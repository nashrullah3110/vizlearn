title: Binary Search: A Practical Guide
intro: Halve the search space on every comparison. Twenty steps are enough to find one item among a million - provided the array is sorted.

## The one assumption that makes it work


[Linear search](linear_search.html) checks every element in order and takes O(n) comparisons. Binary search takes O(log n) by cutting the search space in half on every step. On a million elements, that is 20 comparisons instead of a million &mdash; but it only works if the data is sorted.

## Work one through by hand

Search for <span class="mono-font">23</span> in <span class="mono-font">[2, 5, 8, 12, 16, 23, 38, 56, 72, 91]</span>, ten elements, indices 0&ndash;9.

lo=0, hi=9 &rarr; mid=4 &rarr; a[4]=16 &lt; 23 &rarr; go right, lo=5

lo=5, hi=9 &rarr; mid=7 &rarr; a[7]=56 &gt; 23 &rarr; go left, hi=6

lo=5, hi=6 &rarr; mid=5 &rarr; a[5]=23 &rarr; found, index 5

Three comparisons against a linear search’s six. The gap is unremarkable at ten elements and decisive at a million: linear search averages 500,000 comparisons, binary search takes at most 20.

## Where log n comes from

The search space starts at n and halves every step: n, n/2, n/4, n/8, and so on. The search ends when one element is left, so the question is how many halvings that takes:

n / 2<sup>k</sup> = 1 &nbsp;&rarr;&nbsp; 2<sup>k</sup> = n &nbsp;&rarr;&nbsp; k = log<sub>2</sub>(n)

That is the definition of a logarithm, not an analogy for it. Doubling the array adds exactly one comparison. Going from 1,000 to 1,000,000 elements &mdash; a thousandfold increase &mdash; adds ten.

## Halving the search space

Binary search finds a value in a <strong>sorted</strong> array by repeatedly discarding half of it.

Look at the middle element. If it matches, done. If the target is smaller, everything from the middle rightwards is irrelevant. If larger, everything leftwards is. Repeat on what remains.

Searching for 23 in [2, 5, 8, 12, 16, 23, 38, 56, 72, 91]:

|Step|Range|Middle|Comparison|
|---|---|---|---|
|1|0&ndash;9|16 (index 4)|23 &gt; 16, search right|
|2|5&ndash;9|38 (index 7)|23 &lt; 38, search left|
|3|5&ndash;6|23 (index 5)|Found|

Three comparisons for ten elements. Linear search would have taken six.

The scaling is what makes it important:

|Array size|Linear search|Binary search|
|---|---|---|
|100|100|7|
|1,000,000|1,000,000|20|
|1,000,000,000|1,000,000,000|30|

Thirty comparisons for a billion items. That is the practical meaning of O(log n).

## Experiments to try

1. <strong>Count the halvings.</strong> Set <strong>Array Size</strong> to 25 and press <strong>Next Step</strong> repeatedly, watching the shaded region shrink. It takes about five steps, because 2<sup>5</sup> = 32 is the first power of two above 25.
2. <strong>Double the array, add one step.</strong> Run a search at <strong>Array Size</strong> 12 and count the steps. Now set it to 24 and count again. One extra step, not twice as many &mdash; that is the logarithm, visible directly.

## Traps worth knowing

- <strong>Integer overflow in the midpoint.</strong> Writing <span class="mono-font">mid = (lo + hi) / 2</span> overflows when lo and hi are large. Use <span class="mono-font">mid = lo + (hi &minus; lo) / 2</span>. This bug sat in the JDK’s binary search for nine years.
- <strong>Off-by-one in the bounds.</strong> The two conventions &mdash; inclusive <span class="mono-font">hi = n &minus; 1</span> with <span class="mono-font">while (lo &lt;= hi)</span>, or exclusive <span class="mono-font">hi = n</span> with <span class="mono-font">while (lo &lt; hi)</span> &mdash; are both correct, and mixing them gives an infinite loop or a missed last element. Pick one and keep it.
- <strong>Assuming the array is sorted.</strong> Binary search on unsorted data does not error; it silently returns wrong answers, which is far worse. If sortedness is an assumption rather than an invariant, it will eventually be violated.
- <strong>Wanting the first duplicate.</strong> Plain binary search returns <em>some</em> match, not the leftmost. Finding the first occurrence needs the variant that keeps searching left after a hit instead of returning.

## Where it is used

- <strong>Database indexes.</strong> A B-tree is binary search generalised to disk pages.
- <strong>`bisect.insort`</strong> for maintaining a sorted list.
- <strong>Version bisection</strong> &mdash; `git bisect` is binary search over commits.
- <strong>Numerical root finding</strong> &mdash; bisection on a continuous function.
- <strong>Rate limiting and capacity planning</strong> &mdash; the answer-search pattern above.
- <strong>Timestamp lookups</strong> in log and time-series data.
