title: Binary Search Trees
intro: Binary search made into a structure &mdash; and what happens when it loses its shape.

## The problem it solves

A <strong>binary search tree</strong> keeps its values in sorted order by position. At every node: the entire left subtree is smaller, the entire right subtree is larger. Searching then works exactly like binary search &mdash; compare, discard half, repeat.

## Search, Insert, Delete

Searching is a walk: compare with the current node, go left if smaller, right if larger, stop when equal or when you fall off the tree. Insertion follows the same walk and attaches the new node where the search failed.

Deletion is the fiddly one, with three cases:

- <strong>Leaf</strong> &mdash; just remove it.
- <strong>One child</strong> &mdash; the child takes its place.
- <strong>Two children</strong> &mdash; replace the value with its <em>in-order successor</em> (the smallest value in the right subtree), then delete that successor. Only this choice preserves the BST rule.

## In-Order Traversal Sorts For Free

Visit left subtree, then the node, then the right subtree. Because of the BST rule, this emits every value in <strong>ascending sorted order</strong> &mdash; press <em>In</em> and read the output.

The other two orders have their own uses: <strong>pre-order</strong> (node first) is how you copy or serialise a tree, and <strong>post-order</strong> (node last) is how you delete one safely, since children are freed before their parent.

## The Fatal Weakness

Press <strong>Sorted input</strong>. Inserting already-sorted values means every new value is larger than everything before it, so it always goes right. The tree becomes a single downward chain &mdash; a linked list wearing a tree costume.

Height goes from O(log n) to O(n), and every operation degrades with it. This is not a rare edge case: inserting sorted data is extremely common in practice.

## Which Is Why Self-Balancing Trees Exist

<strong>AVL trees</strong> and <strong>red-black trees</strong> detect when a subtree grows lopsided and perform <em>rotations</em> to restore balance, guaranteeing O(log n) regardless of insertion order. Red-black trees are what back <span class="mono-font">std::map</span> in C++ and <span class="mono-font">TreeMap</span> in Java.<p>Compare the height readout after pressing <em>Balanced</em> versus <em>Sorted input</em> with the same values &mdash; the gap is exactly what balancing buys.</p>

## BST or Hash Table?

A hash table is faster for pure lookup &mdash; O(1) versus O(log n). But a BST keeps its data <strong>ordered</strong>, which a hash table cannot. Use a tree when you need sorted iteration, range queries ("all values between 20 and 50"), or nearest-neighbour lookups. Use a hash table when you only ever ask "is this exact key present?".

## Ordered structure, not just storage

A binary search tree keeps one invariant at every node:

<strong>Everything in the left subtree is smaller; everything in the right subtree is larger.</strong>

That single rule makes search work like binary search: compare, then discard half the tree.

```
        8
      /   \
     3     10
    / \      \
   1   6      14
      / \    /
     4   7  13
```

Searching for 6: 6 &lt; 8 so go left; 6 &gt; 3 so go right; found. Three comparisons for seven nodes.

|Operation|Balanced|Degenerate|
|---|---|---|
|Search|O(log n)|O(n)|
|Insert|O(log n)|O(n)|
|Delete|O(log n)|O(n)|
|In-order traversal|O(n)|O(n)|
|Minimum / maximum|O(log n)|O(n)|

The difference between those columns is the whole subject, and it is what balanced trees exist to guarantee.

## Why an in-order traversal is sorted

Visit the left subtree, then the node, then the right subtree, and values come out in ascending order &mdash; because everything left is smaller and everything right is larger, recursively.

```python
def inorder(node, out):
    if node:
        inorder(node.left, out)
        out.append(node.value)
        inorder(node.right, out)
```

That is the property hash tables cannot offer, and it is why BSTs are used where ordering matters:

- <strong>Range queries</strong> &mdash; all values between 10 and 50, found by traversing a subtree.
- <strong>Nearest neighbour</strong> &mdash; the closest value to a target.
- <strong>Sorted iteration</strong> without sorting.
- <strong>Successor and predecessor</strong> of a given value.
- <strong>Minimum and maximum</strong> &mdash; walk left or right to the end.

A hash table does none of those. That is the trade: O(1) unordered lookup, or O(log n) with order.

## The degenerate case

Insert 1, 2, 3, 4, 5 into an empty BST in that order and every node becomes the right child of the last. The tree is a linked list, and every operation is O(n).

<strong>Sorted input produces the worst possible tree.</strong> That is not a rare pathological case &mdash; inserting records in id order, or in date order, is entirely normal.

Three responses:

<strong>Self-balancing trees.</strong> AVL and red-black trees rotate on insertion to keep the height O(log n) automatically. This is what production implementations use.

<strong>Randomised insertion order,</strong> if you control it. Expected height O(log n).

<strong>A different structure.</strong> A sorted array with binary search, or a skip list, or a B-tree for disk-based data.

|Tree|Balance rule|Character|
|---|---|---|
|AVL|Heights differ by at most 1|Strictly balanced; faster lookups|
|Red-black|Colour rules bound the height|Fewer rotations; faster insertion|
|B-tree|Many keys per node|Designed for disk pages|
|Treap|Random priorities|Simple, probabilistic balance|

Red-black trees are what most standard libraries use for ordered maps &mdash; C++'s `std::map`, Java's `TreeMap` &mdash; because they balance insertion and lookup cost well.

## Guided tour

1. <strong>Insert a few values</strong> and watch each one walk down the tree, going left or right at every comparison.
2. <strong>Search for something.</strong> The highlighted path shows roughly half the remaining tree being discarded at each step.
3. <strong>Press In-order traversal.</strong> The values come out perfectly sorted &mdash; that is the BST rule paying off.
4. <strong>Press Sorted input.</strong> The tree collapses into a straight line and the height jumps to n &mdash; every search is now linear.
5. <strong>Delete a node with two children</strong> and note which value replaces it: the in-order successor, the only choice that keeps the ordering intact.

## In one line

A BST turns the binary-search idea into a living structure with O(log n) search, insert and delete &mdash; but only while it stays bushy. Sorted input degenerates it to a linked list, which is precisely why self-balancing variants exist and why they, not plain BSTs, are what production libraries ship.

## Deletion, the awkward operation

Insertion and search are straightforward. Deletion has three cases, and the third is where implementations go wrong.

<strong>A leaf.</strong> Remove it.

<strong>One child.</strong> Replace the node with its child.

<strong>Two children.</strong> Replace the node's value with its <strong>in-order successor</strong> &mdash; the smallest value in its right subtree &mdash; then delete that successor, which by construction has at most one child.

```python
def delete(node, value):
    if not node:
        return None
    if value < node.value:
        node.left = delete(node.left, value)
    elif value > node.value:
        node.right = delete(node.right, value)
    else:
        if not node.left:
            return node.right
        if not node.right:
            return node.left
        succ = node.right                      # find the in-order successor
        while succ.left:
            succ = succ.left
        node.value = succ.value
        node.right = delete(node.right, succ.value)
    return node
```

The predecessor (largest in the left subtree) works equally well. Either choice preserves the ordering invariant, which is what matters.

Note that repeated deletions can unbalance a tree even if insertions were balanced &mdash; another argument for a self-balancing implementation.

## Where trees beat hash tables

|Need|Structure|
|---|---|
|Lookup by exact key|Hash table &mdash; O(1)|
|Range queries|Tree|
|Sorted iteration|Tree|
|Nearest key|Tree|
|Minimum or maximum|Tree, or a heap|
|Predictable worst case|Balanced tree &mdash; O(log n) guaranteed|

The last row is worth noting: a hash table's O(1) is an average, with an O(n) worst case; a balanced tree's O(log n) is a guarantee. For latency-sensitive systems that certainty sometimes wins.

In Python specifically, there is no built-in balanced tree. The practical alternatives are `dict` for unordered lookup, `bisect` on a sorted list for range queries when insertions are rare, and the third-party `sortedcontainers` package, which provides sorted list, dict and set types with excellent constant factors.

## B-trees, and why databases use them

A B-tree node holds many keys &mdash; hundreds &mdash; rather than one, so the tree is very shallow: a few levels for millions of records.

The reason is disk. Reading from disk or SSD happens in pages of several kilobytes, and the cost is dominated by the number of page reads rather than the comparisons within a page. A binary tree with a million nodes is 20 levels deep, meaning up to 20 page reads. A B-tree with 200 keys per node is 3 levels deep &mdash; 3 reads.

That is why <strong>every relational database index is a B-tree</strong> (usually a B+ tree, with all values in the leaves and the leaves linked for range scans). It is the same ordering invariant, restructured around the hardware.

## Questions people ask

<strong>Why not always use a hash table?</strong> Because it has no order. Range queries, sorted iteration and nearest-key lookups all need a tree.

<strong>What makes a tree balanced?</strong> Height O(log n). AVL and red-black trees enforce it with rotations on insertion and deletion.

<strong>What happens with sorted insertions?</strong> An unbalanced tree degrades to a linked list &mdash; O(n) operations. This is common in practice, not a corner case.

<strong>How do I do a range query?</strong> Traverse in order, pruning subtrees entirely outside the range.

<strong>Does Python have a balanced tree?</strong> Not in the standard library. Use `bisect` on a sorted list, or `sortedcontainers`.

<strong>What is the difference between a BST and a heap?</strong> A BST orders left-node-right for sorted access; a heap only orders parent against children, giving O(1) access to the extreme value and no ordering otherwise.

## Recap in one screen

- Left subtree smaller, right subtree larger &mdash; that invariant gives O(log n) search on a balanced tree.
- An in-order traversal yields sorted values, which is what hash tables cannot do.
- Sorted insertions produce a degenerate O(n) tree, so self-balancing (AVL, red-black) is what production uses.
- Deletion with two children replaces the node with its in-order successor.
- B-trees widen the nodes to match disk pages, which is why every database index is one.
