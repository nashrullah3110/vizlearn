title: Sliding Window
intro: Stop recomputing what barely changed.

## The problem it solves


The <strong>sliding window</strong> technique maintains a contiguous range over an array or string and moves it along, updating a running summary incrementally rather than rebuilding it. It turns O(n&middot;k) into O(n).

There are two variants: fixed-size and variable-size. A fixed-size window slides one position at a time.

## Fixed Windows: Add One, Remove One

To find the maximum sum of k consecutive elements, the naive approach sums each window from scratch. That takes k additions per position, or O(n · k) work in total.

But sliding from position i to i+1 only removes one element and adds one:

Two steps instead of k, no matter how large k is. Compare the step counters as you raise k. The sliding window's count does not move.

For `[2, 1, 5, 1, 3]` with a window of three, the first sum is `2 + 1 + 5 = 8`. Slide one place: subtract 2 and add 1 to get 7. Slide again: subtract 1 and add 3 to get 9. The maximum window sum is 9; each move takes constant work, so the full scan is O(n).

## Variable Windows: Grow and Shrink

Harder problems let the window <em>change size</em>. The pattern is always the same:

- <strong>Expand</strong> the right edge until the window meets (or violates) some condition.
- <strong>Contract</strong> the left edge while the condition still holds, recording the best answer.

Both pointers only ever move forward, so though the code holds nested loops, each element is added once and removed once. Total work is still <strong>O(n)</strong>. That amortised argument is the part people find surprising.

## How to Spot One

Reach for a sliding window when the problem asks about a <strong>contiguous</strong> subarray or substring, and phrases it as longest/shortest/maximum/minimum meeting a condition.

The critical requirement is that the running summary can be updated incrementally. Sums and counts work. If the condition needs the whole window recomputed. A median, say. You need a heavier structure such as a heap or balanced tree alongside the window.

## Try it yourself

1. <strong>Run max-sum with k = 3.</strong> Watch each slide subtract one value and add one. Two steps, never three.
2. <strong>Raise k to 5.</strong> The naive cost climbs while the sliding-window step count stays flat. That is the whole point.

## Where it is used

- <strong>Rate limiting.</strong> Requests in the last 60 seconds is a sliding window over timestamps.
- <strong>Streaming statistics.</strong> Moving averages, rolling maxima, and any windowed aggregate over a data stream.
- <strong>Network protocols.</strong> TCP's sliding window controls how much unacknowledged data may be in flight.
- <strong>Time-series features.</strong> Rolling means and standard deviations for forecasting models.
- <strong>Text handling.</strong> Finding substrings with given character properties; n-gram extraction.
- <strong>Anomaly detection.</strong> Comparing a recent window against a baseline.

Rate limiting is a common production use. A sliding log or counter can enforce a quota over a rolling interval. A fixed-window counter is simpler, but can allow nearly twice the intended rate when requests fall on opposite sides of a window boundary.

## Common mistakes

- <strong>Shrinking in the wrong condition</strong> &mdash; the longest/shortest inversion described above.
- <strong>Recording the answer at the wrong point,</strong> before rather than after restoring validity.
- <strong>Not removing from the state when shrinking,</strong> so counts drift.
- <strong>Using it on non-contiguous problems.</strong> Sliding window is only for runs; subsequences need dynamic programming.
- <strong>Recomputing the aggregate from scratch,</strong> which discards the entire edge.
- <strong>Off-by-one in the window size:</strong> the width is `right - left + 1`.
