title: Greedy Algorithms
intro: Fast, simple, and wrong just often enough to be dangerous.

## Before the details

A <strong>greedy algorithm</strong> builds a solution one step at a time, always taking whatever looks best <em>at that moment</em>, and never revisiting a decision. No backtracking, no lookahead.

## When Greedy Is Provably Correct

Two properties must hold:

- <strong>Greedy choice property</strong> &mdash; a globally optimal solution can be reached by making locally optimal choices. You never need to sacrifice now for later.
- <strong>Optimal substructure</strong> &mdash; after making that choice, what remains is a smaller instance of the same problem.

Proving the first usually needs an <em>exchange argument</em>: show that any optimal solution can be modified to include the greedy choice without getting worse.

## Activity Selection: Greedy Wins

Given activities with start and finish times, pick the most that do not overlap. The greedy rule is: <strong>always take the one that finishes earliest</strong> among those still compatible.

Why is that safe? Finishing earliest leaves the maximum possible time for everything after it. Any optimal schedule can have its first activity swapped for the earliest-finishing one without reducing the count &mdash; that is the exchange argument, and it makes greedy provably optimal here.

Note that sorting by <em>duration</em> or <em>start time</em> both fail. The specific greedy criterion matters enormously.

## Coin Change: Greedy Fails

With coins {1, 5, 10, 25} greedy works &mdash; always take the largest coin that fits. That is why it feels natural at a till.

Now switch to <strong>greedy FAILS</strong>, using coins {1, 3, 4} and amount 6. Greedy takes 4, then 1, then 1 &mdash; <strong>three coins</strong>. The optimum is 3 + 3 &mdash; <strong>two coins</strong>. Taking the biggest coin first stranded the algorithm in a worse position.

Nothing about the greedy code is buggy. The <em>problem</em> simply lacks the greedy choice property for that coin set, and only dynamic programming is guaranteed correct.

## Famous Greedy Algorithms That Do Work

- <strong>Dijkstra</strong> &mdash; always expand the nearest unvisited node. Correct only when edge weights are non-negative.
- <strong>Kruskal and Prim</strong> &mdash; always take the cheapest safe edge. Provably build minimum spanning trees.
- <strong>Huffman coding</strong> &mdash; always merge the two least frequent symbols. Produces optimal prefix codes.
- <strong>Fractional knapsack</strong> &mdash; take the best value-per-weight first. Works because items can be split; the 0/1 version cannot, and needs DP.

## Try it yourself

1. <strong>Run activity selection.</strong> Watch it pick the earliest finisher and reject everything that overlaps &mdash; and confirm the result matches the true optimum.
2. <strong>Run coin change with friendly coins.</strong> Greedy and optimal agree, which is why the approach feels obviously right.
3. <strong>Now run the failing case.</strong> Greedy returns 3 coins; the optimum is 2. Same algorithm, different coin set.
4. <strong>Slide the amount</strong> in the failing case. Some amounts greedy gets right by luck; others it does not. There is no warning &mdash; that is what makes it dangerous.
5. <strong>Compare the two verdicts.</strong> A greedy algorithm gives you no signal when it is wrong; you must prove correctness in advance.

## In one line

Greedy algorithms are fast and elegant when the greedy choice property holds — and silently wrong when it does not. Always ask whether a locally best move can ever block a globally better one. If it can, reach for dynamic programming instead.
