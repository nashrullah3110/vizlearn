title: A* Pathfinding Algorithm: A Practical Guide
intro: Dijkstra with a sense of direction. Adding an estimate of the remaining distance steers the search toward the goal instead of expanding uniformly - and if that estimate never overestimates, the path is still optimal.

## The problem with searching in every direction


Dijkstra’s algorithm expands outward from the source in rings of equal cost. If the goal is due east, it still explores just as far north, south and west before reaching it. On a large map that is enormous wasted effort. The algorithm has no idea where it is going.

A* adds that idea.

## f = g + h

Every node carries three numbers:

- <span class="mono-font">g(n)</span> &mdash; the actual cost of the best known path from the start to n. This is exactly Dijkstra’s distance.
- <span class="mono-font">h(n)</span> &mdash; the <strong>heuristic</strong>: an estimate of the left cost from n to the goal.
- <span class="mono-font">f(n) = g(n) + h(n)</span> &mdash; the estimated total cost of a route through n.

A* is then exactly Dijkstra with the priority queue ordered by f instead of g. Set <span class="mono-font">h(n) = 0</span> everywhere and you get Dijkstra back exactly &mdash; A* is a strict extension, not a different algorithm.

## Admissible, steady, and why it stays best

A heuristic is <strong>admissible</strong> if it never overestimates the true left cost. That single property is what guarantees A* finds a best path.

The reason: if h never overestimates, then f(n) never overestimates the cost of the best route through n. So when the goal is popped with total cost f, no unexplored node can be hiding a cheaper route. Any such node would have had a smaller f and been popped first.

Overestimate, and that breaks. An inflated h can make the true best route look worse than a bad one, and A* will return the bad one. The common heuristics on a grid are admissible by construction:

- <strong>Manhattan</strong> <span class="mono-font">|dx| + |dy|</span> &mdash; admissible when movement is 4-directional, because that is the exact distance with no obstacles.
- <strong>Euclidean</strong> <span class="mono-font">&radic;(dx&sup2; + dy&sup2;)</span> &mdash; admissible always. Since a straight line is the shortest doable route, but weak (too low) on 4-directional grids.
- <strong>Zero</strong> &mdash; admissible and useless: this is Dijkstra.

Note that Manhattan is <em>not</em> admissible if diagonal movement is allowed, because the diagonal route is shorter than |dx| + |dy|. That mismatch is the most common way people accidentally break optimality.

## Choosing the heuristic is the whole design

The heuristic decides how much better than Dijkstra A* is, and getting it wrong is the usual failure.

<strong>Too weak</strong> (close to 0) and A* degenerates towards Dijkstra, exploring almost all of it.

<strong>Not admissible</strong> and the result is suboptimal. The classic mistake on a 4-directional grid is using Euclidean distance: it underestimates correctly. So it is admissible. But Manhattan distance is a <em>tighter</em> underestimate and so explores far less. Conversely, using Manhattan distance when diagonal movement is allowed <em>over</em>estimates and breaks optimality.

<strong>Too expensive to compute</strong> and the per-node saving is lost. h is evaluated for every node examined.

The practical rule: <strong>use the tightest admissible estimate that is cheap to compute</strong>, and match it to the actual movement rules.

For road networks the straight-line distance is admissible but weak, because roads are not straight. Production routing engines use landmark-based heuristics: precompute distances from a few hundred landmark nodes, and use the triangle inequality to derive much tighter bounds. That is one of the techniques that makes continental route planning interactive.

## Guided tests

1. <strong>See the search become directional.</strong> Press <strong>Run Algorithm</strong> and watch the explored region. It stretches toward the goal rather than spreading in a circle &mdash; that elongation is h doing its job.
2. <strong>Turn the heuristic off.</strong> Set <strong>Heuristic</strong> to the zero or Dijkstra option and press <strong>Reset Grid</strong>, then run again. The explored area balloons into an even blob. The path found is the same length; the work to find it is far greater.

## Where it is used

- <strong>Game pathfinding.</strong> The default algorithm for moving units around a map, often on a grid or navigation mesh.
- <strong>Robotics.</strong> Motion planning over occupancy grids, often with variants handling smooth space.
- <strong>Route planning.</strong> Real navigation systems use A* with landmark heuristics, or contraction hierarchies which precompute shortcuts.
- <strong>Puzzle solving.</strong> Sliding tiles, Rubik's cube and similar. Where the heuristic is a relaxation of the puzzle. For the 15-puzzle, the sum of Manhattan distances of each tile from its home.
- <strong>Word ladders and state-space search</strong> often, where the graph is made on demand.
- <strong>Automated planning</strong> in AI, where the state space is enormous and heuristics are important.

The puzzle case illustrates a general technique for inventing heuristics: <strong>solve a relaxed version of the problem</strong>. Ignoring that tiles block each other gives the Manhattan-distance heuristic. This is admissible because the real puzzle can only be harder.
