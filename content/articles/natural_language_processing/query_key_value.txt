title: Query, Key and Value: A Practical Guide
intro: The three projections every transformer is written in, and why there are three rather than two.

## Quick Context

The <a href="attention_mechanism.html" style="color: var(--accent-primary)">previous module</a> described attention as score, normalise, blend. That description works, but it leaves one thing vague: what exactly is being compared against what?

The query&ndash;key&ndash;value framing answers that, and it is worth learning properly because every transformer paper, diagram and implementation is written in it.

## A soft dictionary lookup

Attention is easiest to read as a lookup that returns a blend rather than one entry.

In an ordinary dictionary you present a key and get back exactly one value. In attention you present a <strong>query</strong>, compare it against <em>every</em> key, and get back a weighted mixture of all the values &mdash; weighted by how well each key matched.

- <strong>Query</strong> &mdash; what this position is looking for.
- <strong>Key</strong> &mdash; the label each position advertises.
- <strong>Value</strong> &mdash; what each position actually contributes when selected.

All three are linear projections of the same input, with separate learned matrices:

<p class="mono-font">Q = XW<sub>Q</sub>&nbsp;&nbsp;&nbsp;K = XW<sub>K</sub>&nbsp;&nbsp;&nbsp;V = XW<sub>V</sub></p>

That is where every parameter in the mechanism lives. Attention itself has no weights &mdash; it is a fixed formula applied to these three projections.

## Where they come from

All three are linear projections of the same input embedding:

Q = X W<sub>Q</sub> &nbsp;&nbsp; K = X W<sub>K</sub> &nbsp;&nbsp; V = X W<sub>V</sub>

The three weight matrices are learned. This is the part people find surprising: the same word produces three different vectors, because it plays three different roles. As a query it asks a question; as a key it advertises what it can answer; as a value it supplies content.

And the whole mechanism is one formula:

Attention(Q, K, V) = softmax( QK<sup>T</sup> / &radic;d<sub>k</sub> ) V

## Why keys and values are separate

It is reasonable to ask why we need both &mdash; why not match against the values directly and save a matrix?

Because how easily something is <em>found</em> is a different question from what it <em>contains</em>. A word might be highly relevant to a query while the information it should pass on is quite unrelated to why it matched. Splitting the two lets the model learn addressing and content independently, and in practice that separation is what allows different heads to specialise.

## Why three separate projections

The obvious question: if all three come from the same input, why not use the input directly for all of them?

Because the three roles want different information. What a token is <em>looking for</em> is not the same as how it wants to <em>be found</em>, and neither is the same as what it should <em>contribute</em>.

Take "it" in "The cat sat on the mat because it was warm". As a query, "it" needs to search for a nearby noun that could be warm. As a key, "mat" needs to advertise itself as a warmable surface. As a value, "mat" contributes its full semantic content. Separate matrices let the model learn those three functions independently.

The clearest demonstration is that Q and K are used only to compute compatibility, and V only to produce output. A token can be highly attended to for one reason and contribute something quite different &mdash; which a single shared projection could not express.

## The computation, step by step

<p class="mono-font">Attention(Q, K, V) = softmax(QK&#7488; / &radic;d<sub>k</sub>) V</p>

For a sequence of 4 tokens with head dimension 64:

|Step|Operation|Shape|
|---|---|---|
|1|`QKᵀ` &mdash; every query against every key|4&times;4|
|2|Divide by `√64` = 8|4&times;4|
|3|Softmax over each row|4&times;4, rows sum to 1|
|4|Multiply by V|4&times;64|

Row i of the 4&times;4 matrix holds token i's attention weights over all four tokens. Multiplying by V replaces token i's representation with the weighted mixture.

The `√dₖ` division is not cosmetic. Dot products of d-dimensional vectors grow with d, so without scaling the scores reach the tens or hundreds, the softmax becomes nearly one-hot, and the gradient through it approaches zero. Dividing by `√dₖ` keeps the variance of the scores near 1 regardless of dimension.

## Things to try

1. <strong>Follow one lookup end to end.</strong> Set the <strong>Stage</strong> slider to 1 and step it up to 4. You see the raw dot products appear, get divided by the square root of the head dimension, become weights through softmax, and finally blend the value vectors into one output.
2. <strong>Change who is asking.</strong> Set the <strong>Query Word</strong> to drank. The scores rearrange completely &mdash; the same six keys, a different question, a different answer.
3. <strong>Break the scaling.</strong> Set the <strong>Head Dimension</strong> slider to 64 and untick <strong>Scale by 1/&radic;d_k</strong>. The raw scores grow large, softmax saturates, and the weights collapse onto a single key with entropy near zero. In a real model that means a vanishing gradient and a layer that stops learning.
4. <strong>Then fix it.</strong> Tick <strong>Scale by 1/&radic;d_k</strong> again with the dimension still at 64. The scores come back into a sane range and the distribution is usable again. That single division is the entire reason the mechanism is called <em>scaled</em> dot-product attention.
5. <strong>Check the low-dimension case.</strong> Set the <strong>Head Dimension</strong> slider to 1. Now the scaling barely matters, because there was never anything to blow up. The correction only earns its keep as dimension grows.

## Why divide by √d k

If the components of the query and key are roughly independent with unit variance, their dot product is a sum of d<sub>k</sub> such products, so its variance grows with d<sub>k</sub> and its typical magnitude grows with &radic;d<sub>k</sub>. At d<sub>k</sub> = 64 the scores are around eight times larger than at d<sub>k</sub> = 1.

Softmax is exponential, so those larger gaps translate into near-one and near-zero weights. That is bad in itself &mdash; the layer stops blending &mdash; and worse for training, because softmax's gradient is almost zero once it saturates. Dividing by &radic;d<sub>k</sub> cancels the growth exactly and keeps the scores in the range where softmax is still responsive.

## The three kinds of attention

The same formula covers every attention in a transformer; only where Q, K and V come from changes:

<table> <tr><th>Kind</th><th>Query from</th><th>Key and value from</th></tr> <tr><td>Encoder self-attention</td><td>the input</td><td>the input</td></tr> <tr><td>Decoder self-attention</td><td>the output so far</td><td>the output so far (masked)</td></tr> <tr><td>Cross-attention</td><td>the decoder</td><td>the encoder</td></tr> </table>

Cross-attention is the classic encoder&ndash;decoder attention of the previous module. When query, key and value all come from the same sequence you get <a href="self_attention.html" style="color: var(--accent-primary)">self-attention</a>, which is the next module.

## Traps worth knowing

- <strong>Assuming Q, K and V are the same vector.</strong> They are three different projections of it, with three different learned matrices, and conflating them makes the rest of the architecture impossible to follow.
- <strong>Dropping the scaling.</strong> It looks like a detail and is not. Without it, wide heads saturate and training stalls.
- <strong>Thinking the weights are a similarity between words.</strong> They are a similarity between a <em>query projection</em> of one word and a <em>key projection</em> of another. Those projections are learned, so two synonyms need not attend to each other at all.
- <strong>Forgetting the last multiply.</strong> Softmax gives weights, not output. The output is those weights applied to V, and V is a different projection again.

## Summing up

Attention is a soft dictionary lookup: the query says what a position is looking for, each key says how well that position matches, and each value says what it contributes once matched, with all three being separate learned projections of the same input. Every key matches to some degree, so the output is a weighted blend rather than a single retrieved entry, and the whole mechanism is softmax(QKᵀ/&radic;d_k)V. Keys and values are kept apart because findability and content are different things, and the &radic;d_k division exists because dot products grow with dimension and would otherwise saturate the softmax into a hard, ungradient-able argmax.

## Multiple heads, and where they come from

Multi-head attention runs several of these computations in parallel with different learned projections, then concatenates the outputs and applies one more projection.

```python
import torch, torch.nn.functional as F

def attention(x, Wq, Wk, Wv, mask=None):
    Q, K, V = x @ Wq, x @ Wk, x @ Wv
    scores = Q @ K.transpose(-2, -1) / (K.size(-1) ** 0.5)
    if mask is not None:
        scores = scores.masked_fill(mask == 0, float("-inf"))
    return F.softmax(scores, dim=-1) @ V
```

With a model dimension of 512 and 8 heads, each head projects to 64 dimensions, so the total work is roughly the same as one 512-dimensional head &mdash; and the model gets 8 independent views instead of 1.

The masking line is how causal generation and padding are both handled: setting a score to negative infinity makes its softmax weight exactly zero.

## Cross-attention, and the caching trick

In <strong>self-attention</strong> Q, K and V all come from the same sequence. In <strong>cross-attention</strong> the queries come from one sequence and the keys and values from another &mdash; a decoder querying an encoder's output, or a text query attending to image patches.

That asymmetry has a practical consequence during generation, and it is the basis of the most important inference optimisation in language models.

When generating token by token, the keys and values for all previous tokens do not change &mdash; only the new token's query is new. So they can be computed once and cached:

<strong>Without a KV cache,</strong> generating the 1,000th token requires recomputing keys and values for all 999 previous tokens. Generation is quadratic in output length.

<strong>With a KV cache,</strong> each new token computes its own K and V, appends them, and attends against the stored ones. Generation becomes linear.

The cost is memory: the cache holds two tensors per layer per token, which for a large model and a long context runs to many gigabytes. That is exactly what <strong>multi-query</strong> and <strong>grouped-query attention</strong> address, by sharing key and value projections across heads and shrinking the cache several-fold.

## Questions people ask

<strong>Why is it called query, key, value?</strong> By analogy with a database lookup. The analogy is genuinely useful and the mechanism is soft rather than exact.

<strong>Are Q, K and V the same size?</strong> Q and K must match, since they are dotted together. V can differ in principle and is usually the same size in practice.

<strong>Do they have separate weight matrices?</strong> Yes &mdash; three per head, plus one output projection per layer.

<strong>What is `dₖ`?</strong> The dimension of a single head's key vectors, typically 64. It is what the scaling factor is derived from.

<strong>Why not use cosine similarity instead of a dot product?</strong> The dot product is cheaper, and the scaling plus LayerNorm already keeps magnitudes controlled. Some architectures do normalise the queries and keys.

<strong>Can K and V come from a different source than Q?</strong> That is precisely cross-attention, and it is how decoders read encoders and how multimodal models connect modalities.

## Recap in one screen

- Query is what a position seeks, key is how a position advertises itself, value is what it contributes.
- All three are learned linear projections of the input; attention itself has no parameters.
- Score with `QKᵀ`, scale by `√dₖ`, softmax, then weight the values.
- The scaling prevents softmax saturation and vanishing gradients in high dimensions.
- Keys and values do not change during generation, which is what makes KV caching &mdash; and linear-time decoding &mdash; possible.
